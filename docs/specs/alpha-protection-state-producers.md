# Alpha protection and classification state producers

Status: FINAL / STABLE / HELD.

This is a bounded original-client contract for the storage, production and consumption of the creature word at `+0x7E`, the `0x20` bit of the byte at `+0x124`, and the world fields at `+0xB4` and `+0xB8`. It records concrete initialization, copying, streaming and behavioral changes. It does not assign faction, allegiance, ownership or player-interface meanings to raw flags unless an original relation proves that meaning. It is not a complete hit-application or generation contract.

The evidence root is `disassembled alpha cube world`. The supported image is `binary/Cube.exe`, a 32-bit PE image with preferred base `0x00400000`, length 3,885,568 bytes and SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`. All addresses below are RVAs; the original instruction listing `decompiled/client/assembly.txt` prints them as virtual addresses (RVA plus `0x00400000`). Evidence consists of that image, that listing and individually selected original function files under `decompiled/client/functions/`. No server image, replacement implementation, runtime observation or earlier project contract was used as evidence.

## Storage identities

A creature object embeds its data block at creature `+0x10`. The appearance object inside that block begins at data `+0x68`, which is creature `+0x78`. The appearance object holds a two-byte flags word at its own `+0x06`, so creature `+0x7E` and data `+0x6E` name the same storage. A generation descriptor holds an appearance object at descriptor `+0x74`; its flags word is descriptor `+0x7A`. These bases matter: an equal numeric offset in an item or another object is not evidence of a creature flag write.

| Storage | Width and interpretation established here |
| --- | --- |
| Creature `+0x7E` | Raw 16-bit word. The classifier reads it zero-extended and checks mask `0x1A00`, which is the union of bits `0x0200`, `0x0800` and `0x1000`. Hit application separately checks `0x2000`. |
| Creature `+0x124` | Low byte of a raw 16-bit data flags word at data `+0x114`. The relationship helper reads only that byte and checks `0x20`; the copies, resets and stream field described below move or clear both bytes. |
| Creature `+0x60` | One-byte discriminator read by the relationship and hit paths. Its complete value taxonomy is unresolved here. |
| Creature `+0x64` | 32-bit identifier compared exactly, over all 32 bits, by the classifier. |
| World `+0xB4` | One-byte mode; the consumers cited here distinguish only zero from nonzero. |
| World `+0xB8` | Four-byte native pointer compared with creature addresses. It is not an actor identifier. |

The client object embeds its world at client `+0x2E4`, so client `+0x398` and `+0x39C` are the same storage as world `+0xB4` and `+0xB8`. The client keeps its current creature pointer at client `+0x8006D0`. Evidence: `0x03B6CB–0x03B6D1`, `0x03C180–0x03C1BC`, `0x059827–0x05982B`, `0x059F31–0x059F57`, `0x062219–0x06222C`, `0x21002B–0x210059`.

## What the consumers decide

The classifier at `0x044680` takes a creature as its receiver and returns a Boolean in the low byte of the result register. If any bit of `0x1A00` is set in creature `+0x7E`, the answer is false regardless of identifier. Otherwise the answer is true exactly when the full 32-bit value at `+0x64` is one of the following 32 hexadecimal values:

`13, 14, 16, 17, 19, 1A, 1B, 1E, 1F, 20, 21, 22, 23, 35, 37, 38, 39, 3A, 43, 44, 4A, 57, 59, 5C, 5D, 62, 64, 6A, 6B, 91, 92, 93`.

Every other identifier gives false; for example `0x00000013` qualifies and `0x00000113` does not, so a matching low byte is not enough. The routine reads nothing besides those two fields: not `+0x60`, not `+0x124`, no owner identifier and no world pointer. It calls nothing, draws no random value and writes no creature storage. Only the low result byte is the Boolean; the upper result bits carry no defined meaning. Evidence: `0x044680–0x044759`; `decompiled/client/functions/00444680.c`.

The ordered two-creature relation at `0x196CA0` takes two creature pointers as stack arguments and performs no null check on either. The argument positions matter. The result is false when the first discriminator is `5` and the second is `0`, and false when either discriminator is `6`; these exclusions are decided before any `0x20` check. Apart from those exclusions: when exactly one discriminator equals `1`, the result is true. When both equal `1`, the classifier is evaluated on the first and then the second creature, and differing answers give true. When both equal `1` with matching answers, the classifier is evaluated a second time on the first and then the second creature (four evaluations in total) before the byte checks. When neither discriminator equals `1`, or both do with matching answers, the result is true if either creature's byte `+0x124` has bit `0x20` set, the first creature being checked first, and false otherwise.

Passing the same creature twice is not specially rejected: a discriminator-`1` creature paired with itself yields false with its `0x20` bit clear and true with it set. A bit in the upper byte of the word, such as `0x2000` at creature `+0x124`, does not satisfy the low-byte `0x20` check. The relation draws no random value, writes nothing and performs no identifier, link or owner lookup. Evidence: `0x196CA0–0x196D2C`; `decompiled/client/functions/00596ca0.c`.

The world hit-application routine at `0x195A60` (receiver: the world; first stack argument: a hit record; second stack argument: an output list) has admission rules of its own, independent of the classifier. It first looks up the record's 64-bit target identifier at record `+0x08` in the world map at world `+0x04`. A missing entry, a null mapped pointer, or a binary32 value at target creature `+0x16C` that is not greater than zero ends the routine; an unordered (NaN) value there does not end it. For a surviving target whose byte `+0x60` is zero while world `+0xB8` is null, the routine appends a copy of the record to the output list through `0x086290` and returns, before the source lookup and every later write. This is a delivery route, not evidence of any local change to the target.

Otherwise the routine looks up a source actor using the record's separate 64-bit identifier at record `+0x00`; a missing source is treated as null. When the record's binary32 amount at `+0x10` is strictly positive, the target's binary32 field `+0x1190` is reduced (and floored at zero), and a target byte `+0x68` equal to `0x54` is replaced by zero with `0xBB8` stored at target `+0x12C`. When the amount is not negative and the source is nonnull, the routine writes the two actors' 64-bit fields at `+0x11D0`, adjusts entries of the source map at `+0x13AC` and the target map at `+0x13A4`, and calls `0x1A0970`. All of this happens before the target's `0x2000` check, so failing that check does not undo it.

At `0x195CE7–0x195D6A`, a target whose word `+0x7E` has `0x2000` set continues only if its map at `+0x13A4` holds at least one entry whose binary32 value is strictly greater than zero and whose 64-bit key resolves in world `+0x04` to a nonnull actor with byte `+0x60` equal to zero. Zero-valued entries, unresolved keys and null mapped actors do not qualify, and the qualifying actor need not be the current source. With no qualifying entry the routine returns, skipping everything after this point. A target with `0x2000` clear skips this requirement. Immediately afterwards, a record byte `+0x45` equal to `3` also ends the routine.

Two later gates differ from each other. Only for a non-negative amount, the portion at `0x195DBD–0x195E36`, which may replace target binary32 fields `+0x4C`, `+0x50` and `+0x54` with the record's values at `+0x38`, `+0x3C` and `+0x40`, is skipped for a target with discriminator `6`, and otherwise runs only when world `+0xB4` is zero and the target discriminator is nonzero, or when the target pointer equals world `+0xB8`. The portion beginning at `0x195ED2` runs only when world `+0xB4` is zero or the target pointer equals world `+0xB8`; it is reached only for record byte `+0x45` values other than `1` and `4`, which return earlier after their own target writes. Writes made before `0x195ED2` are not made conditional on that later gate. The `0x1A00` classifier mask is therefore not a general hit-immunity check, and the other record-category and type checks in this routine remain in force. Evidence: `0x195AAB–0x195B55`, `0x195BD5–0x195D74`, `0x195D7A–0x195E36`, `0x195E69–0x195EED`; selected portions of `decompiled/client/functions/00595a60.c`.

## Default values, reset scope and preservation

The creature constructor at `0x03B690` builds the data block at creature `+0x10` through `0x03C100`. That data constructor builds the appearance at data `+0x68` through `0x028750`, which stores zero to the entire flags word at appearance `+0x06`; a normally constructed creature therefore starts with word `+0x7E` equal to zero. The data constructor then stores zero to the entire word at data `+0x114`, so the low-byte `0x20` bit also starts clear. These are explicit stores, not assumptions about allocator contents. The same data constructor stores byte `3` at creature `+0x60` and 32-bit zero at creature `+0x64`; later producers may replace both.

Reset scope matters. The data reset at `0x0465C0`, called on creature `+0x10` from `0x046330`, zeroes data `+0x114`, then builds a fresh temporary appearance with `0x028750` and assigns it to data `+0x68`, so both flags words end at zero. The narrower data reset at `0x047270`, called on creature `+0x10` from `0x047110`, also zeroes data `+0x114` but makes no write to the appearance object, so it keeps the existing `+0x7E` word. These statements concern those two reset routines only, not every effect of their callers.

Appearance assignment at `0x059800` copies the whole source word at appearance `+0x06` to the destination. Data assignment at `0x04B040` and data copy construction at `0x066050` both use that appearance assignment and separately copy the whole word at data `+0x114`. Neither removes `0x1A00`, `0x2000` or the low-byte `0x20`. These are field-by-field copies; they do not establish that appearance padding bytes are copied. None of these operations draws a random value or publishes a hit.

Evidence: `0x028750–0x02875C`, `0x03B6CB–0x03B6D1`, `0x03C180–0x03C1BC`, `0x04633A–0x04633D`, `0x046697–0x046699`, `0x046738–0x046754`, `0x047113–0x047134`, `0x047270–0x04730D`, `0x04B0E7–0x04B0FA`, `0x059827–0x05982B`, `0x0660F6–0x066109`; original function files `00428750.c`, `0043c100.c`, `004465c0.c`, `00447270.c`, `0044b040.c`, `00459800.c`, `00466050.c`.

## Generation and world-update producers

The descriptor constructor at `0x1ADB20` builds an appearance at descriptor `+0x74` through `0x028750`, so descriptor `+0x7A` starts at zero. A concrete nonzero producer sits inside generator `0x1CC510`. At `0x1D3AC3` the generator checks bit `0x04` of the byte at offset `1` of its current record, a record obtained from the two-coordinate lookup helper `0x1C46F0`; when that bit is clear, the descriptor-producing branch is skipped. One route to `0x1D3AC3` additionally requires that record's byte at offset `0` to equal `4` (`0x1D3611`); whether other routes reach it, and the broader generator admission, remain open.

When the `0x10F0`-byte allocation and construction of this branch's descriptor succeed, the generator stores 32-bit `1` at descriptor `+0x28`, then sets bit `0x1000` in descriptor `+0x7A` at `0x1D3BA0`, then stores a 32-bit kind at descriptor `+0x2C`, then calls nested helpers (`0x1F8530`, `0x1F7A60`, `0x06EBE0`) on the descriptor, then sets bit `0x0200` at `0x1D3C2C`. Both bit-set operations keep every other bit. Later it stores byte `1` at descriptor `+0x10E8` (`0x1D3D2F`) and only then appends the descriptor pointer to the pointer vector at `+0x18` of the generator's current container object (`0x1D3D40`). This branch is therefore a verified producer of the classifier-excluding bits `0x1000` and `0x0200`, and of the descriptor byte used by the later `0x2000` producer.

Between the two bit-set operations there is exactly one direct random draw in this branch's own code: its result is divided, unsigned, by the candidate count and the remainder selects the kind. A second direct draw follows the `0x0200` operation and precedes the `+0x10E8` store and the append. The nested helpers were not audited for draws of their own, so no complete draw count for descriptor creation is claimed; only the placement of the flag stores relative to these two direct draws is established. An empty candidate list and allocation failure are outside this relation. Evidence: `0x1ADB99–0x1ADBB1`, `0x1D36A9`, `0x1D3AC3–0x1D3D40`; `decompiled/client/functions/005cc510.c`.

The world-update routine at `0x20C510` carries these flags into a creature. After allocating and constructing a creature with `0x03B690`, it copies, at `0x21002B–0x210059`, the low byte of descriptor `+0x28` to creature `+0x60`, the full descriptor `+0x2C` to creature `+0x64`, and the appearance at descriptor `+0x74` to creature `+0x78` through `0x059800`. Descriptor word `+0x7A` therefore arrives unchanged in creature word `+0x7E`. The source of these values is the descriptor being processed, not its vector position or any world-owner identifier.

A concrete descriptor `0x2000` producer precedes that creation. After earlier descriptor and context admission not characterized here, `0x20FCFE–0x20FD19` requires a nonnull context object whose 32-bit field `+0x34` equals `5`, and descriptor word `+0x7A` with `0x1000` set; otherwise the routine proceeds to creation without this producer. When descriptor `+0x28` is not `6`, the routine copies context `+0x3C` to descriptor `+0x34` and context byte `+0x40` to descriptor byte `+0x58`; value `6` skips only those two copies. It then calls the imported seed function with the 32-bit sum of context `+0x30` and descriptor `+0x48`, then calls helper `0x1C7730` with the descriptor and an explicit `1`. Only after that call returns does it re-read descriptor `+0x7A`: when the word has `0x0200` set and descriptor byte `+0x10E8` is nonzero, it sets `0x2000` and keeps the remaining bits. When `0x0200` is clear, it instead calls `0x0C7E80` on nine descriptor sub-objects and makes no write to the word; when `0x0200` is set but the byte is zero, it makes no write either. No path here clears an existing `0x2000`. The later appearance copy then carries `0x2000` into the hit-application check above. The identity of the context object and the full effects of `0x1C7730` are unresolved. Evidence: `0x20FCFE–0x20FE32`, `0x20FFBF–0x20FFE0`, `0x21002B–0x210059`.

A separate creature-creation branch, located at `0x2157A8–0x215BA6`, establishes a concrete `0x0800` producer. The listing does not attribute these bytes to a function, but they are the entry at zero-based index `12` of the second dispatch table of world update `0x20C510` (`0x211E04–0x211E1B`), selected when the processed actor's byte `+0x68` equals `0x5C`, and their exits jump to `0x211F2F`, `0x211F3B`, `0x211F41` and `0x215EC0`, the last of which the listing attributes to that routine. This contract gives the selector value no action name. The branch runs only when world `+0xB4` is zero and the processed actor's discriminator is nonzero, or when the processed actor pointer equals world `+0xB8`. It then calls `0x03CAA0` twice on the processed actor with signed argument `-1`. The signed 32-bit value at actor `+0x6C` must not exceed the first returned integer, and the 32-bit sum of that value and a step value prepared earlier in world update must be strictly greater than the second returned integer; equality at the second comparison does not create a creature. How that step is prepared and what `0x03CAA0` computes are outside this contract.

The branch then walks the world map and counts nonnull actors whose 64-bit field `+0x198` equals the processed actor's 64-bit identifier at `+0x08`. A signed count greater than `2` abandons creation; a count of `2` proceeds. The walk applies no discriminator filter. The new creature is allocated (`0x1E60` bytes) and constructed, and its discriminator byte becomes `3` when the processed actor's discriminator is zero and `1` otherwise.

Next the branch consults the processed actor's collection of 32-bit candidates at `+0x13F8`. When it is not empty, one direct random draw is made and its unsigned remainder by the element count selects the candidate; when it is empty, value `0x25` is used without a draw. This selection always happens before the branch reads the processed actor's 32-bit field `+0x13F4`, even when its result is later discarded. When that field equals `1`, the new creature receives the processed actor's `+0x64`, its block at `+0x300` (through `0x04AF00`) and its appearance (through `0x059800`). When it equals `2`, the branch looks up the processed actor's 64-bit field `+0x11D0` in the world through `0x02F000`, falls back to the processed actor when the lookup yields null, and copies the same three items from the resulting actor. Any other value stores the selected candidate at new creature `+0x64` and calls `0x03F7C0` with the new creature's `+0x64` field, its appearance and an explicit zero. The nested behavior of `0x03F7C0` is not closed here.

After every alternative, at `0x215A2E–0x215A42`, the new creature's whole word `+0x7E` is rewritten with `0x0200` cleared and `0x0800` set; all other bits are kept, so a copied `0x1000` or `0x2000` survives. Later, at `0x215B88–0x215BA6`, the branch copies the processed actor's 64-bit identifier to new creature `+0x198` and inserts the new creature pointer into the world map. This establishes a stored link relation without establishing an ownership label for it. Allocation failure, exceptional unwinding and the created creature's full lifetime are not closed. Evidence: `0x211E04–0x211E1B`, table at `0x222C84` with index bytes at `0x222CCC`, `0x2157A8–0x215A42`, `0x215B88–0x215BA6`.

The direct random draws identified above call `rand` from `MSVCR110.dll` through import slot RVA `0x2FC468`, and the seed call at `0x20FD38` calls `srand` from the same DLL through import slot RVA `0x2FC4B4`. These identities come from the image's PE import descriptors and the call operands. Nothing about the random algorithm, seed lifetime or cross-thread behavior is inferred from the import names.

## The low-byte `0x20` producer boundary

The data flags-word setter at `0x02F160` can change the low-byte bit when given a suitable mask. Its receiver is a data block, not a creature base. When the low byte of its second stack argument is nonzero, it sets the bits of its 16-bit first argument in data `+0x114`; when that byte is zero, it clears exactly those bits. Other bits are kept. It performs no category validation, no random draw and no event publication.

All 26 direct calls to `0x02F160` in the client listing pass a constant mask, and the masks used are `0x0001`, `0x0004`, `0x0008`, `0x0010`, `0x0040`, `0x0080`, `0x0200` and `0x0400`. None passes `0x0020`. Several direct writes outside that helper change other bits while keeping `0x20`, for example clearing masks `0xFFEF` at `0x07E8EC` and `0x2194BA`, `0xFFFB` at `0x0A6E41` and `0xFDFF` at `0x21F034`, and constant bit sets of `0x0040`, `0x0004` and `0x0001`. Whole-word stores of computed or zero values also exist (for example at `0x0258C1`, `0x03BC6F`, `0x0C82DE` and `0x207090`); they were not individually characterized and do not form a complete inventory of indirect writers.

The verified ways for a set `0x20` bit to reach a creature are therefore whole-word and data copies and the raw stream field below. Its first gameplay setter, any interface control, any authority needed to set it and any unobserved indirect writer remain unresolved. Naming this bit as a faction or permission on the strength of the relationship reader alone would be unsupported. Evidence: `0x02F160–0x02F185`, the 26 direct calls to it and the cited direct writes; `decompiled/client/functions/0042f160.c`.

## State transfer and connection replacement

The creature-data serializer at `0x0CDAA0` has separate fields for the appearance object at data `+0x68` and the flags word at data `+0x114`; in its 64-bit presence header these occupy zero-based positions `13` and `14`. The appearance field is `0xAC` bytes long, and when present it carries the creature `+0x7E` word inside it. Its selector `0x0CB930` includes the field when forced or when comparison `0x0CC840` reports a difference; that comparison checks the whole appearance `+0x06` word, so a change in any of its 16 bits can cause inclusion. No claim is made that padding takes part in the comparison. The flags-word selector `0x0CB670` includes two bytes when forced or when the whole word differs; it neither isolates nor normalizes `0x20`. The appearance field precedes the flags-word field.

The matching memory reader `0x0CCFA0` and socket reader `0x0CD3E0` use the same two positions. An absent field leaves existing storage untouched; it does not clear flags. For a present field with enough remaining bytes, the memory reader copies all `0xAC` appearance bytes (`0x0CC1C0`) or both flags bytes (`0x0CBED0`) without checking any protection or classification mask. When too few bytes remain, it moves the read position to the end of the buffer and skips that field's copy; fields already copied stay copied. The socket helpers (`0x0CC240`, `0x0CBF40`) receive straight into the destination object or word, so a short or failed receive can leave the destination partly overwritten; no rollback is established. Whole-message admission, staging and publication locking are not characterized by these field helpers. Evidence: original files `004cdaa0.c`, `004cb930.c`, `004cb670.c`, `004cc840.c`, `004ccfa0.c`, `004cd3e0.c`, `004cc1c0.c`, `004cbed0.c`, `004cc240.c`, `004cbf40.c`, checked against their instruction ranges.

The connection-start routine at `0x06FC50` shows that a received block is not always adopted as actor state. It receives a separate 64-bit identifier and a `0x1168`-byte data block into a temporary data object. On the route taken when that identifier is non-negative, it copy-constructs a second temporary from the previous current creature's data block (`0x070211–0x070221`), then destroys the actors in the world map, looks up the replacement current creature by identifier and constructs one when the lookup yields null, and assigns the saved old data to the replacement creature's `+0x10` (`0x070333–0x070343`). That assignment carries the old appearance flags and old flags word as described above. Receipt of the raw block is therefore not sufficient evidence that its flags become the replacement creature's flags on this route. This observation is not extended to other incoming state routes. Evidence: `0046fc50.c`; `0x0701A1–0x070343`.

## World mode and designated-pointer lifetime

The world constructor at `0x18EB00` stores the low byte of its second stack argument into world `+0xB4` and stores a null pointer into world `+0xB8`. It does not normalize the mode byte to `0` or `1`. The client constructor `0x059C40` passes zero for that argument when constructing its embedded world (`0x059F31–0x059F57`). After inserting its initial current creature into the world map, the client constructor calls `0x087E90` with the value at client `+0x8006D0`. That setter assigns its four-byte argument to world `+0xB8` without rejecting null, checking membership or deriving an identifier. Normal client start-up therefore has mode zero together with a designated creature pointer; designation does not require a nonzero mode. Evidence: `0x18EC09–0x18EC12`, `0x059F31–0x059F57`, `0x062219–0x06222C`, `0x087E90–0x087E9D`.

When the address given to `0x06FC50` is nonempty, the routine stores byte `1` at client `+0x398` (`0x06FCA7`) before socket creation, address resolution, connection and handshake. A nonzero mode is therefore not proof of an established connection or a completed handshake. Failure exits that store zero to the mode after their cleanup were found at `0x06FE47`, `0x06FEE9`, `0x07018C`, `0x070745` and `0x070931`. Not every exceptional or early exit was shown to do the same, so no exhaustive failure-state guarantee is made.

On the successful replacement route, `0x070408` stores the then-current creature pointer from client `+0x8006D0` into client `+0x39C`, updating world `+0xB8` after the data assignment above. This changes pointer identity only; it compares no faction and does not designate other actors whose link field happens to match that creature.

In the worker routine `0x069C10`, the tail at `0x06A845–0x06A869`, when client byte `+0x800585` is nonzero, closes the socket, clears the socket field and stores zero to client `+0x398`. The disconnect routine `0x0719F0` does nothing unless client byte `+0x800585` is nonzero; it then clears that byte, and if the socket field is nonzero it closes the socket, clears the field and stores zero to the mode (`0x071A5B`). It next waits, through the imported `WaitForSingleObject` with an infinite timeout, on each nonnull handle at client `+0x800590` and `+0x800594` and clears those fields, calls `0x201CB0` on the embedded world, and stores zero to the mode again (`0x071AAD`). No direct write addressed as client `+0x39C` occurs in `0x0719F0`, `0x069C10` or anywhere in `0x06FC50` other than `0x070408`. This absence promises nothing about nested callbacks, destruction or pointer validity during exceptional transitions. Evidence: `00469c10.c`, `0046fc50.c`, `004719f0.c`; instruction ranges at the cited sites.

## Remaining bounds

This audit proves concrete producers for each bit of the `0x1A00` exclusion mask, a concrete pre-creation `0x2000` producer, the default, reset and copy behavior, preservation through the selected stream fields, and the client mode and designation transitions. It does not prove these are the only writers.

## Unresolved

- Whether the cited producers are the only writers of creature `+0x7E`, of the `0x20` bit at creature `+0x124`, and of world `+0xB4` and `+0xB8`, including writes through indirect aliases and every state-publication route.
- The first gameplay setter of creature `+0x124` bit `0x20`, any interface control for it and any authority it requires.
- The full admission of generator `0x1CC510` before `0x1D3AC3`, including every route to that point, the size and meaning of the record returned by `0x1C46F0`, and random draws made inside the nested helpers of the descriptor branch.
- The identity of the context object checked at `0x20FD06`, the earlier descriptor and context admission in world update, and every effect of `0x1C7730`.
- The behavior of `0x03F7C0` and `0x03CAA0`, the preparation of the step value used at `0x2157ED`, and the meaning of selector value `0x5C` at actor `+0x68`.
- The complete value taxonomy of discriminator `+0x60` and of kind `+0x64`; no faction label follows from the values the readers use.
- All callers of the two data resets and their surrounding effects.
- Null and stale pointers where no internal guard is shown, malformed streams, impossible container lengths, allocation failure, exceptional floating-point values beyond the cited comparisons, concurrent visibility outside the cited operations, complete fatal processing, and full actor and descriptor destruction.
- Any behavior of a separate server executable; none is inferred from the client's zero and nonzero branches. Earlier held artifacts remain outside this artifact's evidence and are unchanged.

## Re-certification (2026-11-22)

A fresh source-only author re-checked every statement in this document against the original client image (hash confirmed), its instruction listing, its import table and the cited original function files; Infinite-Cubes material was not needed and was not used.
