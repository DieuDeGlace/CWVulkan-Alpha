# Original client path-state expansion and list order

Status: FINAL / STABLE / HELD. This independent, code-free contract covers original client setup RVA `0x1A9F90`, one-step operation RVA `0x1AAAB0`, and coordinate-list production RVA `0x1A7C90`. It closes the ordinary container, score, selection, update, and predecessor transitions, and the setup-time population of actor `+0x1468`. The large terrain/spatial classification inside the step is identified but remains partly unclosed. The description does not assign a standard pathfinding algorithm to the native routines.

The supported original is `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. Paths cited below are relative to `Documents/disassembled alpha cube world`. Original image disassembly was checked directly, including returns and cleanup omitted by the decompiler. No reconstruction, replacement implementation, runtime, or earlier contract is evidence for this document.

## Inputs and persistent search state

Setup and step receive the world in ECX and an actor pointer as their one stack argument. Both return with four argument bytes removed. List production receives the actor as its stack argument and does not require a world query. The one-step routine returns a Boolean in AL. Its apparent void decompile is incomplete: the original image explicitly returns true following an ordinary nonterminal expansion and false at its terminal/no-work/reset exits. Setup and list production have no established Boolean-status contract here. [Evidence: `binary/Cube.exe`, RVAs `0x1A9F90–0x1A9FB4`, `0x1AAAA9–0x1AAAAE`, `0x1AAAB0–0x1AAAF5`, `0x1AD17F–0x1AD19A`, `0x1AD2E4–0x1AD312`, `0x1A7C90–0x1A7CB4`, `0x1A7D95–0x1A7DA5`; `decompiled/client/functions/005a9f90.c`, `005aaab0.c`, `005a7c90.c`.]

Actor `+0x1428` and `+0x1440` are separate supplied endpoint triplets, each three signed 64-bit raw coordinates. This audit calls them the start and destination because setup seeds the former and later comparisons use the latter. Their producers, freshness relative to actor `+0x10`, and the reasons a caller starts or resumes a search are unclosed. Neither endpoint is implicitly substituted with current actor position by these three routines. [Evidence: `binary/Cube.exe`, RVAs `0x1A9FB9–0x1AA008`, `0x1AAB00–0x1AAB19`, `0x1A7CA6–0x1A7CC9`.]

The following roles are established by accesses, independently of symbolic type names:

| Actor field | Width and established role |
| --- | --- |
| `+0x1408` | 32-bit pointer to a remembered entry in the coordinate-record map, or that map's end sentinel |
| `+0x140C`, `+0x1410` | 32-bit map-header pointer and 32-bit count of coordinate records |
| `+0x1414`, `+0x1418` | 32-bit header pointer and 32-bit count of a separate unique set of pending coordinate keys |
| `+0x141C/+0x1420/+0x1424` | three 32-bit converted start coordinates written by setup |
| `+0x145C` | 32-bit field set to zero by setup; a wider status meaning is not established |
| `+0x1460`, `+0x1464` | 32-bit header pointer and 32-bit count of the produced coordinate list |
| `+0x1468`, `+0x146C` | 32-bit header pointer and count of a separate unique set containing resident spatial-record pointer values |

Each ordinary coordinate key contains exactly three signed 32-bit components in first-horizontal, second-horizontal, third-coordinate order. Its associated record contains six 32-bit words: accumulated score, destination score, selection score, and a three-component predecessor coordinate. In a native map node the key's storage pointers begin at node `+0x10`, and the six-word record begins at node `+0x1C`; the destination-score word is consequently node `+0x20`. These are coordinate keys, not creature IDs or pointers. [Evidence: `binary/Cube.exe`, RVAs `0x1A9DA0–0x1A9E48`, `0x1A9ECB–0x1A9EEF`, `0x1A9F0F–0x1A9F5C`; `decompiled/client/functions/005a9da0.c`, `005a9e50.c`, `005a7a40.c`.]

## Coordinate conversion, ordering, and equality

Endpoint conversion uses RVA `0x02F040`. It performs signed 64-bit division by raw `65536`, retains a signed 32-bit quotient, and additionally subtracts one for every negative raw component. This subtraction also occurs at an exactly integral negative coordinate. It processes the third component first, then the second, then the first; the output remains in first/second/third order. It is not a uniform mathematical floor at negative integral boundaries. Ordinary use requires representable grid quotients and nonoverflowing bounds. [Evidence: `binary/Cube.exe`, RVAs `0x02F040–0x02F0FE`; `decompiled/client/functions/0042f040.c`.]

The map and pending-key set use signed lexicographic comparison of the stored 32-bit component sequences. First horizontal component is decisive first, then second horizontal component, then third component. Equal three-component keys are equivalent regardless of their source allocation address. A negative component, including a high-bit pattern, sorts before a nonnegative one when that component is the first difference. Signed zero compares normally. The general comparator also orders a proper shorter prefix before a longer sequence, but the audited ordinary callers always construct three components. [Evidence: `binary/Cube.exe`, RVAs `0x1A78A0–0x1A78F8`, `0x1A7C10–0x1A7C8D`; `decompiled/client/functions/005a78a0.c`, `005a7c10.c`.]

Lookup RVA `0x1A9DA0` returns the six-word record for an exactly equal map key or a null pointer. Membership RVA `0x1A9CA0` returns AL true only for an equal key in the pending set. Both construct a temporary three-component key and release its temporary storage afterward. The map lookup's returned record remains resident separately from the temporary key. Pending insertion through RVA `0x1A7700` is unique: an equivalent key retains one pending entry rather than creating a duplicate. Map access through RVA `0x1A7A70` similarly obtains an existing record or creates one for a new key. [Evidence: `binary/Cube.exe`, RVAs `0x1A9CA0–0x1A9D30`, `0x1A9DA0–0x1A9E48`, `0x1A9EB0–0x1A9F0A`, `0x1A7B26–0x1A7B44`; `decompiled/client/functions/005a7700.c`, `005a7a70.c`.]

These signed coordinate comparisons differ from actor `+0x1468`, whose keys are compared as unsigned 32-bit pointer values. Neither ordering uses an actor's role, kind, own ID, or insertion age as a key component. Terrain admission can separately reject coordinates that the coordinate containers are capable of ordering. [Evidence: `binary/Cube.exe`, RVAs `0x1A78BA–0x1A78C4`, `0x18E7D0–0x18E8CD`, `0x1AB640–0x1AB6A0`; `decompiled/client/functions/0058e7d0.c`.]

## Setup order and initial score

Setup first invokes actor clearing helper RVA `0x02EF10`. That clears coordinate records, pending coordinates, the produced coordinate list, the remembered-entry pointer, and the pointer set at `+0x1468`. The remembered pointer becomes the coordinate-map end sentinel. The original helper's final jump to RVA `0x27E480` explicitly uses actor `+0x1468` as receiver. Endpoint storage remains an input to the subsequent setup work. [Evidence: `binary/Cube.exe`, RVAs `0x1A9FA5–0x1A9FB4`, `0x02EF10–0x02EFB6`; `decompiled/client/functions/0042ef10.c`, `0067e480.c`.]

Setup converts the start and writes the three words at `+0x141C/+0x1420/+0x1424`. It converts the start again for the seed key, writes zero to `+0x145C`, and converts the destination. For ordinary signed differences, the integer destination-score relation is twice the sum of ten times the larger absolute horizontal difference, four times the smaller absolute horizontal difference, and ten times the absolute third-coordinate difference. The absolute-value, products, additions, and final doubling use 32-bit integer arithmetic. This document does not substitute Euclidean length or another distance relation. Signed minimum-integer absolute value and overflow are outside the ordinary domain. [Evidence: `binary/Cube.exe`, RVAs `0x1A9FB9–0x1AA069`; destination-score helper RVA `0x1A9D40–0x1A9D98`; `decompiled/client/functions/005a9d40.c`.]

The seed has a distinct conversion boundary: the integer relation is converted to binary32 by `CVTDQ2PS`, then truncated back to signed 32 bits by `CVTTSS2SI`. This can change a large ordinary integer score through binary32 rounding. The converted value is stored both as the seed's destination score and its selection score. Its accumulated score is exactly one, and its predecessor is the seed's own three-component start key. Thus the seed's selection word is the rounded destination score itself, not that value plus one. The seed is installed through RVA `0x1A9E50`, which publishes its pending key and remembered-entry candidate. [Evidence: `binary/Cube.exe`, RVAs `0x1AA05D–0x1AA095`.]

After seed publication, setup explicitly clears actor `+0x1468` again, then completes the two endpoint spatial scans below. A step called later observes the set produced by those scans, rather than a per-step rebuilding of endpoint overlap. [Evidence: `binary/Cube.exe`, RVAs `0x1AA09A–0x1AA0A8`, `0x1AA0AD–0x1AAAA4`.]

## Actual population and lifetime of actor +0x1468

Setup scans around the start endpoint first and the destination endpoint second. For each endpoint it converts its raw triplet to a signed 32-bit grid triplet, scales each component back to signed 64-bit raw units, and adds a center offset: binary32 `0.5` times `65536` on each horizontal axis, and binary32 actor `+0x88` times `0.5`, then times `65536`, on the third axis. Every offset passes through x87-to-signed-64 conversion RVA `0x28D946`. The endpoint center therefore uses grid coordinate plus a half-cell horizontally, and grid coordinate plus converted actor half-height vertically. It is not the unchanged raw endpoint. [Evidence: `binary/Cube.exe`, RVAs `0x1AA0AD–0x1AA199`, `0x1AA54F–0x1AA652`.]

From each center's horizontal raw coordinates, setup uses signed division by `65536`, retains the low 32-bit quotient, and divides by eight toward zero. It scans the inclusive three-by-three neighborhood around those coarse coordinates, first coordinate outermost, second inner. Coarse coordinates must be within `0..0x1FFFFF`. Chunk lookup RVA `0x034D10`, or its inline counterpart on the second scan, rejects chunk coordinates outside `0..0xFFFF` and uses resident region/chunk tables. Buckets come from chunk `+0xAC`, with second remainder times 32 plus first remainder and an eight-byte stride. Resident entries are traversed in their existing next-pointer order. Missing region/chunk/bucket routes produce no set insertion; these paths do not invoke loading or generation. [Evidence: `binary/Cube.exe`, RVAs `0x1AA17F–0x1AA276`, `0x1AA638–0x1AA7D1`; `decompiled/client/functions/00434d10.c`, `00434a90.c`, `005a9f90.c`.]

An entry's spatial-record pointer is taken from entry `+8`. Record selector values 7, 6, and 9 are excluded. For selectors 1, 8, 2, 3, and 5, record byte `+0x30` must be nonzero; other selectors do not receive this byte gate. Record coordinates are three signed 64-bit words at `+8/+0x10/+0x18`, sizes are binary32 at `+0x24/+0x28/+0x2C`, and the 32-bit orientation operand is `+0x20`. Odd orientation swaps the two local horizontal sizes, including for negative odd values. No descriptor ordinal or creature ID participates in these tests. [Evidence: `binary/Cube.exe`, RVAs `0x1AA276–0x1AA2FA`, `0x1AA7D1–0x1AA856`; `decompiled/client/functions/005a9f90.c`.]

Overlap is tested in horizontal-first, horizontal-second, third-axis order. Each horizontal record half-size and actor half-size is separately multiplied in binary32 by `65536` and truncated to signed 64 bits, record first, actor second. Record lower edge must be less than or equal to actor-center upper edge, while actor-center lower edge must be strictly below record upper edge. On the third axis the record coordinate is a base: it must be at or below center plus converted actor half-height, and center minus actor half-height must be strictly below record base plus its converted full third size. There is no nonnegative-size clamp. A record passing all gates inserts the 32-bit pointer value itself, copied from entry `+8`, into actor `+0x1468`. [Evidence: `binary/Cube.exe`, RVAs `0x1AA2FA–0x1AA50D`, `0x1AA856–0x1AAA5A`; insertion helper RVA `0x18E7D0`, node-value copy RVA `0x0C9580`; `decompiled/client/functions/004c9580.c`.]

The two scans accumulate a unique union of pointer values. Seeing the same pointer through several buckets or both endpoints does not duplicate it. Distinct records with equal coordinates or sizes remain distinct pointers. Insertion compares unsigned pointer values, and the stored entry is a pointer-sized value, not a copy of the record. Clearing this set deletes its container nodes; the inspected clear path does not delete the referenced spatial records. Their ownership, removal, pointer reuse, and lifetime protection are unclosed. [Evidence: `binary/Cube.exe`, RVAs `0x18E7D0–0x18E8CD`, `0x22FBC0–0x22FC1E`, `0x27E480–0x27E4C4`; `decompiled/client/functions/0058e7d0.c`, `0062fbc0.c`, `0042ca80.c`, `0067e480.c`.]

The step's spatial scan checks membership in this set before its record geometry. A present pointer is skipped exactly by pointer equality. The step does not refresh the set as its selected coordinate moves. Its setup-time endpoint association therefore remains cached until a reached clearing/setup operation or another writer changes it. This is a bounded writer/consumer result, not an exhaustive inventory of every writer in the entire image. [Evidence: `binary/Cube.exe`, RVAs `0x1AB640–0x1AB6B2`; `decompiled/client/functions/005aaab0.c`.]

## One-step admission, selection, and tie order

A zero coordinate-record count returns false immediately. Otherwise pending count is tested as unsigned against 500 and record count as unsigned against 20000. Exceeding either bound clears actor search/list/pointer-set state through RVA `0x02EF10` and returns false. Equality at either bound is admitted. The limits are checked once before expansion; insertions within that invocation can exceed them and are detected only on a subsequent step. [Evidence: `binary/Cube.exe`, RVAs `0x1AAAC8–0x1AAB00`, `0x1AD2F9–0x1AD312`.]

Under the limits, the destination endpoint is converted afresh. A zero pending count then returns false while retaining the record map and remembered pointer. Otherwise the pending set is traversed from its smallest key through in-order successors, using RVA `0x1C3EA0`. Each pending key is looked up in the record map. The first found record becomes the candidate; a later record replaces it only if its selection score is strictly smaller under signed 32-bit comparison. Equal selection scores keep the first in traversal order. Therefore ordinary equal-score selection ties resolve by signed lexicographic first/second/third coordinate order, not insertion or neighbor-production order. [Evidence: `binary/Cube.exe`, RVAs `0x1AAB00–0x1AAB98`; `decompiled/client/functions/005c3ea0.c`.]

The selected pending entry is removed before comparison with the destination grid. Erasure releases that pending node and its key storage and decrements the pending count; the corresponding six-word coordinate record remains in the separate record map. An exact three-component match with destination returns false after this removal, without neighbor expansion or clearing the record map. There is no distance tolerance in this goal test and no write to `+0x145C` on this branch. [Evidence: `binary/Cube.exe`, RVAs `0x1AAB98–0x1AABF7`, `0x03F6CE–0x03F715`.]

An ordinary selected non-destination coordinate proceeds through geometry classification and neighbor consideration once, and returns true after that expansion even if no neighbor was inserted or improved. It does not perform another minimum-score selection in the same call. The map/pending consistency assumption matters: missing record lookups are skipped during scanning, but an all-missing or corrupt pending set does not receive a separately established safe fallback. [Evidence: `binary/Cube.exe`, RVAs `0x1AAB42–0x1AABF7`, `0x1AD17F–0x1AD19A`, `0x1AD2E4–0x1AD312`.]

## Bounded geometry classification inputs

For the selected grid coordinate, the step forms a raw center with horizontal offset `32768` and vertical offset obtained from binary64 actor height times `0.5` times `65536`, converted to signed 64 bits. This binary64 vertical calculation differs from setup's binary32 half-height products. It obtains a binary32 zero/zero/`0.01` offset through converter RVA `0x02C460`, and actor binary32 half-sizes through the same converter. Each component supplied to that converter is multiplied in binary32 by `65536`, stored as binary32, and truncated through RVA `0x28D946`. The two bound corners pass through RVA `0x02F040` and their grid ranges are expanded by one cell for classification. The center arithmetic helpers RVA `0x02C800` and the conversion helper operate on complete 64-bit components, in axis order. [Evidence: `binary/Cube.exe`, RVAs `0x1AABF7–0x1AAE0A`, constants RVAs `0x345DE8` (binary64 `0.5`), `0x2FD588` (binary64 `65536`), `0x302A88` (binary64 `32768`), immediate `0x3C23D70A` at `0x1AACA0`; `decompiled/client/functions/0042c460.c`, `0042c800.c`.]

The first reached cell query is RVA `0x02F860`, with a zero final hint and the constructed center's third coordinate reduced by a converted offset. Byte `+3` bit 1 of that returned cell is retained independently of the five-bit blocking-type test. Its environmental meaning is not established here. Then a resident terrain boundary scan classifies lower/upper interior, faces, edges, and corners. It treats low-five-bit types zero and two as nonblocking; other types contribute classification flags. It subsequently scans resident spatial buckets, applies the cached pointer-set exclusions, and computes additional record-derived support and horizontal-admission flags. The complete relationship between terrain inputs, all classification flags, and record geometry remains unclosed in this bounded contract. In particular these flags must not be replaced by guessed independent walkability predicates. [Evidence: `binary/Cube.exe`, RVAs `0x1AAF50–0x1AB5CE`, `0x1AB606–0x1AC3D0`; `decompiled/client/functions/005aaab0.c`, `0042f860.c`, `0042f7e0.c`.]

Reached resident dependencies include chunk lookup RVAs `0x034D10/0x034A90`, cell lookup RVAs `0x02F860/0x02F7E0`, and stored cell accessor RVA `0x02F730`. They read world `+0xBC`, region `+0x10018`, chunk terrain `+0xA8`, and spatial buckets `+0xAC`. Column base/count and stored cell data, missing/lower/upper sentinels, and per-record geometry contribute to classification. Signed 64-bit comparison helpers RVAs `0x194660/0x194690` compare signed high words followed by unsigned low words. The spatial branch also reaches selector-dependent gates and compares three words beginning at bucket entry `+0x0C` with actor `+0x1478`; the producers and full behavioral role of that comparison are unresolved. No coordinate/ID identity is inferred merely from these offsets. [Evidence: `decompiled/client/functions/00434d10.c`, `00434a90.c`, `0042f7e0.c`, `0042f730.c`, `00594660.c`, `00594690.c`; `binary/Cube.exe`, RVAs `0x1AB6B2–0x1AC39B`.]

For the closed score transitions below, the lower-interior terrain-classification flag is the byte at native frame offset EBP minus `0x94`, tested at RVAs `0x1AC88E/0x1AC910` and analogous neighbor branches. This document calls it the lower-interior flag without assigning an environmental name. It has a direct effect on edge scores even when record-derived support also admits the same branch. Geometry producers and caller scheduling are the explicit boundary of the conditional transition contract below.

## Neighbor sequence and record transitions

When their respective geometry gates admit consideration, candidate coordinates are processed in this exact order relative to the selected key: first horizontal minus one; first horizontal plus one; second horizontal minus one; second horizontal plus one; the four horizontal diagonals in minus/minus, plus/minus, minus/plus, plus/plus order; third coordinate minus one; third coordinate plus one. There is no random permutation, sort by candidate score, or second selection pass between these branches. All candidates retain the selected coordinate on unaffected axes. [Evidence: `binary/Cube.exe`, RVAs `0x1AC3D0–0x1AD2E4`, call sites `0x1AC464`, `0x1AC64F`, `0x1AC831`, `0x1AC9E0`, `0x1ACB60`, `0x1ACCB1`, `0x1ACE25`, `0x1ACF83`, `0x1AD0F6/0x1AD1B5`, `0x1AD28C`; `decompiled/client/functions/005aaab0.c`.]

For an admitted coordinate absent from the record map, the step computes a fresh destination score with the integer relation above using a fresh conversion of the current destination endpoint. Unlike the setup seed, newly considered neighbors do not round this integer score through binary32. Their accumulated score is the selected record's accumulated word plus the branch cost below; their selection score is the 32-bit sum of accumulated and destination scores. The predecessor is the selected coordinate, copied as three 32-bit words. [Evidence: `binary/Cube.exe`, RVAs `0x1AC47D–0x1AC528`, `0x1AC668–0x1AC719`, `0x1AC84A–0x1AC8C2`, `0x1AC9F9–0x1ACA75`, and later corresponding neighbor branches; helper RVA `0x1A9D40`.]

For an admitted coordinate already present in the record map, the step first requires that coordinate still be present in the pending set. A record removed from pending by an earlier selection is not reopened by these update branches. The proposed accumulated score must then be strictly smaller under signed 32-bit comparison. Equality retains the existing scores and predecessor. On improvement the old destination-score word is reused, selection score is recomputed from the improved accumulated score and that old destination score, and the predecessor becomes the current selected coordinate. [Evidence: `binary/Cube.exe`, RVAs `0x1AC548–0x1AC5A2`, `0x1AC740–0x1AC79A`, `0x1AC8DF–0x1AC955`, later membership/improvement branches through `0x1AD2DF`; `decompiled/client/functions/005a7a40.c`, `005a9ca0.c`.]

The branch costs added to the selected accumulated score are:

| Candidate | Lower-interior flag set | Flag clear |
| --- | --- | --- |
| first horizontal minus/plus one | 10 | 20 |
| second horizontal minus one, new record | 10 | 30 |
| second horizontal minus one, existing pending improvement | 10 | 20 |
| second horizontal plus one | 10 | 20 |
| any admitted horizontal diagonal | 14 | 24 |
| third coordinate minus one | 0 | 0 |
| third coordinate plus one | 0 | 40 |

The asymmetric new-record cost 30 is confirmed in native instructions: the branch adds 10 and, with the flag clear, another 20. The corresponding existing-record improvement branch adds only another 10. It is not normalized to match the other cardinal branches. All score arithmetic here is 32-bit integer arithmetic; there is no saturation or nonnegative clamp. [Evidence: `binary/Cube.exe`, RVAs `0x1AC87F–0x1AC893`, `0x1AC901–0x1AC915`, cardinal and diagonal score branches `0x1AC3D0–0x1AD07D`, vertical branches `0x1AD0F6–0x1AD2DF`.]

Each cardinal branch retains a local success flag only when it actually inserts a new record or improves an existing pending record. Passing geometry alone does not set this flag. Each diagonal additionally requires both corresponding cardinal success flags from this same invocation and its own corner/support geometry conditions. Consequently a geometrically available cardinal whose equal-cost or already-selected record is retained can prevent a diagonal from being considered. These local flags, and later branch-carried classification bytes, mean neighbor admission cannot generally be treated as ten independent geometry queries. The exact complete geometry predicate for every neighbor remains unclosed here. [Evidence: `binary/Cube.exe`, RVAs `0x1AC3D0–0x1ACB60`, `0x1ACB60–0x1AD08A`; `decompiled/client/functions/005aaab0.c`.]

Publication helper RVA `0x1A9E50` first obtains or creates the coordinate-map record and copies all six supplied words in order. It then inserts the coordinate in the pending set, whose duplicate policy leaves one entry. Finally it considers the remembered map-entry pointer at actor `+0x1408`. An end-sentinel remembered pointer is replaced; otherwise replacement requires a strictly smaller signed destination score than the remembered entry currently holds. Equal destination scores retain the prior remembered pointer. This remembered choice is based on destination score, whereas pending selection is based on selection score; they are distinct decisions. No equal-score predecessor replacement is added by publication. [Evidence: `binary/Cube.exe`, RVAs `0x1A9EC6–0x1A9F62`; `decompiled/client/functions/005a9e50.c`.]

## Coordinate-list production and partial chains

RVA `0x1A7C90` converts the current start endpoint and the current destination endpoint before clearing the old coordinate list. It detaches and deletes every old list node, retains the list header, and sets count `+0x1464` to zero. It chooses an initial terminal coordinate from the remembered map-entry key if `+0x1408` is not the map end sentinel; otherwise it uses the freshly converted destination. It does not require this remembered key to equal the destination or still be pending. [Evidence: `binary/Cube.exe`, RVAs `0x1A7CA6–0x1A7D3E`.]

The terminal coordinate is inserted at the front of the list before testing whether it already equals the converted start. Each list node stores the three 32-bit coordinate words at node `+8/+0x0C/+0x10`. The insertion helper copies those words; it does not convert them back to raw fixed-point coordinates or retain a pointer to a map key. If terminal equals start, the produced list contains that single coordinate. [Evidence: `binary/Cube.exe`, RVAs `0x1A7D3E–0x1A7DA5`; `decompiled/client/functions/005a6b60.c`.]

Otherwise the routine looks up the current coordinate in the record map and reads its three predecessor words. A missing map record stops production immediately, retaining the list already built. A predecessor equal to the current coordinate also stops without inserting a duplicate. Any other predecessor is copied into a new node inserted at the front, and becomes the next lookup coordinate. Reaching start stops on the next equality test. Thus an ordinary complete chain is published in start-to-terminal order even though its records are followed backward. The output terminal may be a remembered partial destination-score candidate. [Evidence: `binary/Cube.exe`, RVAs `0x1A7D81–0x1A7E54`.]

The predecessor guard compares its signed iteration counter with the map's record count before each lookup and stops only when the counter is greater, not equal. Starting from zero, it permits up to record-count plus one predecessor lookups in the ordinary representable domain. It is a length guard rather than a visited-coordinate set: a longer cycle can leave a partial list with repeated coordinates before that guard stops it. There is no rollback of partial output, no separate completeness flag returned by this routine, and no deletion of map records or pending keys during list production. In the ordinary count domain, insertion at count `0x0CCCCCCB` reaches the native length-error service; allocator and length-error exceptional behavior are outside the ordinary list contract. [Evidence: `binary/Cube.exe`, RVAs `0x1A7D56–0x1A7D70`, `0x1A7DA8–0x1A7DC5`, `0x1A7E25–0x1A7E54`.]

## Boundaries and unresolved dependencies

The closed transitions assume stable, well-formed search containers, valid actor/world pointers, three-component keys, representable endpoint grid quotients, nonoverflowing score/bound/count arithmetic, and successful allocations. Native signed absolute value and score arithmetic are not promoted to unlimited precision; malformed counts, negative overflowed scores, minimum signed integers, damaged trees/lists, and allocation failure are not assigned a normalized outcome. The explicit signed/unsigned comparisons and setup float-rounding boundary remain part of the contract. Floating-point control for setup and geometry conversions is ambient; the routines do not establish a private rounding mode. [Evidence: the original arithmetic and call boundaries cited above; conversion helpers RVAs `0x28D946/0x28D9E0`.]

No random-number or seed access is present in the closed container, score, selection, rebuild, or setup pointer-overlap operations. Resident geometry still depends on terrain/spatial producers not audited here. The full classification scan, its sentinels and selector-specific geometry, the provenance of actor `+0x1478`, endpoint/dimension producers, and all external reset/call scheduling remain unclosed. No shortest-route, eventual-completion, complete terrain-admission, whole-frame, or server-equivalence guarantee follows from this document.

No lock, record ownership transfer, or lifetime pin is established by these three entry points. Setup allocates and mutates search containers; a step mutates records, pending keys, and the remembered pointer; list production deletes old list nodes and publishes new ones. The pointer set owns its set nodes but has no established ownership of the referenced spatial records. Its cached pointers can become stale if external publication/removal/reuse occurs. Independently changing endpoints between setup, step, and list production can also mix epochs because destination conversion is repeated while existing record destination scores and predecessors are retained. Those synchronization and lifetime routes are explicitly unresolved. Native security-cookie and exception/allocator services are protection/error boundaries, not evidence of synchronization.
