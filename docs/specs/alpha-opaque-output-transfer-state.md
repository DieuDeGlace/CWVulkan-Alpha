# Alpha opaque-terrain output and transfer-state provenance

This is a bounded, original-evidence, code-free contract for the ordinary opaque-terrain draw region at RVAs `0x0b1a6b–0x0b1d9a` inside the renderer at RVA `0x0ac260`. The supported image is `binary/Cube.exe`, SHA256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. Addresses below are RVAs unless explicitly identified as interface offsets. Original citations are relative to the original Alpha evidence root. Public Microsoft Direct3D declarations and documentation are used only to identify APIs, format values and documented API behavior.

The established local result is narrower than a complete display transfer function. The terrain binder selects an embedded vertex/pixel program pair and supplies an output-alpha constant of one. The bound terrain pixel program has no sampled scene texture and no RGB gamma-encoding operation. The draw region does not establish the device's sRGB-write bit or install a gamma ramp. Device creation supplies a documented default starting point, but the complete lifetime of inherited device state through every callback is not closed by this trace. A universal identity transfer, universal sRGB encoding, and a universal power of `1/2.2` are therefore all unestablished. Missing assignments are not substituted for provenance.

Evidence boundaries

The original sources used are `binary/Cube.exe`, `decompiled/client/assembly.txt`, individually named original function exports, and `decompiled/client/assembly-functions/004ac260.asm` and `decompiled/client/assembly-functions/00459c40.asm`. The renderer and constructor pseudocode exports timed out; their instruction exports and original image bytes supply those paths. Embedded pixel-program bytes were examined directly from the supported original image using the Microsoft disassembler. No replacement SDK, engine, tests, probes, captures, logs, history, reconstruction or earlier specification supplied facts. Earlier held artifacts remained unopened and unchanged.

The four-byte COM slot layout is identified from Microsoft's public [Direct3D 9 interface declarations](https://raw.githubusercontent.com/microsoft/win32metadata/main/generation/WinSDK/RecompiledIdlHeaders/shared/d3d9.h). Relevant device-interface byte offsets are `0x40` Reset, `0x44` Present, `0x54` SetGammaRamp, `0x58` GetGammaRamp, `0x94` SetRenderTarget, `0x98` GetRenderTarget, `0xe4` SetRenderState, `0xec` CreateStateBlock, `0xf0` BeginStateBlock and `0xf4` EndStateBlock. Declaration and program binding use `0x15c`, `0x170` and `0x1ac`; indexed drawing uses `0x148`. These identifications depend on the object being the traced Direct3D device, not merely on a coincidentally matching offset in another object's table.

Device and back-buffer provenance

The application initializes Direct3D with version argument 32, creates an adapter-zero hardware device, and stores its device pointer in the original global at RVA `0x36b1b4`. The initial presentation parameters are cleared before their fields are filled. They request windowed presentation, discard swap effect, automatic depth/stencil format numeric 75, and immediate presentation interval `0x80000000`. The initial back-buffer-format field remains numeric zero, rather than explicitly requesting an eight-bit ARGB format. Under the documented windowed `D3DFMT_UNKNOWN` rule, the runtime selects the current display-mode format. Consequently, the exact initial back-buffer color format depends on that display mode.

The controller constructor receives this same device pointer from the application and stores it at controller `+0x134` through its base construction. The terrain program object receives the same device pointer at its own `+0x1c`. These are positively traced pointer origins; the terrain device is not inferred merely from method names.

The resize/display-mode reset routine has a different explicit color-format request. For a positive selected width and height, it clears a new presentation-parameter structure, supplies numeric format 21, and sets windowed/full-screen from the saved mode choice. Format 21 is `D3DFMT_A8R8G8B8`; format 75 is `D3DFMT_D24S8`. The routine requests discard swap effect and the immediate interval again. It retries Reset after 100 ms sleeps until success. Its selected multisample type is zero when the saved selection is zero, otherwise twice the saved selection. None of these format or multisample settings is an sRGB-write assignment.

After a successful reset, the explicit implicit-swap-chain color-format request is therefore A8R8G8B8. The initial UNKNOWN-format case remains distinct until such a reset actually occurs. This contract does not assume that every first terrain draw has already passed through that reset. In windowed presentation the runtime may convert between the back-buffer and desktop formats; a successful A8R8G8B8 request does not prove the desktop format or a physical display transfer function. Microsoft documents the [presentation-parameter fields and UNKNOWN rule](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dpresent-parameters), the [format identifiers](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dformat), and the loss of prior device state on [Reset](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-reset).

Original evidence: `decompiled/client/functions/004c8720.c`, RVA `0x0c8720`, confirmed creation arguments in `binary/Cube.exe` and `decompiled/client/assembly.txt` at `0x0c875b–0x0c87d5`; application argument passing at `0x0c8fc5–0x0c8ff9`; `decompiled/client/assembly-functions/00459c40.asm`, `0x059c7d–0x059cbe`; `decompiled/client/functions/0043b4c0.c`, RVA `0x03b4c0`; `decompiled/client/functions/00447c20.c`, RVA `0x047c20`; `decompiled/client/functions/004c8940.c`, RVA `0x0c8940`, reset parameter stores/calls at `0x0c89de–0x0c8a7a` in `decompiled/client/assembly.txt`.

Render-target switching and saved state

The terrain draw region has no local render-target selection. It draws to the render target currently bound on the traced device. There is a native GUI render-surface mechanism, so the distinction between a swap-chain surface and a temporarily bound texture surface cannot be settled from the terrain draw alone.

The GUI frame setup reads render target zero into GUI-engine `+0x2cc` and later releases that reference at GUI frame completion. This is a reference to the target current when GUI setup begins. Its existence is not a copy of the frame's pixels and does not identify it as an offscreen postprocessing image. A separate render-surface begin routine saves the currently bound color and depth surfaces into surface-object `+0x44` and `+0x48`, then binds that object's own color/depth surfaces if its color surface exists. Its corresponding end routine explicitly rebinds the saved color/depth surfaces and releases the saved references. Thus a normally paired, successful begin/end operation restores the surface it received; it does not universally select the back buffer.

The GUI render-surface allocation path creates a one-level render-target texture with numeric format 21 and an associated depth/stencil surface with numeric format 75. This establishes A8R8G8B8/D24S8 for that allocation path. It does not establish that ordinary terrain is rendered into that texture. Neither the terrain region nor the traced GUI frame setup samples the saved target reference as the scene image.

These routines save surface pointers and, in other GUI paths, CPU-side transformation matrices. They are not evidence of a Direct3D state-block capture of all render state. No native CreateStateBlock/BeginStateBlock/EndStateBlock sequence was recovered in the traced initialization, terrain binder or GUI surface helpers. No state-block Apply whose captured sRGB value could establish the terrain value was identified. This is a bounded trace result, not a proof that an arbitrary callback or an omitted indirect path cannot apply a state block. Microsoft documents that a [state block captures selected device state at creation](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-createstateblock); a hypothetical block cannot be treated as a reset to defaults without tracing what it captured.

The native GUI virtual-table identities were confirmed against original image data at RVA `0x322584`: its frame setup resolves to RVA `0x288b60`, completion to `0x28a250`, surface begin/end to `0x28d290`/`0x28c770`, and surface allocation to `0x28d350`. Original evidence: `decompiled/client/functions/00688b60.c`, `decompiled/client/functions/0068a250.c`, `decompiled/client/functions/0068d290.c`, `decompiled/client/functions/0068c770.c` and `decompiled/client/functions/0068d350.c`; `decompiled/client/functions/00650980.c`, RVA `0x250980`, for GUI frame dispatch.

Terrain draw state and sRGB provenance

At terrain-region entry, the binder at RVA `0x047d10` makes exactly the declaration, vertex-program and pixel-program binding calls identified above. It does not apply a state block or set render-target/sRGB/gamma state. The program-object initialization creates the ordinary pixel program from embedded original bytes beginning at RVA `0x2feb50`; that resulting handle is the one selected by this binder. The controller uses the same program object at controller `+0x800580`.

Before iterating the opaque terrain buffers, the region supplies its color/fog and other program constants, supplies output alpha 1 through the pixel-constant helper at RVA `0x047fb0`, and explicitly sets numeric render state 22 to value 2, identified as clockwise culling. At the buffer draw it binds stream zero with eight-byte stride, binds the index buffer, and invokes indexed triangle-list drawing. Those bindings do not decide the output transfer function.

On the ordinary renderer path leading to this region, explicit device assignments include depth enable 1 and depth comparison 4 at frame entry. Before the ordinary world drawing, alpha blending is enabled and RGB source/destination factors are set to numeric 5 and 6, source alpha and inverse source alpha. These facts do not establish every inherited blend operation, write mask or render-target state. With the supplied alpha equal to one and the ordinary additive blend operation, the RGB blend result reduces to the terrain source contribution at a covered passing pixel. The additive operation is a condition here; it is not silently inferred solely from the absence of a nearby blend-operation assignment.

The embedded ordinary terrain pixel program writes its RGB result and uses the supplied alpha constant for its alpha output. It does not sample a render-target texture, and the recovered instruction stream contains no RGB power, logarithm/exponential or piecewise sRGB encode at its output. This is a statement about those original bytes, not a proposed shader or an assertion that its input colors have a calibrated physical interpretation. Device output conversion remains a separate stage.

Direct3D render state 194 (`0xc2`) is `D3DRS_SRGBWRITEENABLE`, whose documented default is zero. A8R8G8B8 is a storage format; its name does not itself select sRGB encoding. The bit and format support determine whether device writes use the API's sRGB behavior. Microsoft describes the [state and its default](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3drenderstatetype) and the separation between [pixel processing, sRGB writes and presentation](https://learn.microsoft.com/en-us/windows/win32/direct3d9/gamma).

The traced creation/reset establishes a default-state starting point. The recovered explicit SetRenderState calls in the renderer and the inspected GUI frame/surface paths do not assign state 194. However, a complete proof of the effective value at every terrain draw would also require closure of the intervening GUI element dispatch, native callbacks and prior frame history. This trace does not claim that closure. Therefore the effective sRGB-write bit at an arbitrary reached terrain draw is held as unresolved, with default zero as a documented origin candidate. It is not reported as a positively observed zero merely because no assignment was found nearby.

The same distinction applies to render-target identity. Under successful creation/reset, no intervening unpaired target change, and successful paired restoration of any temporary GUI target, the implicit swap-chain target remains the ordinary destination. Outside those bounded conditions, its identity must follow the actual saved/bound surface chain. The draw itself neither queries its format nor repairs a target left bound by another path.

Later rendering and potential color transforms

The opaque terrain call is not the end of the frame. The renderer continues with other world geometry, effects and GUI work before EndScene. Later passing geometry or transparent overlays can replace or blend with an opaque terrain pixel. The ordinary terrain pixel result is therefore not a promise of the final presented pixel at that screen coordinate.

No mandatory full-screen scene-texture gamma-encode program was identified in the recovered renderer path between that terrain draw and EndScene. The recovered ordinary program, sky/water variants and the inspected GUI copy/filter programs are not evidence for adding such a pass. In particular, a later binding of another embedded program cannot be renamed a gamma pass solely because it changes color.

There are actual native color adjustments in the GUI program created from original bytes at RVA `0x320e28`. It has texture opacity, brightness, contrast and saturation inputs, a textured/untextured branch, and mask/filter composition. The GUI geometry routine supplies its pixel constants from geometry fields `+0xac`, `+0xb0`, `+0xb4` and `+0xb8`, and supplies texture enable and filtering selections separately. Those parameters affect that GUI geometry's sampled colors. They are not inherently a full-frame transfer: a full-screen effect on the terrain would require a positively traced full-screen draw whose sampled image contains the terrain result. That capture/binding/coverage chain is not established here.

Additional inspected GUI programs perform color modulation/copy, two-by-two/three-by-three/four-by-four sampling, and horizontal/vertical weighted blur. Their original bytes begin at RVAs `0x321420`, `0x321530`, `0x321778`, `0x321a98`, `0x321f00` and `0x322270`. These programs contain sampling, color arithmetic and alpha handling rather than an sRGB encoding operation. The render-surface blur routine changes blend/sampling state for its pass and restores selected settings; it does not provide a captured value for state 194. It is not justified to apply its blur or GUI brightness/contrast globally to ordinary terrain without establishing that specific path.

The final GUI traversal is invoked before the renderer's ordinary EndScene. That traversal includes element dispatch and an optional callback object, rather than a single fixed full-screen copy. The effective final color of a particular terrain pixel under every menu, overlay, callback or render-surface condition remains outside the closed portion of this trace. No unconditional absence of later color modification is claimed.

Original evidence: `decompiled/client/assembly-functions/004ac260.asm`, late GUI dispatch at `0x0bb075–0x0bb07b`, EndScene at `0x0bbb1a–0x0bbb29`, and earlier conditionally reached EndScene exits at `0x0ad667–0x0ad67f` and `0x0ae25d–0x0ae279`; `decompiled/client/functions/00650980.c`, RVA `0x250980`; `decompiled/client/functions/0068ab70.c`, RVA `0x28ab70`, GUI per-geometry constants and program selection; `decompiled/client/functions/0068a350.c`, RVA `0x28a350`, embedded-program creation; `decompiled/client/functions/0068c7c0.c`, `decompiled/client/functions/0068cad0.c` and `decompiled/client/functions/0068cf10.c` for copy, blur and sampling choices; original `binary/Cube.exe` at the pixel-program RVAs listed above.

Presentation and gamma ramps

The application frame routine dispatches the controller render slot, then calls the original device's Present with all four arguments null. The controller virtual table in original image data at RVA `0x2ffdc8` resolves that render slot to RVA `0x0ac260`. The Present is the device-interface method, not the swap-chain Present variant carrying a flags argument. This call does not request `D3DPRESENT_LINEAR_CONTENT`. Its null rectangles request presentation of the whole source to the normal destination window under the documented API rules. Any windowed scaling or desktop-format conversion remains runtime presentation behavior rather than a terrain shader operation. See Microsoft's [device Present documentation](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-present) and [windowed linear-content presentation description](https://learn.microsoft.com/en-us/windows/win32/direct3d9/gamma).

No positively identified device SetGammaRamp or GetGammaRamp invocation was recovered in the traced creation, reset, frame, terrain or GUI surface chains. The supported image's import table does not directly import a Windows gamma-ramp setter. The image does import dynamic-library/procedure lookup facilities, so this import-table result is not a proof about every dynamically resolved call. No application-generated ramp contents, exponent, calibration flag or capability-driven gamma-ramp policy can be assigned from this trace.

The documented gamma ramp is a separate swap-chain/display operation and can be capability/mode dependent. Microsoft documents that SetGammaRamp can silently have no effect in an unsupported presentation mode and distinguishes calibrated versus directly supplied tables. Those facts do not establish the owner's actual adapter, OS calibration or monitor response. A documented default or an application that does not assign a ramp is insufficient to identify the full physical display transfer. See [SetGammaRamp](https://learn.microsoft.com/en-us/windows/win32/api/d3d9/nf-d3d9-idirect3ddevice9-setgammaramp). This contract makes no claim that physical output is identity or that it applies a particular gamma curve.

Original evidence: `decompiled/client/functions/004c85f0.c`, RVA `0x0c85f0`; `decompiled/client/assembly.txt` and original bytes at `0x0c86db–0x0c8702`; original `binary/Cube.exe`, controller virtual table at `0x2ffdc8` and PE import directory. The reset and initialization routines cited above contain no established ramp assignment.

The remaining source gaps are the complete callback/element-dispatch closure between device initialization or reset and the terrain draw; proof of target restoration on every exceptional or early-exit path; any dynamic device/state-block/gamma-ramp invocation outside the recovered chain; and a complete full-screen capture/transform/coverage chain for every later overlay. Failed COM calls, lost devices, non-returning callbacks and corrupted state are not assigned successful-path behavior. The scoped shader bytes and positively traced API arguments remain valid evidence within those limits.

No unconditional final transfer equation is authorized by this artifact. In particular, this evidence does not establish an additional gamma-correction stage or license replacing the unresolved state with a guessed exponent. This document contains no implementation guidance or shader code.
