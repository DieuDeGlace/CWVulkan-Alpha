# Alpha client world-clock input

Status: FINAL / STABLE / HELD after complete author readback. This independent contract covers the original client socket clock input, the separately established stored `time` record, their assignment boundaries, and the meaning of world `+0xA4`. A per-frame replay of cached network clock values is not established by the examined original paths.

## Supported evidence and field identities

The supported image is original `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. All addresses below are RVAs. Evidence paths are relative to the original root `Documents/disassembled alpha cube world`. Original function exports and discovered assembly were supplemented by scoped disassembly of the supported image, including receive-switch bodies missing from the original decompilation. No reconstruction, implementation material, runtime findings or prior project contracts were used.

The client’s embedded world starts at client `+0x2E4`. Consequently world `+0x80015C` is client `+0x800440`, and world `+0x800160` is client `+0x800444`. Each is a separate four-byte field. This relationship is directly used by the socket receiver: it enters protection through client `+0x2E4`, then writes client `+0x800444` and `+0x800440`. The enclosing client routine also supplies client `+0x2E4` to world routine `0x20C510`. [Evidence: original binary, `0x06CBB1–0x06CBE0`; `decompiled/client/assembly-functions/00488ee0.asm`, `0x089024–0x08902F`, `0x08CF20–0x08CF49`.]

In the world clock block, `+0x80015C` participates in signed 32-bit arithmetic and comparison against `86,400,000`; exceeding that threshold increments `+0x800160` and subtracts `86,400,000`. This supports a within-period clock field and a period counter. This contract assigns no calendar epoch, network timestamp type or wall-clock synchronization meaning to either field. Incoming assignment preserves their raw four-byte contents. [Evidence: `decompiled/client/assembly-functions/0060c510.asm`, `0x20C672–0x20C6E2`.]

## Socket record admission and assignment

Receive routine `0x06B740` operates on the client pointer carried by its supplied context. It runs while client byte `+0x800585` remains nonzero and its local stop flag remains clear. At the beginning of each packet iteration it zeros a local four-byte packet-kind word and obtains socket client `+0x8006CC`. Positive socket-read results advance the destination pointer and reduce the requested byte count. A read result of minus one exits through the receive failure path; a zero result falls through to packet-kind interpretation without a completed-header test. Kinds at most fifteen use the original byte-remapping and destination tables at RVAs `0x06D1A4` and `0x06D180`. Kind five selects the body at `0x06CB42`. [Evidence: `decompiled/client/functions/0046b740.c`; original binary, `0x06B7F3–0x06B8B7`, `0x06D0DD–0x06D0EC`; original dispatch-table bytes.]

The kind-five body requests four bytes into its first local word, then four bytes into its second local word. Each request can comprise several positive `recv` results. There is no per-record source ID, target ID, ownership selector, world identifier, sequence number or elapsed value in this eight-byte clock body. After the two read sequences, the visible body performs no range, ordering, sign, freshness, elapsed-time or string-length test on the two words.

It then enters the embedded world’s protection helper `0x201CB0`, loads the first received word and the second received word, and stores the first to world `+0x800160` before storing the second to world `+0x80015C`. The stores are ordinary separate four-byte integer stores. There is no numeric conversion, byte-order conversion, scaling, interpolation, clamp or normalization between the local words and these stores. It leaves through helper `0x201E90`, then returns to the receive loop. This is an application in the receive routine for each admitted kind-five body; it is not deferred into the frame aggregate. [Evidence: original binary, `0x06CB42–0x06CBE5`, especially stores `0x06CBCC` and `0x06CBD2`.]

The original read-error distinction matters. A minus-one result in either payload read sets the local stop flag and bypasses these assignments. A zero result from the first read proceeds to the second read; a zero result from the second proceeds to assignment. Neither path proves that all eight bytes were freshly received. The two payload local words are not zeroed by the kind-five entry. On a short or zero-result path, their untouched bytes cannot be assigned a new-record value by this contract. Previous contents of those stack locations can therefore reach the world; this does not establish a valid retained network snapshot or a deliberate stale-record policy. The complete-record behavior above applies when both four-byte reads complete. [Evidence: original binary, `0x06CB42–0x06CBFC`, zero-result continuations `0x06CBEA–0x06CBFF`; receive prologue `0x06B740–0x06B7F3`.]

The kind-five branch itself makes no random draw. It does not append a clock record to a persistent application queue or set a “new clock available” field in the examined branch. After assignment, the clock values remain in the world until some later world activity or input changes them. A later frame’s use of those fields is established; a later frame copying the same received pair into them again is not established by this receive path.

## Handshake boundary and frame placement

Connection routine `0x06FC50` establishes the socket and performs its initial reply and creature-state exchange. On its accepted reply path, it processes a following kind-zero record with an eight-byte creature identity and a `0x1168`-byte state body, then enables the client receive activity and creates its worker handles. The examined handshake body does not assign this world clock pair or establish a retained clock pair for a frame consumer. Clock assignment is independently established in the subsequent kind-five receive branch. This statement does not specify the remote sender’s initial packet order beyond the bytes explicitly read by this client handshake. [Evidence: `decompiled/client/functions/0046fc50.c`, accepted reply `0x10` and subsequent kind-zero branch; worker setup near the end of that branch.]

The examined enclosing client frame routine `0x088EE0` enters protection on the embedded world at `0x08902F`. Its explicit leave for that world is at `0x09D2EA`; the intervening leave at `0x08D5EB` addresses a different client subobject. The world-call sequence at `0x08CF2E` and `0x08CF49` lies between the embedded-world enter and leave sites. Both world call sites pass the caller’s mutable aggregate and a null optional input pointer. No clock pair is supplied as an additional world argument there. The receive branch uses the same world protection helpers; on normally balanced ownership, its assignment must acquire that protection rather than being tied to a prescribed position between the frame’s subdivided world calls. The complete nested-call lock balance, callback behavior, exceptional exits and all competing drivers have not been audited. [Evidence: frame assembly, `0x089024–0x08902F`, `0x08CF20–0x08CF49`, `0x08D5E5–0x08D5EB`, `0x09D2E4–0x09D2EA`; `decompiled/client/functions/00601cb0.c`, `00601e90.c`, which address the critical section at supplied world `+0x8000C0`.]

The original backend-pointer leads at client `+0x8006C8` have a separate observed function. Before world calls, helpers `0x0DD6A0`, `0x0DD5E0` and `0x0DD640`, called at `0x08CE6A`, `0x08CE81` and `0x08CE94`, copy and clear three backend record lists into aggregate `+0x00`, `+0x58` and `+0x20`. After the world calls, `0x0DC8E0` is called with that aggregate at `0x09C26D` and distributes aggregate records into backend per-connection collections, with conditional spatial work. Those examined boundaries supply record-list aggregates; they do not establish an incoming clock-pair cache or its per-frame replay. Their full transport drivers and nested helper effects remain outside this clock-input contract. [Evidence: frame assembly, `0x08CE48–0x08CE99`, `0x09C256–0x09C26D`; `decompiled/client/functions/004dd6a0.c`, `004dd5e0.c`, `004dd640.c`, `004dc8e0.c`.]

## World string length and stored clock input

World `+0xA4` is the four-byte length of the byte string beginning at world `+0x94`. World `+0xA8` is its capacity. The constructor sets capacity to fifteen, length to zero, and the first inline byte to zero. String access selects the inline buffer when capacity is below sixteen and the stored buffer pointer otherwise. Reset routine `0x1A52E0` copies its supplied string into this object using the original string-assignment helper. The helper updates the four-byte length and terminating zero. Thus the zero/nonzero clock gate at world `+0xA4` directly tests whether this string is empty. It does not establish a pause flag or a network-connected boolean. [Evidence: `decompiled/client/functions/0058eb00.c`, initial fields `+0x94/+0xA4/+0xA8`; original binary and discovered assembly, `0x18EBDF–0x18EBF3`, `0x1A55F2–0x1A5638`; `decompiled/client/functions/0040c0a0.c`; frame string accesses at `0x089334–0x08935B`.]

The supplied string has a proven storage use. With world byte `+0xB4` zero and the newly copied string nonempty, reset routine `0x1A52E0` constructs the path `Save/world_` followed by that string and `.db`, and opens the backend at world `+0xAC`. Open helper `0x0497B0` creates a table for key/value blobs. Read helper `0x049810` selects a blob by key, and `0x0498D0` copies the returned bytes into a temporary byte buffer. This is a local stored-record route. Its original SQL and path literals establish that it is not a socket clock queue. No dependency-library implementation was inspected. [Evidence: `decompiled/client/functions/005a52e0.c`, `004497b0.c`, `00449810.c`, `004498d0.c`; reset sites `0x1A5624–0x1A578E`; original string bytes at RVAs `0x31A7A4`, `0x301E5C`, `0x315B40`.]

The queried key is the four-byte string `time`. On reported lookup success, the reset routine consumes the returned buffer from cursor zero. If at least four bytes are available, it assigns the first four bytes to world `+0x800160`. If at least eight bytes are available, it next assigns bytes four through seven to world `+0x80015C`. Lengths four through seven permit only the first assignment; lengths below four permit neither. Bytes beyond the first eight have no further clock consumer in this block. Failed lookup leaves both clock fields untouched by this block. There is no requirement that a successful blob be exactly eight bytes, no atomic two-field replacement, and no clock-range validation. [Evidence: original binary and `decompiled/client/assembly.txt`, `0x1A57A6–0x1A57E1`; stores `0x1A57C3`, `0x1A57DB`.]

The record is queried during reset, not once per world-update invocation. The read uses a select operation and does not delete the key or consume a freshness marker. A retained stored blob can therefore be read again by a later qualifying reset without a new socket clock packet. This establishes repeatable stored-record loading at reset; it does not establish repeated assignment on each ordinary frame. The constructor initially assigns `43,200,000` to world `+0x80015C` and zero to `+0x800160`, then calls reset with an empty string. Later resets do not perform those constructor default assignments before the conditional stored-record read. A missing or short stored record can therefore leave preexisting clock fields partly or wholly retained. [Evidence: `decompiled/client/functions/0058eb00.c`, defaults and initial `0x1A52E0` call at `0x18EDE5–0x18EE1D`; `005a52e0.c`; read wrappers `00449810.c`, `004498d0.c`.]

One independently identified reset caller is the client worker at `0x06A8A0`. It compares the current world seed/string with the requested pair held at client `+0x800A50/+0x800A54`, performs other work, and enters the reset region when its mismatch condition requires it. It explicitly acquires world protection before the call to `0x1A52E0` at `0x06AFAB`, supplying that requested seed and string. Packet kind fifteen in receive routine `0x06B740` constructs an `online_`-prefixed string from a received four-byte value and calls `0x06F620`, which updates the requested pair. This establishes a route from an incoming world-selection record to the supplied string and eventual reset opportunity. It does not make `+0xA4` a packet-age or pause field. The complete worker scheduling, request coalescing and exact reset-versus-frame race order remain unresolved. [Evidence: `decompiled/client/functions/0046a8a0.c`, comparison near its entry and reset call `0x06AFAB`; `0046f620.c`; original binary, kind-fifteen body `0x06B8BE–0x06BA0A`, string literal at RVA `0x301038`.]

## Subsequent local changes and limits

The incoming words are not protected from subsequent local clock work. Near the beginning of each world call, the routine adds elapsed times ten or one hundred to world `+0x80015C`, depending on its preliminary creature-scan flag. An empty string at world `+0x94` then forces that field to `32,400,000`, regardless of the received value. A signed value strictly greater than `86,400,000` increments the period field and has the period length subtracted, repeatedly while that comparison remains true. These are world-call effects following any clock input that acquired protection earlier. Other actor/action clock mutations in the large world routine are not re-audited here. [Evidence: world assembly, `0x20C672–0x20C6E2`.]

The named `time` writer is also a local database operation. At a counter-based gate in the world routine, nonzero backend handle through world `+0xAC` and nonempty world string permit an eight-byte blob containing world `+0x800160` first and `+0x80015C` second to be supplied to `0x0499C0`. Its nested `0x0499F0` helper uses key-based database insert/update operations. These helpers do not establish network transmission or acknowledgement. The socket kind-five assignment does not itself write this blob in its examined branch. The database’s transaction, durability, locking and failure semantics remain outside the game-owned wrapper evidence. [Evidence: world assembly, `0x20C6E4–0x20C838`; `decompiled/client/functions/004497a0.c`, `004499c0.c`, `004499f0.c`.]

The closed input behaviors are the immediate kind-five assignment and the conditional reset-time stored-record load. No periodic frame assignment from a retained network clock cache was established from the supplied backend/frame leads. A complete audit of every possible indirect writer, all backend drivers or every synchronization participant is not claimed. The original discovered assembly has missing receive-switch bodies; the scoped binary disassembly closes the kind-five body without treating the rest of those omissions as empty behavior. Packet delivery cadence, remote sender identity policy, reconnection ordering, socket EOF contents, operating-system scheduling and concurrent observers outside the documented protection calls remain unresolved. Reset’s wider seed initialization and random draws are outside the scalar clock assignment block; no whole-reset purity or random-state invariance is asserted. There is no server-equivalence claim or guarantee that an incoming pair survives unchanged to a particular rendered frame.
