# Alpha client world-clock input

Status: FINAL / STABLE / HELD after complete author readback and source-only re-certification (2026-11-22). This independent contract covers the original client socket clock input, the separately established stored `time` record, their assignment boundaries, and the meaning of world `+0xA4`. A per-frame replay of cached network clock values is not established by the examined original paths.

## Supported evidence and field identities

The supported image is original `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. All addresses below are RVAs. Evidence paths are relative to the original root `Documents/disassembled alpha cube world`. The exported function listings and discovered instruction listing were supplemented by a scoped disassembly of the supported image, including receive-switch bodies that the exported listings omit, and by reading the image's dispatch-table bytes, import table and string literals. No reconstruction, implementation material, runtime findings or other project contracts were used.

The client's embedded world starts at client `+0x2E4`. Consequently world `+0x80015C` is client `+0x800440`, and world `+0x800160` is client `+0x800444`. Each is a separate four-byte field. The socket receiver uses this relationship directly: it enters protection on client `+0x2E4`, then writes client `+0x800444` and `+0x800440`. The enclosing client frame routine also supplies client `+0x2E4` to world routine `0x20C510`. [Evidence: original binary, `0x06CBB1–0x06CBE0`; `decompiled/client/assembly-functions/00488ee0.asm`, `0x089024–0x08902F`, `0x08CF20–0x08CF49`.]

In the world clock block, `+0x80015C` takes part in signed 32-bit addition and comparison against `86,400,000`; exceeding that threshold increments `+0x800160` and subtracts `86,400,000`. This supports a within-period clock field and a period counter. This contract assigns no calendar epoch, network timestamp type or wall-clock synchronization meaning to either field. Incoming assignment preserves their raw four-byte contents. [Evidence: original binary, `0x20C672–0x20C6E2`.]

The world protection used throughout this contract is the pair of helpers `0x201CB0` and `0x201E90`. Each forms the address of the critical-section object at world `+0x8000C0`; the first passes it to the imported `EnterCriticalSection`, the second to the imported `LeaveCriticalSection`. [Evidence: original binary, `0x201CB0–0x201CBD`, `0x201E90–0x201E9D`; import-table entries at `0x2FC070` and `0x2FC074`.]

## Socket record admission and assignment

Receive routine `0x06B740` operates on the client object reached through its supplied context. It runs while client byte `+0x800585` remains nonzero and its local stop flag remains clear. At the beginning of each packet iteration it zeros a local four-byte packet-kind word, takes the socket at client `+0x8006CC` and requests four bytes into that word. Positive read results advance the destination and reduce the outstanding count. A read result of minus one leaves the receive loop; a zero result proceeds to packet-kind interpretation without a completed-header test. Kinds that compare unsigned at most fifteen are routed through a sixteen-entry byte remap at `0x06D1A4` and a destination table at `0x06D180`; larger kinds go straight to the loop tail. The remap sends kind five to the body at `0x06CB42` and kind fifteen to the body at `0x06B8BE`. [Evidence: `decompiled/client/functions/0046b740.c`; original binary, `0x06B7F3–0x06B8B7`, `0x06D0DD–0x06D0EC`; original dispatch-table bytes.]

The kind-five body requests four bytes into a first local word, then four bytes into a second local word, each from the same client socket. Each request can be satisfied by several positive socket reads. The eight-byte clock body carries no per-record source ID, target ID, ownership selector, world identifier, sequence number or elapsed value. After the two read sequences the body performs no range, ordering, sign, freshness, elapsed-time or length test on the two words.

It then enters world protection, loads the first and second received words, and stores the first to world `+0x800160` before storing the second to world `+0x80015C`. The stores are ordinary separate four-byte integer stores. There is no numeric conversion, byte-order conversion, scaling, interpolation, clamp or normalization between the received words and these stores. It leaves world protection and returns to the loop tail of the receive routine. The assignment therefore happens inside the receive routine for each admitted kind-five body; it is not deferred into the frame aggregate. [Evidence: original binary, `0x06CB42–0x06CBE5`, stores at `0x06CBCC` and `0x06CBD2`.]

The read-error distinction matters. A minus-one result in either payload read sets the local stop flag and bypasses both assignments. A zero result in the first payload read, including one after a partial positive read, proceeds to the second read; a zero result in the second proceeds to assignment. Neither path proves that all eight bytes were freshly received. The two payload words are not initialized by the kind-five entry or elsewhere in the receive routine. On a short or zero-result path their unfilled bytes hold whatever the stack locations previously contained, and those bytes can reach the world. This does not establish a valid retained network snapshot or a deliberate stale-record policy. The complete-record behavior above applies when both four-byte reads complete. [Evidence: original binary, `0x06CB42–0x06CC09`, zero-result continuations `0x06CBEA–0x06CBFF`; receive prologue `0x06B740–0x06B7F3`.]

The kind-five body makes no random draw. It does not append a clock record to a persistent queue and does not set a "new clock available" field. After assignment the values remain in the world until later world activity or input changes them. A later frame's use of those fields is established; a later frame copying the same received pair into them again is not established by this receive path.

## Handshake boundary and frame placement

Connection routine `0x06FC50` establishes the socket and performs its initial reply exchange. On the accepted reply kind `0x10` it reads a following four-byte kind. When that kind is zero it reads an eight-byte creature identity and a `0x1168`-byte state body; it applies that state under world protection only when the identity, read as a signed 64-bit value, is non-negative. In either sign case it then sets client byte `+0x800585` and creates its two worker threads. The examined handshake body contains no store to either clock field and establishes no retained clock pair for a frame consumer. Clock assignment is established only in the subsequent kind-five receive body. This statement does not specify the remote sender's packet order beyond the bytes this client handshake reads. [Evidence: `decompiled/client/functions/0046fc50.c`, accepted reply `0x10`, the following kind-zero branch and worker creation at the end of that branch.]

The examined client frame routine `0x088EE0` enters protection on the embedded world at `0x08902F`. Its explicit leave for that world is at `0x09D2EA`; the intervening leave at `0x08D5EB` addresses a different client subobject at client `+0x800D44`. The world-call sites at `0x08CF2E` and `0x08CF49` lie between the embedded-world enter and leave sites. The first site repeats a call with an elapsed argument of twenty; the second passes a caller-held elapsed value. Both pass the caller's mutable aggregate and a null optional input pointer, and neither supplies a clock pair as an argument. Because the receive body uses the same world protection, its assignment, on normally balanced ownership, falls before or after the frame's protected span rather than at a prescribed position between the subdivided world calls. [Evidence: frame assembly, `0x089024–0x08902F`, `0x08CF20–0x08CF49`, `0x08D5E5–0x08D5EB`, `0x09D2E4–0x09D2EA`.]

The backend object at client `+0x8006C8` has a separate observed role. When it is present, helpers `0x0DD6A0`, `0x0DD5E0` and `0x0DD640`, called at `0x08CE6A`, `0x08CE81` and `0x08CE94` before the world calls, each move one backend record list into the aggregate at `+0x00`, `+0x58` and `+0x20` respectively and then empty the backend list. After the world calls, `0x0DC8E0` is called with the aggregate at `0x09C26D` and distributes aggregate records into backend per-connection collections, with conditional distance-based work. These boundaries supply record-list aggregates; they do not establish an incoming clock-pair cache or its per-frame replay. [Evidence: frame assembly, `0x08CE48–0x08CE99`, `0x09C256–0x09C26D`; `decompiled/client/functions/004dd6a0.c`, `004dd5e0.c`, `004dd640.c`, `004dc8e0.c`.]

## World string length and stored clock input

World `+0xA4` is the four-byte length of the byte string beginning at world `+0x94`. World `+0xA8` is its capacity. The constructor sets capacity to fifteen, length to zero and the first inline byte to zero. Access selects the inline bytes when capacity is below sixteen and the stored buffer pointer otherwise. Reset routine `0x1A52E0` copies its supplied string into this object through the original string-assignment helper, skipping the copy when the supplied object is this same string. The helper maintains the four-byte length and terminating zero. Thus the zero/nonzero clock gate at world `+0xA4` tests whether this string is empty. It does not establish a pause flag or a network-connected boolean. [Evidence: original binary, constructor stores `0x18EBDF–0x18EBF3`, reset copy `0x1A55F2–0x1A5638`; `decompiled/client/functions/0040c0a0.c`; frame string accesses at `0x089334–0x08935B`.]

The supplied string has a proven storage use. With world byte `+0xB4` zero and the newly copied string nonempty, the reset routine forms the path `Save/world_`, then that string, then `.db`, and opens the backend at world `+0xAC` with it. Open helper `0x0497B0` closes any previous handle, opens the file and creates a table of keyed blobs. Read helper `0x049810` selects a blob by key, and `0x0498D0` copies the returned bytes into a temporary byte buffer. This is a local stored-record route. Its SQL and path literals establish that it is not a socket clock queue. No dependency-library implementation was inspected. [Evidence: `decompiled/client/functions/004497b0.c`, `00449810.c`, `004498d0.c`; original binary, reset sites `0x1A5624–0x1A578E`; string literals at RVAs `0x31A7A4`, `0x301E5C`, `0x315B40`.]

The queried key is the four-byte string `time`. On reported lookup success, the reset routine reads the returned buffer starting from a cursor that it has set to zero. If at least four bytes are available, it assigns the first four bytes to world `+0x800160`. If at least eight bytes are available, it then assigns bytes four through seven to world `+0x80015C`. Lengths four through seven permit only the first assignment; lengths below four permit neither. Bytes beyond the first eight have no clock consumer in this block. Failed lookup leaves both clock fields untouched by this block. A successful blob need not be exactly eight bytes, the two fields are not replaced atomically as a pair, and no clock-range validation occurs. [Evidence: original binary, `0x1A573B–0x1A57E1`, stores at `0x1A57C3` and `0x1A57DB`.]

The record is queried during reset, not once per world-update invocation. The read uses a select operation and neither deletes the key nor consumes a freshness marker. A retained stored blob can therefore be read again by a later qualifying reset without a new socket clock packet. This establishes repeatable stored-record loading at reset; it does not establish repeated assignment on each ordinary frame. The constructor assigns `43,200,000` to world `+0x80015C` and zero to `+0x800160`, then calls reset with seed `123` and an empty string, so the constructor's own reset does not open a store. Later resets do not repeat those default assignments before the conditional stored-record read. A missing or short stored record can therefore leave preexisting clock fields partly or wholly retained. [Evidence: original binary, constructor defaults and reset call `0x18EDE5–0x18EE1D`; reset `0x1A5624–0x1A57E1`; read wrappers `decompiled/client/functions/00449810.c`, `004498d0.c`.]

One identified reset caller is the client worker at `0x06A8A0`. Near its entry it compares the requested seed and string held at client `+0x800A50` and `+0x800A54` with the current world seed and string, performs other work, and enters the reset region when the mismatch requires it. It acquires world protection before the reset call at `0x06AFAB`, supplying the requested seed and string. Packet kind fifteen in the receive routine reads a four-byte value and builds the string `online_` followed by that value's signed decimal text. When either the value differs from the requested seed at client `+0x800A50` or the built string differs from the requested string, it calls `0x06F620`, which, under world protection, stores the value as the requested seed and copies the built string into the requested string; when both already match, that call is skipped. This establishes a route from an incoming world-selection record to the supplied string and a later reset opportunity. It does not make `+0xA4` a packet-age or pause field. [Evidence: original binary, worker comparison `0x06A8F1–0x06A941`, protection and reset call `0x06AF7E–0x06AFAB`, kind-fifteen body `0x06B8BE–0x06BA0A`, request updater `0x06F620–0x06F6FB`; string literal at RVA `0x301038`; import-table entry at `0x2FC358`.]

## Subsequent local changes

The incoming words are not protected from later local clock work. Each world call takes an elapsed amount as its first argument. After a preliminary scan of its creature list, which sets a flag when a qualifying creature is found, the routine adds the elapsed amount to the counter at world `+0x8000BC` and adds the elapsed amount times one hundred (flag set) or times ten (flag clear) to world `+0x80015C`. An empty string at world `+0x94` then forces that field to `32,400,000`, regardless of any received value. While the signed field is strictly greater than `86,400,000`, the routine increments the period field, subtracts `86,400,000`, and calls world routine `0x1F0C80` with the world call's second argument once per iteration. These effects follow any clock input that acquired protection earlier. [Evidence: original binary, `0x20C541–0x20C6E2`.]

The named `time` writer is also a local database operation. Immediately after the period loop, the routine compares the signed quotient by ten thousand of the updated `+0x8000BC` counter with the signed quotient by ten thousand of that counter plus the elapsed amount. When the two differ, the backend handle reached through world `+0xAC` is nonzero and the world string is nonempty, it builds an eight-byte blob holding world `+0x800160` first and `+0x80015C` second and supplies it with key `time` to `0x0499C0`. The nested helper `0x0499F0` tests for an existing key and then updates or inserts the blob. These helpers do not establish network transmission or acknowledgement. The kind-five receive body does not write this blob. [Evidence: original binary, `0x20C6E4–0x20C838`; `decompiled/client/functions/004497a0.c`, `004499c0.c`, `004499f0.c`.]

## Closed behaviors

The closed input behaviors are the immediate kind-five assignment in the receive routine and the conditional reset-time stored-record load. No periodic frame assignment from a retained network clock cache was found on the examined backend and frame paths. Reset's wider seed initialization and random draws lie outside the scalar clock assignment block; no whole-reset purity or random-state invariance is asserted. There is no server-equivalence claim and no guarantee that an incoming pair survives unchanged to a particular rendered frame.

## Unresolved

- Effects of world routine `0x1F0C80`, called once per period rollover, are not audited; whether it touches either clock field is open.
- Other actor or action clock mutations elsewhere in the large world routine are not re-audited.
- The contents that reach the world on a short or zero-result kind-five read are stack residue; no value or policy is specified for them.
- The complete nested lock balance of frame routine `0x088EE0`, its callback behavior, exceptional exits and every competing driver of world protection are not audited.
- Complete worker scheduling, request coalescing and the exact reset-versus-frame ordering are not established.
- Every possible indirect writer of the two clock fields, all backend transport drivers and every synchronization participant are not claimed to be audited. The exported listings omit further receive-switch bodies; only the kind-five and kind-fifteen bodies are closed here, and the others are not treated as empty.
- Packet delivery cadence, remote sender identity policy, reconnection ordering, socket end-of-stream contents, operating-system scheduling and observers outside the documented protection calls remain open.
- Database transaction, durability, locking and failure semantics lie in the bundled database library, which was not inspected.

## Re-certification (2026-11-22)

A fresh source-only author re-checked every statement in this document against the original client image, using a scoped disassembly of that image, its dispatch tables, import table and string literals, and the exported listings; no reconstruction or implementation material was used. The image identity, field offsets and widths, constants, store order, protection helpers and reset-blob length rules were confirmed. The kind-fifteen description was corrected: its call that updates the requested seed and string is conditional and is skipped when both already match. The handshake description was refined to state that the received state is applied only for a non-negative identity while the receive activity and workers are enabled in either case. Omissions were filled: the per-rollover call to `0x1F0C80`, the exact ten-thousand quotient test that gates the `time` writer, the constructor's reset seed of `123`, and the import identities of the protection helpers. The audit of `0x1F0C80`, the full lock balance of the frame routine, worker and reset ordering, the remaining receive bodies and the database library's semantics remain open, as listed under Unresolved.
