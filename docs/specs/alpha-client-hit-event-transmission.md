# Alpha client hit-event transmission and bounded local replay

Status: FINAL / STABLE / HELD (re-certified 2026-11-22). This independently worded source-side contract states the original client routing, copied fields, queue consumption and the local incoming boundary needed to assess source/self records. It does not certify a replacement implementation, network acceptance or server behavior.

The evidence root is `disassembled alpha cube world`. The supported image is `binary/Cube.exe`, 3,885,568 bytes, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. Addresses below are RVAs except named object, list or record offsets. Evidence is restricted to individually identified original client routines, the original client instruction listing and executable bytes. Where the listing omits instructions (the receive worker's message cases), facts were read from the image bytes directly. No other contract, reconstruction source, replacement implementation, SDK, probe, capture, log or implementation history supplies facts. No original server counterpart or server echo policy is inferred.

## Shared frame output and the outgoing source-ID filter

Client frame `0x088EE0` constructs one output aggregate at `0x08CE35`. Its hit-record list occupies the aggregate's base: a four-byte pointer to the list's sentinel node followed by a four-byte element count. The frame passes that same aggregate to its world-update calls at `0x08CF2E` and `0x08CF49` (world update `0x20C510`). That world update calls the generic-hit producer `0x196D30` directly at several sites. The producer appends records with a 72-byte payload through the ordinary 80-byte node append path; which producer argument carries the aggregate's base list at each call site was not re-traced (see Unresolved).

Later in the frame, the four-byte client socket field `+0x8006CC` must be nonzero to enter the direct outgoing-queue copy region; when it is zero, the frame skips that whole region and continues at the recipient-route gate described below. Inside the region, the frame walks the shared hit list from first node to sentinel. For each record it compares the record's source identifier at `+0x00/+0x04` with the controlled creature's identifier at creature `+0x08/+0x0C`, requiring equality of both 32-bit words. Only a full 64-bit source-ID match appends a copy to the client hit queue at `+0x8006EC`, whose element count is at client `+0x8006F0`. The same region then applies the same source-ID test to two further aggregate lists of other record kinds (queues `+0x8006F4` and `+0x8006FC`); those formats are outside this contract.

This filter does not read the record's target ID, amount, critical byte, category or trailing flags for admission. It does not compare source ID with target ID. There is no other gate in this region besides the socket field and the source-ID comparison; in particular no world mode byte or world pointer test occurs there. The controlled creature pointer is read from client `+0x8006D0` and dereferenced without a null check in this region, so a valid controlled creature is a precondition rather than a tested case.

The walk does not unlink anything. The step routine `0x068D30` records the current node and moves to its next link. Matching records are appended at the outgoing queue's tail (inserted before its sentinel) in their original relative order; nonmatching records remain in the shared aggregate.

The generic producer's source/self auxiliary record is built from a zero-initialized record (`0x059A30` zeroes the defined fields from `+0x14` to `+0x46`, not the padding, so the critical byte, the two four-byte fields at `+0x18`/`+0x1C`, the three vector fields and the three trailing bytes including category `+0x45` are zero). Both identifiers are set to the source creature's identifier (creature `+0x08/+0x0C`), the 24 position bytes come from creature `+0x10` to `+0x27`, and the amount at `+0x10` is the negation of the auxiliary value. After appending that record, the producer adds the un-negated auxiliary value directly to the same creature's binary32 health at creature `+0x16C`. The outgoing filter makes no distinction between producer cases: a source/self record whose source ID equals the controlled ID passes the same test as any other record with that source ID, and source-equals-target is not excluded. This is an identity-routing rule, not a claim that every such record is delivered.

## What copies preserve, and what the raw send includes

The frame's queue append `0x086290` and the sender's list-copy constructor `0x058FD0` both create nodes through `0x051EE0`, which allocates an 80-byte node through `0x06D810` and fills its payload through the field copy routine `0x0599A0`. The list-copy constructor creates a fresh sentinel and then walks the source list in order through the range-copy routine `0x0540C0`, so it allocates independent nodes rather than taking over the original shared or queued nodes. Each append checks the element count against the limit 53,687,090 before incrementing it.

| Hit-record offset | Width | Field copy behavior |
| --- | --- | --- |
| `+0x00` | 64-bit source identifier | Both 32-bit words copied unchanged. |
| `+0x08` | 64-bit target identifier | Both words copied unchanged. |
| `+0x10` | Binary32 amount | Four bytes copied unchanged; no sign, critical or magnitude adjustment. |
| `+0x14` | One-byte critical field | Copied unchanged. |
| `+0x18`, `+0x1C` | Two four-byte fields | Copied unchanged. `+0x18` is read as a signed duration by the incoming branch below; other meanings are not assigned here. |
| `+0x20–+0x37` | 24 position bytes | Six four-byte pieces copied unchanged. |
| `+0x38`, `+0x3C`, `+0x40` | Three binary32 vector fields | Each copied unchanged. |
| `+0x44`, `+0x45`, `+0x46` | Three one-byte fields, category at `+0x45` | Each copied unchanged. |
| `+0x15–+0x17`, `+0x47` | Four padding bytes | Not written by the field copy routine. No defined value or preservation is established for them. |

A node is 80 bytes: two four-byte list links followed by the 72-byte payload. Neither link is sent as part of the hit payload.

The sender does not serialize the fields one by one. For each queued hit it requests one four-byte send containing the numeric message kind 7, then one send of 72 contiguous bytes beginning at node offset `+0x08`. The raw outgoing request therefore includes the payload's padding bytes, even though the field copies neither preserve nor define them. Padding is not a gameplay field and must not be described as guaranteed zero or as an exact copy of the producer's original padding.

There is no target/source identity recheck, source-equals-target exclusion or category distinction in this sender loop. Each send result is compared only with -1 (failure abandons the batch); a short positive write is not completed by a retry. These facts describe requested bytes and the original caller checks, not delivery or TCP message boundaries.

## Sender queue consumption and state-message order

The original sender worker `0x069C10` runs while the client active byte `+0x800585` is nonzero and sends on the socket held in `+0x8006CC`. Each batch begins by requesting a four-byte message whose value is kind 0. It then acquires the lock of the world embedded at client `+0x2E4` (lock `0x201CB0`, release `0x201E90`).

Under that lock it first copies the client hit queue `+0x8006EC` into a local list with the list-copy constructor, then copies the queues `+0x8006F4` and `+0x8006FC` of other record kinds. After further work on other pending data, it resets the hit queue's sentinel links to itself, sets count `+0x8006F0` to zero and frees the former queued nodes; it then does the same for the two other queues. This consumption happens before any hit is transmitted and does not wait for per-hit acknowledgment. The local copy is the source of the later kind-7 sends.

Still under the same lock, after clearing those queues, the worker reads the controlled creature's identifier (creature `+0x08/+0x0C`) and copies the controlled creature's state beginning at creature `+0x10` through the state copy routine `0x066050`. That copy includes the binary32 health at creature `+0x16C`, which sits at snapshot offset `+0x15C`. It then releases the world lock. The captured state is the state at that moment, not a pre-effect snapshot of any one event.

The worker builds the state message by writing the captured eight-byte identifier into a buffer and calling the state encoder `0x0CDAA0` with the previous snapshot, the current snapshot and a first-message flag that starts set. The encoder processes the snapshot field at `+0x15C` among its fields. Its delta selection and encoding are not reconstructed here, so this contract does not assert that health is present in every state payload.

After the kind-0 header, the worker requests a four-byte encoded-state length and then the state payload. On success it replaces its previous snapshot with the current one and clears the first-message flag. Two optional messages can follow before the hits: a kind-10 message (length, then two bytes per text unit) when a pending text length is nonzero, and a kind-6 message with a 300-byte body when the controlled creature's field `+0x1310` is nonzero. Only then does it walk the local hit list in order, sending kind 7 and each 72-byte payload. Kind-8 (40-byte) and kind-9 (112-byte) records from the other two queues follow the hits. Within a batch, the state requests therefore precede the hit requests.

For a locally produced auxiliary self record, the producer's direct health addition happens before the frame's later queue-append site. The frame acquires the world lock at `0x08902F` and releases it only at `0x09D2EA`; the only other lock/release pair in the frame (`0x08D55B`/`0x08D5EB`) is on a different object at client `+0x800D44`. The sender's copy, clear and state capture use the same embedded world lock. A batch containing that queued record therefore captures controlled state after the direct effect and the queue insertion. Later changes before the capture can also affect that state; captured health is not equated with one isolated addition.

The shared frame aggregate survives the direct source-ID filter. The frame destroys it at `0x09D365` through cleanup `0x067C70`, which empties each member list and finally, at `0x067ED0–0x067F0D`, empties the base hit list, frees its nodes and frees its sentinel. The outgoing queue and the sender's local list hold their own copies, so that cleanup does not revoke already-copied records. No retry or requeue is established for a send failure after the client queue was cleared.

## Separate optional recipient distribution in the client image

After the direct outgoing-queue region (or directly, when the socket field was zero), the frame tests client pointer `+0x8006C8`. When it is nonnull, the frame calls `0x0DC8E0` with the same shared aggregate. This is an additional route; it is not the source-ID comparison above and is not evidence of behavior in `Server.exe`.

That client-image routine locks through the world pointer held at object `+0x04` and walks the recipient-pointer array delimited by object `+0x28` (start) and `+0x2C` (end). For each nonnull recipient pointer it first passes a different aggregate list (aggregate `+0x18`) to routine `0x0545A0` with recipient `+0x30` as destination, and then appends a copy of the entire shared hit list to the tail of the recipient's hit queue at recipient `+0x18`, using the same ordered range-copy routine `0x0540C0`. Both copies precede the routine's later recipient-creature lookup and distance tests for other lists. No source-ID, target-ID, source-equals-target, category, amount or distance test filters this hit-list copy.

Shared records rejected by the direct source filter can therefore still enter this recipient route if that object and a recipient are present. The shared list is copied, not consumed. The transport for these recipient queues, recipient lifecycle and any later filtering are not closed here, and no conclusion about server broadcast, exclusion of the originating peer or echo delivery is drawn from this partial client-image route.

Sources: `decompiled/client/functions/004dc8e0.c`, `004540c0.c`; original frame pointer gate and call `0x09C256–0x09C26D`; object lock and recipient admission `0x0DC916–0x0DC955`; other-list copy `0x0DC95B–0x0DC975`; complete hit-list copy `0x0DC97A–0x0DC9A2`; later recipient lookup `0x0DC9A7–0x0DC9DE`.

## Incoming client records and conditional source/self replay

The incoming client boundary uses different framing from the outgoing single-record kind 7. Receive worker `0x06B740` reads a four-byte kind and dispatches kinds below 16 through the byte table at `0x06D1A4` and the address table at `0x06D180`; kind 4 goes to `0x06CC0E`. That case reads a four-byte length, sizes a byte buffer to it and requests that many bytes through receive helper `0x086B60` (a -1 result abandons the case), then constructs a fresh aggregate (`0x066880`), decodes another aggregate component (aggregate `+0x18`) with `0x058310`, and then decodes the hit component with decoder `0x0583F0`. The hit decoder reads a four-byte signed count and, for a positive count, reads each 72-byte record in order and appends a copy. There is no source/target identity filter or self-ID exclusion in that decoding. Malformed counts, truncated buffers and decoder failure cases are not certified here.

Under the embedded world lock (acquired at `0x06CEE8`), the receiver appends copies of the decoded hits to the tail of client incoming hit list `+0x800630` in their decoded order, alongside copies of the other decoded components into neighboring client lists. Nothing between that lock and its release at `0x06D088` performs a health operation. The temporary aggregate is destroyed afterwards (`0x06D093`) independently of the client-list copies.

Later frame processing walks `+0x800630` and resolves each record's target identifier at record `+0x08` through the world. The local effect branch requires the resolved pointer to equal the controlled creature pointer `+0x8006D0`. It does not require a foreign source, does not compare source and target IDs and does not distinguish a generic auxiliary self record. Within that branch, category values 1 and 5 have their own operations, which are not reconstructed here; every other category value, including 0 and 3, reaches the ordinary health branch.

In the ordinary health branch, the controlled creature's binary32 health at `+0x16C` must compare ordered and strictly greater than zero, otherwise the branch does nothing. A positive amount triggers an additional step that is bypassed for zero, negative or unordered amounts. A positive signed value at record `+0x18` raises the creature's four-byte field `+0x12C` to at least that value; a zero or negative value leaves it unchanged. The branch then subtracts the stored amount directly from health, so a negative amount increases health. If the result compares ordered and less than zero it is replaced with positive zero. The result is then compared with the value returned by the health-limit routine `0x044DB0`; only a result strictly greater than that limit is replaced by the value of a second call to the same routine, and equality is retained. The limit formula is outside scope. The branch does not read the critical byte, so the amount is not scaled again by it.

A separate later pass walks the same incoming list and appends to the shared frame output list only records whose full source ID differs from the controlled creature's ID (either word unequal). Local-source records are excluded from that forwarding even when their target was the controlled creature and the local branch already ran. The frame then clears the incoming list through `0x06F870` at `0x0905C4`, using the list address it saved before the first walk. Application and forwarding are independent decisions, followed by consumption of the incoming list.

Consequently, if an emitted negative category-0 self record is actually received on this incoming path with both IDs still naming the controlled creature, and controlled health is ordered positive, the local branch can apply its negative amount as a further health increase, subject to the stated limit. Its local source ID prevents forwarding by the later pass but does not suppress the earlier local health operation. The client evidence alone does not establish that the original server echoes such a record, which recipients receive it, or how server state interacts with the earlier outgoing state snapshot. Neither an unconditional double application nor a no-replay guarantee is established.

## Re-certification (2026-11-22)

A fresh source-only author re-checked this document against the original `binary/Cube.exe` (size and SHA-256 confirmed), its instruction listing, routine exports and, where the listing omits the receive cases, the image bytes. The RVAs, record offsets and widths, node size, queue offsets, send kinds and sizes, lock scope, consumption order and the incoming replay conditions were confirmed. Corrections: the earlier statement that every category other than 0 has its own local operation was narrowed to categories 1 and 5 (category 3 also reaches the ordinary health branch); the duration rule was restated as "a positive value at `+0x18` raises creature `+0x12C`, a zero or negative value leaves it unchanged"; and the claim that the producer appends to the frame aggregate's base list was moved to Unresolved because the argument binding was not re-traced. Added confirmed detail covers the zero-socket path to the recipient route, the earlier recipient call for another list, the other component decoded before the hits, the optional kind-10/kind-6 and following kind-8/kind-9 sends, and the separate `+0x800D44` lock in the frame. The items under Unresolved remain open.
