# Alpha server buff-update admission and ranged/critical record producers

This is an original-evidence, code-free behavioral contract for the standalone Alpha server. It answers whether a living creature whose numeric role byte at creature `+0x60` is zero reaches resident-buff countdown, and distinguishes that admission from action ownership and production of resident types 9, 10 and 11. Numeric role, action, class and subclass values are retained without assigning unproved gameplay names. This document does not replace a general buff serialization or transport contract.

The supported image is `binary/Server.exe`, SHA256 `1ffbcbce251e1506a63c9ce18ab0009d5553fcbb9e6202be2bc3a7d870d34fb1`, preferred image base `0x00400000`. Every address below is an RVA in that image. Evidence paths are relative to the original Alpha evidence root. The original image, its original decompilation and its instruction exports were the only behavioral sources. No reconstruction, existing contract, replacement implementation, tests, captures or diagnostics supplied facts.

The decisive result is that numeric role zero does not exclude a living, non-null entry of the server world's creature map from the resident-buff countdown. Nonzero roles have additional AI scheduling; that schedule does not govern the buff countdown. Several action-production paths and a regeneration/reset path have mode or local-pointer gates, but their rejected branches rejoin before resident countdown. Consequently, an action that the server does not produce for a non-local role-zero creature does not imply that its resident buffs stop aging.

Some exported action blocks have no owning-function annotation or are absent from the per-function export; original image bytes confirm these branches.

The server caller and elapsed time

The standalone caller constructs a world with its mode argument zero. The world constructor stores that mode byte at world `+0xb4` and initializes the local-creature pointer at world `+0xb8` to null. The caller itself does not assign a local creature later in its body. This is an initialization and caller-body finding, not an exhaustive claim that every server dependency is unable to modify the pointer. The countdown conclusion is independent of the pointer's value.

The running server loop samples the Windows millisecond timer, drains queued input into an input aggregate, acquires the world protection scope, creates the output aggregate, and invokes the world update once. The elapsed argument is the current sampled 32-bit timer value minus the previous sampled value. The previous sample is updated after the call. Output distribution and other loop work follow; the caller releases its protection scope and requests a 20 ms sleep before the next iteration. The running flag controls continuation. This caller has no numeric-role selection and no separate fixed-rate buff scheduler.

The actual buff delta is therefore the measured interval between successive samples, including prior loop work and scheduling delay. It is not a fixed 20 ms value, an AI accumulator, or the world day-clock scale. The caller supplies the 32-bit subtraction directly, without a demonstrated clamp or fixed-step subdivision. The world update saves those 32 bits at entry and later subtracts that same value from each resident record's 32-bit time field. Ordinary nonnegative intervals are millisecond countdowns. Extremely long stalls, signed overflow, abnormal timer histories and shutdown races have no additional validated behavioral guarantee here.

At the beginning of the world update, a distinct role-zero/action-`0x54` examination can select a factor of 100 rather than 10 for the day-clock increment. This changes the day-clock expression, not the saved elapsed argument later used by buffs. Its role-zero condition is not a countdown admission gate.

Creature admission and the gates that do not exclude countdown

The relevant pass traverses the creature map at world `+0x4`. An empty map produces no creature work. For each entry, a null creature pointer advances to the next entry. The routine processes that creature's queued work before its health admission test. In mode zero it then clears the processed queue; the nonzero-mode branch leaves that clear operation out. This queue distinction joins the same health test.

The health at creature `+0x16c` is first clamped down to the calculated maximum. A finite health value at or below zero advances to the next creature before resident countdown. A finite positive value continues. The role-zero comparison occurs after this test and skips an AI block, not the creature itself. For a nonzero role in mode zero, elapsed time is accumulated at creature `+0x13c4`. When the `+0x12c` timer permits and the accumulated interval reaches at least 32 ms, a non-null AI object at `+0x13e4` receives the accumulated interval; the accumulator is then reset on that eligible path. Role zero and nonzero mode bypass this AI scheduling. All these ordinary paths join at RVA `0x13793b` and proceed toward action handling and resident countdown. A missing AI object or an accumulator below 32 does not defer the countdown.

The action byte is creature `+0x68`. The original dispatch handles values 1 through 110 through a byte selector and destination table; zero and values above 110 use the default. These are action-body destinations inside the same creature update. They must not be mistaken for independent update functions. The following gates are relevant to the traced consumers:

| Work | Admission to that work | Rejected path |
| --- | --- | --- |
| Common action body containing actions `0x05`, `0x11`, `0x14`, `0x1e`, `0x1f` | Nonzero world mode; or nonzero creature role; or creature equals world local pointer | Default action join, then countdown |
| Ranged body for actions `0x16`, `0x17`, `0x1a` | Creature equals world local pointer; or mode zero and role nonzero | Common pre-countdown join |
| Body for actions `0x32`, `0x37`, `0x60` | Creature equals world local pointer; or mode zero and role nonzero | Common pre-countdown join |
| Ranged body containing actions `0x25`, `0x2b`, `0x2d`, `0x2e` | Creature equals world local pointer; or mode zero and role nonzero | Common pre-countdown join |
| Regeneration/reset work at RVA `0x137d01` | Mode zero; or creature equals world local pointer | Cooldown processing, then countdown |
| Resident-buff countdown itself | Non-null creature admitted by the finite positive-health test and ordinary returning action work | No additional role/mode/local-pointer filter |

The common body has a different nonzero-mode rule from the three ranged bodies. A single ownership rule must not be inferred for every action. In the standalone world as initialized, mode is zero and the local pointer is null, so a non-null role-zero creature fails each listed action-production gate. It still passes the listed countdown admission if alive. The default action path joins at RVA `0x137d01`; restoration paths at `0x137cfb` restore the saved elapsed argument and reach the same join. Regeneration may be skipped for a non-local creature in nonzero mode, but cooldown traversal and the resident-list traversal remain downstream of that skip.

Original direct branches within the main creature/action region do not reveal an additional role-zero advance-to-next-creature edge. The null-entry and nonpositive-health branches are the two direct early advances found before the ordinary action/countdown join. This establishes native control-flow admission for well-formed state and returning callees. It does not promise progress through allocation failure, an exception, a non-returning virtual AI callback, corrupted iterators, or a callback that invalidates the creature. Queued work can alter state before the health test; being alive at the beginning of the outer server loop is not a substitute for being alive at this admission point.

Resident application, consumption and later unlink

The resident list is creature `+0x1178`, with count at `+0x117c`. For the present scope, its 24-byte record has a type byte at record `+0`, a binary32 value at `+4`, signed 32-bit remaining time at `+8`, and a 64-bit embedded source identifier at `+0x10`. The intervening padding is not assigned behavioral meaning. The fresh-record initializer explicitly sets type, value, time and both source halves to zero; it does not establish zero padding.

The ordinary type lookup returns the first matching resident record in list order. It does not check whether the record's remaining time is positive. Ordinary application of type 9, 10 or 11 walks the same order, replaces all 24 payload bytes of the first matching record, and returns immediately. It neither visits further matches nor changes the resident count in that replacement case. If no record matches, ordinary application appends one at the tail and increases the count. These rules also apply when the supplied time is zero. They do not establish global uniqueness if duplicate records already exist.

Each traced consumption path first asks whether its type is present. On success it constructs a fresh record of the same type with value zero, time zero and embedded source zero; applies that record through ordinary application; and then appends a 40-byte buff event. This overwrites the first match's prior value, prior time and prior embedded source. It is not an in-place edit of only the time, and it is not a direct unlink of one or all matches. The outer source and outer target IDs of the event are both the consuming creature's 64-bit ID from creature `+8`. The embedded source inside the copied resident record remains zero. Self/self outer IDs do not fill the embedded source with self.

Fresh producer records described below likewise have value zero and embedded source zero, but time 30000. They apply before their event is appended. The event consists of outer source at event `+0`, outer target at `+8`, and the 24-byte record at `+0x10`. The embedded source is consequently at event `+0x20`. The buff-event list at output aggregate `+0x58` receives a tail copy of all 40 bytes. Repeated producer or consumer calls can append repeated events even when they overwrite the same first resident node. Padding bytes copied into records/events are not a validated zero-filled wire promise.

Countdown subsequently visits every resident node of the admitted creature. It subtracts the saved elapsed argument from the signed 32-bit time and collects nodes whose resulting time is nonpositive. After the scan it unlinks the collected nodes and decreases the resident count. This later expiry phase can remove multiple expired records of the same type. It is separate from the first-match application/consumption operation. A zero-time consumption normally becomes expired in this same creature pass for an ordinary nonnegative delta, including zero. No additional type-9/10/11 removal event is appended by this expiry path. Before unlink, a zero-time record can still satisfy presence-only checks.

A distinct full-creature reset clears the whole resident list and sets its count to zero. That all-record clear must not be attributed to the ranged consumers. This document does not specify all callers or admission conditions of the reset.

Type 9: application, resource admission and consumption

One confirmed producer follows a successful hit-application return in the common action body. It requires action `0x1e`, then performs a probability-helper call with binary32 0.25, and only after a successful draw checks that creature subclass `+0x141` is zero. It then applies a fresh type-9, value-zero, time-30000, embedded-source-zero record and appends its self/self buff event. The event append precedes the append of a separate visual/sound record with numeric kind `0x2f`. Failure of the hit-application return avoids this producer. The probability draw occurs before the subclass check, so an ineligible subclass can still consume that draw.

A second confirmed type-9 producer lies in a projectile-hit path later in the world update. At its immediate producer gate the associated creature must exist and must either be the world's local creature or have nonzero role in mode zero. The path performs the binary32 0.25 probability-helper call before testing that the copied projectile flag from projectile `+0x5c` is zero, projectile 32-bit kind `+0x60` equals 1, and projectile byte `+0x64` equals 1. On success it applies the same fresh type-9 record and appends the self/self event before kind-`0x2f` visual/sound output. The hit-application call for that candidate follows these producer/event operations. These immediate conditions are in addition to upstream target eligibility and spatial intersection gates; those dependencies are bounded below.

Presence of type 9 also affects helpers before it is consumed. For actions `0x1f`, `0x21`, `0x25`, `0x2b`, `0x2d`, `0x2e` and `0x5f`, the resource-cost helper returns zero when it finds type 9; without it the corresponding return is binary32 approximately 0.3 (`0x3e99999a`). A separate action-start helper, for selected new actions `0x1f`, `0x21`, `0x25`, `0x2e` and `0x5f`, can advance the action clock at `+0x6c` to the current action's native timing threshold when type 9 is present. These checks use presence, not the resident value/time/source. The action-start clock change does not itself replace or unlink the resident record.

The common-body consumer checks action `0x1f` and action time `+0x6c` at least the current action threshold returned by RVA `0x7db0`. If type 9 exists, it replaces the first match with the fresh zero-time type-9 payload and appends the self/self event before proceeding to the target traversal. The check is not an all-match clear and does not require the old resident time to be positive.

The ranged emission path also consumes type 9 for actions `0x25`, `0x2b`, `0x2d` and `0x2e`. Its projectile flag is set from those action values. After preparing and appending the projectile to the world's projectile list, and after adjusting resource/charge fields, this path checks that flag and type-9 presence. It applies the zero-time type-9 record and appends the self/self buff event. It then appends the projectile to the output aggregate's projectile channel at `+0x20`, appends separate visual/sound output, and rejoins before this creature's resident countdown. This is native operation order across distinct lists; it is not a claim that a receiver observes those channels in that call order. Detailed firing-threshold interpolation for multi-emission actions is outside this contract.

Type 10: charge application and consumption

The confirmed projectile-hit producer first requires an associated creature and the immediate ownership condition of local pointer equality or mode zero with nonzero numeric role. It calls the probability helper with binary32 approximately 0.15 (`0x3e19999a`) before testing that projectile byte `+0x5c` is zero, creature class `+0x140` equals 2 and subclass `+0x141` equals 1. Success applies a fresh type-10, value-zero, time-30000, embedded-source-zero record and appends its self/self buff event. The kind-`0x2f` visual/sound append follows. Thus a failed flag or class/subclass test can still follow a consumed probability draw. The draw is an independent producer roll, not the preceding critical-result boolean.

In the later charging work for actions `0x08`, `0x18`, `0x19`, `0x1b`, `0x3b`, `0x3f` and `0x40`, after the native action threshold has been reached, finding type 10 sets charge field `+0x144` to current resource field `+0x170`. The following clamp limits charge to that resource value. This presence check does not read the resident value/time/source or consume the record. It is later than the resident countdown in this creature's update.

The ranged emission body for actions `0x16`, `0x17` and `0x1a` makes its projectile flag true when the stored shot amount at creature `+0x13b4` is positive, or when the action is `0x17`. If that flag is true and type 10 is present, it applies the zero-time type-10 record and appends the self/self buff event. The projectile's later insertion into the world's projectile list, its insertion into output aggregate `+0x20`, and its visual/sound append follow that consumption event append. The ordinary emission crosses its native timing threshold; action `0x1a` has an additional charge-dependent timing branch. This document establishes the consume site, flag and ownership gate, rather than every emission rule of those actions.

A separate consumer in the action group `0x32`, `0x37`, `0x60` acts when the old action time is at or below its threshold and old time plus the saved elapsed delta is strictly above it. These three actions' threshold helper returns zero. Before the type lookup it copies charge `+0x144` into shot amount `+0x13b4`, subtracts that charge from resource `+0x170`, and clears `+0x144`. If type 10 is then found, it performs the same first-match zero-time replacement and self/self event append. That event is downstream of the resource/charge changes and upstream of this creature's resident countdown.

Type 11: critical predicate, production and consumption

The type-11 producer helper requires creature `+0x128` to be nonzero, class `+0x140` to equal 4 and subclass `+0x141` to equal 1. It adds binary32 0.25 to resource `+0x170` and caps values greater than 1 at 1. It then applies a fresh type-11, value-zero, time-30000, embedded-source-zero record and appends the self/self event. The resource change precedes resident application; resident application precedes the buff-event append. This helper makes no random draw of its own and has no independent role/local-pointer test. Its callers supply their own admission.

Confirmed call sites include world target-lookup paths at RVAs `0x138ee0`, `0x139140` and `0x13e400`, each requiring a successful creature lookup before the call. The hit-event application routine also calls it for event discriminator byte `+0x45` equal to 4, after that routine's target and event-admission logic. In particular, that hit-event routine has a separate branch that relays rather than locally applies a hit when the world local pointer is null and the target's numeric role is zero. This is a hit-application ownership branch, not a resident countdown branch. The complete causal meanings of those event discriminators and target-action paths are not renamed here.

The critical predicate scans to the first type-11 record. If found, its comparison threshold becomes 1. Otherwise it uses the base critical-stat helper plus creature `+0x1190` multiplied by binary32 approximately 0.15 (`0x3e19999a`). In either case it still obtains a random value, converts it to a floating fraction using 32767, and succeeds only when the fraction is strictly less than the threshold. A type-11 presence therefore does not remove the random draw; an endpoint fraction of exactly 1 fails a threshold of 1. The predicate does not read type 11's stored value, time or embedded source, and does not replace or remove any record.

The two traced projectile-hit regions call this critical predicate before their later type-10 or type-9 producer probability calls. A true critical result doubles that candidate damage value. The later producer roll remains a separate call; the producer's immediate checks do not require the critical boolean to be true. Upstream paths and damage computation can perform other random draws; this relative order is not a complete global random-draw contract.

The common action body consumes type 11 at action time `+0x6c` equal to zero for actions `0x05`, `0x11` and `0x14`, on the resource-cost branch that selects these actions. It copies resource `+0x170` to shot amount `+0x13b4`, clears the resource, and then looks up type 11. Presence causes first-match replacement with the fresh zero-time type-11 payload, then the self/self event append, then setting creature byte `+0x13c0` to 1. The resource transfer occurs even when type 11 is absent. The native cost helper returns zero for these action values; no class test is repeated immediately around this type lookup. Earlier in the same common body, class 4/subclass 1 with one of these actions and action time zero sets `+0x128` to 600. These details do not convert the consumer into a direct unlink. The path rejoins ahead of resident countdown.

Probability order and phase boundaries

The probability helper used by the type-9/type-10 producers always takes its own random draw. Before that draw, when creature bytes `+0xaa8` and `+0xaa9` select its special cases, it scales the requested probability: `+0xaa8` equal to 3 and `+0xaa9` in 0, 1, 2 or 12 multiplies by binary32 0.5; values 8 or 10 multiply by binary32 approximately 0.3 (`0x3e99999a`). Other cases preserve the requested probability. It then compares its normalized random fraction strictly below the resulting probability. These draws occur at the stated call sites even when a later flag or subclass check fails. Evidence: `decompiled/server/functions/0040f220.c`, RVA `0xf220`; original `binary/Server.exe`, constants at RVAs `0x1586cc`, `0x1586d0` and `0x158834`.

The action-body consumers and the successful-hit type-9 producer run before the current creature's resident-list traversal; their replacements therefore participate in that traversal. A fresh 30000-time producer in that position can already lose the current delta, and a zero-time consumer can be unlinked without another buff event. The later projectile-hit producers at RVAs `0x14794a` and `0x1486cc` occur after the main creature traversal has ended at `0x145c21`. Their fresh record is not revisited by the earlier creature-countdown pass in that same world call. It first loses time on a later admitted creature update. The three type-11 helper sites occur in different positions within the creature phase; no universal same-pass countdown guarantee is assigned to all their target creatures, since target-map order and which target has already been visited matter.

The output event retains the supplied producer time 30000 or consumption time zero even if the resident record is subsequently decremented or unlinked during that world call. Event append makes a copy. It does not retain a live pointer to the resident payload. Buff events preserve append order within their own list. This contract distinguishes that list order from call order across projectile, hit and visual/sound lists, and does not re-specify aggregate serialization or network delivery ordering.

Limits and held result

This contract establishes standalone server scheduling, native saved elapsed time, living-creature countdown admission, the enumerated ownership gates, first-match type-9/10/11 mutation, later all-expired-node unlink, semantic payload/source contents and the stated event-append order. It does not assign gameplay names to numeric role or action values, claim that every possible producer or consumer in both Alpha executables has been exhausted, or establish a standalone client's update cadence. The owner-supported `binary/Cube.exe` was not needed to prove the server behavior covered here.

The complete upstream projectile collision geometry, hostility and target-selection helpers; every event discriminator's gameplay meaning; base critical-stat calculation; every multi-shot timing interpolation; all callers of action-start and full-creature reset helpers; arbitrary AI callback side effects; and possible world-local-pointer mutation inside server dependencies remain outside this bounded trace. Their exact call sites or numeric conditions are retained where needed, rather than filling those gaps with inferred gameplay rules. These limits do not weaken the direct role-zero countdown admission result.

Malformed/truncated transport input was not exercised or accepted as a safe native contract. Corrupt list/map nodes, invalid creature pointers, uninitialized semantic input, allocation failure, nonfinite health/resource values and out-of-range timer histories do not have validated recovery behavior in this document. Padding bytes are specifically excluded from the semantic-zero claims. No implementation guidance or pseudocode is supplied.
