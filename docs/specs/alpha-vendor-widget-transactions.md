# Original vendor widget rows and transactions

Status: FINAL / STABLE / HELD. This independent, code-free contract covers the original client inventory widget reached through update services RVA `0x0C6350` and `0x0C64C0`, the row indices consumed by vendor lookup, selected-group refresh, and bounded purchase, buyback, and buyback-list publication routes. Full widget rendering, item generation, unrelated interface branches, and a complete inventory or transport system are outside its scope.

The supported image is `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. Evidence paths are relative to `Documents/disassembled alpha cube world`. Evidence is the original image, `decompiled/client/assembly.txt`, and individually identified original function exports cited below. The important row, integer, copy, and payment branches were checked in native instructions. Earlier held prose, reconstruction, replacement code, runtime observations, and implementation history are not evidence.

## Widget and buffer identity

The client constructs an inventory widget at RVA `0x064249` and stores its pointer at client `+0x80095C`. It passes variant value 3, retained as widget 32-bit `+0x194`, and sets widget `+0x160` to the address of client inventory buffer `+0x800C0C`. Widget `+0x164` is the client pointer. The widget's current group index is the separate signed 32-bit field `+0x1B4`; constructor `0x0C1BB0` initializes it to zero. Variant 3 and current group 1 are different fields and decisions. [Evidence: `binary/Cube.exe`, RVAs `0x064224–0x06425E`, constructor `0x0C1BB0–0x0C1F74`; `decompiled/client/functions/004c1bb0.c`.]

The buffer begins with three 32-bit pointers describing a contiguous outer collection of 12-byte group descriptors. Each group describes a contiguous collection of `0x11C`-byte entries: raw 32-bit quantity, then a `0x118`-byte item. Widget `+0x184/+0x188` are hover group/index words, while `+0x18C/+0x190` are a separate selected group/index pair. Widget `+0x198/+0x19C/+0x1A0` describe a per-group 32-bit scroll vector, `+0x1A4` is its current scroll-range count, `+0x1A8/+0x1AC` are integer cell dimensions, and `+0x1B0` supplies a pending group choice. These field roles are established by the consumers, not by an inferred profession or symbolic item-group layout. [Evidence: `binary/Cube.exe`, RVAs `0x0C20AB–0x0C20E5`, `0x0C23E6–0x0C2406`, native bodies `0x0C5A60–0x0C5BA7`, `0x0C6350–0x0C64B5`, `0x0C6610–0x0C67A0`; `decompiled/client/functions/004c5a60.c`, `004c6610.c`.]

## Layout, quantity filtering, and row identity

Update `0x0C6350` does nothing when widget `+0x160` is null. Otherwise it obtains two supplied dimensions through services `0x22F600` and `0x2291D0`, narrowing each return to binary32. It subtracts binary32 10 from the first and divides by the binary32 conversion of integer cell width plus five; `CVTTSS2SI` yields the column count C. It subtracts binary32 40 from the second and divides by the converted cell height plus five to obtain the row count R with the same truncation. These are scalar binary32 operations. It resizes the scroll vector to the current logical outer group count, supplying zero for newly added words. [Evidence: `binary/Cube.exe`, RVAs `0x0C6359–0x0C63FC`; `decompiled/client/functions/004871e0.c`.]

An empty outer collection or a current group at or above its logical count sets `+0x1A4` to one. A valid current group with an empty entry range sets that word and its group scroll word to zero. For ordinary positive C, R and nonempty entry count N, the nonempty-group calculation takes the integer quotient of N minus one divided by C, subtracts R, adds two, and retains at least one. The division at `0x0C6474` is unsigned; the subsequent lower-bound comparison is signed. This result M is stored at `+0x1A4`, and a current scroll value above M minus one is reduced to M minus one. This service does not filter N by quantity or item category, and does not clamp a negative existing scroll value upward. Negative group indices, zero columns, malformed spans, overflow, invalid dimensions, and divide faults have no normalized fallback established here. [Evidence: `binary/Cube.exe`, RVAs `0x0C63FC–0x0C64B5`.]

Update `0x0C64C0` reads that computed range and current-group scroll word to publish scroll-control geometry. After a dimension-service call whose result is discarded, its additional admissions are a nonnull control pointer at widget `+0x178`, nonzero M, and a nonempty scroll vector. In the ordinary positive-range domain it divides the truncated second dimension minus 70 by M for the control height; with M greater than one its position uses the current scroll value and integer division by M minus one, plus an offset of 35. M at or below one uses the fixed offset 35. The geometry call also uses the first dimension minus 28. The renderer/control implementation and complete geometry representation are unclosed. Neither update service consumes an item, changes an entry quantity, or rebuilds the inventory buffer. [Evidence: `binary/Cube.exe`, RVAs `0x0C64C0–0x0C660C`; `decompiled/client/functions/004c64c0.c`.]

The bounded row pass in widget routine `0x0C2050` first calls `0x0C6350` and resets both hover words to -1. It uses only the current group's entry sequence. Its first visible entry index is that group's scroll value times C, and the end is the lesser of N and first index plus R times C. It advances actual entry indices in increasing order; it neither sorts nor compacts away zero or negative quantities. A cell's horizontal position varies fastest across C columns. The row identities are those actual buffer indices, not ordinal numbers among positive quantities. [Evidence: `binary/Cube.exe`, RVAs `0x0C2090–0x0C20E5`, `0x0C21C9–0x0C2302`; `decompiled/client/functions/004c2050.c`, scoped row pass.]

For each visited cell the routine performs its rectangle hit test before the item/quantity drawing predicate. Bounds are inclusive at the lower horizontal/vertical edges and exclusive at the upper edges for ordinary ordered coordinates. A hit stores current group and actual entry index into `+0x184/+0x188`. The subsequent icon predicate normally admits a nonzero quantity, but widget variant 2 or 3 bypasses that quantity restriction. Thus the vendor's variant 3 reaches the icon service even for zero quantities; a negative quantity also reaches the service with a different color input. Actual item icon behavior is not closed here. A separate quantity-text pass requires positive quantity and category exactly one of `1/10/12/13/11/21`; this narrower text predicate does not change row identity or hover admission. [Evidence: `binary/Cube.exe`, RVAs `0x0C2302–0x0C246B`, `0x0C246B–0x0C2584`; `decompiled/client/functions/004c2050.c`, quantity-text pass beginning with the positive-count/category test.]

Selection service `0x0C6610`, when called with its byte argument nonzero, requires only nonnegative hover index before copying hover group/index into selected group/index and issuing feedback selector `0x55`. It does not impose quantity or category admission. Its zero-argument route only updates selection-control visibility/position. Group-choice service `0x0C5A60` requires a nonnull inventory pointer, nonnegative pending group, and a choice different from the current group. It writes the new current group, updates layout, selects either -1/-1 for an empty/unavailable group or the first index of that group's visible range, updates controls, issues feedback `0x56`, and calls client service `0x0815C0`. The latter refreshes the vendor buffer only when the supplied widget pointer equals client `+0x80095C`. The ordinary conclusion assumes valid group and scroll indices. [Evidence: `binary/Cube.exe`, native bodies `0x0C5A60–0x0C5BA7`, `0x0C6610–0x0C67A0`, `0x0815C0–0x0815D6`; original exports `004c5a60.c`, `004c6610.c`, `004815c0.c`.]

## Current group 1 refresh and live list identity

Client refresh service `0x0A2300` tests this same current group field `+0x1B4` against exactly 1. The equal branch resizes client buffer `+0x800C0C` to two groups, empties group index 1 by setting its end to its begin, then appends entries from the client list at `+0x800D3C` into that group. It starts at the header's previous node and follows previous links until the first node has been included. It copies raw entry quantity and item fields without a positivity or category filter. This is the reverse of the live list's next-link order. [Evidence: `binary/Cube.exe`, RVAs `0x0A2304–0x0A2363`, entry append `0x086700–0x086775`; `decompiled/client/functions/004a2300.c`, `00486700.c`.]

With current group not 1, a nonnull cached actor pointer at client `+0x8008D8` supplies group assignment from actor `+0x11DC`, followed by separate actor `+0x11E8`, item `+0x11EC`, and words `+0x1304/+0x1308` into client buffer `+0x800C18`, `+0x800C1C`, and `+0x800D34/+0x800D38`. A null cached pointer leaves those buffer values unchanged by that branch. Both branches then call the two update services with the **vendor widget** receiver client `+0x80095C`. These copies and control updates are not a synchronization snapshot, and do not prove that a later live-list node still equals a displayed item. [Evidence: `binary/Cube.exe`, RVAs `0x0A2365–0x0A23C5`; `decompiled/client/functions/0044ad30.c`, `0044aff0.c`.]

The reached item assignment/copy constructors `0x02C5E0/0x00EE70` copy item bytes `+0/+1`, `+4` through `+0x0E`, word `+0x10`, bytes `+0x14` through `+0x113`, and word `+0x114`. They leave item bytes `+2/+3/+0x0F/+0x12/+0x13` unwritten. The entry copy stores the 32-bit quantity before invoking the item constructor for entry `+4`. Buffer rows are separately owned element copies in ordinary valid storage, rather than shared pointers to actor or buyback entries; capacity and unassigned bytes have no invented all-zero guarantee. [Evidence: `binary/Cube.exe`, native bodies `0x02C5E0–0x02C672`, `0x00EE70–0x00EF10`, `0x051F10–0x051F41`, `0x086700–0x086775`.]

## Transaction lookup and admission services

The bounded transaction opportunity in client input routine `0x07B600` is entered for supplied integer selector 1 or 2; selector zero and other values have other paths. Prior input-side effects and the external meaning of these selectors are not closed. The route first asks `0x07B450` for a valid player-inventory hover group/index: that helper requires its inventory panel active, nonnegative indices within the player's current collections, and quantity nonzero. If it obtains those indices, a separate player-item route has priority. Otherwise the handler asks direct-slot service `0x07B1B0`; a nonnull item with category nonzero also has priority over vendor purchasing. Only a missing/category-zero direct item reaches vendor lookup `0x07B550`. [Evidence: `binary/Cube.exe`, RVAs `0x07CCFA–0x07CD65`, `0x07D7ED–0x07D808`, `0x07DA30–0x07DA47`; `decompiled/client/functions/0047b450.c`, `0047b1b0.c`.]

Vendor lookup requires the interface object at client `+0x8008C4` active. It reads vendor widget hover group `+0x184` and index `+0x188`, checks both nonnegative and within the current buffer's group/entry counts, and returns the item address at entry `+4`. It does **not** test the row quantity, item category, current group equality with the hover group, cached vendor identity, position, or health. Current group `+0x1B4` then determines normal purchase versus group-1 buyback; it is not used to choose the hover item's address. These are distinct reads which require ordinary stable state for a matching-row interpretation. [Evidence: `binary/Cube.exe`, RVA `0x07B550–0x07B5E4`, `0x07DA30–0x07DA54`; `decompiled/client/functions/0047b550.c`.]

Capacity service `0x03E4A0` is called on the local player actor with a supplied item. Categories other than 1, 11, and 20 return true at this boundary. For those three categories it begins with zero, optionally includes actor `+0x11E8` when actor item `+0x11EC` matches through equality service `0x02F4A0`, and then visits all groups and entries in increasing storage order, adding each matching entry's raw 32-bit quantity. There is no positive/nonzero quantity filter for this sum. Category 20 rejects a signed sum at least one; all three reject a signed sum at least 50. Additions wrap as native 32-bit arithmetic; malformed counts and full equality behavior are explicit dependency limits. [Evidence: `binary/Cube.exe`, RVA `0x03E4A0–0x03E546`; `decompiled/client/functions/0043e4a0.c`, `0042f4a0.c`.]

The player's 32-bit field `+0x1304` is the payment word used here. Affordability compares the returned signed price with that word using a signed comparison. The following additions/subtractions are ordinary 32-bit arithmetic without saturation at these stores. No transaction-local health, distance, actor-ownership, or network-acknowledgment check is added by the inspected purchase/buyback bodies. Wider caller/input gates and transport are not inferred from that absence.

## Price boundary

Item price service `0x0C76E0` starts with binary32 multiplier `0.2`; categories 3/4 use two, 5/6/9 use one, 7/8 use 1.5, and category 23 uses 100. For category 3, subtype `0x0F/0x10/0x11/5/10/11/0x12/8/6/7` doubles that multiplier. It supplies the item's signed 16-bit `+0x10`, converted to binary32, and zero-extended byte `+0x0C` to scalar helper `0x045F60`. The returned binary32 value is multiplied by binary32 ten, then the selected multiplier, and converted to signed 32 bits with `CVTTSS2SI`. If this first integer is below one, the service returns one. Otherwise it calls the scalar helper again and repeats the two products and conversion for the actual return, without a second minimum test. Prices are recomputed by transaction callers; they are not cached in a row. [Evidence: `binary/Cube.exe`, RVA `0x0C76E0–0x0C77F9` and its category table; `decompiled/client/functions/004c76e0.c`.]

In helper `0x045F60`, the first input has binary32 one subtracted, then is multiplied by binary32 `0.05`, then has one added. Binary32 one divided by that result is subtracted from one, and the result multiplied by binary32 three. That final value is promoted to binary64 as the exponent of a precise-power call with binary64 base two. The result is immediately narrowed to binary32 and saved. The second integer input is converted to binary32, multiplied by binary32 `0.25`, promoted to binary64, and supplied to a second power call with base two. Its result is immediately narrowed to binary32 and multiplied by the saved first result in binary32. The routine returns that product through x87. The imported power implementation, exceptional operands, control state, and upper input lanes remain unclosed. [Evidence: `binary/Cube.exe`, RVA `0x045F60–0x045FE5`, power thunk `0x28D8D4`.]

The relevant exact constants are binary32 `0.2` bits `0x3E4CCCCD`, `0.05` bits `0x3D4CCCCD`, `0.25` bits `0x3E800000`, one `0x3F800000`, two `0x40000000`, three `0x40400000`, 1.5 `0x3FC00000`, ten `0x41200000`, and 100 `0x42C80000`; the binary64 power base is `0x4000000000000000`. Native data locations include RVAs `0x2FCDBC`, `0x2FCDB4`, `0x345D98`, `0x345DC0`, `0x345E10`, `0x2FCD70`, `0x2FCDE0`, `0x345E74`, `0x2FD0B4`, and `0x345E18`. Ordinary arithmetic is separately rounded binary32 with ambient floating-point controls; invalid conversion results or unstable imported math do not inherit an invented clamped-price guarantee.

## Normal purchase order

With current group not 1 and a valid hover item pointer, the handler first calls price service on that buffer item and rejects insufficient signed funds. It then calls capacity service on the player with that item. Capacity rejection issues the original carry-limit notification and feedback selector `0x31`, then leaves this branch without an inventory-add call or payment subtraction. A successful capacity result calls inventory-add service `0x06EBE0` on player inventory `+0x11DC`, with the item pointer and destination-group argument -1. Only after that service returns does it recompute the price from the same buffer item and subtract it from player `+0x1304`, then issue feedback `0x39`. No inventory-add success value is checked. [Evidence: `binary/Cube.exe`, RVAs `0x07DC3D–0x07DD6B`.]

The normal purchase body does not decrement the displayed entry quantity, remove a buffer row, mutate the cached actor's stock, or call vendor refresh `0x0A2300`. It does not require the displayed quantity to be positive or nonzero. The item category and count normalization, automatic destination group, stacking, special counters, allocation failures, and any no-op behavior inside inventory-add are not made into a universal one-unit promise here. In particular, the original add service has an explicit category-zero bypass; caller payment remains ordered after its return. [Evidence: `binary/Cube.exe`, RVAs `0x07DD24–0x07DD6B`; `decompiled/client/functions/0046ebe0.c`, category-zero admission.]

The normal success continuation updates the **player inventory widget** at client `+0x800954` through `0x0C6350`, then `0x0C64C0`; it then reaches client service `0x0A14C0`. The latter's recipe/other-interface work is outside this contract. Insufficient funds takes a shorter continuation without the purchase feedback or those two player-widget updates. None of these paths constitutes a server acceptance or a transaction rollback protocol. [Evidence: `binary/Cube.exe`, RVAs `0x07DC50`, `0x07DD70–0x07DD8D`.]

## Group-1 buyback order

Group 1 first maps the hover **index** to the live list at client `+0x800D3C`: it traverses next links from the first live node while a counter begins at list count `+0x800D40` minus one and decreases. It selects the node whose counter equals vendor hover index `+0x188`. There is no item-equality comparison between the buffer item returned by vendor lookup and this live node's item at node `+0x0C`. This mapping agrees with the reversed buffer copy only for stable, matching list/count/hover state. A failed mapping exits without the buyback mutations below. [Evidence: `binary/Cube.exe`, RVAs `0x07DA47–0x07DA87`.]

The selected node's 32-bit quantity is at `+8`. The handler initializes separate attempted and successful unit counters to zero. A signed positive quantity enters the unit loop; zero or negative quantity bypasses it. Each attempt first calls player capacity service with the **live node item**. Capacity failure produces the carry-limit notification and feedback `0x31`, and ends the loop while preserving earlier successful transfers. If capacity passes, affordability uses a fresh price of the **buffer hover item**. When affordable, the handler calls inventory-add with the live node item and group -1, then recomputes price from the **live node item**, subtracts that returned amount from player `+0x1304`, and increments the successful count. There is no second affordability check for this latter amount. [Evidence: `binary/Cube.exe`, RVAs `0x07DA87–0x07DB1B`, `0x07DB30–0x07DBDB`.]

Every attempt increments the attempted counter and compares it signed against the node's current quantity, which is reread at the loop test. An unaffordable attempt does not end the loop or increment successful count; remaining attempts can repeat the capacity/price tests. The live node quantity is not reduced during those attempts. After the loop the handler subtracts only the successful count from node `+8`. Exact zero removes the node from the doubly linked list and decrements client list count; a negative remaining quantity is not normalized or erased by this exact-zero gate. Thus an initially zero-quantity mapped node is removed even with no unit transfers, whereas an initially negative one is retained on this path. [Evidence: `binary/Cube.exe`, RVAs `0x07DB15–0x07DB2B`, `0x07DBDB–0x07DC0C`.]

After reaching that post-loop block, the handler issues feedback `0x39`, calls vendor refresh `0x0A2300`, then the two player-widget updates and `0x0A14C0`. Feedback and refresh also occur when no unit was affordable or an initial capacity rejection prevented all transfers. Partial successful additions/payments remain; there is no rollback of them when a later attempt fails capacity. The ordinary relation between displayed and live items is a lifetime/freshness condition, not a comparison enforced by this transaction. [Evidence: `binary/Cube.exe`, RVAs `0x07DC0C–0x07DC38`, `0x07DD70–0x07DD8D`.]

## Confirmed buyback-list publication

One ordinary inventory-entry sale route is independently established in the same input routine. It requires valid nonzero-quantity player hover indices from `0x07B450`, the interface branches at client `+0x800900` and `+0x8008F8` inactive, and the vendor interface at `+0x8008C4` active. It copies the player's source item to private storage, decrements the source quantity, and normalizes a post-decrement nonpositive result to quantity zero plus a zero category/subtype word. It next prices the saved item and adds the returned amount to player `+0x1304`, then issues feedback `0x3A`. These source counts are admitted as nonzero rather than signed positive; malformed arithmetic inherits the native decrement/comparison boundary. [Evidence: `binary/Cube.exe`, RVAs `0x07CD44–0x07CE74`.]

That route then constructs a list entry with raw quantity one and the saved item, appends it at the live list's tail through `0x051F10`, increments list count, and links the new node. When the resulting count is unsigned above ten, it removes the current first node if present and decrements the count. It finally refreshes the vendor buffer. A separate admitted direct-slot sale route prices and credits the original slot item first, copies it into a quantity-one tail entry, applies the same count/oldest-node policy, refreshes, and only then clears the original slot's category/subtype word. The two sale routes therefore have different source-clear timing. They do not merge equal sold items into one buyback node in these bodies. Other sale admission and item-slot branches remain outside this bounded publication evidence. [Evidence: `binary/Cube.exe`, RVAs `0x07CE79–0x07CF67`, `0x07D84B–0x07D998`; `decompiled/client/functions/00451f10.c`.]

## Limits

Ordinary conclusions require valid widget, player, cached actor, vector and list storage; correctly aligned spans; consistent live list count; positive usable layout dimensions; and stable pointers while the native services execute. No examined update or transaction installs a whole-operation lock, reserves stock, pins an actor/list node, validates hover generation against a refresh, or makes payment and inventory mutation atomic. Calls can observe earlier partial mutations and refreshed data; allocation/error, callback, imported-math, unmasked exception, overflow, malformed-index/count, and concurrency behavior remain explicit bounds.

This audit closes the stated caller arithmetic, indices, gates, and ordered service calls. Full visual rendering, tooltip/asset behavior, upstream input selection, item generators, complete inventory-add/equality semantics, all payment-counter producers, unrelated interface branches, networking, server reconciliation, and complete transaction-system behavior remain unclosed. Direct price/update/transaction code here introduces no random draw; no total-RNG claim is made for untraced nested or subsequent services.
