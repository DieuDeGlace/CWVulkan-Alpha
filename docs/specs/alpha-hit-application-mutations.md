# Alpha hit-application primitive mutations

This original-only, code-free contract covers the client hit applier at RVA `0x195a60`, specifically categories 0, 1, 3 and 5 and the mutations preceding its fatal continuation. The supported image is `binary/Cube.exe`, SHA256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, image base `0x00400000`. All routine addresses below are RVAs. Evidence paths are relative to the original Alpha evidence root. No earlier contracts, replacement code, SDK, tests, probes, captures, logs, implementation history or reconstruction supplied facts. Earlier held artifacts remained unopened and unchanged.

The contract retains numeric creature roles, kinds, classes and category values rather than assigning unproved gameplay names. “Health” denotes creature `+0x16c`; “resource” denotes `+0x170`; “shield” denotes the resident type-6 value depleted by category 5. Other fields are described by offsets. The caller supplies a world, a hit record, an output aggregate and an additional binary32 argument. That last argument is passed into the later fatal continuation; it has no identified role in the primitive mutations specified here.

The scoped hit fields are a 64-bit source ID at hit `+0`, 64-bit target ID at `+8`, binary32 amount at `+0x10`, signed 32-bit fields at `+0x18` and `+0x1c`, binary32 vector components at `+0x38`, `+0x3c`, `+0x40`, and the category byte at `+0x45`. This is a partial field contract, not a declaration that unlisted hit bytes are absent or padding. Input source/target IDs and creature-resident IDs are kept distinct where the native operations use them differently.

The primary source is `decompiled/client/functions/00595a60.c`, supported by `decompiled/client/assembly.txt` and original `binary/Cube.exe` bytes. The instruction export resolves cases where the decompiler presents a stored float as an integer or loses register arguments to helpers. In particular, shield depletion is a binary32 subtraction, not an integer conversion.

Admission and mutations before category dispatch

The world creature map at world `+4` is searched using the hit's target ID. A missing map entry, null mapped creature, or finite target health at or below zero ends this application before any of the target mutations below. A found creature with finite positive health continues. A hit with no world-local creature pointer at world `+0xb8` and a role-zero target at target `+0x60` is instead appended to the output aggregate's hit list, using the native hit-copy operation, and returns without locally applying the following target changes. The world mode byte `+0xb4` is not part of that particular relay condition.

Otherwise the source ID is looked up in the same world map. A missing or null source becomes an absent source pointer. There is no general source-exists, source-alive, hostility, range, damage-eligibility or category check at this point. Later operations have their own narrower checks.

For a strictly positive hit amount, before the category is inspected, the applier reduces target scalar `+0x1190`. The reduction is one quarter of the hit amount divided by a power of two. The power's exponent is one quarter of the sum of the target's signed 32-bit `+0x190` and unsigned byte `+0x1a8`, minus one inside that sum. The integer sum precedes conversion to binary32. The exponent arithmetic is binary32, promoted to binary64 for the power helper; the power result is converted to binary32 before the division. The subtraction is stored, and a result below zero is then replaced with positive zero. This is not a reduction of the hit's amount.

Still for a positive amount, if target action byte `+0x68` equals `0x54`, it is set to zero and target signed timer `+0x12c` is set to 3000. That action cancellation follows the `+0x1190` change. It can therefore affect the vector attenuation test later in this same hit application.

For a nonnegative amount and a present source, the following relationship work occurs next, still before the protection/category gate:

1. Source `+0x11d0/+0x11d4` receives the input target ID, followed by target `+0x11d0/+0x11d4` receiving the input source ID.
2. In source map `+0x13ac`, the value keyed by the input target ID increases by binary32 1. A missing keyed value is inserted with zero before the increment.
3. In target map `+0x13a4`, the value keyed by the input source ID increases by a scaled hit amount plus binary32 `0x3c23d70a`, approximately 0.01. The scaling selection is specified below. The native addition order is scaled amount plus that 0.01 constant, then the old map value.
4. The relationship-report/nearby-propagation helper at RVA `0x1a0970` runs with the present source and target. Its effects and order are specified below.

These operations are not conditional on the later health-eligibility predicate. A zero-amount hit can consequently update IDs, counts and relationship values. A category-3 hit can execute this whole prelude. A negative amount skips this nonnegative-source relationship prelude.

The relationship scale is selected in this order. It is 1 when the source satisfies RVA `0x044520`: source class `+0x140` is 3; or source kind `+0x64` is `0x75`, `0x56` or `0x68`; or source bytes `+0xaa8/+0xaa9` select category 3 and subtype 6, 7, 8, 10, 11 or 12. If that test is false, kind `0x19` selects scale 10. Otherwise category byte `+0xaa8` equal to 3, the item predicate at RVA `0x044820` true, and source subclass `+0x141` equal to 1 select scale 20. The item predicate accepts category 3 with subtype 5, 6, 7, 8, 10, 11, 15, 16, 17 or 18. All remaining cases select scale 2. The first successful earlier case prevents later selection.

After this prelude the applier tests bit `0x2000` of target's unsigned 16-bit field `+0x7e`. When clear, the body continues. When set, it traverses target map `+0x13a4` and requires some strictly positive stored value whose keyed ID resolves to a non-null world creature of numeric role zero. That resolved creature need not be the input source, and this gate does not test its health. Failure to find such an entry returns after any prelude mutations already performed. Success admits the later category body. A prelude-created or increased entry can affect this decision in the same application.

Ordered category body and independent ownership checks

Once admitted by that gate, category 3 returns immediately. It does not run the subsequent vector, status, resource, shield, health or fatal-check body. Its earlier prelude is not rolled back.

For the other scoped categories, the applier next handles the incoming vector only when the hit amount is nonnegative. It starts with the three hit vector components. When target timer `+0x12c` is positive and the hit's signed `+0x18` is at most zero, all three components are multiplied by binary32 `0x3dcccccd`, approximately 0.1. The timer used here includes any 3000 assignment from the earlier action cancellation.

Replacing target vector `+0x4c/+0x50/+0x54` requires all of the following: target role is not 6; either world mode is zero and target role is nonzero, or target pointer equals the world-local pointer; and the attenuated incoming squared length is at least the existing squared length. Each component square and each length addition uses binary32 arithmetic; the first two component squares are combined before the third is added. Equality accepts replacement. The vector is replaced as three components, not added to the old vector. A role-zero non-local target therefore does not receive this replacement in mode zero, even though later scalar/status or health operations may be admitted.

Still within the nonnegative-amount branch, a strictly positive signed hit `+0x18` zeros target `+0x34`, `+0x38` and `+0x3c`. This reset does not repeat the role-6 or local-pointer vector-replacement gate. It can occur when vector replacement did not occur.

Next, for every admitted non-category-3 hit regardless of amount sign, a strictly positive signed hit `+0x1c` raises target signed timer `+0x130` to the greater of its old value and the supplied value. Nonpositive supplied values leave it unchanged.

Category 1 then increases resource `+0x170` by binary32 0.25 and caps a result above 1 at binary32 1, before returning. This addition occurs for positive, zero or negative hit amounts. There is no lower clamp, health predicate, final health ownership test or fatal check on this category-1 branch. It does not perform the later timer-`+0x12c` maximum operation, although the earlier positive-hit action cancellation can already have written that timer.

Category 4 has its own early helper branch at this position. It is outside the requested category contract and is identified only to delimit category 0/5 behavior: it returns after that helper, before the generic timer/health branch. It must not be treated as a category-0 alias.

For categories 0 and 5, a strictly positive signed hit `+0x18` now raises target signed timer `+0x12c` to the greater of its current value and the supplied value. This is after vector handling and after the `+0x130` change. The applier then admits shield/health work only if world mode is zero or target pointer equals the world-local pointer. A nonzero-mode non-local target returns here with any earlier scalar, ID, relationship, vector-reset and status changes retained.

Positive category-0 health and its eligibility predicate

For a strictly positive amount on category 0 after the final ownership gate, the target must pass the predicate at RVA `0x03e310`. If a source pointer exists, it must pass the same predicate as well; target eligibility is checked first. With an absent source, target eligibility alone permits the subtraction. The applier subtracts the original full hit amount from target health in binary32 and stores the result. This branch neither checks a type-6 shield nor caps the positive damage amount. It does not clamp the result to zero until the following fatal check.

The eligibility predicate's meaningful result is its low byte. It accepts numeric roles 0, 1, 3 and 5. Role 6 is accepted except when signed/unsigned 32-bit kind `+0x64` has the bit pattern for `0x8c`, `0x8d` or `0x8e`. Roles other than those accepted cases return false. It checks neither current health, source/target identity, map membership, hostility, protection bits nor world ownership. In particular a found source is not required to be alive by this predicate. A failed predicate prevents this health subtraction; it does not undo the already described changes or suppress the subsequent health-based fatal test.

A zero amount on category 0 performs no health change, but can reach the final fatal test after its earlier common mutations. Negative category-0 amounts use the healing branch below and do not call this eligibility predicate.

Original evidence: `decompiled/client/functions/0043e310.c`, RVA `0x03e310`, confirmed against `binary/Cube.exe` bytes at `0x03e310–0x03e344`; `decompiled/client/assembly.txt`, positive ordinary health branch `0x195fcc–0x196003`, zero/negative selection at `0x196008–0x196011`, fatal-test join at `0x196133`.

Positive category-5 shield traversal and events

For a strictly positive amount on category 5 after the final ownership gate, the applier traverses the target resident list at `+0x1178` in its existing list order. It visits every record and processes every type-6 match. It does not stop at the first shield, test the old capacity/time for positivity, distribute the amount between shields, or reduce the amount after an earlier match. Each match loses the entire original hit amount independently.

A resident payload begins eight bytes after its list-node links. Its type is payload byte `+0`, value is binary32 `+4`, remaining time is signed 32-bit `+8`, and embedded source ID is the 64-bit field at `+0x10`. For each type-6 match, the applier subtracts the hit amount from that record's binary32 value and stores the difference. If that difference is nonpositive, it then writes value zero and remaining time zero. If the difference is positive, remaining time is left unchanged. The type, embedded source ID and other copied payload bytes are left unchanged in both cases.

Immediately after each match's mutation, a 40-byte buff event is assembled and tail-appended to output aggregate `+0x58`. Its outer source and target IDs are copied from the input hit IDs. Its embedded 24-byte resident payload is copied from that exact mutated record, including its preserved embedded source ID. The input outer source is not written into the record's embedded source. Duplicate type-6 records can consequently produce multiple events in traversal order, including events for records that already had zero value/time.

This path advances through the original node links. It does not call resident application, unlink a node, free a shield node, reduce resident count `+0x117c`, or clear other records. Setting time to zero is not proof of unlink. No overflow damage from a depleted shield is subtracted from health here, and no shield means no health subtraction on this category-5 positive branch. A later independent resident-update pass may remove an expired record; its scheduling and behavior are outside this hit-applier contract.

After the traversal, the path joins the same health-based fatal check as category 0. The shield branch itself has not reduced health. Category-5 zero amounts skip depletion; category-5 negative amounts take the healing branch instead. Both are distinct from the positive shield traversal.

Original evidence: `decompiled/client/assembly.txt` and original `binary/Cube.exe`, category selection/list start at `0x195eed–0x195f20`, binary32 value write and depletion at `0x195f20–0x195f4c`, record/event copy and append at `0x195f4c–0x195fb6`, traversal advance and join at `0x195fb9–0x195fc7`; `decompiled/client/functions/0043b660.c`, RVA `0x03b660`, event semantic initialization; `decompiled/client/functions/004460a0.c`, RVA `0x0460a0`, tail append; `decompiled/client/functions/00451c70.c`, RVA `0x051c70`, full 40-byte event copy.

Negative amounts and the maximum-health cap

After the final ownership gate, a strictly negative amount on category 0 or 5 increases health by subtracting that negative amount. This is a direct binary32 operation, without the positive-damage eligibility predicate. The tentative new health is stored before the maximum-health helper at RVA `0x044db0` is called. If tentative health exceeds that helper's binary32 result, the helper is called again and its newly calculated result is stored as health. Otherwise the tentative value remains. No lower clamp is introduced at this stage.

The maximum-health helper can be described in stages. For a level value L, its level-growth factor is a power of two with exponent three times the difference between one and the reciprocal of one plus binary32 `0x3d4ccccd` times L minus one. Here `0x3d4ccccd` is approximately 0.05, and L minus one is grouped before multiplication. The base calculation uses the target's signed 32-bit `+0x190` converted to binary32. A second power-of-two factor uses one quarter of target unsigned byte `+0x1a8`; for numeric role zero that second factor is replaced by the power of two with exponent exactly one. The two converted binary32 power results are multiplied, then multiplied by target binary32 `+0x178`.

Class byte `+0x140` then multiplies the result by binary32 `0x3fa66666` for class 1, `0x3f8ccccd` for class 2, or `0x3f99999a` for class 4, approximately 1.3, 1.1 and 1.2 respectively. Other classes make no change at this stage. Class 1 with subclass `+0x141` equal to 1 additionally multiplies by exactly 1.25.

Item contributions are then added in this order, and only for the listed item category at each creature-relative base: category 3 at `+0x990`, category 3 at `+0xaa8`, category 4 at `+0x530`, category 6 at `+0x648`, category 5 at `+0x760`, category 7 at `+0x878`. Each eligible item contribution comes from RVA `0x0c70b0` with that item base.

That item helper returns zero outside item categories 3, 4, 5, 6 and 7. Its item coefficient is 1 for category 4 and 0.5 for the other accepted categories. A variation factor starts by dividing a remainder by 20 in binary32, subtracting that quotient from binary32 1, and then adding binary32 1. The remainder is obtained by shifting the item's 32-bit `+4` value left three bits with 32-bit truncation, treating that result as unsigned, and taking its remainder modulo 21; its range 0 through 20 is exactly representable on conversion to binary32. Item byte `+0x0d` then adds 1 for value 1, adds 0.5 for value 26, or adds 0.75 for value 27; other values add nothing.

The item's effective level is its signed 16-bit `+0x10`, converted to binary32, plus binary32 `0x3dcccccd` times its signed 32-bit `+0x114` converted to binary32. The helper at RVA `0x045f60` calculates the same level-growth factor described above at that effective level, multiplies it by a second power-of-two factor whose exponent is one quarter of unsigned byte `+0x0c`, and returns the binary32 product. The item contribution multiplies that product by 5, then by the item coefficient, then by the variation factor. The maximum-health helper adds each eligible contribution sequentially to its running value.

These are numeric stages rather than an assertion of arbitrary-real arithmetic: the scalar arithmetic and stores around the powers use the original binary32 operations, with binary64 power calls on the promoted exponents and binary32 conversion of each power result. The underlying precise-power library's internal approximation is not re-specified here. Nonfinite fields, singular denominators and integer overflow histories are outside the successful finite-input bounds of this contract.

Relationship report, propagation and healing-side updates

The helper at RVA `0x1a0970` first reads target map `+0x13a4` at the source creature's own resident ID from source `+8`, creating a zero entry if absent. It appends a 24-byte relationship report to output aggregate `+0x50`, carrying target creature ID, source creature ID and that map value. These helper IDs come from creature fields; the applier's preceding direct map/ID writes instead used the input hit IDs.

It then traverses the world creature map. For a non-null candidate other than the source and target, it requires the relationship predicate at RVA `0x196ca0` for candidate/source and squared distance from candidate to target strictly below 64. Coordinates are signed 64-bit creature fields at `+0x10`, `+0x18` and `+0x20`; differences are converted to binary32 and multiplied by exactly `1/65536` before squared-length comparison. If the candidate's map `+0x13a4` value keyed by the source's own resident ID is exactly zero, the helper writes binary32 0.5 and appends another relationship report for candidate/source. Lookup can insert a missing zero entry. A nonzero existing value is not overwritten. This helper has no health subtraction, shield unlink, random draw or category check.

For a negative amount, after healing/capping and only in world mode zero, the applier additionally traverses the world creature map. For each non-null candidate satisfying the relationship predicate for source/candidate, it requires an already existing candidate map `+0x13a4` entry keyed by the healed target's own resident ID. When present, the candidate map value keyed by the source's own resident ID is decreased by the negative amount multiplied by binary32 approximately 0.1; for finite negative amounts this is an increase. That source-keyed value may be newly inserted with zero. The report/propagation helper then runs with source/candidate. Thus health storage/capping precedes this traversal; each candidate map change precedes its own report and possible nearby propagation. No such healing-side traversal occurs in nonzero world mode.

The source lookup can be absent at entry, but the mode-zero negative-amount traversal does not guard that pointer before passing it to the relationship predicate, which dereferences its first argument. It is therefore not established as a safe source-less healing path. With the healed target still represented in a well-formed world map, the traversal has a non-null candidate and can reach that null-source dereference. No recovery behavior is assigned to it. This is distinct from the expressly allowed absent-source case on positive ordinary health subtraction.

The relationship predicate is ordered. It rejects first-role 5 with second-role 0, or either role 6. If one operand has role 1 and the other does not, it accepts, subject to that earlier rejection. Two role-1 operands are accepted when their species classifier results differ. Otherwise it accepts only when either operand's byte `+0x124` has bit `0x20` set.

That classifier at RVA `0x044680` is true only when its unsigned 16-bit `+0x7e` has no bits from mask `0x1a00` and its 32-bit kind is in this set: `0x13`, `0x14`, `0x16`, `0x17`, `0x19`, `0x1a`, `0x1b`, `0x1e`, `0x1f`, `0x20`, `0x21`, `0x22`, `0x23`, `0x35`, `0x37`, `0x38`, `0x39`, `0x3a`, `0x43`, `0x44`, `0x4a`, `0x57`, `0x59`, `0x5c`, `0x5d`, `0x62`, `0x64`, `0x6a`, `0x6b`, `0x91`, `0x92`, `0x93`. Its meaningful result, like health eligibility, is the low byte; incidental high return bits do not add another condition.

Fatal boundary and compact category comparison

Categories 0 and 5 that reach the final ownership-admitted amount branch join a health test at RVA `0x196133`. If health is positive, the applier returns through the normal epilogue. If finite health is at or below zero, it writes health zero, appends a visual/sound record with numeric kind `0x1b` at the target position to aggregate `+8`, and resets target action-time field `+0x6c` to zero. It then enters the fatal continuation, beginning with the position/chunk lookup at `0x196193`. Loot, rewards, quests, ownership cleanup and subsequent fatal side effects are outside this contract. Their internals are not inferred from the primitive hit behavior.

The trigger is actual stored health at this join, not a category name, the shield capacity becoming zero, the hit's raw amount alone, or merely satisfying the positive-damage eligibility predicate. Category 1 and category 3 return earlier. A final ownership rejection also returns earlier. Under ordinary finite state, a category-5 positive shield-only hit does not itself make an initially living target's health nonpositive, because that branch never subtracts health.

Limits and held result

This contract specifies ordinary finite scalar/vector/state mutations and their native order. It does not validate malformed or truncated hit inputs, null object internals, corrupt maps/lists, uninitialized padding, allocation failure, nonfinite arithmetic, out-of-range levels or timers, exception recovery, concurrent mutation or fatal-continuation internals. The routine has no traced transaction that rolls back earlier writes after a later admission failure. Buff expiry scheduling and independent incoming-hit production are not specified here. No implementation guidance, pseudocode or original code is supplied.
