# Alpha client prerequisites for the main menu

**Author status — FINAL / STABLE / HELD**

## Scope and reference

This contract traces ordinary startup of the original 32-bit Windows client to its maximized window, first presentation and main-menu text. The source image is `Cube.exe`, 3,885,568 bytes, preferred image base `0x00400000`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`. Addresses below are RVAs. Evidence comprises its PE import descriptors and constants, disassembly and scoped routine decompilations, and the supplied original files named below. A window handle exists well before Alpha asks Windows to show it. Startup can return before that request, request a quit afterward, or wait in a graphics reset.

## Order before the window is shown

| Stage | What the client requires or does |
| --- | --- |
| Windows loader | Direct imports include `d3d9.dll`, `DINPUT8.dll`, `FreeImage.dll`, `zlib1.dll`, `MSVCP110.dll` and `MSVCR110.dll`. The image also imports `WINMM.dll`, `WS2_32.dll`, `KERNEL32.dll`, `USER32.dll`, `SHELL32.dll`, `ole32.dll`, `IPHLPAPI.DLL` and `GLU32.dll`. Failure to resolve an ordinary import can precede the client's own dialogs. These names come from the client import table. Transitive dependencies of individual DLL builds are outside this trace. |
| Window class and handle | CRT code calls the application at `0x0C8AE0`. It requests Winsock 2.2, then registers class `Cube` and creates a window also titled `Cube`, initially 800 by 600 at (200, 200) without the visible style. An unsuccessful registration or null handle returns from startup. The Winsock return is unused here. See `0x0C8B0F–0x0C8BD5`. |
| Direct3D | At `0x0C8BDB` the client runs the graphics checks below. A failed check produces the Cube World Direct3D initialization dialog and returns. After success it enumerates adapter 0's X8R8G8B8 modes and collects distinct width-height pairs. A zero mode count skips that collection. See `0x0C8BE0–0x0C8D8C`. |
| Settings and sound | The client reads desktop dimensions, reads `options.cfg`, constructs the audio manager, attempts `data2.db`, then initializes XAudio2. Audio failure produces the XAudio2 initialization dialog and leaves startup before input or client construction. Volume is set only after successful audio initialization. See `0x0C8D92–0x0C8E14`, `0x222DA0` and `0x223530`. |
| DirectInput | The client creates DirectInput 8 and sets up the system keyboard and mouse before processing its command line. A nonzero DirectInput creation result produces the DirectInput8 initialization dialog and leaves startup. The individual devices have a different failure behavior, described below. See `0x0C8E19–0x0C8ED0`. |
| Client and content | The normal route attempts to create the relative directory `Save`, then constructs the client at `0x059C40`. The directory creation result is unused. The client constructs its data managers, reads its interface resources and prepares its menus before returning to the caller. Only then does the caller invoke `ShowWindow` with the maximized setting, hide the system cursor, update the window and set focus. See `0x0C8F06–0x0C9037`. |

## Graphics, audio and input details

At `0x0C8720–0x0C87D5` Alpha requests Direct3D 9 with SDK version 32, then creates one HAL device on adapter 0 with hardware vertex processing and multithreaded device access (flags `0x44`). Its first request is windowed and uses desktop width and height, default/unknown backbuffer format, discard swap effect, no multisampling, automatic D24S8 depth/stencil and immediate presentation. This request precedes reading the user's fullscreen, resolution and antialiasing options. Failure returns to the Direct3D dialog. The traced initialization makes one attempt with those parameters.

The device must also accept the graphics resources. Alpha registers the literal font search directory `c:\windows\fonts` and initializes its interface renderer and game renderer in turn. Both check vertex declarations and embedded shaders. The game renderer checks one shader-model-3 vertex shader and five shader-model-3 pixel shaders. The interface renderer also checks creation of vertex and index buffers. A failed renderer initialization reaches the same Direct3D dialog as a failed device creation. See `0x0C8807–0x0C891A`, `0x28A350` and `0x047E10–0x047FAC`. The dialog alone cannot identify a failed shader, device setting or graphics driver.

Audio uses in-process COM activation of the legacy XAudio2 class `5A508685-A254-4FBA-9B82-9A24B00306AF` with interface `8BCF1F58-9FE7-4583-8AC6-E2ADC465C8BB`. It checks activation, engine initialization and creation of the default mastering voice. A negative result at any of those checks fails audio initialization. The startup call is unconditional, including with zero volume. The original file set includes `XAudio2_8.dll`. The startup routine uses the COM identifiers above, and the client's PE has no direct import for that DLL. The registered provider and available output device on any particular machine require separate evidence. See `0x223530`, `0x0C8DC5–0x0C8E14` and the identifiers at `0x302D68–0x302D87`.

DirectInput version `0x0800` creates the system keyboard first, selects its data format and attempts acquisition. The system mouse follows with its own format, nonexclusive background cooperation with the window and acquisition. After each device-creation call Alpha immediately uses the returned device pointer. It does not check that call's result before using the pointer. An unavailable device can therefore fail before a menu appears without taking the DirectInput initialization dialog branch. The format, cooperation and acquisition results have no startup rejection branch here. The focused input loop requests 256 keyboard bytes and 16 mouse bytes. These device setup calls contain no gamepad enumeration. See `0x0C8E2D–0x0C8ED0` and the focused input path in `0x0C8AE0`.

## Configuration and original files

Paths below are the spellings passed by the client. Bare filesystem names use the process working directory. A SQLite blob key is a name within its database. The client does not change the working directory in the startup sequence traced here.

| File or entry | Startup use and failure behavior |
| --- | --- |
| `options.cfg` | Optional text settings. On a failed open/read the reader returns to the caller. It preserves existing values for settings it has not read. The static defaults are windowed, antialiasing 0, render distance 50, sound and music volumes 100, camera speed 50, smoothness 80, invert Y 0, language 0 and minimum time step 9. Both resolution fields start at zero and are replaced by desktop dimensions before the file is read. The parser accepts `fullscreen`, `resolutionX`, `resolutionY`, `antiAliasing`, `renderDistance`, `soundVolume`, `musicVolume`, `cameraSpeed`, `cameraSmoothness`, `invertY`, `language` and `minTimeStep`. See `0x0CE660`, `0x0CE6E0`, `0x2F9F10` and `0x0C8D92–0x0C8DB4`. |
| `data2.db`, `data4.db`, `data1.db`, `data3.db` | In this sequence the audio manager opens the first store. During client construction, speech opens the fourth-numbered store, the model loader opens the first-numbered store, and the interface icon loader opens the third-numbered store. All use a SQLite helper that requests read/write and create access, and attempts to create a key/value blob table after a successful open. A newly created empty store supplies none of the shipped assets. Merely opening the store does not establish that its keys are available. See `0x222EB0`, `0x059F57`, `0x18EBB3`, `0x0E1AFE`, `0x05A6CD`, `0x0EE37D`, `0x05E0F8–0x05E12D` and `0x0497B0`. |
| `dict_en.xml` | The speech constructor explicitly asks for this key inside `data4.db`. A missing or empty result skips dictionary parsing, and construction continues with built-in entries. The original store also contains `dict_de.xml`. This constructor requests the English key directly. The traced startup does not establish a German selection route. The title-menu drawing routine itself contains the literal labels “Start Game”, “Options” and “Exit”. See `0x0E1B3C–0x0E1BDE`, `0x0E2735` and `0x183320`. |
| `interface.plx` | A system object attempts a separate relative file open before registering interface callbacks. On open failure its loader returns false and the caller proceeds to registration without checking the result. See `0x05A724`, `0x1843B0–0x184452` and `0x00D010`. |
| `db.dat` | The client opens this separate binary file, seeks to its end, then reads the reported length. A zero length takes an early constructor return before ordinary menu assembly. For a nonzero length the client passes the contents through its own validation and records a pending quit if that check returns zero. The supplied original file is 32 bytes. This is distinct from the SQLite stores. A failed open has no separate friendly diagnostic here, and its precise downstream outcome is unverified. See `0x05ABE0–0x05AD8D` and the constructor return at `0x065AA5`. |
| `gui.plx`, `quest-tag.plx`, `help.plx`, `start.plx`, `cursor.plx` | The client reads the first four interface scenes in the listed order, then reads the cursor scene later in construction. The common reader opens each supplied path directly and returns false if the open fails. The constructor goes on to find named objects, and some uses require a real object. For example it looks up `star1` in the start scene and immediately clones the result. A missing node can therefore prevent initialization inside the constructor even without a file-specific dialog. An independent fatal effect for each of the five files is unproved. See `0x05C120–0x05C3B7`, `0x061E46–0x061E9A`, `0x253770`, `0x233D70` and `0x2326D0`. |
| `resource1.dat`, `resource2.dat` | Both contain font data. The font manager accepts the DAT suffix on the same path as TTF, can use registered font data or a file, caches successful faces by basename, and tries registered search directories after an unsuccessful load by name. The client explicitly tests `resource1.dat` and then `resource2.dat`. A missing face at either check sets the pending-quit flag. A text widget has its own fallback to `arial.ttf` when its requested face fails. That fallback does not satisfy the two named startup checks. The menu draw also requests `resource1.dat` and guards text drawing on the result. See `0x05DDAD–0x05DE57`, `0x239800`, `0x25F260`, `0x264770` and `0x183320`. |
| `Save/characters.db`, `Save/worlds.db` | Client construction opens these two stores later using the same create-capable database helper. A pre-existing character or world is not an explicit condition of the menu entry path. See `0x064EFC–0x065035`. |

## A shown window and a usable menu

A pending quit set by the content checks does not itself cancel the call to show the window. The message loop checks it at `0x0C90B3` and posts a quit message at `0x0C90BE`. A window may therefore be shown briefly before ordinary menu interaction is possible.

The frame path updates the client, draws and presents. A separate graphics reset uses the client area in windowed mode or configured dimensions in fullscreen mode. While the device keeps rejecting the reset, Alpha sleeps 100 milliseconds and retries with the same presentation settings. There is no attempt limit or alternate format in that loop. This can delay a usable frame even after initial device creation succeeded. See `0x0C85F0`, `0x0C8940` and `0x0C8A58–0x0C8A7A`.

These branches establish native startup requirements and failure modes. Which DLL version Windows resolves, whether a particular driver accepts the requested resources, whether COM can open the default audio output, and whether a specific desktop session supplies usable input devices are host observations. This contract does not assign a cause to any observed launch.
