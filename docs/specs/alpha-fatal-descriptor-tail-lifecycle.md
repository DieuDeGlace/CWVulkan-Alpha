# Alpha fatal descriptor-tail lifecycle

Status: FINAL / STABLE / HELD. Re-certified on 2026-11-22 against the original client image. This original-only contract closes the concrete descriptor destruction reached by the fatal regional-completion tail walk in client RVA 0x195A60, the meaning and verified producer of the cell's +0xA0 boundary, and selected construction, activation, rebuilding and backing-storage paths. It distinguishes that destruction from a separate path which also removes instantiated creatures. It does not certify every possible writer of the pointer vector or every surrounding world lifecycle; open points are collected under "Unresolved".

## Image and evidence identity

The evidence root is identified relatively as `disassembled alpha cube world`. All evidence paths below are relative to that root. The supported original image is `binary/Cube.exe`, 3,885,568 bytes, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base 0x00400000. All addresses below are RVAs within that image.

The statements below rest on native instructions decoded directly from the image bytes and on original RTTI and vtable bytes read from the image. The exported listing `decompiled/client/assembly.txt` omits some instructions and was used only to locate instruction boundaries. Individually identified files under `decompiled/client/functions` served as cross-references; the file for routine 0x1E4850 carries a decompilation-timeout notice, so its findings use native instructions only. No reconstruction source, earlier held document, implementation or runtime material was used.

C denotes the cell object returned by spatial helper 0x034D10. S denotes a descriptor pointer stored in C's +0x18 vector. A denotes a separately instantiated creature. T denotes the creature resolved at the start of 0x195A60 from W's creature map, whose coordinates select the completion area. W denotes the world object that 0x195A60 receives as its receiver. These labels do not assume that S and A share an allocation or lifetime.

## Concrete pointed type and virtual entry

The verified tail producers allocate 0x10F0-byte descriptor objects and construct them through RVA 0x1ADB20. That constructor installs the vtable at image RVA 0x31DBEC. The four bytes preceding that vtable point to the complete-object locator at 0x3481DC, which names the type descriptor at 0x3679E8; its original RTTI name is `.?AUSpawn@cube@@`. Thus `cube::Spawn` is an image-established descriptor identity, not a name inferred from reconstruction.

The first function pointer in that vtable is RVA 0x1ADDB0. This is the virtual method reached when the fatal walk invokes the first vtable entry of an ordinary S constructed by that path. The call supplies S as receiver and one four-byte argument equal to 1. Entry 0x1ADDB0 first runs the descriptor destructor body 0x1ADCA0. It then tests the low bit of its argument and, because the argument is 1, releases S's own allocation through the scalar-deallocation thunk at 0x28D66E. It returns the former receiver pointer; the fatal caller ignores it.

This closes the virtual identity for the observed concrete descriptor. It is not an arbitrary game action callback on that path. A vtable replacement, a different concrete type inserted by an unclosed writer, a corrupt pointer or duplicate ownership is outside this identity guarantee. The two producer families inspected below use this same constructor; an exhaustive inventory of every possible vector writer is not claimed.

Evidence: native 0x1ADB20–0x1ADC9B, 0x1ADCA0–0x1ADDA2 and 0x1ADDB0–0x1ADDCE; vtable bytes at 0x31DBE8–0x31DBEF; locator bytes at 0x3481DC; RTTI name at 0x3679F0. The fatal virtual invocation itself is at 0x19660B.

## Cell pointer vector and the +0xA0 boundary

C+0x18 is the four-byte pointer to the beginning of a pointer vector; C+0x1C is its logical end and C+0x20 its capacity end. Each element is a four-byte S pointer. The count used here is the byte distance between end and beginning, shifted arithmetically right by two (a signed element count). C+0xA0 is a four-byte element index, not a byte offset, vector capacity or creature count.

Cell constructor 0x2240F0 zeros the three vector members and C+0xA0. In the successful new-cell construction path within 0x1E4850, native 0x1EDD53–0x1EDD64 obtains the current descriptor-vector count through 0x087F50, stores that count at C+0xA0, and then calls tail producer/rebuilder 0x1D9460 with C as its argument. Descriptors already present at this boundary form the retained prefix. Entries added afterward form the removable tail. The fatal completion walk does not move +0xA0 to the new vector end and does not turn it into a counter of removed objects.

The same new-cell path allocates a 0xC8-byte cell and runs constructor 0x2240F0 at 0x1E495F–0x1E4984, after spatial helper 0x034D10 at 0x1E4952 reported the requested cell absent. The cell-pointer publication at 0x1EE05A stores C into its world block's cell-pointer array at block offset +0x10018. Those sites establish cell storage and publication separately from creature-map insertion. Full generation between them, other cell-loading routes and every later boundary producer remain outside this contract.

Spatial helper 0x034D10 performs no allocation. It returns null when either requested cell coordinate is negative or not less than 0x10000, or when the containing 64-by-64 cell block is absent; otherwise it returns the four-byte entry of that block's cell-pointer array at +0x10018, selected by the first coordinate's position within the block times 64 plus the second coordinate's position.

Under the ordinary valid invariant, +0xA0 lies between zero and the current pointer-vector count. If it is zero, the whole vector is a tail for these consumers. The fatal code does not validate or clamp a malformed boundary before using it as a signed index. Out-of-range, negative or overflowed values therefore have no safe prefix-retention guarantee.

Evidence: native 0x2240F0–0x22433E (zeroing of +0x18, +0x1C, +0x20 at 0x22415B–0x224169 and of +0xA0 at 0x224271); 0x087F50; 0x034D10–0x034D85; the new-cell and boundary/publication sites in 0x1E4850 named above; the fatal reads at 0x1965E7–0x1965FD.

## Verified tail construction and rebuilding

Rebuilder 0x1D9460 runs with W as receiver and acts only when W's four-byte member +0xA4 is nonzero. It begins at the existing tail index C+0xA0. For each old tail descriptor, it first searches W's creature map using the descriptor's complete eight-byte identifier at S+0x48. When that key resolves to a map node whose creature pointer A is nonnull, the rebuilder invokes A's first virtual method with argument 1, then obtains the matching-key range and erases it from W's creature map. Only afterward does it invoke the descriptor's own first virtual method with argument 1, skipping that call for a null slot. The vector end is reread after each element. It then truncates C's descriptor vector back to +0xA0 through resize helper 0x00D9D0.

This is an explicit creature-removal path. It is separate from fatal completion, whose descriptor-tail walk performs no creature lookup, creature virtual call or world-map erasure. The creature virtual destructor's transitive work is not reconstructed here; its invocation and the following map-node removal are established boundaries.

After that old-tail cleanup, the rebuilder may take a regional-data route. That route requires both cell coordinates at C+0x60 and C+0x64, after division by 8 toward zero, to lie in 0 to 0x1FFF, a present world block, a regional entry whose four-byte member +0x54 is nonzero, and an exact match between that entry's two four-byte values at +0x60/+0x64 and C's coordinates. On that route it allocates one new 0x10F0-byte S through 0x1ADB20, populates descriptor state and content, creates a 0x0C-byte behavior object through 0x0DC2D0, attaches child objects to it and stores it at S+0x109C (0x1D99DE). It then calls 0x03F7C0 and 0x1C7730 for S, assigns the eight-byte identifier, and appends S to C+0x18. Those preparation helpers and item generators can consume randomness; this is not the destruction path's draw count.

The identifier is computed in signed 64-bit arithmetic from the sign-extended four-byte cell coordinates and position: the C+0x64 coordinate times 2^24, plus the C+0x60 coordinate times 2^8, plus the element index at which S is placed (the vector count before the append). The low four bytes are stored at S+0x48 and the high four bytes at S+0x4C.

If that regional-data route is not admitted, the rebuilder calls fallback generator 0x1D6040 with C and a second four-byte argument of zero. The fallback first returns without generating when any current tail descriptor's identifier resolves in W's creature map to a node with a nonnull creature pointer. On its examined generating path it adds its second argument to the four-byte cell member C+0xA4, then destroys every current tail descriptor through that descriptor's first virtual method with argument 1 (null slots skipped, no creature lookup or erasure) and truncates the vector back to C+0xA0 through 0x00D9D0. Its creation sites allocate 0x10F0-byte objects through 0x1ADB20 and create 0x0C-byte behavior objects through 0x0DC2D0. Its final tail pass starts at C+0xA0, assigns each added entry the identifier described above using that entry's vector position, and calls the same two preparation helpers on each. The fallback has further terrain, actor and generation predicates whose meanings are not closed here. Its presence does not prove that a fatal completion always or immediately recreates a tail.

Another original caller, 0x1D9AD0, runs with W as receiver, requires W byte +0xB4 equal to zero, W+0xA4 nonzero and a nonnull world block, and then invokes 0x1D9460 (at 0x1DA1D9) for every nonnull entry among that block's 64-by-64 cell pointers at +0x10018. Afterwards it sets the block's byte +0x15A18 to 1. Its full scheduling and reset policy is outside this audit. Deleting a tail is therefore not, by itself, evidence of a permanent prohibition on later descriptor creation.

A null descriptor slot reached by the rebuilder's initial identifier lookup, or by the fallback's initial identifier check, is not protected: the lookup reads through the slot before any null test. Malformed pointer slots are not made safe by this contract.

Evidence: native 0x1D9460–0x1D9AC9, including old-tail cleanup 0x1D9494–0x1D954A, route admission 0x1D95E1–0x1D96F2, allocation 0x1D96F4–0x1D970C, behavior creation 0x1D9897–0x1D98B4, preparation 0x1D99EC/0x1D99FD, identifier 0x1D9A02–0x1D9A3C, append 0x1D9A3F–0x1D9A98 and fallback call 0x1D9AA7; native 0x1D6040, especially 0x1D60F8–0x1D617D, 0x1D658D–0x1D65C6, constructor calls 0x1D703F/0x1D7583 and final pass 0x1D7958–0x1D79D9; native 0x1D9AD0–0x1DA1EF. Matching-key range and erasure helpers are 0x209280 and 0x27EB10.

## Fatal completion removal order

Routine 0x195A60 resolves T from W's creature map and returns at once if T is absent or T's four-byte floating value at +0x16C is not greater than zero. The removal block is reached only on a later path where that same value is no longer greater than zero; that path stores zero into it. Within the block, a completion flag is cleared at 0x196393 and set only at 0x196510.

The block is skipped entirely when W byte +0xB4 is nonzero, when no regional record is found through 0x087DA0 for T's +0x1B0 and +0x1B4 coordinates each divided by 8 toward zero, or when that record's byte +0x41 already equals 2. Further gates involve T's two-byte member +0x7E (bit 0x2000), the record's four-byte kind at +0x34 together with T's byte +0x1D38, and a qualifying entry in a map rooted at T+0x13A4; their meanings are listed under "Unresolved". The record kind then selects the outcome. Kinds 1 to 5 and 13 set the completion flag directly and set record byte +0x41 to 2. Kinds 7 to 12 increment the record's four-byte counter at +0x44, set byte +0x41 to 1, and, when the counter is not less than the signed four-byte limit at +0x48, set the flag and set byte +0x41 to 2. Kind 6 and kinds outside 1 to 13 skip the block.

On both of the outcomes that reach it, a regional completion record carrying T's coordinates divided by 8 toward zero is appended to an output list (call at 0x196579) before any descriptor-tail removal. Removal follows only when the completion flag is set. The routine then visits the cell area whose origin is T's signed +0x1B0 and +0x1B4 coordinates, each divided by 8 toward zero and multiplied back by 8. Under unchanged coordinates and ordinary bounds, it visits eight first-coordinate values in ascending order, with eight second-coordinate values ascending inside each first-coordinate visit, and queries 0x034D10 on W for each.

For each nonnull C, it starts at the signed index C+0xA0 and walks to the current pointer-vector end using a signed comparison. A null element skips the virtual invocation. A nonnull ordinary S reaches the concrete destruction sequence above. The vector beginning and end are reloaded after each element. After the walk, including when the starting index was already at or past the count so that no element was visited, the code rereads C+0xA0 and calls vector-resize helper 0x00D9D0 with that value.

The resize helper compares the current count with the requested value as unsigned numbers. For valid ordinary shrinkage it only sets the vector's logical end to the retained-prefix boundary; an equal count leaves the vector unchanged. It does not free the vector's backing allocation, reduce capacity, clear any discarded pointer slot, invoke descriptor destructors again, or erase C from the world's cell-pointer array. Discarded storage can still contain old pointer bytes beyond the logical end; those bytes are not live vector entries. The boundary member +0xA0 is unchanged by this fatal operation. When the requested value exceeds the count, including a negative value read as unsigned, the helper instead takes a growth path that may reserve capacity and zero-fills the new elements, so a malformed boundary cannot be described simply as tail removal.

The first coordinate's starting base is computed once before traversal. The second base is recomputed for each outer step, and both coordinate upper limits are recomputed from T's current members during traversal. No immutable copy of the target coordinates is kept across virtual invocations. For the verified ordinary Spawn destructor, however, the destruction chain described below writes neither T, creature coordinates, cell coordinates nor world mappings. With valid disjoint ownership and unchanged external state, this concrete path therefore supplies no game callback that changes the area bounds while the walk runs. That conclusion is conditional on the established concrete type and valid ownership; it does not extend to corrupt pointers, another unproved vtable target or allocator failure or reentrancy.

Evidence: native 0x195A8E–0x195AF7 (T resolution and first value test), 0x196133–0x196150 (second value test and zero store), 0x196393–0x196501 (flag clear and gates), dispatch bytes at 0x196C78–0x196C90, 0x196501–0x196579 (counter, flag and append), 0x19657E–0x196685 (area walk, invocation at 0x19660B, resize at 0x19662A); resize helper 0x00D9D0–0x00DA5F.

## Descriptor-owned backing destruction

The concrete destructor body reinstalls the Spawn vtable and then has the following storage effects, in this order:

| Descriptor storage | Ordinary destruction effect |
| --- | --- |
| Four-byte pointer S+0x109C | If nonnull, passed directly to scalar deallocation |
| Three-word range S+0x10BC/+0x10C0/+0x10C4 | If its first pointer is nonnull, that pointer is deallocated and all three four-byte members are zeroed |
| Three-word range S+0x10AC/+0x10B0/+0x10B4 | Same conditional deallocation and three-member reset |
| Three-word range S+0x10A0/+0x10A4/+0x10A8 | Same conditional deallocation and three-member reset |
| Outer three-word range S+0x0F6C/+0x0F70/+0x0F74 | For a nonnull beginning pointer, inner storage records are released, the outer allocation is freed, then the outer triple is zeroed |
| S's own allocation | Freed afterward by 0x1ADDB0 because argument 1 has its low bit set |

The inner-storage helper at 0x239CF0 walks the outer range from its beginning to its logical end (S+0x0F70) in 12-byte records. For each record with a nonnull first pointer it deallocates that backing pointer and zeroes the record's three four-byte members. It invokes no virtual method on the stored contents. The outer allocation is released after those inner backing allocations.

In particular, the first +0x109C operation is a direct storage deallocation, not a virtual destruction of the pointed object. No release of that object's own children can be inferred from this call. That pointer is not set to zero before S itself is freed on the argument-1 route.

The concrete chain contains no world or creature lookup, hit application, map erasure, coordinate conversion, game virtual callback, random or seed call or output-record append. It reads and resets descriptor storage and calls the runtime library's scalar-deallocation import. No write to a creature's health, the fatal target's coordinates, W's creature-map nodes or the world cell-pointer table appears in that chain. Imported allocator internals and invalid aliasing of supposedly owned allocations are outside the established game-side effects.

Evidence: complete native 0x1ADCA0–0x1ADDA2 and 0x239CF0–0x239D2D. The thunk at 0x28D66E is a single indirect jump through the import slot at image RVA 0x2FC3F0, identified in the function index as the MSVCR110.DLL scalar deallocation import; this audit does not treat it as a hidden game callback.

## Creature activation is a separate ownership boundary

The world update at 0x20C510 walks a cell's descriptor-pointer vector at C+0x18, using its element count, and separately admits descriptor activation. The gates confirmed in this pass are: a time window held in S+0x40 and S+0x44, which is enforced only when those two values differ; absence of an instantiated creature under the identifier at S+0x48; and a marker check in which a negative four-byte S+0x38 is clamped to zero, while a positive S+0x38 requires S+0x3C to differ from a reference value held by the update's context object. Full input collection and every other activation predicate are outside this contract; a stored descriptor is not proof of immediate activation.

On the verified successful creation route at 0x20FFBA–0x21000E, the world allocates a distinct 0x1E60-byte creature, runs creature constructor 0x03B690 with the identifier at S+0x48, and stores the new pointer in W's creature map under that identifier. It then copies descriptor configuration and cell and index associations into the creature. The descriptor is neither moved into the creature allocation nor removed from C because activation succeeds.

Several owned-data boundaries are explicit. Descriptor arrays at +0x10AC and +0x10BC are copied into creature members +0x13E8 and +0x13F8 through assignment helper 0x27A7B0, and S+0x10B8 is copied into creature+0x13F4. That helper copies contents into destination storage, allocating destination backing when required, rather than transferring the source pointer triple. The data rooted at S+0x0F6C is copied to creature+0x11DC through 0x04AFF0 and its nested container-assignment helpers; their inspected paths assign or construct 12-byte inner vector records and allocate or copy their 0x11C-byte elements. They do not establish a transfer of ownership of S's outer or inner allocations to the creature. The range at S+0x10A0 is passed to helper 0x209080 for creature+0x148C, whose copy semantics are not closed here; activation then scans that range's elements to choose an index stored in creature members +0x1484 and +0x1488. Item semantics and all invalid-alias cases are outside this storage observation.

When S+0x109C is nonnull, activation invokes that object's virtual method at vtable offset +4 and stores the result in creature+0x13E4; it does not store S+0x109C itself there. For the concrete 0x0C-byte object constructed by 0x0DC2D0 in the examined tail generators, whose vtable is at image RVA 0x303A00, that entry is 0x0DC400: it allocates a new 0x0C-byte object and runs copy constructor 0x0DC200, which creates a separate child list and fills it with the results of each source child's own +4 virtual entry. The outer result is therefore a distinct allocation on the successful ordinary route. When S+0x109C is null and the four-byte S+0x28 is not 6, activation instead builds a fresh 0x0C-byte behavior through 0x0DC2D0, attaches children to it and stores that in creature+0x13E4; when S+0x28 is 6 no behavior is stored there by this route.

Consequently the known fatal Spawn destruction is not an instruction to destroy its corresponding instantiated creature. The fatal tail walk contains no creature-identifier lookup or map removal. The explicit creature deletion and map erasure performed by rebuilder 0x1D9460 must not be added to fatal completion. Conversely, this audit does not certify every later user of a deleted descriptor index or every lifetime of cloned behavior children.

Evidence: native 0x20FB48–0x20FBA5 (vector source and count), 0x20FBAB–0x20FC29 (gates), 0x20FFBA–0x2101FC (creation and copies), 0x210208–0x2103BF (behavior and array copies); 0x27A7B0–0x27A8B5; 0x04AFF0–0x04B02F and nested helpers 0x04AD30, 0x04AA20, 0x04A410, 0x049CB0, 0x04A700; behavior entries 0x0DC2D0, 0x0DC400, 0x0DC200 and vtable bytes at 0x303A00–0x303A07.

## Final cell ownership and limits

The cell destructor at 0x224390 walks the entire C+0x18 vector, not only its tail, and invokes each nonnull element's first virtual method with argument 1. Later it frees the vector's backing allocation if its beginning is nonnull and zeroes the three vector members. This supplies an independent ordinary ownership boundary for retained-prefix descriptors as well as any surviving tail. The full cell destructor also manages unrelated arrays and objects; its world-removal callers and all their side effects are not closed here. The cell's deleting wrapper at 0x224760 runs that destructor and then frees C when its argument's low bit is set.

The supported conclusions require valid live cells, ordinary vector boundaries, the observed concrete descriptor type and unique ownership of released allocations. Rebuilder creature deletion, fatal completion's descriptor-only destruction, the fallback's descriptor-only tail cleanup and final cell teardown have different proved boundaries and are not interchangeable operations.

Evidence: native 0x224414–0x224432 (full-vector invocation), 0x224651–0x22466F (backing release), 0x224760–0x22477E.

## Unresolved

- The meaning of the fatal-block gates on T's two-byte member +0x7E bit 0x2000, the record kind 5 combined with T byte +0x1D38, and the T+0x13A4 map search (an entry whose floating value at +0x18 exceeds zero and whose key resolves to an instantiated creature with byte +0x60 zero) was not closed; only their presence and order are stated.
- The meaning of each regional record kind at +0x34, of the record found through 0x087DA0, and of the appended completion record's content and consumers.
- Any proximity requirement for descriptor activation, and every activation predicate other than those confirmed above. An earlier statement that activation requires proximity to an eligible world creature was not re-confirmed in this pass.
- The meaning of W+0xA4, W byte +0xB4, cell member C+0xA4 and world-block byte +0x15A18.
- The fallback generator's terrain, actor and generation predicates, and whether every fatal completion is followed by tail recreation.
- The copy semantics of helper 0x209080 for S+0x10A0, the exact concrete identities and copy behavior of behavior children, and the transitive work of the creature virtual destructor.
- Whether every deserialization, modification or uninspected generator stores only Spawn descriptors; whether any descriptor pointer can be duplicated; and full world unload, reload, persistence, synchronization, exceptional allocation behavior and every indirect vector writer.

## Re-certification (2026-11-22)

A fresh source-only author re-checked every statement in this document against the original client image identified above, decoding native instructions directly from the image bytes and reading the RTTI, vtable and dispatch bytes in place. The image size and hash, the Spawn type identity, the destruction order, the field offsets and widths, the boundary producer, the walk order and the resize behavior were confirmed. One statement was moved to "Unresolved": the activation proximity gate. Several statements were sharpened or completed: the completion route's confirmed gates and kind dispatch, the fatal value test on T, the resize call made even when no tail element is visited, the lookup helper's bounds, the rebuilder's unconditional behavior creation on its regional route, the identifier composition, the fallback's own descriptor-only tail cleanup, and the activation handling of a null S+0x109C and of S+0x10A0 and S+0x10B8. What remains open is listed under "Unresolved".
