# Alpha client startup and initial window boundary

Status: FINAL / STABLE / HELD. This contract covers the supported original client's executable dependencies, entry-to-window ordering, direct early exits and selected blocking boundaries. Creation of the native game window and the later request to show it are distinct milestones. Broader game construction, complete graphics initialization and every runtime initializer remain outside scope. Points that could not be confirmed are collected under "Unresolved points" rather than asserted.

The evidence root is identified relatively as `disassembled alpha cube world`. The supported image is `binary/Cube.exe`, 3,885,568 bytes, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`. It is a PE32 x86 Windows GUI executable (machine `0x14C`, subsystem 2), with preferred image base `0x400000`, entry RVA `0x28E1E0` and image size `0x3BC000`. Its DLL-characteristics field is `0x8140`: the image is marked relocatable at load (dynamic base), no-execute compatible and terminal-server aware, and it carries a base-relocation directory. RVAs below are relative to that image. The audit used original executable bytes and the original instruction listing, without reconstruction, runtime execution or other contracts.

Normal loading must resolve this image's direct imports before its entry routine can execute. A missing or incompatible direct dependency, an unresolved named export or an unresolved ordinal can therefore prevent the application from reaching its own window-creation call. This is an executable-loader prerequisite, not a failure produced by the later Direct3D or DirectInput admission checks. The supported image is x86; a same-named DLL of incompatible architecture does not satisfy that image's import requirement.

Neither an XAudio DLL nor a D3DX DLL appears in this direct import table. The image imports `LoadLibraryA`, `LoadLibraryW` and `GetProcAddress`, reached through import thunks at RVAs `0x28D47C`, `0x28D4E2` and `0x28D494` respectively. Their presence alone does not establish a particular dynamically loaded dependency. The inspected direct path from entry to the show request contains no explicit request for a named DLL through these services. A literal-string inspection of the image, in both single-byte and wide form, finds DLL filename strings only for the 14 direct imports; the only XAudio-related strings are the XAudio2 diagnostic text and internal type-identification names, neither of which is a DLL filename. This does not exclude indirect, constructed-name or dependency-owned loading.

The audio startup route makes a COM activation request after game-window creation. The application describes failure of this route as an XAudio2 initialization failure. The executable evidence establishes the COM class/interface request, not the filename or version of the DLL selected by the operating system's COM registration.

## Work before the application's window request

The PE entry at RVA `0x28E1E0` first initializes the stack-protection cookie and then enters native runtime startup. Before calling the application routine, runtime startup obtains the initial show-mode value from the runtime, serializes initialization through a four-byte ownership word at image RVA `0x36E2E4` (the value written is a per-thread identifying value), and examines a four-byte initialization state at `0x36E2E8`.

Ownership acquisition is an atomic compare-and-exchange that retries while a different ownership value remains present; the retry at `0x28E217`–`0x28E225` has no timeout, sleep or yield. A thread that finds its own value already present takes a separate nested route and does not release ownership afterwards. An initialization state equal to 1 calls the runtime fatal-message exit with numeric reason `0x1F`. For an uninitialized state (zero), startup sets the state to 1 and runs the error-returning initializer range bounded by RVAs `0x2FC8C8` and `0x2FC8DC`; a nonzero result leaves startup with value `0xFF` before the application routine. It then runs the second initializer range bounded by `0x2FC62C` and `0x2FC8C4` and records initialization state 2. The first range holds four nonnull entries and the second 165, each range also containing one null entry. A non-nested owner then releases the ownership word.

Those initializers are a real prerequisite to this application's window call. Their entire transitive work has not been reconstructed. The four entries of the first range are a process-type and runtime-mode setup routine at `0x28E0DC`, an exit-handler table allocation at `0x28D674` (which returns a nonzero failure value when its allocation fails), a processor-feature detection routine at `0x28E4B8`, and a routine at `0x28E645` that installs an unhandled-exception filter. The first entry of the second range is native argument setup at RVA `0x28E195`; it calls the runtime main-argument service and invokes the fatal-message exit with reason 8 for a negative result.

After initializer processing, startup contains a guarded optional callback through the four-byte slot at image RVA `0x36E2EC`: the call requires a nonnull slot and a successful check that the slot lies in a non-writable section of the current image. The slot lies in zero-initialized image storage. Startup then scans the native single-byte command line past the executable portion, honouring quotation marks and multibyte lead bytes, skips following blanks, and calls the application routine at RVA `0x0C8AE0` from `0x28E307`. The four arguments are the image's load base as the instance value, zero as the previous instance, the remaining command-line text and the show-mode value. The load base is supplied as a relocated immediate; it equals `0x400000` only when the image loads at its preferred base. Detailed runtime exception and termination behavior remains outside this boundary.

The application's first direct startup work records the instance at image RVA `0x36B1C4` and requests socket-library version `0x0202` at `0x0C8B0F`. Its return value is not tested before continuing to class registration. It prepares a window class named `Cube` (wide text at RVA `0x302DB8`), with window procedure RVA `0x0C83F0`, zero class-style and extra-byte fields, the supplied instance, a null class cursor, background value 6 and the name `Cube` in both the class-name and menu-name fields. It requests an icon named `Cube` from the supplied instance; that return is placed into the class description without a separate failure branch.

The image's resource directory contains one resource: type 24 (manifest), identifier 1, language 1033, data RVA `0x370060`, length 381 bytes. The manifest requests execution as the invoking user with UI access disabled and contains no dependent-assembly declaration. There is therefore no embedded menu or icon resource named `Cube` in this image. No extra application-side resource validation is visible in this direct path.

## Creation, failure exits and later visibility

The application calls `RegisterClassW` at RVA `0x0C8B88` and tests the returned 16-bit atom for zero. Zero bypasses window creation and reaches the common return at `0x0C9534`; there is no application message box on this branch and no retry or acceptance of an already registered class.

With a nonzero atom, it calls `CreateWindowExW` at `0x0C8BC8`. The requested extended style is zero; class and title are both `Cube`; style is `0x06CF0000` (the standard overlapped-window style combined with clip-siblings and clip-children); requested position is 200, 200 and requested outer dimensions are 800 by 600. Parent window, explicit menu handle and creation parameter are null, and the instance is the stored application instance. The returned window handle is stored at image RVA `0x36B1C0`, then tested for null. Null also reaches the common return without a diagnostic. That common return yields application result zero. When the runtime's managed-image flag is clear, which holds for this image because it has no managed-code header, runtime startup then passes the application result to process exit.

The initial style does not contain the visible bit `0x10000000`. A successful window handle therefore marks creation before the application's later explicit show request. The immediate next call, at `0x0C8BDB`, is the graphics initialization routine at RVA `0x0C8720`. A false byte result shows a message box owned by the created window, with caption `Cube World`, an OK-only button set and text stating that Direct3D could not be initialized and recommending the latest DirectX End-User Runtime; the application then returns result zero. That generic diagnostic does not identify which nested graphics prerequisite failed.

That graphics routine calls `Direct3DCreate9` with SDK-version argument `0x20`. A null result fails. It then requests device creation through the returned object, supplying adapter 0, device-type value 1, the created window handle and behavior-flag value `0x44`; any result other than zero fails this stage and releases the Direct3D object. Further renderer, font and auxiliary-object initialization also precedes the routine's final success byte. Their complete assets, capabilities and failure requirements are not reconstructed here. Thus an existing `d3d9.dll` is a loader prerequisite, while successful graphics initialization is a later, stricter prerequisite to the application's show request.

On graphics success, display-mode enumeration, retrieval of the two primary screen dimensions and intervening initialization calls precede the audio activation call at `0x0C8DC5`. A false audio result shows the XAudio2 diagnostic (same caption, button set and runtime recommendation) and leaves the normal startup path through cleanup at `0x0C9514` and result zero. The audio routine does not test the `CoInitializeEx` return before the activation request. It rejects a negative activation result, a negative result of the following audio-object initialization (releasing the object) and a negative result of the following output-voice creation; these are signed failure tests. Two later allocations inside the routine are not failure conditions: a failed allocation leaves a null member and the routine still reports success.

The application calls `DirectInput8Create` at `0x0C8E2D`, with the supplied instance, version `0x0800`, the interface identifier `bf798031-483a-4da2-aa99-5d64ed369700` stored at image RVA `0x31E290`, and no outer object. It admits exactly return value zero. Any nonzero value shows the DirectInput8 diagnostic and leaves through cleanup and result zero. After admitted input creation, keyboard and mouse device setup (whose individual results are not tested here), wide command-line retrieval and parsing, an attempt to create the `Save` directory, and client allocation and construction precede visibility. The client object allocation requests `0x1001018` bytes; on a null allocation the constructor call at `0x0C8FF9` is skipped and a null client reference is stored at image RVA `0x36B1C8`, with startup continuing to the show request. The constructor's transitive file, content and initialization requirements are outside this contract.

The explicit `ShowWindow` request occurs at RVA `0x0C900F`, with the created handle and numeric show command 3. Cursor clearing and cursor hiding follow, then `UpdateWindow` at `0x0C902B`, focus assignment to the window, a one-millisecond timer-period request at `0x0C903F`, and then the main message and frame loop. These calls establish native ordering; they do not guarantee that any particular pixels were painted or that the window became foreground or visibly rendered on a particular system.

## Blocking boundaries and remaining limits

Before the application window call, the runtime initialization ownership retry has no native timeout. DLL-loader initialization, runtime initializers, socket-library startup and operating-system window operations are synchronous dependencies whose duration and complete failure behavior were not audited. A missing dependency can stop execution before the entry routine runs; an early runtime failure can stop it before the application routine; class-registration or creation failure returns without a usable game-window handle.

After a handle exists, each of the three startup diagnostics is a modal message box shown before its failure return, so acknowledgement can delay exit while the window has not reached its explicit show request. Native construction and COM or driver operations can also delay that later milestone; no general startup timeout is established.

The registered window procedure dispatches message kinds 5 (size) and 7 (focus gain) to the routine at RVA `0x0C8940`. That routine obtains extents either from stored screen dimensions or from the window's client area, and proceeds only for positive width and height and a nonnull graphics device. It then requests a device reset; while the reset result is nonzero it sleeps 100 milliseconds and retries, with no retry limit. This is a further synchronous window-message blocking route once a graphics device exists. It is not shown to run during the initial creation call, because device creation has not yet occurred on the direct application path at that point.

No exact loader error text, dependency search order, registry-selected audio DLL, redistributable installer version, device-driver diagnosis, complete initial-resource requirement or comprehensive reason for an absent visible window follows from this evidence alone. In particular, the absence of a shown game window does not establish that the executable failed before `CreateWindowExW`; several substantial prerequisites occur after handle creation and before `ShowWindow`. This contract establishes their order and audited admission tests without reconstructing broader game initialization.

## Unresolved points

- The complete transitive work of the 169 runtime initializers, including whether any of them block, access files or load further libraries.
- How the operating system treats the missing `Cube` icon and menu resources during class registration and window creation.
- Actual DLL search results, forwarded exports, dependencies of the direct-import DLLs and their own initialization behavior.
- Which DLL file the operating system's COM registration selects for the audio class request, and its version.
- Whether initializer effects ever place a nonzero value in the optional callback slot at `0x36E2EC`.
- The full set of message kinds that reach the reset routine: a further call site at `0x0C86D6` inside the window procedure also reaches it, and its triggering message was not characterized.
- The complete asset, capability and failure requirements of the graphics routine after device creation, of the keyboard and mouse device setup, and of the client constructor.

## Re-certification (2026-11-22)

A fresh source-only author re-checked this document against the original image bytes and original instruction listing. Image identity, size, hash, entry, base, import directory and the 14 direct imports, the GUIDs, window class fields, window style, position and size, call order and the reset retry behavior were confirmed. Corrections: the instance value is the relocated load base rather than a fixed `0x400000`; the routine at `0x28E645` installs an unhandled-exception filter rather than registering exit handlers, which is instead the role of the table allocation at `0x28D674`; and process exit after the application returns depends on the runtime's managed-image flag, which is clear for this image. Additions confirmed from the image: the dynamic-base characteristics, the DirectInput interface identifier, device-creation arguments, diagnostic captions, the null-allocation route for the client object and the non-failing audio allocations. The open points are listed under "Unresolved points"; nothing previously asserted was found unconfirmable beyond those items.
