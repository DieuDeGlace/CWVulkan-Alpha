## Query interface and resident records

Each query is called with the world/object pointer in the object register and two stack arguments, signed 32-bit integer coordinates called X (first) and Y (second) here; it removes eight argument bytes on return. Each returns a binary32 scalar represented on the x87 return stack. The queries read resident pointers from a 1024 by 1024 table beginning at object `+0x4000BC`. The first coordinate selects a row; the second selects a column. Each slot is four bytes, so slot (row, column) is at object `+0x4000BC + 4096 × row + 4 × column`. The query does not allocate a record, fill a missing entry, change an entry, reseed a random generator, or request a random draw. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF040–0x1EF59D`, `0x1F0720–0x1F0C7D`.]

Only these pointed-to record fields are consumed by the queries:

| Record offset | Width and interpretation | Query use |
| --- | --- | --- |
| `+0x00` | Signed 32-bit integer | First point coordinate, compared with distorted X |
| `+0x04` | Signed 32-bit integer | Second point coordinate, compared with distorted Y |
| `+0x08` | One byte | Selected by query `0x1EF040` exactly when equal to one |
| `+0x18` | Signed 32-bit integer | Selected by query `0x1F0720` exactly when less than zero (signed comparison with zero) |

The table slot's own indices do not replace the point coordinates stored in the record. The queries do not consume the creator's float fields at `+0x0C` and `+0x10`, nor its integer at `+0x14`. The two predicates are tested independently in their respective routines. No inferred category name or relationship between the predicates is required for the query arithmetic. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF11C`, `0x1EF28B–0x1EF29E`, `0x1EF4FE`, `0x1F07FC`, `0x1F096B–0x1F097E`, `0x1F0BDE`.]

## Ordered window and admission passes

For each coordinate, the routine forms a lower candidate index from coordinate minus `16384` and an upper candidate index from coordinate plus `16384`. Those additions are native 32-bit integer operations that wrap on overflow. Each adjusted value then divides by `16384` with truncation toward zero, using sign correction and arithmetic shift. This is not floor division for a negative adjusted value. The first (row) bounds come from X and the second (column) bounds from Y. The bounds are calculated from the original coordinates, before the later distortion. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF05E–0x1EF0B7`, `0x1F073E–0x1F0797`.]

All passes visit rows in increasing first-index order and columns in increasing second-index order, with inclusive bounds. A lower first index greater than its upper index returns zero immediately. An empty second-index interval performs no record work and cannot produce a nonzero result. The directly tested slot admission conditions, in this order, are: nonnegative row, nonnegative column, row-base index less than `0x20002F`, column less than `1024`, and a nonnull loaded pointer. The row-base index is first index times `1024` plus `0x10002F`, computed with a 32-bit left shift; with these calculated first-index widths the test bounds the row to the resident table. Any failed admission at a visited slot returns zero for the whole query. It does not omit that slot and blend the remaining entries. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF0C1–0x1EF13F`, `0x1EF241–0x1EF272`, `0x1EF3E0–0x1EF413`; corresponding query `0x1F0720` regions are `0x1F07A1–0x1F081F`, `0x1F0921–0x1F0952`, `0x1F0AC0–0x1F0AF3`.]

The first pass is a membership precheck. In each row it visits columns until it encounters that query's selected predicate or exhausts the row. A selected entry sets a persistent found flag and immediately advances to the next row; it does not examine or admission-test later columns in the same row during this first pass. Finding a selected entry does not terminate the outer row pass. At the end, absence of any selected entry returns zero without calling the distortion helper. If at least one was found, two further full passes follow, and they do require all slots in the rectangle. Thus the first pass alone is not proof that the complete rectangle was resident. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF11C–0x1EF13F`, `0x1EF55A–0x1EF562`, `0x1F07FC–0x1F081F`, `0x1F0C3A–0x1F0C42`.]

These routines take no locks around the three traversals. They reload pointers and predicate fields. The contract below assumes the relevant entries and records remain valid and unchanged while a query runs; it is not a snapshot or lifetime guarantee under eviction or publication races.

## Distorted integer query point

After a successful membership precheck, the first helper call has first argument signed Y converted exactly to binary64 and multiplied in binary64 by stored `0.0005`, and second argument binary64 exactly `3423` (bits `0x40AABE0000000000`). The returned scalar is binary32 despite its x87 return transport. It stores to binary32, multiplies by exactly three (bits `0x40400000`) in binary32, then multiplies that result by exactly `256` (bits `0x43800000`) in binary32. This is the additive distortion of X. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF145–0x1EF191`, `0x1F0825–0x1F0871`; `binary/Cube.exe`, double data RVAs `0x302B38`, `0x31DE40`, float data RVAs `0x2FCD70`, `0x302AB8`.]

The second helper call has first argument signed X converted exactly to binary64 and multiplied by the same stored binary64 `0.0005`, and second argument exactly `23421` (bits `0x40D6DF4000000000`). Its binary32 return is separately multiplied by three, then `256`, both in binary32, to distort Y. The exact double `0.0005` bit pattern is `0x3F40624DD2F1A9FC`; it is not a float constant promoted to double. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF196–0x1EF1D5`, `0x1F0876–0x1F08B5`; `binary/Cube.exe`, data RVAs `0x302B38`, `0x31DEB8`.]

Original signed X converts separately to binary32, has the first distortion added in binary32, and converts by native truncating binary32-to-signed-32-bit conversion. Original signed Y converts separately to binary32, adds the second distortion in binary32, and undergoes the same conversion. These two integers are the distorted point used for both remaining passes. The decompiler's unsigned temporary types do not change the signed conversions and subsequent sign extension in the image. There is no use of a distorted point to recalculate the candidate window. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF1CE–0x1EF226`, `0x1F08AE–0x1F0906`.]

Because every helper corner value lies in `[-1 + 2^-30, 1]` and both interpolation weights lie in `[0, 1]`, the helper's binary32 return lies in `[-1, 1]` for finite inputs, and each distortion lies in `[-768, 768]`. This bound is a consequence of the stated arithmetic under default rounding, not a separate clamp.

## Integer squared-distance minimum and ratio

The second full traversal obtains a signed 32-bit integer distance value for every candidate. It sign-extends each stored point coordinate and each corresponding distorted query coordinate to 64 bits, shifts each left sixteen bits, and subtracts query from stored point with 64-bit borrow. Each resulting signed 64-bit difference loads exactly through x87 and stores to binary32, rounding once under the x87 rounding control. The first difference multiplies by exactly `1/65536` in binary32 and is squared in binary32. The second difference separately multiplies by `1/65536` and is squared in binary32. The squared second difference has the squared first difference added in binary32. The sum converts to signed 32-bit integer with truncation toward zero. The conversion happens after the floating-point squared sum; an exact integer square calculation is not equivalent to the stated path. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF278–0x1EF340`, `0x1F0958–0x1F0A20`; `binary/Cube.exe`, float data RVA `0x2FCD94`, bit pattern `0x37800000`.]

The sixteen-bit shift and the `1/65536` scale cancel exactly: each scaled binary32 difference equals the exact integer difference of the two signed 32-bit coordinates rounded once to binary32. The 64-bit difference cannot overflow for any 32-bit inputs.

The first candidate becomes the minimum. Later candidates replace it only when their converted signed integer distance is strictly smaller under a signed comparison. An equal value keeps the earlier candidate. The minimum's record pointer is retained to distinguish absence of a candidate, but its membership does not alone select the query result. All candidates participate in the final weighting pass. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF344–0x1EF3A4`, `0x1F0A24–0x1F0A84`.]

The third full traversal repeats the same distance calculation for each slot. It subtracts the saved minimum integer distance with native 32-bit integer subtraction, converts that signed difference to binary32, and multiplies by binary32 `0.0000005`, whose exact bit pattern is `0x350637BD` and value is approximately `4.999999987376214e-7`. A comparison with binary32 one (bits `0x3F800000`) caps only values strictly greater than one to one. Exactly one minus the resulting value is then calculated in binary32 as that candidate's weight. There is no lower clamp on the scaled distance difference at this site. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF3AA–0x1EF3B2`, `0x1EF419–0x1EF502`, `0x1F0AF9–0x1F0BE2`; `binary/Cube.exe`, float data RVAs `0x31DCDC`, `0x345DC0`.]

Two accumulators begin at positive zero. For each candidate, its weight is first added in binary32 to the total accumulator. The weight is then added in binary32 to the selected accumulator only if that query's predicate currently matches. Both traversals retain row-major order. After all candidates, the total must compare strictly greater than zero. Otherwise, including an unordered comparison, the routine returns positive zero. On success it divides selected accumulation by total accumulation in binary32, stores the quotient as binary32, and loads that stored value to the x87 return stack. There is no later saturation. [Original: `decompiled/client/assembly.txt`, RVAs `0x1EF3AA–0x1EF3C9`, `0x1EF4F8–0x1EF59D`, `0x1F0A8A–0x1F0AA9`, `0x1F0BD8–0x1F0C7D`.]

For stable records and representable nonnegative converted distance sums, the minimum subtraction is nonnegative, every weight is between zero and one, and at least one minimum-distance entry has weight one. Under those conditions the total is positive and the returned ratio is between zero and one. This is a consequence with stated numeric conditions, not an unconditional range claim for arbitrary pointed-to bytes or conversion exceptions. A selected record can contribute zero when its scaled squared-distance difference from the minimum reaches one. The output is a weighted selected fraction, not the nearest record's boolean and not a weighted average of record `+0x0C`, `+0x10`, or `+0x18` values.

The representability condition holds whenever every slot of an admitted rectangle holds an unchanged record produced by creator `0x1D7A70` for that slot, and any special-reference record among them was created from nonnegative reference floats. Such a record's point coordinates lie in `[16384 × index + 1024, 16384 × index + 15360]` for its own table indices. Admission requires both coordinates to be positive with upper indices below `1024`; for coordinate values from `16384 × k` through `16384 × k + 16383` the window is cells `k - 1` through `k + 1` (cells zero and one for values below `16384`). With the distortion at most `768` in magnitude, each coordinate difference is then at most `32512` in magnitude. The binary32 squared sum is at most `2114060288`, below `2^31`, and the integer conversion is in range. A special-reference record created from a reference value in `(-16384, 0)` passes the index match for index zero yet quantizes to a coordinate as low as `-13312`; that case, and records written by other native paths, are not covered by this bound.

## Direct scalar helper at RVA 0x0C0EF0

The helper takes two binary64 stack arguments and returns a binary32 scalar through x87; the caller removes the sixteen argument bytes. It reads no world pointer, seed field, resident table, mutable noise table, or random state. It computes four corner values by integer arithmetic and two cosine interpolation weights. The queried distortion helper therefore has no seed parameter; seed dependence of the final query arises from resident records. [Original: `decompiled/client/functions/004c0ef0.c`; `decompiled/client/assembly.txt`, RVAs `0x0C0EF0–0x0C10F9`.]

The second input converts first to signed 32-bit integer by truncation toward zero; the first input converts next. The integers convert back to binary64. The adjacent corner coordinate is obtained by adding exactly one (bits `0x3FF0000000000000`) to the corresponding integer represented as binary64 and converting to signed 32-bit integer by truncation. Negative coordinates use truncation, not a floor-based preceding lattice cell. Four corners combine first-coordinate integer plus fifty-seven times second-coordinate integer. These sums and products retain their low 32 bits. [Original: `decompiled/client/assembly.txt`, RVAs `0x0C0EFD–0x0C0F77`; `binary/Cube.exe`, double data RVA `0x345DF8`.]

For each combined integer, the helper takes its bitwise exclusive-or with its own low-32-bit left shift by thirteen. It squares the resulting 32-bit value, keeps the low 32 bits, multiplies by `0xEC4D`, adds `0x0131071F`, multiplies by that same shifted/exclusive-or value, and subtracts `0x2DF722F3`. Each integer arithmetic step keeps its low 32 bits. A mask retains only the low thirty-one bits. That nonnegative integer converts exactly to binary64, multiplies by exactly `2^-30`, and is subtracted from exactly one in binary64. This is deterministic integer mixing; it makes no `rand` or `srand` call. [Original: `decompiled/client/assembly.txt`, RVAs `0x0C0FC1–0x0C10D8`; `binary/Cube.exe`, double data RVA `0x302B20`, bit pattern `0x3E10000000000000`.]

For the first interpolation weight, the first input has its truncated integer subtracted in binary64; that remainder multiplies by stored binary64 `3.1415927`, exact bits `0x400921FB5A7ED197`, and enters the imported cosine routine. One minus the returned binary64 cosine is multiplied by exactly one half (bits `0x3FE0000000000000`) in binary64. The helper then calculates the analogous weight for the second input with a second cosine call. The stored angle coefficient is not the mathematical value of pi rounded to binary64. The import is `MSVCR110.dll` `_libm_sse2_cos_precise` through IAT VA `0x006FC444`; in the identified DLL it is exported at RVA `0x036F80`, and its argument and result pass in an SSE register. The cosine routine's internal approximation is not recovered by this contract. [Original: `decompiled/client/assembly.txt`, RVAs `0x0C0F54–0x0C0FBC`, `0x0C0FC6–0x0C1007`; `binary/Cube.exe`, double data RVAs `0x302B48`, `0x345DF8`, `0x345DE8`, imported thunk RVA `0x28D7A4`, import table; `game-files/msvcr110.dll`, export table.]

At the lower second-coordinate corner, the helper multiplies the lower-first-coordinate corner value by one minus the first weight, multiplies the adjacent-first-coordinate corner by the first weight, and adds those binary64 products. That row result multiplies by one minus the second weight. The upper second-coordinate row is separately blended by the same first weight; that row result multiplies by the second weight. The lower-row product is then added to the upper-row product. Products, complements, and additions are separate binary64 operations. The final double stores, loads through x87, narrows by a store to binary32, and reloads the binary32 for return. No clamp, normalization of the corner values, fused multiply-add, or random-state update appears. [Original: `decompiled/client/assembly.txt`, RVAs `0x0C102D–0x0C10F9`.]

Each successful membership precheck therefore leads to exactly two such helper calls and four imported cosine calls. The precheck's zero return performs none. This count excludes unrelated caller work and says nothing about the internal cosine implementation.

## Resident-record creation and seed dependence

RVA `0x1D7A70` receives two signed 32-bit table indices, first index i and second index j, and removes eight argument bytes on return. It rejects either index outside zero through `1023` and returns null without other work. It returns an existing table pointer immediately, before reading the derived seed or touching random state. On a missing entry it reads signed integer S at object `+0x800188`, reseeds the imported random generator with i plus `4234` plus `1024` times j plus three times S, using native 32-bit integer operations, and allocates `0x1C` bytes through the imported allocation operator. The returned pointer is used without a null test. Record `+0x14` receives i plus `1024` times j plus S. Byte `+0x08` initially receives zero. The creator takes no lock. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7A70–0x1D7B05`; `decompiled/client/functions/005d7a70.c`.]

The source of S is directly established in initializer `0x1A52E0`: its first explicit 32-bit seed argument is stored at object `+0x800164` and passed to `srand`; the first following `rand` result is reduced by signed remainder modulo `100000` and stored at `+0x800188`. Later draws initialize other fields; they are not inputs to a record creator that subsequently reseeds itself. The seed initializer also clears resident records, as described below. [Original: `decompiled/client/assembly.txt`, RVAs `0x1A5319–0x1A5349`; `decompiled/client/functions/005a52e0.c`.]

The creator compares i with a value derived from the reference binary32 at object `+0x8000F0`, and only if that matches, compares j with a value derived from the reference binary32 at `+0x8000F4`. Each reference value converts to signed 32-bit integer with truncation, then divides by `256` with truncation toward zero, then divides that integer by `64` with truncation toward zero. Both index matches are required for the special-reference branch. The two-stage division is what the original instructions perform. The seed initializer later sets both reference floats to exact binary32 bits `0x4B002080`, value `8396928`; with those values the special-reference indices are i = `512` and j = `512`. How other paths may update the reference point is outside this contract. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7B09–0x1D7B52`, `0x1A55F8–0x1A560B`.]

The first random draw after the creator's reseed always occurs. Its remainder modulo two chooses a central-float path when zero; the special-reference branch also forces that path after consuming the draw. In the ordinary central-float path, two further draws populate `+0x0C` and `+0x10`, then one additional draw is tested for remainder zero modulo ten. If that test succeeds, byte `+0x08` is set to one, a further draw replaces `+0x10`, and another further draw replaces `+0x0C`, in that order. A special-reference record consumes the two initial float draws but skips the modulo-ten draw and these replacements. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7B56–0x1D7B74`, `0x1D7C29–0x1D7CD5`.]

When the first draw has nonzero remainder modulo two and the special-reference condition is false, the creator instead consumes a parity-choice draw and a value draw for float `+0x0C`, followed by a parity-choice draw and a value draw for float `+0x10`. Byte `+0x08` stays zero on this path. The float values do not affect the subsequent point position or raw signed field except through their consumption of these draws. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7B7A–0x1D7C24`.]

For completeness, the float values are as follows; every draw is converted exactly and nominal decimal constants denote the stored bit patterns given. The central first-float value converts its draw to binary32, multiplies by binary32 `0.4` (bits `0x3ECCCCCD`), divides by binary32 `32767` (bits `0x46FFFE00`), and adds binary32 `0.3` (bits `0x3E99999A`). The central second-float value instead converts its draw to binary64, multiplies by binary64 `0.4` (bits `0x3FD999999999999A`), divides by binary64 `32767` (bits `0x40DFFFC000000000`), adds binary64 `0.4000000059604645` (bits `0x3FD99999A0000000`), and narrows to binary32. The alternate float path multiplies its value draw in binary32 by `0.1` (bits `0x3DCCCCCD`), divides by binary32 `32767`, and adds binary32 `0.9` (bits `0x3F666666`) only for an odd parity-choice draw. A modulo-ten-selected replacement first writes `+0x10` from a draw times `0.2` (bits `0x3E4CCCCD`), divided by `32767`, plus `0.8` (bits `0x3F4CCCCD`), all in binary32; it then writes `+0x0C` from another draw times `0.5` (bits `0x3F000000`), divided by `32767`, in binary32. These are stored floats, despite integer-typed assignments in the decompile. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7B8A–0x1D7CD5`; `binary/Cube.exe`, float data RVAs `0x2FD318`, `0x2FCDC0`, `0x2FD338`, `0x2FCB7C`, `0x2FD31C`, `0x2FCDBC`, `0x2FCDC8`, `0x345DA0`, double data RVAs `0x31DD70`, `0x302A80`, `0x31DD78`.]

Every ordinary record then consumes a position draw for the second coordinate, followed by a position draw for the first. Each draw uses signed remainder modulo `15360`, adds `512`, and adds `16384` times its corresponding table index (j for `+0x04`, i for `+0x00`). The special-reference branch consumes neither position draw; it converts the reference floats at `+0x8000F4` and `+0x8000F0` by truncation directly to signed 32-bit point coordinates `+0x04` and `+0x00`. Both coordinates are then quantized separately: add `2047` only to a negative value, clear the low eleven bits, and add `1024`. Thus ordinary generated positive point coordinates occupy centers spaced by `2048` within their table region, from `1024` through `15360` above the region base. With the initializer's reference values, a special-reference record's point is `8397824` on both axes. No random draw occurs in quantization. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7CDA–0x1D7D67`.]

The raw value for record `+0x18` is determined after point quantization. A first call to helper `0x0C0EF0` uses binary64 i times stored `1.4` (bits `0x3FF6666666666666`) plus signed S converted to binary64; the second input is binary64 j times the same stored `1.4`, plus that seed double, plus exactly `843` (bits `0x408A580000000000`), with each addition/multiplication performed separately in that order. Its binary32 result has one added, multiplies by exactly `100`, and has exactly `70` subtracted, all in binary32. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7D2B–0x1D7DF4`; `binary/Cube.exe`, double data RVAs `0x31DD90`, `0x31DB70`, float data RVAs `0x345DC0`, `0x2FD0B4`, `0x2FCE4C`.]

A second call to the same helper uses binary64 i times exactly four (bits `0x4010000000000000`) plus the seed double, and j times four plus the seed double plus `843`. Its binary32 result multiplies by exactly thirty (bits `0x41F00000`) in binary32 and is added to the preceding binary32 value. The sum converts to signed 32-bit integer by truncation toward zero and stores to `+0x18`. These are two ordered helper calls; the second result is added after the first call's binary32 add/multiply/subtract chain. Each helper makes its two cosine calls but no random draw. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7DB4–0x1D7E3E`; `binary/Cube.exe`, data RVAs `0x302B50`, `0x2FCD78`.]

If this raw integer is positive, it is retained and the record is published. If it is nonpositive, byte `+0x08` is first cleared. On the special-reference branch, one additional random draw supplies signed remainder modulo fifty plus twenty as the replacement `+0x18`, after which the record publishes and returns. On the ordinary branch, the creator subtracts one hundred from `+0x18` with native 32-bit arithmetic and floors the signed result at negative one hundred. For a representable nonpositive raw value without subtraction overflow, the replacement is therefore exactly negative one hundred. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7E41–0x1D7E89`.]

The ordinary nonpositive branch then consumes one parity-choice draw and two further float-value draws. An even choice replaces `+0x0C` and then `+0x10` with their alternate high values, each draw times `0.1`, divided by `32767`, plus `0.9`, in binary32. An odd choice replaces those fields with their central first-float and central second-float calculations above, in that order. These three draws occur after the raw signed-field decision and do not move the point or restore byte `+0x08`. Publication stores the record pointer in the table only after this work, and the creator returns that pointer. [Original: `decompiled/client/assembly.txt`, RVAs `0x1D7E8C–0x1D7F48`.]

The draw totals for one successful missing-entry creation are consequently:

| Creation path before raw signed-field result | Draws if raw value is positive | Draws if raw value is nonpositive |
| --- | --- | --- |
| Special-reference record | 3 | 4 |
| Ordinary central path, modulo-ten test nonzero | 6 | 9 |
| Ordinary central path, modulo-ten test zero | 8 | 11 |
| Ordinary alternate path | 7 | 10 |

All totals include the first parity draw and exclude `srand`, allocation, and cosine calls. Existing entries and invalid creator indices consume zero draws and no reseed. For newly created records on the stated finite/representable paths, byte `+0x08 == 1` can survive only on the ordinary central path with modulo-ten test zero and a positive raw `+0x18`. The special-reference record never gains that byte value here. These creator facts do not prove that every record remains unmodified by all other native paths.

## Original runtime random operations

The client's import table identifies `MSVCR110.dll` `rand` at IAT VA `0x006FC468` and `srand` at IAT VA `0x006FC4B4`. In the identified original DLL, `srand` at RVA `0x0A494D` obtains a runtime context through helper `0x00E590` and writes the supplied 32 bits at context `+0x14`. `rand` at DLL RVA `0x0A492A` obtains the same kind of context, multiplies its 32-bit state by `214013` (`0x343FD`), adds `2531011` (`0x269EC3`), keeps the low 32 bits, stores the new state, shifts it right sixteen logically, and masks with `32767`. A missing-entry creator reseeds before any draw. With the same seed, reference fields, indices, runtime copy, and stable floating-point environment, its draw sequence begins from that per-entry seed independently of previous draws in that runtime context. Querying these two scalars leaves the random state untouched, whereas causing a record to be created elsewhere can affect later unrelated random consumers in the same runtime context.

## Cache setup, fill, and removal

The world constructor's original nested loops set 1024 by 1024 pointers beginning at `+0x4000BC` to zero, together with the corresponding pointers of the other table at `+0xBC`. A separately traced producer entry, RVA `0x1DA280`, rejects invalid table coordinates and skips work if its other table beginning at `+0xBC` already has the central entry. On the missing-central-entry path it invokes the record creator for a five-by-five neighborhood, first-index offset negative two through positive two outside, second-index offset negative two through positive two inside. Invalid edge neighbors are passed to the creator and return null there. Immediately after those twenty-five creator calls the producer reseeds the imported generator with its own seed expression, so its later draws do not continue from any creator's final state. This is an external fill path, not an implicit part of either scalar query. The rest of the large producer is outside scope. [Original: `decompiled/client/assembly.txt`, RVAs `0x193357–0x193397`, `0x1DA2DF–0x1DA36A`; `decompiled/client/functions/005da280.c`, prelude.]

## Caller conversion and remaining numeric limits

The directly checked caller `0x19D640` receives, as its first stack argument, a pointer to a structure whose first two signed 64-bit components lie at `+0x00` and `+0x08`. At its two queried call sites it first divides the `+0x08` component by signed `65536` with the statically linked signed 64-bit division routine at RVA `0x28D9E0`, retains the low 32-bit quotient, then divides the `+0x00` component the same way and retains its low 32-bit quotient. That routine divides magnitudes and restores the sign, so the quotient truncates toward zero; a negative component greater than `-65536` yields zero, not negative one. It passes the `+0x00` quotient as X and the `+0x08` quotient as Y. Each returned x87 value stores to binary32 immediately. The `0x1F0720` call is conditional on preceding scalar comparisons in that caller; `0x1EF040` is reached later on every path through the checked range. Broader caller admission and downstream uses are outside this artifact. [Original: `decompiled/client/assembly.txt`, RVAs `0x19D6AC–0x19D6C2`, `0x19D9E0–0x19DA56`, `0x19DD6A–0x19DDA2`; `binary/Cube.exe`, RVA `0x28D9E0`.]

All stated scalar SSE products, sums, subtractions, divisions, and conversions retain the widths and order described above. The original code does not use a compensated reduction, fused multiply-add, double-precision replacement of the query's float distances, or an unsigned minimum-distance comparison. Cache pointers and coordinates can be reloaded between passes; the original code supplies no query-local immutable copy.

Out-of-range truncating float-to-integer conversions, NaNs/infinities, nondefault exception handling, x87 precision/rounding control, SSE rounding/denormal modes, arbitrary invalid pointers, and integer-overflow effects beyond the explicitly identified native-width operations are not promoted into a meaningful-input guarantee. In particular, a negative or invalid converted squared-distance result can invalidate the nonnegative-weight range argument; the bound above excludes that only for creator-produced records. The cosine routine's approximation and runtime context initialization are bounded external numeric dependencies. No environmental label, hidden clamp, fallback cache creation, new random draw, or replacement missing-entry policy is inferred.
