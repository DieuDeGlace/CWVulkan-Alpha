# Alpha client source-admission plane production

This is an independent, original-only behavioral contract for the six planes beginning at client offset `+0x1000FA4`, their publication inside renderer RVA `0x0AC260`, and their use by admission helper RVA `0x07F760`. It covers the projection, matrix product, coefficient extraction, coordinate conversion and reference relationship established below. It does not establish the upstream following policy, the scheduling of update and rendering, or the behavior of unexamined callbacks.

The supported image is `binary/Cube.exe`, SHA256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred base `0x00400000`. All addresses below are RVAs. Evidence paths are relative to the original evidence directory `disassembled alpha cube world`. Original instructions and image constants take precedence over reduced decompiler expressions. No replacement implementation, reconstruction, runtime observation or other contract supplies evidence for this document.

## Storage and matrix convention

The published plane array contains six consecutive 16-byte records. Each record contains four binary32 coefficients in the order X coefficient, Y coefficient, Z coefficient, constant. The first coefficient addresses are `+0x1000FA4`, `+0x1000FB4`, `+0x1000FC4`, `+0x1000FD4`, `+0x1000FE4` and `+0x1000FF4`. The consumer reads these records in that ascending order. There is no separate length, enabled flag or validity test in RVA `0x07F760`. [Evidence: `binary/Cube.exe`, RVAs `0x07F877–0x07F907` and `0x0AEE2E–0x0AF33C`; `decompiled/client/assembly-functions/004ac260.asm`.]

For the matrix descriptions here, row and column numbers are zero based. A binary32 element in row r and column c occupies float index r plus four times c, or byte offset four times r plus sixteen times c. This is the actual accessor convention at RVA `0x0128D0`. Consequently a matrix multiplies a column vector, with its fourth column supplying affine translation. The vector accessor at RVA `0x028970` advances four bytes per coefficient. These definitions avoid relying on a graphics-library storage convention. [Evidence: `decompiled/client/functions/004128d0.c`, RVA `0x0128D0`; `decompiled/client/functions/00428970.c`, RVA `0x028970`; `binary/Cube.exe`, matrix helper RVAs `0x024990` and `0x024F30`.]

Two matrices supply the plane product. P is the 64-byte projection copied into client `+0x800A90`. V is the existing 64-byte matrix at client `+0x26C`. The renderer also copies V into separate local storage, but the plane-product call itself reads client `+0x26C`, rather than that local copy. [Evidence: `decompiled/client/assembly-functions/004ac260.asm`, RVAs `0x0AED91–0x0AEDBA` and `0x0AEE14–0x0AEE29`.]

## Projection construction

On the publication path, renderer RVA `0x0AC260` constructs a local projection with helper RVA `0x027910`. Its four binary32 inputs, in argument order, are an angular value, an aspect value, a near parameter and a far parameter. The angular value is bits `0x3F060A92` when bit `0x0400` of the 16-bit field at selected creature `+0x124` is set, and bits `0x3F5F66F4` when that bit is clear. The selected pointer is read from client `+0x8006D0`. Those angular values are approximately `0.5235987901687622` and `0.8726646900177002`, respectively. This identifies the native selector and values without assigning a player or camera role to that pointer. [Evidence: `decompiled/client/assembly-functions/004ac260.asm`, RVAs `0x0AE4B3–0x0AE5D3`; `binary/Cube.exe`, the immediate operands in that range.]

The aspect value is formed by converting each signed 32-bit field at client `+0x11C` and `+0x120` separately to binary32, dividing the first converted value by the second in binary32, then toggling the quotient's sign bit. It is therefore the negative of that quotient; the numerator and denominator are not first divided as integers. There is no zero-denominator, sign or range guard in this construction. The near parameter has bits `0x3DCCCCCD`, approximately `0.10000000149011612`; the far parameter has bits `0x44FA0000`, exactly `2000`. [Evidence: `binary/Cube.exe`, RVAs `0x0AE4EA–0x0AE5D3`; `decompiled/client/assembly-functions/004ac260.asm`; sign mask at image RVA `0x345F70`, whose low 32 bits are `0x80000000`.]

Helper RVA `0x027910` first multiplies the angular input by binary32 `0.5`, bits `0x3F000000`. That rounded binary32 value is widened to binary64 and supplied in the low binary64 lane of XMM0 to thunk RVA `0x28D9CE`, identified by the original import evidence as `MSVCR110.DLL!_libm_sse2_tan_precise`. The low binary64 result in XMM0 is immediately narrowed to binary32. The helper divides binary32 `1`, bits `0x3F800000`, by that narrowed value to obtain a scale h, then divides h by the supplied aspect value for the horizontal scale. No degree-to-radian conversion occurs in this helper. Imported tangent evaluation remains a callee boundary; its internal algorithm and exceptional-result policy are not established here. [Evidence: `binary/Cube.exe`, RVAs `0x027910–0x027948`; `decompiled/client/functions/00427910.c`; `decompiled/client/external_functions.csv`; image constants at RVAs `0x345DA0` and `0x345DC0`.]

The depth coefficients use the supplied near value n and far value f. The helper computes f minus n in binary32. It separately computes the binary32 product n times f, divides that product by the rounded difference, and toggles the quotient's sign bit. It also divides f by that same rounded difference. Thus the product, difference and divisions each have their own binary32 rounding boundary. The complete nonzero matrix entries are below; every unlisted entry is explicitly written as positive zero.

| Entry | Stored value and evaluation |
|---|---|
| P, row 0 column 0 | h divided by the supplied aspect, binary32 |
| P, row 1 column 1 | h |
| P, row 2 column 2 | f divided by the rounded binary32 difference f minus n |
| P, row 2 column 3 | Sign-toggled binary32 quotient of rounded n times f divided by that difference |
| P, row 3 column 2 | Exactly positive one, bits `0x3F800000` |

In particular, row 3 column 3 is explicitly zero. There is no symmetric-depth coefficient containing f plus n and no factor of two in the stored depth translation. [Evidence: `binary/Cube.exe`, RVAs `0x02794C–0x0279D3`; `decompiled/client/functions/00427910.c`.]

The renderer passes the local projection storage to an indirect interface call with selector `3` at RVAs `0x0AE62C–0x0AE63F`. Later it copies sixteen 32-bit words from that storage into client `+0x800A90`, before constructing the plane product. The caller-established values and copy are closed here. Effects of the intervening indirect calls, including possible reentrancy or mutation through supplied pointers, are not independently closed. [Evidence: `decompiled/client/assembly-functions/004ac260.asm`, RVAs `0x0AE62C–0x0AE63F` and `0x0AED91–0x0AEDA5`.]

## Product and direct coefficient publication

At RVA `0x0AEE29`, helper RVA `0x024F30` receives P as its implicit input matrix, a separate local output, and V as its other input. It first copies all sixteen P elements to the output. Its arithmetic then produces the matrix M equal, in ordinary matrix notation, to P multiplied by V. It does not produce V multiplied by P. For each output row and column, the four products pair V's column entries, in component order 0, 1, 2, 3, with P's corresponding row entries. Each product is a scalar binary32 multiplication. The first two products are added, the third is added to that rounded sum, and the fourth is added last. Each addition is binary32. The full four-term evaluation remains present even when P contains structural zeroes; there is no fused multiply-add. Outputs are stored in row order, with columns 0 through 3 within each row. [Evidence: `binary/Cube.exe`, RVAs `0x024F30–0x0252E8` and `0x0AEE14–0x0AEE29`; `decompiled/client/functions/00424f30.c`.]

The renderer then extracts four coefficients per plane from M. The following table gives the mathematical row combinations and the actual memory order of the six records. Each coefficient comes from the corresponding column of the stated rows, including column 3 for the constant.

| Consumer index | Client start | Combination | Zero-allowance algebraic clip bound |
|---|---|---|---|
| 0 | `+0x1000FA4` | Row 3 plus row 0 | Homogeneous coordinate plus clip X is nonnegative |
| 1 | `+0x1000FB4` | Row 3 minus row 0 | Homogeneous coordinate minus clip X is nonnegative |
| 2 | `+0x1000FC4` | Row 3 plus row 1 | Homogeneous coordinate plus clip Y is nonnegative |
| 3 | `+0x1000FD4` | Row 3 minus row 1 | Homogeneous coordinate minus clip Y is nonnegative |
| 4 | `+0x1000FE4` | Row 3 plus row 2 | Homogeneous coordinate plus clip depth is nonnegative |
| 5 | `+0x1000FF4` | Row 3 minus row 2 | Homogeneous coordinate minus clip depth is nonnegative |

Each coefficient is one scalar binary32 addition or subtraction followed by a binary32 store. There is no length calculation, square root, reciprocal, division by the XYZ normal length, or later normalization in this publication block. The four coefficients retain the product matrix's scale. The native subtraction operand order is always row 3 minus the other row. For the plus combinations, native addition operand order is: plane 0 uses row 3 first for X, Z and constant, and row 0 first for Y; plane 2 uses row 3 first for X and Z, and row 1 first for Y and constant; plane 4 uses row 3 first for X and constant, and row 2 first for Y and Z. These operand details do not authorize a NaN-payload policy for the external math calls. [Evidence: `binary/Cube.exe`, RVAs `0x0AEE2E–0x0AF33C`; `decompiled/client/assembly-functions/004ac260.asm`.]

Publication is direct and incremental. The native write order is plane 0, plane 1, plane 2, plane 3, plane 5, then plane 4; within each plane the order is X, Y, Z, constant. The final store, at RVA `0x0AF33C`, completes plane 4. All sixteen elements of M have been computed before the first plane coefficient is stored. There is no second plane array, pointer swap, publication counter or plane-local synchronization operation in this extraction sequence. This statement concerns that sequence, not the containing routine's critical section. [Evidence: `binary/Cube.exe`, RVAs `0x0AEE14–0x0AF33C`; `decompiled/client/assembly-functions/004ac260.asm`.]

## Depth and allowance meaning

The projection's depth convention is positive forward Z with homogeneous coordinate equal to transformed Z. In real arithmetic its depth quotient maps n to zero and f to one. This is a statement of the matrix relation, not a claim that the separately rounded native coefficients reproduce those endpoints exactly. The extracted planes nevertheless use homogeneous coordinate plus and minus clip depth. Their lower depth condition is clip depth at least negative homogeneous coordinate, rather than clip depth at least zero. The native lower plane is not row 2 alone. [Evidence: projection coefficients at `binary/Cube.exe`, RVAs `0x02796D–0x0279CA`; extraction at RVAs `0x0AF1AB–0x0AF33C`.]

For the nominal unrounded projection, a positive forward-axis coordinate at the lower extracted depth plane is the quotient of n times f by (two times f minus n), approximately `0.05000125` with these parameters; it is not the supplied near value of approximately `0.1`. The nominal upper extracted depth bound is f. Actual admission uses the rounded M, rounded row combinations and rounded point evaluation described here. In particular the subtraction used for the upper depth normal can amplify coefficient-rounding effects, so neither nominal depth value is an exact native-coordinate cutoff. This algebraic consequence does not establish the external graphics interface's clipping or depth-buffer behavior. [Evidence: the preceding original projection and extraction ranges; the nominal relation is derived directly from their stated coefficients.]

Because the normals are not normalized, the allowance accepted by RVA `0x07F760` is an additive value in each stored plane expression. It is not multiplied by that plane's normal length. Describing it as an exact world-distance sphere radius would therefore exceed the evidence. Changing the projection scale or matrix coefficients changes the corresponding geometric meaning of the same allowance. No perspective divide occurs in this admission helper. [Evidence: `binary/Cube.exe`, RVAs `0x07F8D0–0x07F907`; production at RVAs `0x0AEE2E–0x0AF33C`.]

## Fixed-point input and reference relationship

RVA `0x07F760` receives a client object, a pointer to three consecutive signed 64-bit coordinates, a binary32 plane allowance, and a separate binary32 distance limit. Its boolean result is returned in AL. The coordinates have sixteen fractional bits. Client `+0x140`, `+0x148` and `+0x150` are a separate signed 64-bit reference triplet R in that same fixed-point scale. Client `+0x1D8` and `+0x1E0` are signed 64-bit horizontal shifts Sx and Sy, including their high words at `+0x1DC` and `+0x1E4`. [Evidence: `binary/Cube.exe`, RVAs `0x07F760–0x07F8C6`; `decompiled/client/functions/0047f760.c`, with return and comparison behavior resolved from the instructions.]

Before reading any plane, the helper subtracts the supplied point from R in each signed 64-bit component, using low-word subtraction and high-word borrow. It obtains a fixed-point squared-distance quantity through RVA `0x03AC20`: each axis is multiplied by itself retaining the native low 64-bit product, signed-divided by `65536` with truncation toward zero, then accumulated in axis order X, Y, Z with native 64-bit addition. It separately squares the supplied distance limit in binary32, multiplies that rounded result by binary32 `65536`, bits `0x47800000`, and passes the stored binary32 result through the x87 integer-conversion helper at RVA `0x28D946`. For finite representable results that conversion truncates toward zero to signed 64-bit. The fixed squared-distance value must be less than or equal to this threshold to reach the planes. The comparison uses signed high words and unsigned low words. Native integer overflow is not clamped, and the plane allowance does not enlarge this distance gate. [Evidence: `binary/Cube.exe`, RVAs `0x07F770–0x07F820`; `decompiled/client/functions/0043ac20.c`, RVA `0x03AC20`; conversion helper RVA `0x28D946`; image constant at RVA `0x2FCE7C`.]

For a point that passes the distance gate, the plane coordinates are formed by adding Sx to raw point X and Sy to raw point Y in 64-bit integer arithmetic. Raw point Z is unchanged. Each resulting signed 64-bit value is loaded by x87 as an integer, stored as binary32, and then multiplied in scalar binary32 by exactly `2^-16`, bits `0x37800000`. Thus the horizontal integer addition precedes float narrowing and scale conversion. The helper does not first narrow two large coordinates and then add their float forms, and it does not subtract R directly from the point for the plane test. [Evidence: `binary/Cube.exe`, RVAs `0x07F826–0x07F8C6`; constant at image RVA `0x2FCD94`.]

The relationship to V is visible in the native update routine RVA `0x088EE0`. That routine obtains component addresses of the signed 64-bit triplet at client `+0x158`, here called A. It stores the exact native 64-bit two's-complement negations of A's X and Y components into Sx and Sy, respectively. There is no shift for Z and no rounding to a chunk boundary in those stores. The minimum signed 64-bit value follows native wraparound negation rather than an added saturation rule. A and R are distinct storage and are not interchangeable inputs. How A follows another object, the callbacks that can supply it, and the complete preceding construction of R remain outside this audit. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09C367–0x09C37F`, `0x09C44A–0x09C4C7`, `0x09C6C0–0x09C6F1` and `0x09CCF7–0x09CD2C`; helpers `decompiled/client/functions/00412260.c`, RVA `0x012260`, and `decompiled/client/functions/00411df0.c`, RVA `0x011DF0`.]

The same update path resets V to identity. Before its angular work, it adds a two-dimensional translation through RVA `0x034B80`. The amplitude is client binary32 `+0x1E8` multiplied by binary32 `0.5`. A signed 32-bit counter is read through RVA `0x088B80` from the object at client `+0x2E4`, field `+0x8000BC`, therefore client `+0x8003A0`. The first counter read is separately converted to binary32, multiplied by bits `0x3D23D70A` (approximately `0.04`), widened for imported cosine through RVA `0x00E420`, narrowed to binary32, and multiplied by the rounded amplitude; this supplies the Y translation. A second counter read follows the same boundaries using bits `0x3CF5C28F` (approximately `0.03`) and supplies the X translation. The native read/call order is Y term first, then X term. The counter is read twice, so equality of the two observations is not substituted for what the caller actually does. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09CD31–0x09CDDE`; `decompiled/client/functions/00488b80.c`; `decompiled/client/functions/00434b80.c`; `binary/Cube.exe`, RVAs `0x00E420–0x00E43D`; constants at image RVAs `0x2FCDB0`, `0x2FCDAC` and `0x345DA0`.]

V then receives the sign-toggled binary32 components 0, 1 and 2 of client `+0x1A4`, in that order, through rotation helpers RVAs `0x0243D0`, `0x0244F0` and `0x024610`. These helpers modify the corresponding first-three-column pairs and preserve the fourth column's existing translation. Each helper multiplies its angular input by binary32 bits `0x3C8EFA35`, approximately pi divided by 180, before widening for imported cosine and sine; cosine is called first, sine second, and each result is narrowed to binary32 before matrix arithmetic. This closes the inputs and call order needed to distinguish the stored V from a translation by R alone. It does not close the upstream evolution or semantic names of those angular and amplitude fields. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09C2F2–0x09C362` and `0x09CDE3–0x09CE3E`; `decompiled/client/functions/004243d0.c`, `004244f0.c` and `00424610.c`; image constant at RVA `0x2FCDA4`.]

The final reference translation is constructed in fixed-point arithmetic. Helper RVA `0x068E70` copies R and multiplies each component by fixed-point negative one, raw signed 64-bit `-65536`, through RVA `0x02C900`. Each such multiplication retains the native low 64 bits and is followed by signed division by `65536`. Call the resulting triplet N. The update subtracts the fixed-point triplet Sx, Sy, zero from N, and only then converts each component to binary32 and multiplies by `2^-16`, through RVA `0x02C4A0`. Thus it supplies the converted triplet N minus the horizontal shifts to the final translation helper. N agrees with the mathematical negation of R when the intermediate fixed-point products do not overflow; the full-range contract is the actual multiply/divide sequence, not an unrestricted negation assumption. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09CE43–0x09CEB1`; `decompiled/client/functions/00468e70.c`, `0042c900.c`, `0042c7a0.c` and `0042c4a0.c`.]

The final translation helper, RVA `0x024990`, adds the first-three-column weighted translation to V's fourth column. For row 0 it adds the rounded Y and X products with Y as the first operand, then adds the rounded Z product, then the old fourth-column value. For rows 1, 2 and 3 it adds the X and Y products with X as the first operand, then adds the Z product, then the old fourth-column value. Every product and addition is scalar binary32. In ordinary real arithmetic, when N is negative R, this matrix translation compensates the horizontal shift applied to points by RVA `0x07F760`; the orientation-dependent part acts on point minus R, with the earlier two-dimensional translation still present. Native separate integer operations, conversions and float additions remain the numerical contract. Their rounding does not permit replacing this path with an algebraically cancelled float subtraction. [Evidence: `binary/Cube.exe`, RVAs `0x024990–0x024A58`; call at RVA `0x09CEB1`; point conversion at RVAs `0x07F826–0x07F8C6`.]

## Plane evaluation, order and state limits

For each record, RVA `0x07F760` independently multiplies its X and Y coefficients by the already converted X and Y point coordinates, adds those rounded products in X-then-Y order, multiplies the Z coefficient by converted Z, adds that product, adds the constant, then adds the caller's plane allowance last. Every operation is scalar binary32, including the final allowance addition. The allowance is used unchanged for all six planes, without absolute value, nonnegative clamp or normal-length adjustment. There is no matrix multiplication or homogeneous-coordinate division in the consumer itself; it evaluates the published coefficients directly. [Evidence: `binary/Cube.exe`, RVAs `0x07F8D0–0x07F8F7`.]

The native comparison rejects only an ordered result strictly below zero. Either sign of zero passes. An unordered NaN result does not take the rejection branch, provided floating-point execution completes under the ambient exception settings. A failed plane returns false immediately; after all six pass the helper returns true. The plane order is 0 through 5 even though the producer writes plane 5 before plane 4. The helper does not mutate the client, planes or point. The closed caller blocks for admission, projection, matrix product and coefficient extraction contain no explicit game-owned random draw. This does not establish the absence of random dependence in untraced producers of their input state or effects inside imported callees. [Evidence: `binary/Cube.exe`, RVAs `0x07F8FB–0x07F930`, `0x027910–0x0279D3`, `0x024F30–0x0252E8` and `0x0AEE14–0x0AF33C`.]

Renderer program order does not make every admission query use newly produced planes. A conditional source traversal calls RVA `0x07F760` at RVA `0x0AC78A`, supplying a source's fixed-point triplet at `+0x10` and plane allowance exactly `16`. That call precedes the projection construction and plane publication described above. Later admission calls, including RVA `0x0B094D`, follow publication on the normal path. Thus the earlier call reads whatever plane contents were already stored, while later calls can read this invocation's publication if execution reaches that path and no intervening mutation changes the state. Initial array contents, the age of an earlier publication, and a guaranteed update/render relationship are not established. Calling the early contents the previous frame's planes would add an unproved scheduling assumption. [Evidence: `decompiled/client/assembly-functions/004ac260.asm`, RVAs `0x0AC761–0x0AC791`, `0x0AE4B3–0x0AE5D3`, `0x0AEE14–0x0AF33C` and `0x0B090F–0x0B0954`.]

The renderer acquires a native critical section through RVA `0x201CB0` at RVA `0x0AC37E`, using the object at client `+0x2E4`. The wrapper enters the section at that object's `+0x8000C0`, therefore client `+0x8003A4`. The normal path retains that containing section through publication and releases it through RVA `0x201E90` at RVA `0x0BBB31`; earlier release-and-exit paths are present at RVAs `0x0AD67A` and `0x0AE274` and do not reach this publication. This establishes the renderer's protection scope, not a universal lock requirement enforced by RVA `0x07F760`, which does not acquire a lock itself. It does not prove that all other writers or callers use that section, that callbacks cannot reenter, or that R, shifts, V and planes always belong to one update generation. [Evidence: `decompiled/client/assembly-functions/004ac260.asm`, the cited call sites; `decompiled/client/functions/00601cb0.c` and `00601e90.c`.]

The closed arithmetic assumes the specified instructions complete. No local reset of x87 or MXCSR control state is established for these blocks. Integer-to-float rounding, float arithmetic, narrowing, denormal handling and enabled exceptions therefore retain their ambient-control dependence. The imported tangent, cosine and sine implementations, NaN payloads, out-of-range or nonfinite float-to-integer results in the distance conversion, invalid pointers, initial plane initialization, upstream following/clipping/callback semantics, and cross-thread or cross-frame scheduling remain explicit limits. The stored P and V define the closed matrix product and extraction. The published coefficients, supplied point, R, shifts, allowance and distance limit define the closed admission arithmetic.
