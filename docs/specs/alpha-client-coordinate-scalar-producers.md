# Alpha client coordinate scalar producers

Status: FINAL / STABLE / HELD. This original-only contract covers client scalar producers at RVAs `0x1C4DD0` and `0x1C4800`, their shared scalar arithmetic, and the numeric path directly reached by the latter's conditional correction. The results are called the first and second scalar below. No environmental meaning, physical unit, or complementary relationship is assigned to them.

The supported original image is `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, under the evidence root `disassembled alpha cube world`. All addresses below are RVAs; the image base is `0x00400000`. Evidence paths are relative to that root. Original function exports supplied leads, and the original executable independently established parameter types, return values, arithmetic order, and constants. No reconstruction or other contract was used.

## Inputs, outputs, and data dependencies

Both producers receive a world-like owner pointer and two **signed 32-bit integer coordinates**, called X and Y here. Neither coordinate is a binary32 input. In particular, the floating-point parameter label in the decompiled export for RVA `0x1C4800` does not describe the native call: the executable loads each argument as a four-byte integer and uses signed integer conversions. Both return a binary32 scalar loaded onto the x87 stack. The decompiled exports' void signatures and missing final arithmetic do not close the return behavior. [Evidence: `decompiled/client/functions/005c4dd0.c`, RVA `0x1C4DD0`; `005c4800.c`, RVA `0x1C4800`; `binary/Cube.exe`, RVA `0x1C4DEC–0x1C4F0B`, `0x1C481B–0x1C4951`, `0x1C5262–0x1C529C`, and `0x1C4CA7–0x1C4DC7`.]

The shared sampling source is a two-dimensional table of four-byte pointers beginning at owner `+0x4000BC`. There are 1024 pointer positions per row. Each nonnull pointed record supplies signed four-byte coordinates at record `+0x00` and `+0x04`. The first producer, RVA `0x1C4DD0`, samples a **binary32 value at record `+0x10`**. The second, RVA `0x1C4800`, samples a **binary32 value at record `+0x0C`**. Those scalar loads reinterpret the stored four bytes as binary32; they do not numerically convert a 32-bit integer. Record `+0x08` is not a scalar input to these two routines. [Evidence: `binary/Cube.exe`, table accesses at `0x1C4F7A–0x1C4F8A` and `0x1C49BD–0x1C49C7`; coordinate loads and sign extension at `0x1C4F90–0x1C5004`; scalar loads and products at `0x1C5225–0x1C5235` and `0x1C4C68–0x1C4C78`.]

Neither producer populates that table, generates its record coordinates or scalar attributes, reads a world-seed field directly, or writes a cached result. Their output nevertheless depends on the currently populated pointers and pointed values. Record population, seed derivation, mutation, initialization, lifetime, and synchronization are unclosed dependencies. A stable result requires stable supplied data as well as the numeric execution conditions below.

## Shared coordinate warp and candidate order

The original integer coordinates determine an inclusive rectangular candidate window. For each axis, its lower endpoint is the signed quotient of coordinate minus 16384 by 16384, and its upper endpoint is the signed quotient of coordinate plus 16384 by 16384. The additions/subtractions occur in 32 bits first. The native sign correction and arithmetic shift implement division truncated toward zero, including negative values; this is not floor division. Coordinate overflow is not saturated before the division. The window is determined before coordinate warping and is not expanded afterward. [Evidence: `binary/Cube.exe`, RVA `0x1C4DFA–0x1C4E65` and `0x1C4826–0x1C4891`.]

The warp makes two calls to the deterministic two-input helper at RVA `0x0C0EF0`, in this order:

1. The first argument is Y converted exactly from signed 32-bit integer to binary64, then multiplied in binary64 by the stored approximation to `0.0005`; the second argument is binary64 `3423`. Its returned binary32 value is multiplied by binary32 `3`, then by binary32 `256`. This is the displacement added to X.
2. The first argument is X converted to binary64 and multiplied by the same stored coefficient; the second argument is binary64 `23421`. Its returned binary32 value is multiplied by `3`, then by `256`. This is the displacement added to Y.

Each original coordinate is separately converted from signed integer to binary32, its displacement is added in binary32, and the sum is converted to signed 32-bit integer by truncation toward zero. Thus the warp cross-couples the axes and includes binary32 coordinate rounding before the integer result. It is not an integer-coordinate addition of an independently truncated displacement. Both helper calls occur before candidate validation, even if the later query returns its fallback. [Evidence: `binary/Cube.exe`, RVA `0x1C4E34–0x1C4F0B` and `0x1C483E–0x1C4951`; `decompiled/client/functions/004c0ef0.c`, RVA `0x0C0EF0`.]

The candidate scan visits increasing first-axis table index, with increasing second-axis index inside each row. Endpoints are inclusive. At any candidate, a negative index, a first-axis row beyond 1023, a second-axis index beyond 1023, or a null table entry immediately returns the fallback. The routines neither skip that entry nor clamp the window to valid table bounds. An empty window or a scan with no selected record also takes the fallback. [Evidence: `binary/Cube.exe`, RVA `0x1C4F12–0x1C50B6` and `0x1C4957–0x1C4AF6`.]

## Distance, weights, and the two scalar relations

For each candidate, the producer sign-extends both the record coordinate and warped integer coordinate to 64 bits, scales each by 65536 using a 16-bit left shift, and subtracts them in 64 bits. For each axis separately, it converts that signed 64-bit difference through x87 to binary32, then multiplies by binary32 `1/65536`. Each scaled component is squared in binary32. The second-axis square is added to the first-axis square in binary32, and this sum is truncated to signed 32-bit integer. The resulting integer is the distance value used for selection and weights. It represents a truncated squared separation in the ordinary finite, representable case; no square root is taken. Moving the division by 65536 ahead of the first binary32 narrowing is not established as equivalent. [Evidence: `binary/Cube.exe`, RVA `0x1C4F90–0x1C5058` and `0x1C49CD–0x1C4A98`; repeated second-pass arithmetic at `0x1C512F–0x1C51F1` and `0x1C4B89–0x1C4C2E`.]

The first pass retains the smallest distance by **signed** 32-bit comparison. The first candidate initializes the selection regardless of its distance. A later candidate replaces it only for a strictly smaller distance, so equal distance values retain the earlier candidate. Only this minimum integer distance is needed for the second pass; neither routine simply returns the nearest record's scalar. [Evidence: `binary/Cube.exe`, RVA `0x1C5058–0x1C5071` and `0x1C4A98–0x1C4AB7`.]

The second pass repeats the same ordered candidate scan and recomputes each distance from the current record data. It subtracts the first-pass minimum using 32-bit subtraction, converts that signed difference to binary32, and multiplies by the stored binary32 approximation to `0.0000005`. It caps this product at 1 only when the comparison is ordered and the product exceeds 1. The candidate's weight is 1 minus the retained product. There is no separate lower clamp on that product and no upper clamp on the resulting weight. With ordinary consistent distance values, the nearest distance receives weight 1 and sufficiently larger distances receive weight zero. The exact native arithmetic, including overflow and conversion limits, takes precedence over that geometric description. [Evidence: `binary/Cube.exe`, RVA `0x1C51F1–0x1C5221` and `0x1C4C2E–0x1C4C64`.]

Both sums start at positive zero. In scan order, the denominator receives each binary32 weight by one binary32 addition. The numerator receives that record's binary32 scalar multiplied by the weight, followed by one binary32 addition. The scalar product is evaluated even when the weight is zero. When the denominator is ordered greater than zero, a binary32 division of numerator by denominator produces the weighted scalar. Otherwise, including an unordered denominator comparison if execution reaches it, the fallback is returned. [Evidence: `binary/Cube.exe`, RVA `0x1C50BC–0x1C50D8`, `0x1C5217–0x1C5270`, `0x1C4AFC–0x1C4B1B`, and `0x1C4C5A–0x1C4CC0`.]

For the **first scalar**, this weighted value of record `+0x10` is the final normal result. For the **second scalar**, the weighted value of record `+0x0C` is the base result and can receive the correction below. Both producers use binary32 **0.5**, bits `0x3F000000`, as their fallback. There is no unconditional final clamp of either weighted average to the interval from zero to one. The two routines are not established as complements, and their distinct record attributes cannot be substituted for one another. [Evidence: `binary/Cube.exe`, first return `0x1C5262–0x1C529C`; second return `0x1C4CA7–0x1C4DC7`.]

## Conditional correction to the second scalar

After producing a positive-denominator weighted average, RVA `0x1C4800` calls the lookup helper at RVA `0x087DA0`. The supplied coordinates are the original, unwarped X and Y divided by 2048 with truncation toward zero. This lookup is called before testing the weighted average against the correction threshold. It rejects either lookup coordinate outside the signed interval from zero through 8191. For valid coordinates it follows the owner table at `+0xBC`, with 1024 pointers per row, using division by eight for the coarse indices. A nonnull coarse record supplies the address of a `0x68`-byte subrecord, selected by the two remainders modulo eight, beginning at coarse record `+0x14018`. There is no allocation or creation on this path. [Evidence: `binary/Cube.exe`, RVA `0x1C4CC0–0x1C4CEB`; `decompiled/client/functions/00487da0.c`, RVA `0x087DA0`; `00434a90.c`, RVA `0x034A90`.]

Correction occurs only when the base average is **ordered below** binary32 `0.2` with bits `0x3E4CCCCD`, the lookup returned a nonnull subrecord, and that subrecord's four-byte tag at `+0x18` equals 3. The producer passes the original X and Y, sign-extended and scaled by 65536 into separate signed 64-bit values, to the numeric helper at RVA `0x1F8E10` with that subrecord as receiver. The first scalar does not make this lookup or helper call. [Evidence: `binary/Cube.exe`, RVA `0x1C4CF0–0x1C4D50`.]

The helper result is narrowed to binary32. The producer subtracts it from 1 in binary32. If the difference is ordered at or below zero, its squared contribution is positive zero. Otherwise it squares the difference in binary32; an unordered difference also takes this squaring path if floating-point execution completes. It multiplies the squared contribution by binary32 `0.3`, bits `0x3E99999A`, and adds the base average in binary32. A corrected result ordered above 1 is replaced with 1. An unordered corrected result is retained, and there is no lower clamp. If any correction-admission condition fails, the base average is returned unchanged. [Evidence: `binary/Cube.exe`, RVA `0x1C4D55–0x1C4D9B`.]

For the tag-3 path reached here, RVA `0x1F8E10` consumes signed 64-bit reference coordinates at subrecord `+0x00` and `+0x08`, a binary32 divisor parameter at `+0x10`, and the tag at `+0x18`. If that parameter is ordered below binary32 `0.001`, bits `0x3A83126F`, it returns zero immediately. Equality and an unordered comparison continue. Since the caller requires tag 3, the helper's distinct branches for tags 11, 12, 13 and 14 are not reached by this producer and are not specified here. [Evidence: `binary/Cube.exe`, RVA `0x1F8E10–0x1F8E66`; `decompiled/client/functions/005f8e10.c`, RVA `0x1F8E10`.]

The reachable tag-3 arithmetic has these established numeric dependencies and order:

1. It converts the supplied 64-bit Y coordinate to binary64, multiplies by binary64 `-0.0025`, and converts that result to signed 64-bit integer through runtime helper RVA `0x28D946`. It does the same for X second. These conversions truncate toward zero for finite representable inputs. Their results are used as coordinate offsets in the two subsequent lattice-helper calls.
2. In the first lattice call, the first binary64 argument is the signed 64-bit difference between `0x00000080AD580000` and the converted X offset, scaled by `1/65536`. The second is the difference between `0x00000001617D0000` and the converted Y offset, scaled by `1/65536`.
3. The returned binary32 value is multiplied by binary32 `256`, then by binary32 `65536`. Runtime helper `0x28D946` converts that binary32 displacement to signed 64-bit integer. The helper adds the original supplied X coordinate and subtracts the subrecord reference X coordinate using 64-bit arithmetic. This signed difference is narrowed to binary32 and multiplied by binary32 `1/65536`.
4. The second lattice call uses first-argument difference `0x000000000D5F0000` minus the converted X offset and second-argument difference `0x0000000000700000` minus the converted Y offset, each converted to binary64 and scaled by `1/65536`. Its result is multiplied by `256`, then `65536`, and converted to signed 64-bit integer. That displacement is added to supplied Y and reference Y is subtracted. The signed difference is narrowed to binary32 and multiplied by `1/65536`.
5. The helper squares the scaled X and Y differences in binary32, adds the Y square to the X square in binary32, squares its binary32 divisor parameter separately, and divides the distance sum by that square in binary32. It returns that binary32 result on the x87 stack.

[Evidence: `binary/Cube.exe`, reachable generic branch RVA `0x1F9092–0x1F92B5`; `decompiled/client/functions/005f8e10.c`; conversion helper `0068d946.c`, RVA `0x28D946`, and `binary/Cube.exe`, RVA `0x28D946–0x28D9BA`.]

The helper does not clamp this normalized squared value. Its subtraction/addition operations use native 64-bit results; exceptional or overflowing conversions are not given a replacement geometric meaning. No environmental name is assigned to the tag-3 subrecord, its divisor parameter, or the resulting correction.

## Shared deterministic lattice helper

RVA `0x0C0EF0` takes two binary64 scalar arguments, not a world pointer or a mutable random-state object. Each argument is truncated to signed 32-bit integer. Those truncated coordinates and their next integer neighbors select four corner values. Negative fractions are measured from the truncated coordinate, not from a mathematical floor. Corner integer arithmetic wraps in 32 bits. [Evidence: `binary/Cube.exe`, RVA `0x0C0EF0–0x0C0F77`; `decompiled/client/functions/004c0ef0.c`.]

For each corner, the native integer mixing combines the first integer coordinate with 57 times the second. It xors that result with its own 13-bit left shift. It squares the mixed value, multiplies by `0x0000EC4D`, adds `0x0131071F`, multiplies by the mixed value, and adds `0xD208DD0D`, retaining native low-32-bit results. It masks the final value with `0x7FFFFFFF`, converts this nonnegative integer to binary64, multiplies by the exact binary64 value `1/1073741824`, and subtracts the product from 1. This is deterministic coordinate hashing, not a PRNG draw or a seed update. [Evidence: `binary/Cube.exe`, RVA `0x0C0F16–0x0C0F77` and `0x0C0FC1–0x0C10D4`.]

Each axis fraction is multiplied in binary64 by the stored decimal approximation `3.1415927`. The helper calls `MSVCR110.DLL!_libm_sse2_cos_precise`, through thunk RVA `0x28D7A4`, on the first-axis argument, then on the second-axis argument. For each returned binary64 cosine, it subtracts the value from 1 and multiplies by binary64 0.5 to obtain an interpolation coefficient. The first pair of corner values is combined with coefficients one minus the first-axis coefficient and the first-axis coefficient; the second pair is combined the same way. The first combined value is multiplied by one minus the second-axis coefficient, and the second combined value by the second-axis coefficient; those products are added. Every described interpolation operation is binary64 and follows that product/addition order. The result is explicitly narrowed to binary32 before x87 return. No reassociation, fused operation, floor-based neighbor selection, or deferred narrowing is established. [Evidence: `binary/Cube.exe`, RVA `0x0C0F54–0x0C10F9`; `decompiled/client/external_functions.csv`, cosine import.]

The original game caller establishes the binary64 argument/result lane at this cosine boundary, but the imported cosine implementation is not part of this original-image audit. Its approximation, exceptional handling, effects of floating-point controls, and library-version behavior remain unresolved. The coefficient is the listed approximation to pi, not an unspecified full-precision mathematical constant.

The binary32 narrowing of signed 64-bit values uses x87 stores. Signed 32-bit-to-floating conversions and arithmetic use scalar SSE in the producers; float-to-signed-32-bit conversions explicitly truncate. The runtime signed-64-bit conversion helper uses x87 integer conversion plus a residual correction and does not install a private x87 control word. Ambient x87 precision/rounding and exception controls, SSE rounding, denormal controls, and imported cosine behavior remain relevant execution conditions. No producer establishes a private numeric environment. [Evidence: `binary/Cube.exe`, the conversion ranges cited above and RVA `0x28D946–0x28D9BA`.]

There is no distance-range saturation. A masked invalid scalar-SSE conversion, including a squared-distance sum outside the signed 32-bit result range, supplies the native integer-indefinite bit pattern `0x80000000`; subsequent signed comparisons and 32-bit subtraction still act on those bits. Unmasked exceptions can prevent completion. NaN sample scalars are not filtered, and multiplying one by a zero weight still evaluates a floating-point product. This contract does not extend the ordinary weighted-average interpretation to arbitrary malformed pointed data or exceptional numeric inputs.

## Adjacent cached-value boundary and remaining limits

Adjacent wrappers at RVAs `0x1C8310` and `0x1C8350` first call the lookup at RVA `0x0347A0` with X, Y, and an optional supplied column-like object. If it returns a nonnull cell address, they return the binary32 value at cell `+0x04` for the second scalar or cell `+0x08` for the first scalar. Only a null lookup calls the corresponding producer. They do not recompute or validate a nonnull cell's stored scalar. These cell fields belong to a different record from the producer's sample records. [Evidence: `decompiled/client/functions/005c8310.c` and `005c8350.c`; `binary/Cube.exe`, RVA `0x1C8310–0x1C837F`; `004347a0.c`, RVA `0x0347A0`.]

That cell lookup accepts only nonnegative X and Y below `0x01000000`. Without a supplied column object it looks one up using the coordinates divided by 256; with one supplied it checks the object's `+0x60` and `+0x64` coordinate bounds for a 256-by-256 extent. A valid object's pointer at `+0xA8` provides 32-byte cells, selected using the coordinate remainders modulo 256, with the Y remainder selecting the row. The lookup and wrappers do not establish when those scalar cells were populated, whether they still match the sample records, or what invalidates them after a seed/data change. [Evidence: `decompiled/client/functions/004347a0.c`, RVA `0x0347A0`; `00434d10.c`, RVA `0x034D10`; `00434a90.c`, RVA `0x034A90`.]

There are **zero PRNG draws or seed mutations** in the two producers, the shared lattice helper, the reachable tag-3 numeric path, and the inspected lookup/cache-read helpers. Each producer makes two lattice calls, each of which makes two imported cosine calls. An admitted tag-3 correction whose divisor passes its initial threshold adds two lattice calls and four cosine calls, as well as the four signed-64-bit conversion-helper calls described above. No candidate count changes those draw counts because candidate sampling calls no random generator. This statement does not cover sample/cell construction, unrelated owner updates, other tags of RVA `0x1F8E10`, or external library internals.
