# Category 13 and the inventory counter

This contract concerns category **13 decimal, `0x0D`**, in the original Alpha client. It does not concern category `0x13`. The supported original image is `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, with image base `0x00400000`. Addresses below are RVAs. Evidence paths are relative to the original Alpha evidence root. Original native instructions were checked directly where the exported decompilation omits blocks or loses register inputs. No earlier project contract, replacement implementation or runtime observation supplies evidence here.

The supported semantic meaning of inventory `+0x12C` is a **Platinum Coins balance**. Category 13 credits it, the inventory interface displays it beside that exact label, and the adaptation service debits it. It is separate from the category-12 balance at inventory `+0x128` and from creature `+0x194`, which participates in experience and level-up work.

## Field identity and native naming evidence

For a creature whose inventory starts at `+0x11DC`, inventory `+0x128` is creature `+0x1304`, and inventory `+0x12C` is creature `+0x1308`. All four references are 32-bit fields. Inventory-relative `+0x12C` must not be confused with the unrelated creature-relative `+0x12C`. Inventory initialization RVA `0x03C020` explicitly writes zero to both inventory balances. The creature constructor and reset/copy routes use this inventory type; the balance identity does not follow merely from an equal offset in a different native object. [Evidence: `decompiled/client/functions/0043c020.c`, `0043b690.c`, `004772b0.c`; `binary/Cube.exe`, RVAs `0x03C082–0x03C099`, `0x07733B–0x07734D`.]

The original registration sequence associates the pair `(12, 0)` with the UTF-16 text `Coin` and `(13, 0)` with `PlatinumCoin`. Those original strings are at RVAs `0x31B4C0/0x31B4CC`; the corresponding registration instructions are at RVAs `0x1905C3–0x190608`. This establishes native vocabulary for the registered pair; the inventory credit branch itself accepts every item whose category byte is 13, without requiring subtype zero. [Evidence: `binary/Cube.exe`, cited instructions and string bytes; `decompiled/client/functions/0058eb00.c`; `decompiled/client/strings.csv`.]

The inventory rendering routine RVA `0x0C2050` reads its inventory pointer at widget `+0x160`, reads the full word at inventory `+0x12C`, sends it to the signed-integer stream insertion import and appends the literal `Platinum Coins`. The decisive read and formatting calls are at RVAs `0x0C367F–0x0C369D`; the label is at RVA `0x302D14`. The import at IAT RVA `0x2FC2E8` is the signed `int` overload of the wide-character output stream. The value is displayed directly, rather than split into denominations by this sequence. This is original UI evidence for a spendable balance, not an inferred name based on its position beside another field. [Evidence: `binary/Cube.exe`, RVAs `0x0C367F–0x0C369D`, original import directory and label bytes; `decompiled/client/string_references.csv`.]

## Credit through RVA 0x06EBE0

This helper receives an inventory, an item and a 32-bit destination-group argument. With group minus one, it first obtains a group through RVA `0x07FA30`; category 13 takes that helper's default group 1. It then rejects category zero. For a nonzero category, it ensures that the outer group collection includes the selected group before making a local item copy. Consequently a category-13 credit can expand that collection even though it will not insert an ordinary item entry. Explicit group values other than minus one are not replaced by automatic classification. Invalid negative groups other than the sentinel are outside the established valid-input boundary. [Evidence: `decompiled/client/functions/0046ebe0.c`, `0047fa30.c`; `binary/Cube.exe`, RVAs `0x06EBFE–0x06EC51`.]

After copying the item through RVA `0x00EE70`, the helper chooses the amount. For category 13, it sign-extends the copy's 16-bit field at item `+0x10` into a signed 32-bit amount and changes that field in the **local copy** to 1. The original item is not changed by this normalization. The helper then checks the original category byte. Category 12 has its own denomination handling first; category 13 next adds the amount directly to inventory `+0x12C` and returns. The category-13 addition is at RVA `0x06ECF9`. [Evidence: `decompiled/client/functions/0040ee70.c`, `0046ebe0.c`; `binary/Cube.exe`, RVAs `0x06EC4A–0x06ED0F`.]

There is no category-13 subtype, material, rarity, flag, existing-entry or item-equality gate after the common admission described above. In particular, this branch does not search for a matching item, increment a stack entry, occupy an empty entry or append a new ordinary item entry. It also does not write creature experience or invoke level-up. Its terminal balance update is a native 32-bit integer addition. There is no positivity requirement, saturation, lower bound or maximum-balance clamp in this path: a zero amount leaves the balance unchanged, a negative signed amount reduces it, and integer overflow retains the low 32 result bits. The signed 16-bit amount range is minus 32,768 through 32,767. The local normalization to 1 does not change that already extracted amount. [Same evidence, especially RVAs `0x06EC90–0x06EC9C`, `0x06ECF4–0x06ED0F`.]

The same 16-bit item field has other category-dependent uses. Its use here is a supplied quantity for category 13, not a request to add a character level or experience value. The helper's category decision and arithmetic provide that distinction directly. No random draw or floating-point conversion occurs in the amount extraction and terminal credit. Allocation caused by group growth can precede credit; allocation-failure and invalid-pointer behavior are not converted into a successful-credit guarantee.

## Concrete incoming values and copies

A concrete fatal-application producer constructs a category-13 item at RVAs `0x19694D–0x1969BE`. Its computed quantity is narrowed to the low 16 bits at RVA `0x19699A`, and the item category becomes 13 at RVA `0x1969BE`. It first appends an event containing a recipient key and the item to the caller-supplied aggregate's list at `+0x40`. It then compares the recipient creature pointer with world `+0xB8`; only equality reaches the immediate local call to `0x06EBE0` at RVA `0x196A19`, with that creature's inventory and automatic group selection. The list insertion therefore precedes this direct local balance change. The quantity producer and its wider fatal eligibility/recipient selection are not a universal award rule established by this document. [Evidence: `binary/Cube.exe`, RVAs `0x19694D–0x196A19`; `decompiled/client/functions/00595a60.c`.]

The next random draw in that shown producer occurs at RVA `0x196A1E`, after category-13 event construction and any direct local credit. It selects a later item-generation route. It is not a random decision inside the category-13 inventory helper. This audit does not close the later generated item's category, the wider generator's draw stream or all other producers of category-13 items. [Evidence: `binary/Cube.exe`, RVAs `0x196A1E–0x196A69`.]

The world-update item-grant path also appends a key/item event to aggregate `+0x40` before its local inventory call. At RVAs `0x21087E–0x2108A0`, the recipient pointer must equal world `+0xB8`, and item category 25 decimal is excluded; an admitted category-13 item is passed to the same helper with group minus one. The upstream item selection, removal and grant admission are outside this narrow counter contract. [Evidence: `binary/Cube.exe`, RVAs `0x210843–0x2108A0`.]

A separate enclosing-client input path consumes the received item-event list at client `+0x800670`. At RVAs `0x08F770–0x08F7A8`, it looks up the event's first eight bytes as a creature-map key, requires a nonnull result equal to client `+0x8006D0`, excludes item category 25 and credits the item beginning at event `+0x08` through `0x06EBE0` with group minus one. This is a key lookup followed by pointer admission; it is not a comparison of an item category with a creature identifier. No extra category-13 filter is present in this shown admission. Transport authority, replay handling and duplication across local and received routes are not closed here. [Evidence: `binary/Cube.exe`, RVAs `0x08F715–0x08F7A8`.]

Balances can also arrive by state replacement rather than item credit. RVA `0x0772B0` constructs a fresh inventory and copies its zeroed balances to creature `+0x1304/+0x1308`. Original creature snapshot/copy sequences separately transfer the two balances, including RVAs `0x0823E9–0x0823FB` and `0x0876A8–0x0876BD`. These transfers preserve all 32 source bits; they are not category-13 item grants. The latter route constructs a temporary creature and passes it to the original stream writer. [Evidence: `decompiled/client/functions/004772b0.c`, `004821a0.c`, `00487520.c`; `decompiled/client/assembly.txt`, corresponding original instruction ranges.]

Original stream writer RVA `0x04D790` writes creature `+0x1304` first and `+0x1308` second as separate four-byte values at RVAs `0x04DD8F–0x04DDBA`. Reader RVA `0x04BE40` assigns those fields in the same order when their four-byte reads fit, at RVAs `0x04C643–0x04C68F`. No item conversion or denomination normalization occurs at this boundary. On insufficient input the respective assignment is skipped and the cursor moves to the end; this is not a guaranteed zero replacement. Complete format admission, every storage/transport consumer and corrupted-input recovery remain outside scope. [Evidence: `decompiled/client/functions/0044d790.c`, `0044be40.c`; `binary/Cube.exe`, cited ranges.]

## Adaptation payment and mutation order

The original service UI uses `Adaption`, `Adapt` and `Platinum Coins`, with corresponding original string references in rendering routine RVA `0x00F8F0`. Native RTTI identifies `cube::AdaptionWidget`. Its selected-item helper is RVA `0x00F570`; its payment-price helper is RVA `0x00F4F0`. These labels and the balance subtraction below support the service/payment meaning independently of reconstruction terminology. [Evidence: `decompiled/client/functions/0040f8f0.c`; `decompiled/client/strings.csv`, `string_references.csv`, `symbols.csv`; original strings at RVAs `0x2FCD10`, `0x2FCD40`, `0x2FCD54`.]

Selection first uses a direct item pointer at widget `+0x160` when nonnull. Otherwise it obtains the local creature through widget `+0x16C` and client `+0x8006D0`, requires a valid signed nonnegative group and entry index from widget `+0x164/+0x168`, and requires that entry's 32-bit count be nonzero. A negative count is not rejected by that last test. The helper returns only item categories 3, 7, 5, 4, 6, 8 or 9, and rejects an item whose byte `+0x0E` already has bit `0x01` set. The direct-pointer route bypasses the inventory-index checks but retains those item-category and flag checks. [Evidence: `decompiled/client/functions/0040f570.c`; `binary/Cube.exe`, RVAs `0x00F570–0x00F645`.]

At the service input branch RVAs `0x07C748–0x07C806`, a nonzero service UI state is followed by successful input-region helper `0x011340` and a nonnull selection. The branch queries the price once, compares creature `+0x1308` with it using a signed 32-bit comparison, and skips payment when the balance is smaller. Equality is sufficient. On admission it queries the price **again**, then subtracts that second 32-bit result from `+0x1308`. It does not debit `+0x1304`, remove a category-13 item entry, or debit experience. There is no extra nonnegative-price or post-subtraction clamp in this branch. It also has no separate requirement that the selected item's level be below the creature's level: a zero price can admit the subsequent item mutation when the signed balance is at least zero. [Evidence: `decompiled/client/functions/0047b600.c`; `binary/Cube.exe`, RVAs `0x07C748–0x07C7B0`.]

Only after subtraction does it read the low 16 bits of the creature's level field `+0x190`, query selection again and store those bits into item `+0x10`. It then queries selection once more and sets bit `0x01` in item byte `+0x0E`. Finally it requests sound identifier `0x2E` at the creature's position. The item presentation routine RVA `0x0A28C0` appends the original text `(adapted)` when this same bit is set. The separate selection and price calls are observable ordering boundaries; no single saved item pointer or cached first price controls all the subsequent operations. The shown route provides no rollback after debit and no whole-operation lock or freshness guarantee against untraced mutation. [Evidence: `binary/Cube.exe`, RVAs `0x07C7B6–0x07C801`; `decompiled/client/functions/004a28c0.c`, item flag/label branch.]

## Price arithmetic and imported-math boundary

Price helper `0x00F4F0` returns zero when selection is null. Otherwise it reads item `+0x10` as a signed 16-bit value and the creature's `+0x190` as signed 32 bits. When the item value is greater than or equal to the creature value, price is zero. When lower, it reads item byte `+0x0C` unsigned, subtracts one from that byte's widened value, adds the signed item value, converts that integer to binary32 and multiplies by binary32 one quarter. The result is widened to binary64 and supplied with binary64 base 2 to the imported power thunk RVA `0x28D8D4`. [Evidence: `binary/Cube.exe`, RVAs `0x00F4F0–0x00F53F`; `decompiled/client/functions/0040f4f0.c`.]

The mathematical power input is therefore base 2. Its exponent is one quarter of the quantity obtained by adding the signed item value to unsigned byte `+0x0C`, then subtracting one, subject to the stated conversion order. The returned binary64 value in XMM0 is immediately narrowed to binary32, then multiplied by binary32 2. That single binary32 step amount is reused. Starting from signed integer zero, the helper repeatedly converts its current integer accumulator to binary32, adds the step amount, and truncates the result toward zero back to signed 32 bits. There is one iteration for each unit of the creature-value minus item-value difference. It does not increase the exponent, recompute the power or postpone all truncation until the end. [Evidence: `binary/Cube.exe`, RVAs `0x00F544–0x00F567`.]

The exact constants are binary64 2, bits `0x4000000000000000`, at RVA `0x345E18`; binary32 one quarter, bits `0x3E800000`, at `0x345D98`; and binary32 2, bits `0x40000000`, at `0x345E10`. The thunk jumps through IAT RVA `0x2FC454`, whose original by-name import is `MSVCR110.dll!_libm_sse2_pow_precise`. The caller supplies the base in XMM0 and exponent in XMM1 and reads the scalar binary64 result from XMM0. Imported callee accuracy, exceptional behavior and hidden runtime state are not established from the game caller alone. [Evidence: `binary/Cube.exe`, scalar constant bytes, RVAs `0x00F522–0x00F55C`, `0x28D8D4–0x28D8D9`, original import directory.]

The adaptation renderer has an inline price display calculation at RVAs `0x010B88–0x010C2D`: it selects the item, computes the same single power-based step, performs the same integer-to-binary32 addition and truncation for successive item-value-to-creature-value steps, then displays the integer followed by `Platinum Coins`. This is separate evaluation, not proof that the rendered amount is cached for payment. Ambient SSE rounding/control, out-of-range or nonfinite float-to-integer results, integer difference overflow and extremely large iteration counts remain explicit numeric limits. No clamping or price correction is supplied by this contract. [Evidence: `binary/Cube.exe`, cited range; `decompiled/client/functions/0040f8f0.c`.]

## Distinction from category 12 and experience

In `0x06EBE0`, category 12 also extracts the signed 16-bit quantity, but uses item byte `+0x0D` to select units for inventory `+0x128`: byte 10 adds the quantity, byte 11 adds quantity times 10,000, and byte 12 adds quantity times 100. Those are 32-bit integer products/additions. Other byte values do not take those currency returns and can continue into ordinary entry handling. Category 13 instead credits inventory `+0x12C` without that byte-dependent scaling. The inventory UI separately splits `+0x128` by signed divisions/remainders of 100; it does not apply that denomination formatting to the Platinum Coins read described above. [Evidence: `binary/Cube.exe`, RVAs `0x06ECA3–0x06ED12`; `decompiled/client/functions/004c2050.c`, currency display block.]

Experience is creature `+0x194`, not inventory `+0x12C` or creature `+0x1308`. For example, helper RVA `0x1A0BF0` adds a 32-bit event value at event `+0x14` to admitted creatures' `+0x194`, then invokes RVA `0x047B00`. That level-up helper compares and subtracts an experience threshold from `+0x194`, increments the 32-bit level at `+0x190` and refreshes health. Neither this experience addition nor the cited threshold/level writes uses `+0x1308`. The fatal category-13 path's supplied quantity can be derived from other numeric state without making the destination an experience accumulator. [Evidence: `decompiled/client/functions/005a0bf0.c`, `00447b00.c`; `binary/Cube.exe`, RVAs `0x1A0CDF–0x1A0D41`, `0x047B00–0x047C1D`.]

This audit closes the stated client balance identity, ordinary category-13 credit, concrete local/received inputs, direct UI naming and adaptation debit arithmetic/order. It does not enumerate every balance writer, every category-13 award or acquisition path, every UI callback, all inventory validity rules, persistence durability, transport deduplication, server enforcement or imported power internals. No complete economy, atomic transaction or client/server equivalence is inferred from these bounded routes.
