# Alpha creature-map key order

Status: FINAL / STABLE / HELD after complete author readback and source-only re-certification on 2026-11-22. This independent, original-only contract establishes the creature-map key order, lookup and duplicate behavior, and the main actor traversal and bounded mutations in client world routine RVA `0x20C510`.

## Evidence and scope

The supported image is original `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. All addresses below are RVAs. Evidence paths are relative to `Documents/disassembled alpha cube world`. The original helper exports, the complete client instruction listing `decompiled/client/assembly.txt` and the world-routine listing `decompiled/client/assembly-functions/0060c510.asm` were checked against the supported image. Code bytes that the discovered listings do not cover were read directly from `binary/Cube.exe`; their absence from a listing is not treated as empty behavior. No reconstruction, other implementation, runtime material or other contract was used as evidence.

The world's creature map begins at world `+0x04`. Each native entry holds an eight-byte key followed by a four-byte mapped creature pointer. Helper `0x068C90` yields the address of that key/value payload, which lies at entry `+0x10`; the main actor loop reads the mapped pointer at payload `+0x08`. Measured from the entry address that the comparison helpers use, the key words are at `+0x10/+0x14` and the mapped pointer at `+0x18`. These positions distinguish the lookup key from the pointed-to creature's own eight-byte ID at creature `+0x08/+0x0C`. This document does not prescribe a container layout for any other implementation. [Evidence: original binary, `0x068C90–0x068C95`, `0x077D90–0x077E03`, `0x02F000–0x02F027`, `0x03B6BA–0x03B6CE`; world listing, `0x2104D0–0x2104DE`.]

## Exact eight-byte ordering and equality

For an eight-byte key, the four bytes at key `+0x00` form the lower-significance word and the four at key `+0x04` the upper-significance word. The upper words are compared as signed 32-bit integers. Only when the upper words are equal are the lower words compared as unsigned 32-bit integers. Two keys are equal only when both complete words match. The result is exactly the numeric order of signed two's-complement 64-bit integers represented by those eight bytes. It is not unsigned 64-bit order, address order, a lower-word-first comparison or a bytewise lexical comparison. [Evidence: original binary, ordering predicate `0x02C8D0–0x02C8F2`, with signed upper-word branches at `0x02C8DF/0x02C8E1` and the unsigned lower-word branch at `0x02C8E7`; the same signed-upper/unsigned-lower tests appear inline in the lookup at `0x077DB0–0x077DE0`.]

The following full-key bit patterns are in increasing traversal order:

| Key bits, upper word written first | Signed interpretation or distinguishing property |
| --- | --- |
| `0x8000000000000000` | Minimum signed 64-bit value |
| `0xFFFFFFFF00000000` | Negative `4,294,967,296` |
| `0xFFFFFFFFFFFFFFFF` | Negative one |
| `0x0000000000000000` | Zero |
| `0x000000007FFFFFFF` | Positive `2,147,483,647` |
| `0x0000000080000000` | Positive `2,147,483,648`; the lower word's high bit does not make the key negative |
| `0x00000000FFFFFFFF` | Positive `4,294,967,295` |
| `0x0000000100000000` | Positive `4,294,967,296`; upper-word significance controls this boundary |
| `0x7FFFFFFFFFFFFFFF` | Maximum signed 64-bit value |

These examples follow directly from the recovered comparisons. The comparison and map-access helpers make no special exception for zero, all-one bits, an upper-word sign bit or any other negative key. The end position is a separate sentinel and is not represented by any key value. Restrictions imposed by a particular ID producer or receiver are not inferred from the comparison and are not generalized here.

## Lookup, insertion access and duplicate policy

World lookup `0x02F000` passes world `+0x04` and the caller's eight-byte key to `0x077D90`. That helper descends the map in the order above to the first entry whose key is not less than the requested key, and reports that entry only when its key is exactly equal; otherwise it reports the end position. The world lookup then returns the matching entry's mapped pointer, or zero when there is no matching entry. A present entry whose mapped pointer is zero also yields zero, so a zero result alone does not distinguish absence from a present null-valued entry. Neither helper compares the requested key with the creature's own ID or follows the mapped pointer to check identity. Lookup never creates an entry. [Evidence: original binary, `0x02F000–0x02F027`, `0x077D90–0x077E03`.]

Insertion access `0x068AD0` uses the same signed-upper/unsigned-lower order. When an entry with an equal key exists, it returns the address of that entry's mapped-pointer slot and leaves the entry and the slot's contents unchanged. When no equal key exists, it builds a new entry holding all eight supplied key bytes and an initially zero mapped pointer, inserts it, and returns the new slot. Entries whose mapped pointer is zero still occupy their keys: a second entry with an equal key is never created merely because the existing mapping is null. A caller may then write through the returned slot; that separate write is what can replace an existing mapping. [Evidence: original binary, `0x068AD0–0x068B6C`, existing-slot return `0x068B26–0x068B2F`, zero initial mapping at `0x068B43`, new-entry construction `0x0522A0–0x0522D1`.]

The underlying positioned insertion `0x053420` places a new entry directly next to the supplied position only when strict ordering against the neighboring keys confirms the placement; in every other case it falls back to `0x053B40`. The fallback descends from the root and, when it finds an existing entry with an equal key, releases the pending new entry, returns the existing entry and sets the insertion-result byte to zero, without touching the existing mapped pointer. A successful addition links the entry, sets the result byte to one and increments the entry count through `0x1C0420`. Because `0x068AD0` handles an equal key itself before calling `0x053420`, that access path never reaches the duplicate branch; the branch matters only for other callers of the insertion routines. Releasing a pending entry does not destroy any creature. Creature lifetime and a caller's explicit slot replacement are separate matters. [Evidence: original binary, `0x053420–0x053666`, fallback `0x053B40–0x053C8D`, success result store at `0x053C13`, duplicate branch `0x053C68–0x053C8D`, count increment at `0x1C044A–0x1C044B`.]

## Main actor traversal and priority

At `0x210499` the main actor traversal obtains the first entry of world `+0x04` through `0x06F440`, obtains the end position through `0x20A9F0`, and compares the two through `0x0688D0`; an empty map exits directly to the next world phase at `0x21FE61`. The first entry is the one with the least key in the order above. At `0x2104D0` the loop reads the current entry's mapped creature pointer. A null pointer branches straight to the common advance block at `0x21FE21`.

The common advance block calls `0x068D70`, which records the old position as its result and moves the live iterator forward through `0x1C3EA0`. That step reaches the entry with the next greater key, or the end position when none remains. The block then obtains the end position again through a reference to world `+0x04` saved at routine entry, and either returns to `0x2104D0` or leaves for `0x21FE61`. Termination is decided by this iterator-versus-end comparison, not by a count captured at the start of the pass. [Evidence: original binary, `0x06F440–0x06F44D`, `0x20A9F0–0x20A9FB`, `0x0688D0–0x0688E0`, `0x068D70–0x068D84`, `0x1C3EA0–0x1C3EEE`; world listing, `0x20C541–0x20C558`, `0x210499–0x2104E6`, `0x21FE21–0x21FE61`.]

The traversal itself gives no scheduling priority to the creature that world `+0xB8` designates, to a local or remote role, to creature byte `+0x60`, to creature byte `+0x68` or to any creature kind. None of these is consulted when choosing the first entry or its successor. Once an entry is fetched, the creature's fields can change which parts of its body run. For example, the records held at creature `+0x130C` are processed first; health at creature `+0x16C` is then lowered to the maximum returned by `0x044DB0` when it exceeds that maximum; and when the resulting health is nonpositive under an ordered comparison (a NaN value does not take this branch), control goes to the common advance block. Later checks, including creature byte `+0x60` and world byte `+0xB4`, govern conditional work. These decisions inside the body never move an entry ahead of another in the outer traversal. Any apparent role priority caused by a producer assigning negative or positive IDs is a consequence of the entry keys, not a second ordering rule. [Evidence: world listing, `0x2104D0–0x210546`, `0x211A44–0x211B04`, `0x21FE21–0x21FE5B`.]

Neither the null-pointer skip nor the nonpositive-health skip performs a creature-map erase on its way to the common advance block; both reach the same successor step. The common advance block itself neither destroys the creature nor erases or reinserts the current entry. This is not a claim that every earlier part of the body, or every nested call, is free of mutation.

The pass is ordered by entry key even when that key and the creature's own ID differ. The entry fetch does not check that they agree, and the successor step does not read the creature ID. Constructor `0x03B690` copies a supplied eight-byte ID into creature `+0x08/+0x0C`, while insertion access receives its own key pointer and the mapped pointer is written afterward by the caller. A verified creation site at `0x20E80B–0x20E837` supplies the same temporary eight-byte value to the constructor and to insertion access. That establishes agreement for that construction path only; it does not make key/ID equality an enforced property of lookup or traversal. [Evidence: original binary, `0x03B6BA–0x03B6CE`, `0x068AD0–0x068B6C`; world listing, `0x20E80B–0x20E837`.]

## Ordinary mutations before and during the pass

Before the main traversal begins, the world routine can gather creature-map positions in a list local to the invocation and remove them afterward. In the loop at `0x20E376–0x20E417`, for each gathered position it reads the entry's mapped pointer; when that pointer is nonnull it calls the creature's first virtual-table entry with argument one, and it then passes the position to erase helper `0x03EDE0` on world `+0x04`. Only after that does it advance through the separate local list. A second loop of the same shape runs at `0x20F66F–0x20F717`. These sites show that map membership can change before `0x210499`; how each gathered position is selected is outside this contract. The local removal list is not the main actor iterator. [Evidence: world listing, `0x20E34E`, `0x20E376–0x20E419`, `0x20F647`, `0x20F66F–0x20F719`.]

Erase helper `0x03EDE0` first tests whether the supplied position is the end sentinel and, if so, calls an imported error-reporting routine. For a valid position it computes the successor before unlinking, releases the selected entry, decrements the entry count when it is nonzero and returns that successor. It does not destroy the mapped creature, so the explicit virtual call made by the pre-main caller has its own role. Ordinary insertion keeps the addresses of all existing entries, and ordinary erase releases only the selected entry. When the erased entry has two children, the successor entry is relinked into its place rather than having its key and value copied, and the rebalancing helpers `0x02CAC0` and `0x0E37E0` adjust links and colors without copying payloads. These statements concern these valid native operations, not arbitrary memory changes or replacement of the whole map. [Evidence: original binary, `0x03EDE0–0x03F036`, two-child relink `0x03EEA2–0x03EEFB`, release and count update `0x03F014–0x03F02D`.]

Two independently confirmed creation branches can insert into the creature map while the main pass is running. One lies within the per-creature record handling, with insertion access at `0x2111C8` and the mapped-pointer write at `0x2111CD`. The other lies within a selected action body, with insertion access at `0x215BA1` and the write at `0x215BA6`. Both pass world `+0x04` to `0x068AD0`, scan the map with a temporary iterator separate from the outer one, and leave the outer actor iterator to its ordinary later advance. The first site is not covered by the discovered listings and was decoded directly from `binary/Cube.exe`; the second is covered by the complete instruction listing and was checked against the image.

At both sites the key is derived the same way. A temporary candidate starts at eight-byte zero. The scan visits every entry in key order, ignores entries whose mapped pointer is null, and replaces the candidate with an entry's key only when that key is strictly less than the candidate in the order above. The final candidate is then reduced by one as a full 64-bit value: the lower word is decremented and the borrow, when the lower word was zero, is taken from the upper word. The same resulting eight bytes are passed to creature construction and to insertion access. Neither sequence clamps signed underflow. Null-valued entries play no part in the minimum, although insertion access still treats their keys as occupied. The mapped-pointer write follows insertion access unconditionally. [Evidence: original binary, `0x2110C4–0x2111CD`, `0x2157FD–0x21592D`, `0x215B7C–0x215BA6`.]

The second site adds one gate that the first lacks. During the same scan it counts nonnull mapped creatures whose eight-byte field at creature `+0x198/+0x19C` equals the current actor's own ID at `+0x08/+0x0C`. When that count is greater than two, it skips the decrement, construction and insertion and branches to `0x211F2F`. When creation proceeds, the new creature's `+0x198/+0x19C` field is set to the current actor's ID before insertion access. [Evidence: original binary, `0x215866–0x21588B`, `0x2158EA–0x2158F1`, `0x215B88–0x215B94`.]

When the decrement does not wrap past the minimum signed 64-bit value, the generated key is less than every nonnull mapped key that the scan considered, including the current actor's. Inserting it neither restarts the outer iterator nor moves it backward, so the new earlier-key creature is not visited later in the same continuing pass. If the selected minimum is `0x8000000000000000`, the unclamped decrement yields `0x7FFFFFFFFFFFFFFF` and the earlier-key conclusion does not hold. Ignored null-valued entries and any resulting key collision fall under the duplicate and slot-replacement behavior described above. This contract does not assume that such extreme or colliding states occur in an ordinary session.

## Mutation and synchronization limits

The outer pass follows a live iterator rather than a list of creature pointers captured at the start of the pass. For a still-valid current entry, an ordinary insertion with a greater key can change the successor that the next advance reaches; an insertion with a smaller key does not restart the pass. Erasing a future entry removes it from the rest of the traversal. These are bounded consequences of the recovered insertion and successor behavior, not a guarantee that arbitrary calls keep the iterator valid.

The advance block does not look the current entry up again by a saved key, does not compare the creature's own ID, and does not substitute an erase result for an invalidated current position. If the current entry is removed, that validity question belongs to the responsible caller; the examined outer block supplies no general repair rule. Directly changing stored key bytes, freeing a mapped creature while leaving a nonnull pointer, replacing the map, unsynchronized concurrent access and reentrant mutations inside the body lie outside the valid-order guarantee. The erases at `0x218D57` and `0x218EC7` operate on maps held by the current creature at `+0x13A4` and `+0x13AC`; they do not remove the current world creature-map entry. [Evidence: world listing, `0x218BDD–0x218BF4`, `0x218D55–0x218D57`, `0x218CFF–0x218DA3`, `0x218EC5–0x218EC7`, `0x21FE21–0x21FE5B`.]

The comparison, lookup, insertion-access and iterator helpers perform no floating-point conversion and no random draw, and take no lock of their own. Allocation, exception handling, whole-frame protection, asynchronous receive mutations and the large actor bodies are separate dependencies. The supported claim is increasing signed-64-bit entry-key order for the valid map and iterator state described above, together with the explicitly proved body skips and mutations. It is not a frozen-membership, exactly-once-under-arbitrary-mutation, local-player-first or complete actor-lifetime guarantee.

## Unresolved

- The role of the creature's first virtual-table entry called with argument one in the pre-main removal loops is inferred to be destruction of the creature, but that has not been traced into the called routine.
- Whether control returns from the imported error-reporting routine that erase helper `0x03EDE0` calls for an end-sentinel position is not established.
- The meaning of creature field `+0x198/+0x19C`, which the second creation site compares with the current actor's ID and copies into the new creature, is not established beyond those two uses.
- How the positions gathered for pre-main removal are selected, and the full admission conditions that lead into either in-pass creation site, are not specified.
- Behavior on allocation failure, including the null-constructor branches at the creation sites, and the entry-count limit with its length error in `0x1C0420`, is not specified.
- Validity of the outer iterator when the current entry is erased by a nested call, if any call does so, is not established.

## Re-certification (2026-11-22)

A fresh source-only author, working only from the original client image and its listings, re-checked every statement in this document against `binary/Cube.exe` with the SHA-256 above. Each address, offset, key width and signedness, comparison direction, traversal step and mutation site was confirmed. No behavioral statement was found to be wrong. The second in-pass creation site was found to include a count gate, now stated, that the earlier text did not mention. The earlier wording about "maximum-health admission" was replaced by the confirmed clamp-then-nonpositive-skip sequence. Two points that the earlier text stated as fact were moved to the unresolved list: the identification of the first virtual-table call as destruction, and the outcome of the erase helper's end-sentinel check. Wording was rewritten throughout as plain behavioral prose. What remains open is listed in the unresolved section above.
