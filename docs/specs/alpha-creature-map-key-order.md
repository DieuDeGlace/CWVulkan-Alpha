# Alpha creature-map key order

Status: FINAL / STABLE / HELD after complete author readback. This independent, original-only contract establishes the creature-map key order, lookup and duplicate behavior, and the main actor traversal and bounded mutations in client world routine RVA `0x20C510`.

## Evidence and scope

The supported image is original `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, preferred image base `0x00400000`. All addresses below are RVAs. Evidence paths are relative to `Documents/disassembled alpha cube world`. Original helper exports and `decompiled/client/assembly-functions/0060c510.asm` were checked against scoped disassembly of the supported image. Missing main-routine switch bodies were inspected directly where needed; their absence from the discovered assembly export is not treated as empty behavior. No reconstruction, replacement implementation, runtime material or earlier held contract was read for this task.

The world’s creature map begins at world `+0x04`. The relevant native entry payload contains an eight-byte key followed by a four-byte mapped creature pointer. Helper `0x068C90` exposes that payload; the main actor loop reads its mapped pointer at payload `+0x08`. In native entry addresses used by the comparison helpers, the key words are at `+0x10/+0x14` and the mapped pointer at `+0x18`. These field identities distinguish the lookup key from the pointed-to creature’s own eight-byte ID at creature `+0x08/+0x0C`. This document does not prescribe a replacement container layout. [Evidence: `decompiled/client/functions/00468c90.c`, `00477d90.c`, `0042f000.c`, `0043b690.c`; world assembly, `0x2104D0–0x2104DE`.]

## Exact eight-byte ordering and equality

For an eight-byte key, the four bytes at key `+0x00` are the lower-significance word and the four at key `+0x04` are the upper-significance word. The upper word is compared as a signed 32-bit integer. Only when upper words are equal is the lower word compared as an unsigned 32-bit integer. Equality requires both complete words to match. This is exactly the numeric order of signed, two’s-complement 64-bit integers represented by those eight bytes; it is not unsigned 64-bit order, address order, a comparison of the lower word first, or a bytewise lexical comparison. [Evidence: `decompiled/client/functions/0042c8d0.c`; original binary, `0x02C8D0–0x02C8F2`, signed upper-word branches at `0x02C8DF/0x02C8E1`, unsigned lower-word branch at `0x02C8E7`; independent lookup comparisons at `0x077DB0–0x077DE0`.]

The following full-key bit patterns are in increasing traversal order:

| Key bits, upper word written first | Signed interpretation or distinguishing property |
| --- | --- |
| `0x8000000000000000` | Minimum signed 64-bit value |
| `0xFFFFFFFF00000000` | Negative `4,294,967,296` |
| `0xFFFFFFFFFFFFFFFF` | Negative one |
| `0x0000000000000000` | Zero |
| `0x000000007FFFFFFF` | Positive `2,147,483,647` |
| `0x0000000080000000` | Positive `2,147,483,648`; the lower word’s high bit does not make the key negative |
| `0x00000000FFFFFFFF` | Positive `4,294,967,295` |
| `0x0000000100000000` | Positive `4,294,967,296`; upper-word significance controls this boundary |
| `0x7FFFFFFFFFFFFFFF` | Maximum signed 64-bit value |

These examples follow directly from the recovered comparisons. The comparison and map-access helpers contain no special exclusion of zero, all-one bits, an upper-word sign bit or any other negative key. An end iterator is represented separately from key contents. Restrictions imposed by a particular ID producer or receiver are not inferred from the comparator and are not universalized here.

## Lookup, insertion access and duplicate policy

World lookup `0x02F000` supplies world `+0x04` and the caller’s eight-byte key to `0x077D90`. That helper searches according to the order above and returns an entry only for exact key equality; otherwise it returns the map’s end position. The world wrapper returns the matching mapped pointer or zero when there is no matching entry. An existing matching entry whose mapped pointer is zero also produces zero. Thus the wrapper’s zero return alone does not distinguish absence from a present null-valued entry. Neither helper compares the requested key with the creature’s own ID or follows the mapped pointer to validate identity. Lookup does not create an entry. [Evidence: `decompiled/client/functions/0042f000.c`, `00477d90.c`; original binary, `0x02F000–0x02F027`, `0x077D90–0x077E03`.]

Insertion-access helper `0x068AD0` uses the same signed-upper/unsigned-lower order. For an equal key it returns the existing mapped-pointer slot, preserving that slot’s contents and the existing entry. For an absent key it copies all eight supplied key bytes into a new entry with an initially zero mapped pointer and returns that slot. Zero-valued mappings participate in key uniqueness. Their keys are not available for a second equal entry merely because their mapped pointer is null. A caller can subsequently write the returned slot; that separate store can replace an existing mapping. [Evidence: `decompiled/client/functions/00468ad0.c`, `004522a0.c`; original binary, `0x068AD0–0x068B6C`, existing-slot return `0x068B26–0x068B2F`, zero initial mapping at `0x068B43`.]

The checked insertion path through `0x053420` and its fallback `0x053B40` also maintains one entry per equal eight-byte key. In the duplicate fallback, the pending entry allocation is discarded, the existing entry is returned, and the insertion-result byte is zero. The existing mapped pointer is not overwritten by that duplicate-resolution branch. A successful addition reports insertion and increments the entry count through `0x1C0420`. Discarding an entry allocation is not evidence that its pointed-to creature was destroyed. Creature lifetime and any caller’s explicit slot replacement are separate boundaries. Allocation failure and container length-error recovery are not specified here. [Evidence: `decompiled/client/functions/00453420.c`, `00453b40.c`, `005c0420.c`; original binary, duplicate branch `0x053C68–0x053C8D` and insertion-result store `0x053C13`.]

## Main actor traversal and priority

At `0x210499`, the main actor traversal obtains the first entry of world `+0x04` through `0x06F440`, obtains the end position through `0x20A9F0`, and compares those positions through `0x0688D0`. The first position is the least key under the recovered order. At `0x2104D0`, the loop reads the mapped creature pointer from the current entry. A null pointer jumps to common iterator advance at `0x21FE21`.

Common advance calls `0x068D70`, whose effect is to save the old position for its result and advance the active iterator through `0x1C3EA0`. The latter reaches the next entry in increasing key order, or the end position when no greater entry remains. The loop then obtains the map’s current end position again and either returns to `0x2104D0` or exits to the next world phase at `0x21FE61`. Its termination decision is an iterator/end comparison, not a fixed count captured at pass start. [Evidence: `decompiled/client/functions/0046f440.c`, `0060a9f0.c`, `004688d0.c`, `00468d70.c`, `005c3ea0.c`; world assembly, `0x210499–0x2104E6`, `0x21FE21–0x21FE61`; original binary, `0x1C3EA0–0x1C3EEC`.]

This main traversal grants no scheduling priority to the creature designated by world `+0xB8`, a local/remote role, byte selector `+0x60`, action byte `+0x68` or another creature kind. Those properties are not consulted to choose the first entry or its successor. Once fetched, a creature’s fields can change which parts of its body execute. For example, its own `+0x130C` records are processed before maximum-health admission, and ordered nonpositive health then branches to common advance; later role/ownership-related checks govern conditional work. Those body decisions do not move that entry ahead of another entry in the outer traversal. Any apparent role priority caused by a particular producer assigning negative or positive IDs remains a consequence of the entry keys, not a second ordering rule. [Evidence: world assembly, `0x2104D0–0x210546`, `0x211A86–0x211B04`, `0x21FE21–0x21FE5B`.]

The ordinary null-pointer skip and the ordered-nonpositive-health skip contain no creature-map erase at their branch boundary; both reach the same successor operation. The common advance block itself neither destroys the creature nor erases/reinserts the current entry. This is not a claim that every earlier body or nested callback is free of mutation.

The pass is ordered by map entry key even when that key and creature own ID differ. Its entry fetch does not check that equality, and its successor operation does not read the creature ID. The constructor `0x03B690` copies a supplied ID into creature `+0x08/+0x0C`, while insertion access receives an independent key pointer and a later caller store supplies the mapped pointer. A verified creation site at `0x20E814–0x20E837` supplies the same temporary eight-byte ID to the constructor and the map access. That site establishes agreement for its own construction path; it does not turn equality into an enforced invariant of lookup or traversal. [Evidence: `decompiled/client/functions/0043b690.c`, `00468ad0.c`; world assembly, `0x20E80B–0x20E837`.]

## Ordinary mutations before and during the pass

Before main traversal begins, the world routine can collect creature-map positions in an invocation-local list and later remove them. At `0x20E3B0–0x20E3DE`, it obtains a collected map position, calls the mapped object’s virtual destruction entry with argument one when the pointer is nonnull, then calls erase helper `0x03EDE0` on world `+0x04`. It advances the separate local collection afterward. A corresponding later pre-main removal loop appears at `0x20F6B0–0x20F6F2`. These sites establish that membership can change before `0x210499`; the exact selection policy for every collected position is outside this contract. The local removal worklist is not the main actor iterator. [Evidence: world assembly, `0x20E376–0x20E410`, `0x20F66F–0x20F710`.]

The original erase helper rejects an end/sentinel position, computes the erased entry’s successor before removal, frees the selected entry, updates the entry count and returns that successor. It does not destroy the mapped creature itself. The verified pre-main caller’s explicit virtual destruction therefore has its own role. Ordinary insertion preserves the addresses of existing entries, and ordinary erase frees the selected entry while preserving the other entries; the recovered maintenance helpers adjust the ordering relationships without copying existing key/value payloads into a new allocation. These statements concern these valid native operations, not arbitrary memory changes or replacement of the whole map. [Evidence: `decompiled/client/functions/0043ede0.c`, `005c0420.c`, `0042cac0.c`, `004e37e0.c`; original binary, `0x03EDE0–0x03EEFE`, `0x03F014–0x03F036`.]

Two independently confirmed creation branches can also insert into the creature map while the main actor pass is already running. One is within per-creature record dispatch, with map access at `0x2111C8` and the mapped-pointer store at `0x2111CD`. Another is within a selected action body, with map access at `0x215BA1` and the store at `0x215BA6`. Both pass world `+0x04` to `0x068AD0`, use a separate temporary iterator for their ID scan, and leave the saved outer actor iterator to reach its ordinary later advance. These native bodies are missing from the discovered main-routine export and were confirmed directly in `binary/Cube.exe`. Their complete outer action/record admission and constructed-creature dependencies are not re-audited here.

At both sites the key derivation itself is closed: the temporary candidate starts at eight-byte zero; a scan considers only entries with nonnull mapped pointers and retains a key only when it is less than that candidate under the recovered order. The result is then decremented by one using a low-word decrement and high-word carry adjustment. The same resulting eight bytes are supplied to creature construction and map access. There is no signed-underflow clamp in these sequences. Null-valued entry keys do not participate in that minimum selection, although insertion access still treats them as occupied keys. The subsequent mapped-pointer store is unconditional after the access returns. [Evidence: original binary, `0x2110C4–0x2111CD`, `0x2157FD–0x21592D`, `0x215B7C–0x215BA6`.]

When this decrement does not wrap below the minimum signed 64-bit value, the generated key precedes every already mapped nonnull creature considered by the scan, including the current actor. Inserting it does not restart the outer iterator or send that iterator backward. Consequently this newly inserted earlier-key creature is not automatically visited later in the same continuing main pass. If the selected minimum is `0x8000000000000000`, the raw decrement instead produces `0x7FFFFFFFFFFFFFFF`; the earlier-key conclusion does not apply. Ignored null-valued entries and any resulting key collision remain subject to the duplicate/slot-replacement behavior already described. The contract does not assume that extreme or colliding states occur in an ordinary session.

## Mutation and synchronization limits

The outer pass uses a live iterator rather than a complete list of pass-start creature pointers. For a still-valid current entry, ordinary insertion after it in key order can change the successor that a later increment observes; insertion before it does not restart the pass. Erasing a future entry can remove it from the remaining traversal. These are bounded consequences of the recovered insertion and successor behavior, not a guarantee that arbitrary callbacks preserve iterator validity.

The main advance block does not re-find the current entry by a saved key, compare its own ID, or automatically replace an invalid current iterator with an erase result. Removal of the current entry requires that validity question to be resolved by the responsible caller; the examined outer block supplies no general repair rule. Directly changing stored key bytes, freeing a mapped creature while leaving a nonnull pointer, replacing the map, concurrent unsynchronized access and reentrant body mutations are outside the valid-order guarantee. Creature-local maps erased at `0x218D57` and `0x218EC7` belong to creature `+0x13A4` and `+0x13AC`; those sites do not establish removal of the current world creature-map entry. [Evidence: world assembly, `0x218BF4`, `0x218D55–0x218D57`, `0x218DA3`, `0x218EC5–0x218EC7`, `0x21FE21–0x21FE5B`.]

The comparison, lookup, insertion-access and iterator helpers perform no floating-point conversion or random draw and establish no lock of their own. Allocation, exception handling, whole-frame protection, asynchronous receive mutations and the large actor bodies remain separate dependencies. The supported claim is increasing signed-64-bit entry-key order for the valid map and iterator state described above, with the explicitly proved body skips and mutations. It is not a frozen-membership, exactly-once-under-arbitrary-mutation, local-player-first or complete actor-lifetime guarantee.
