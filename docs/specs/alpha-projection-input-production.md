# Alpha client projection input production

This contract covers the original client's main renderer projection constructor, its verified input sources, scalar grouping, stored matrix layout, and bounded device/constant publication. ## Actual frame and projection call relationships

Client construction installs a vtable at image virtual address `0x006FFDC8`. Its entry at byte `+0x28` is frame update RVA `0x088EE0`; byte `+0x2C` is renderer RVA `0x0AC260`. Outer frame routine RVA `0x0C85F0`, with nonnull global device and client pointers, calls the update entry, performs the scoped configuration/resize reconciliation, then calls the render entry, and only afterward invokes the device presentation entry. Therefore the renderer reaches the projection boundary after that frame's update call and any completed reconciliation reset. This is caller-phase ordering, not a complete update, pause, device-loss, or message-loop admission contract. Evidence: `S/004c85f0.c`, original vtable bytes, and constructor vtable publication at `0x059CC3`.

The main perspective construction occurs at renderer call RVA `0x0AE5D3`, targeting helper RVA `0x027910`. This helper receives an output matrix receiver and four successive four-byte stack arguments: full vertical-angle input, signed aspect input, near input, and far input. All four are interpreted as binary32. The output occupies all sixteen components; no previous matrix component survives this constructor. The caller's ordinary route needs a valid pointer read from `C+0x8006D0`, valid dimensions, and a valid device for subsequent publication. The entire renderer's earlier admission and alternative passes are not reconstructed here. Evidence: native RVAs `0x0AE4B3–0x0AE63F` and `S/00427910.c`.

This is not the only perspective calculation in the executable. A separately identified direct call at RVA `0x076450`, inside routine `0x0758C0`, supplies angle bits `0x3F490FDB`, the same signed-dimension ratio pattern, near bits `0x3DCCCCCD`, and far bits `0x447A0000`. Its complete caller/consumer role is outside this contract. Other native routines also reach the tangent import directly. Their existence is not evidence that the main draw uses their angle or far value. Evidence: original instructions `0x076409–0x076450`.

## Main renderer inputs

The angle decision tests the full two-byte word at the object reached through `C+0x8006D0`, member `+0x124`, with mask `0x0400`. The test occurs at RVA `0x0AE4D2`; the corresponding branch at `0x0AE5C1` selects the angle written immediately before the constructor. The intervening scalar calculations do not replace that integer condition. No health, class, action-name, or duration meaning is inferred for the tested word or pointer. Its upstream production is not closed here.

| --- | --- | --- |
| Full vertical angle when mask `0x0400` is nonzero | Argument write at `0x0AE5C3` | Binary32 bits `0x3F060A92`, exactly `0.52359879016876220703125` as a real number. |

The two angle values are radian inputs, approximately 30 and 50 degrees. Their degree descriptions are interpretations of the constants and the half-angle tangent relation, not extra degree-to-radian work performed by this caller. The narrower value is selected by a nonzero tested mask. The near and far inputs are in the coordinate units presented to the perspective operation; this audit does not assign a world-distance unit or recover every fixed-to-view conversion. Evidence for aspect conversion and sign change: `0x0AE548–0x0AE5BB`; sign-mask data at image virtual address `0x00745F70` contains `0x80000000` in each four-byte lane.

The width and height are not divided as integers, nor is an already computed binary64 aspect rounded once at the end. Each signed integer converts to binary32 first; their binary32 division follows; its sign bit is then inverted before the helper receives it. The local constructor path adds no height-zero guard, dimension clamp, aspect epsilon, near/far clamp, or special-case fallback. Ordinary positive published dimensions avoid the height-zero case, but direct calls with zero, negative, enormous, or exceptional inputs are not thereby made safe.

## Where the dimension members are published

Resize/reconciliation routine RVA `0x0C8940` independently establishes the dimension source. When the full four-byte global at image virtual address `0x0076B1D8` is nonzero, it takes signed four-byte right/bottom values from globals `0x0076B1DC` and `0x0076B1E0`. Otherwise it calls `GetClientRect` on the window stored at `0x0076B1C0` and uses the returned `right` and `bottom` members. This native operation does not subtract the rectangle's left/top members. The window-client values are pixel extents supplied by that API; the complete producer and meaning of the nonzero configuration discriminator remain unclosed. Evidence: `S/004c8940.c` and original native body.

Both selected signed values must be strictly greater than zero before this routine enters its reset/publication route. With an available device it builds reset parameters containing those values and repeatedly invokes device vtable byte offset `+0x40` until the result equals zero. Each nonzero result is followed by `Sleep(100)` and another reset attempt. The selected dimensions are retained for these retries. This audit supplies no guaranteed retry completion, asynchronous resize policy, or safe operation following device failure.

After a successful reset, if the client pointer is nonnull, the routine invokes helper RVA `0x077280`, then stores the four-byte right value to `C+0x11C` and the four-byte bottom value to `C+0x120`, at native RVAs `0x0C8A9B/0x0C8AA1`. It then invokes client virtual byte offset `+0x10`, which the installed vtable identifies as RVA `0x082A40`, with those same two values. That callback's UI/device dependencies are not fully audited. The verified stores precede the callback. Zero or negative selected extents do not reach these stores in this routine. Evidence: `S/004c8940.c`, original vtable bytes, and the scoped callback boundary.

Window procedure RVA `0x0C83F0` reaches this routine for message values five and seven. Outer frame `0x0C85F0` can also reach it when the client's configuration members differ from the cached four-byte globals. Those are independently established reachability paths, not an exhaustive resize-call inventory. Base construction `0x03B4C0` does not establish an initialized value for the two dimension members; a complete earliest valid publication/initial-render guarantee remains outside this bounded audit. No back-buffer dimension, viewport origin, or min/max viewport-depth value is inferred merely from the dimension members.

## Constructor arithmetic and component layout

Helper RVA `0x027910` first multiplies the supplied binary32 angle by exact binary32 `0.5`, whose data bits are at image virtual address `0x00745DA0`. It converts the resulting scalar half angle to binary64 and calls thunk RVA `0x28D9CE`. The thunk jumps through IAT virtual address `0x006FC464`, identified by the original import directory as `MSVCR110.dll!_libm_sse2_tan_precise`. The caller supplies the half angle in the low binary64 lane of XMM0 and interprets the returned low binary64 lane as the tangent result. It then converts that result to binary32 before further arithmetic. Evidence: native helper RVAs `0x027913–0x027943`, original thunk, and original image imports.

Let the descriptive scalar `s` mean the binary32 quotient of exact binary32 one divided by that already rounded binary32 tangent result. The vertical coefficient is `s`. The horizontal coefficient is a separate binary32 division of `s` by the supplied signed aspect. The numerator one has bits `0x3F800000` at image virtual address `0x00745DC0`. In particular, the caller does not retain a binary64 reciprocal or multiply a reciprocal aspect into the tangent computation.

For the depth coefficients, the helper forms one binary32 difference, far minus near, and separately forms a binary32 product, near times far. It divides the product by that difference in binary32, then flips the quotient's sign bit to obtain the depth-offset coefficient. It separately divides far by that same rounded difference in binary32 for the depth-scale coefficient. The sign change is not a floating subtraction from zero. There is no fused multiply/add in these scalar relations and no replacement of the rounded product/division by a reassociated depth expression. Evidence: native RVAs `0x027937–0x0279B0`.

The sixteen stored binary32 values are fully determined by the following offset table. Offsets are relative to the output matrix, avoiding ambiguity between row-major and column-major notation.

| Component offset | Stored relation |
| --- | --- |
| `+0x00` | Horizontal coefficient: `s` divided by the signed aspect. |
| `+0x14` | Vertical coefficient `s`. |
| `+0x28` | Depth scale: far divided by the rounded far-minus-near difference. |
| `+0x2C` | Exact binary32 positive one, bits `0x3F800000`. |
| `+0x38` | Depth offset: the sign-bit-inverted quotient of rounded near-times-far product by the rounded difference. |

Evidence: the complete native helper `0x027910–0x0279D3`, also navigable through `S/00427910.c`. The helper has no validation branch and reaches the imported tangent once on an ordinary completing call. It has no direct random or seed call. No random draw is interleaved between the main input selection and this constructor call. That is not a renderer-wide random-stream claim.

## Coordinate and depth relation

One unambiguous interpretation of the physical matrix is four consecutive stored rows used with a row vector. For an input position with components x, y, z and homogeneous component one, the resulting clip components are horizontal coefficient times x; vertical coefficient times y; depth scale times z plus depth offset; and z itself. Equivalently, the same bytes can be described as consecutive columns acting on a column vector with the transposed matrix interpretation. This is a mathematical interpretation of the stored coefficients, not copied shader instructions.

Thus the perspective denominator is positive-view z, and the ordinary positive-dimension caller gives a negative horizontal coefficient and positive vertical coefficient for the stated finite angles. In ideal real arithmetic the depth relation places the near plane at normalized depth zero and the far plane at one. The native stored coefficients follow the rounded operations above, so exact endpoint bit equality is not promised by that ideal interpretation. The coefficient form establishes the zero-to-one depth relation; it does not by itself prove every API clipping decision, rasterizer viewport transform, screen-y orientation, pixel-center rule, or shader output convention. Those require dependencies beyond the scoped matrix producer.

The native device path is Direct3D 9, and the renderer passes this matrix directly to its projection transform selector three through device vtable byte offset `+0xB0`. There is no local clip-depth remapping matrix, near/far swap, or y-sign modification between constructor completion and that publication. A complete installed vertex-shader audit, viewport-state history, depth-range overrides, and driver/API exceptional behavior are not supplied here. This distinguishes the verified native producer and its mathematical depth relation from unproved rasterization behavior.

## Publication order and bounded matrix composition

Immediately after construction, the renderer clears a texture binding at call RVA `0x0AE5EB`. It then publishes an identity matrix to device transform selectors `0x100` and two, at `0x0AE609` and `0x0AE624`, before publishing `P` to selector three at `0x0AE63F`. The shared identity value was completely initialized by helper `0x023E70`. The ordinary device calls use the pointer in `C+0x134`. This sequence describes the reached state publication; it does not identify `C+0x26C` with the identity matrix temporarily installed in selector two. Evidence: native renderer `0x0AE5D8–0x0AE63F` and `S/00423e70.c`.

Later in the same renderer route, instructions `0x0AED91–0x0AEDA5` copy all sixteen four-byte projection components into client storage beginning `C+0x800A90`. The copy performs no transpose or scalar conversion. Next, `0x0AEDAB–0x0AEDBA` snapshots the separate 64-byte matrix at `C+0x26C` into local storage. The projection constructor replaces all components of the temporary previously used by earlier renderer passes, so those earlier temporary values are not retained as hidden perspective components.

At `0x0AEE29`, matrix helper RVA `0x024F30` combines the cached `P` receiver with the separate matrix at `C+0x26C`, producing a local 64-byte result. Under the consecutive-row convention above the relation is `V` times `P`; under the equivalent consecutive-column convention it is `P` times `V`. Each output component is a four-product dot sum: separate binary32 products are accumulated as the first two terms, then the third, then the fourth. There is no fused operation or binary64 accumulation in this helper. This relation does not close later use of every derived value or the production of `V`. Evidence: `S/00424f30.c`, its original native body, and caller `0x0AEE14–0x0AEE29`.

A bounded later matrix-upload call at renderer RVA `0x0B1A36` passes a local object matrix, the earlier snapshot of `C+0x26C`, and the projection temporary to helper `0x0482A0`. Call `0x0B1D40` uses the same view/projection source objects with another local object matrix. This confirms a shader-constant publication route distinct from the device transform state. The complete construction and admission of those object matrices, all draw types, and every later projection consumer remain outside scope. Evidence: original renderer call-site instructions.

For ordinary finite nonaliasing inputs, helper `0x0482A0` first publishes three four-float constant vectors formed from the first three columns of the object matrix. It then forms the object-times-view product and publishes its first three columns in the same form. Finally it forms view-times-projection first, then object times that rounded intermediate, and publishes all four columns. These statements use the consecutive-row convention; the equivalent consecutive-column convention reverses each product order and uses the transposed interpretation. The final grouping is object times the already rounded view-times-projection, rather than an earlier object-times-view result multiplied by projection. Each scalar dot sum uses separately rounded binary32 products and successive binary32 additions; the intermediate matrix is stored as binary32. Transposition/repacking performs no numeric conversion. Evidence: `S/004482a0.c` and its original native body.

The upload helper reaches device vtable byte offset `+0x178` three times, using four-byte starting-register members at manager `+0x24`, `+0x28`, and `+0x2C`, with vector counts three, three, and four respectively. Its source matrices are read, not rewritten by its direct body. This contract does not identify the initial register values, shader declarations, the exact arithmetic used inside the installed shader, or GPU multiply/add precision from those calls alone. Those dependencies remain necessary for a complete vertex-to-pixel result.

## Accuracy, exceptional inputs, and unresolved production

The imported tangent's name does not certify a particular error bound, bit-identical result across runtime DLL versions, instruction path, or nonfinite handling. This audit identifies the executable's requested DLL/export and the scalar width that its caller supplies and consumes; it does not identify a loaded runtime DLL by hash, close its full register-clobber/upper-lane ABI, or reproduce a tangent algorithm. Upper converted lanes are not used as matrix scalars by the caller, but their irrelevance to every possible imported implementation is not independently proved here.

The constructor does not locally establish MXCSR rounding, exception masks, denormal handling, or the imported routine's floating-point controls. The binary32/binary64 operation boundaries above are native instruction boundaries, not a claim that every environment selects round-to-nearest.
