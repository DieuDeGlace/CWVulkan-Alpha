# Alpha world mode, controlled-creature pointer, and first projectile-source admission

Status: FINAL / STABLE / HELD. This is an independently worded, bounded source-side behavioral contract, re-certified on 2026-11-22. It does not certify any replacement implementation or runtime acceptance.

The evidence root is `disassembled alpha cube world`. The supported original images are:

Both images use preferred base `0x00400000`. Every routine and instruction address below is an RVA in `Cube.exe` unless it is explicitly marked as a server RVA. Object offsets are marked as offsets of a named object. Facts come only from the original images and the original decompiled and disassembled listings of those images. No other contract, reconstruction, implementation, runtime capture or implementation history supplies facts here.

The established interpretation is narrow. World `+0xB4` is a byte that the client sets to 1 when it starts an outbound connection attempt; both initial client construction and native server startup construct it as zero. The pointer at world `+0xB8` holds the client's locally controlled creature in the verified client assignment paths; native server construction leaves it null. A null projectile hit source is not by itself a rejection in the first client candidate path described below.

## Field identity and initialization

World `+0xB4` is one byte. World `+0xB8` is a 32-bit pointer. The relevant projectile fields are: the leading 64-bit field at `+0x00`, used as the owner identifier for creature lookup; a 32-bit kind value at `+0x60`; a one-byte element value at `+0x64`; a one-byte flag at `+0x5C`; and a signed 32-bit clock at `+0x68`. On a candidate creature, `+0x08` is its 64-bit identifier, `+0x16C` is binary32 health, `+0x128` is a 32-bit lock word, and `+0x60` is a one-byte control value.

The client world constructor at `0x18EB00` copies the low byte of its second explicit stack argument into world `+0xB4`, then stores null in `+0xB8`. It does not normalize the mode argument to 0 or 1. A later point in the same constructor stores null in `+0xB8` again. The client application constructor at `0x059C40` calls this world constructor with zero as that second argument.

The client embeds the world at application offset `+0x2E4`. Application `+0x398` therefore aliases world `+0xB4`, application `+0x39C` aliases world `+0xB8`, and application `+0x2E8` is world `+0x04`, the world's creature map keyed by 64-bit identifier. These aliases are needed to find the connection transitions; a search for only the world displacement would miss them.

The server world constructor at server RVA `0x0C8570` has the same relevant initialization: it copies its second explicit argument byte into `+0xB4`, stores null in `+0xB8`, and stores null in `+0xB8` again later. Server startup at server RVA `0x149C50` allocates the world (allocation size `0x80029C`) and calls that constructor with both explicit arguments zero. Startup then passes the world pointer to another constructor call at server RVA `0x149EE2` and later calls a world-object routine at server RVA `0x1322D0` from the startup-loop site `0x14A0AE`. This establishes a server startup path with mode zero and no constructor-assigned local-creature pointer. It does not establish that every server caller keeps those values forever.

## Meaning and verified assignments of `+0xB8`

The client setter at `0x087E90` copies its single four-byte argument directly into world `+0xB8`. It performs no null, ownership, control or world-membership check. In the application constructor, the setter is called on application `+0x2E4` with the pointer held at application `+0x8006D0`. Immediately before that call, the constructor stores the same pointer in the world creature map under 64-bit identifier 1 (low half 1, high half 0).

The application's main update routine at `0x088EE0` also uses the application `+0x8006D0` pointer: at `0x09BF70–0x09BF82`, after checking a local byte, the creature's byte `+0x68` (not `0x30`) and application byte `+0x04`, it calls a creature routine at `0x045410` on that pointer; that routine itself declines to proceed when the creature's `+0x128` lock word is nonzero. This ties the pointer to the creature that the local client drives each update, rather than inferring its role from a field name or a single combat comparison.

The connection routine at `0x06FC50` has a separate direct store to application `+0x39C`. After the client reads a four-byte record kind that must be zero (otherwise it leaves through the common exit without a mode reset), an eight-byte creature identifier and a `0x1168`-byte creature record, it tests the identifier as a signed 64-bit value. When the identifier is nonnegative, the client enters the world critical section, looks the identifier up in the world creature map, creates a creature of size `0x1E60` if none is found, updates application `+0x8006D0`, applies the received record and further local values, and then copies the resulting pointer into application `+0x39C` at `0x070408`. Thus world `+0xB8` is refreshed to the current controlled creature in that branch. The store occurs after the creature lookup, replacement and data work, while the world critical section is held, before a following loop that still runs inside that section, and before the section is released at `0x070549` and the network workers are started. When the identifier is negative, the routine skips this whole block, including the `+0x39C` store, and still proceeds to mark the connection active and start the workers.

This assignment is conditional. The audited routine does not establish that every accepted response, short receive, allocation failure or early return leaves a new valid pointer. Startup and connection assignments support "the client's controlled creature" for these paths, not a universal promise that `+0xB8` is always nonnull, valid or the only owned creature.

The disconnect routine has no direct store that clears world `+0xB8`; its direct mode and socket changes are described below. This does not certify the old pointer's validity through all cleanup calls. No nonnull store to the server world's `+0xB8` was established in the bounded server constructor, startup and world-call trace.

## Client network-mode transitions at `+0xB4`

The connection routine at `0x06FC50` receives a destination string. When the string length is zero it jumps to its common exit before any mode store. Otherwise it stores byte 1 into application `+0x398` before it creates the socket, resolves the address, or calls the system connection routine. Mode 1 can therefore describe an attempt in progress; it is not proof of a successful socket or a completed handshake. The socket is created as IPv4 stream (address family 2, type 1, protocol 0), and the port constant is 12345. Broader connection options are outside this contract.

On its established failure cleanup routes, the routine closes the socket, stores zero into the application socket slot `+0x8006CC`, and stores mode zero. The direct mode-reset sites are `0x06FE47`, `0x06FEE9`, `0x07018C`, `0x070745` and `0x070931`. They cover the failed-connect cleanup and several protocol and error cleanup regions. The full classification of every receive result, early return, handshake value and exception is not closed here; these resets must not be expanded into a claim that every failure or return resets the mode.

The accepted connection branch leaves the earlier mode value 1 in place. It later stores 1 into application byte `+0x800585` (the active marker) and starts its two network workers. That byte is separate from world `+0xB4`; the mode byte is not set only when the active marker is set.

The worker routine at `0x069C10` has a cleanup tail guarded by a nonzero active marker. In that tail it closes the application socket, stores socket zero, then stores mode zero at `0x06A869`. This can precede the application's full disconnect handling. The main update at `0x088F2A–0x088F45` calls the disconnect routine when the active marker is nonzero and the socket slot is zero.

The disconnect routine at `0x0719F0` skips its main cleanup body when the active marker is zero. When the marker is nonzero, it first calls a routine at `0x087520` with the controlled-creature pointer, then clears the marker. If the socket slot is nonzero it closes the socket, clears the slot and stores mode zero at `0x071A5B`. It then waits with an infinite timeout on each of the two recorded worker handles that is nonzero, clearing each handle slot, enters the world critical section, and stores mode zero again at `0x071AAD` regardless of the earlier socket check. The critical-section wrappers at `0x201CB0` (enter) and `0x201E90` (leave) operate on world offset `+0x8000C0`; the wrappers themselves do not store the mode or the controlled-creature pointer.

These paths justify describing `+0xB4` as a client network-mode byte in this contract. They do not justify equating nonzero with "server", equating zero with "single player only", or assuming the byte is synchronized with socket validity, worker state or connection success at every intermediate point. Across the whole client listing, the only byte stores through a register base with displacement `0x398` are the application stores listed in this section. Stores made through a world-relative base at `+0xB4` were not exhaustively enumerated beyond the constructor. No in-place change of the server world's mode to 1 is established by the audited server path.

## Null hit-source admission in the first later projectile candidate path

This section concerns the per-projectile update inside the client routine at `0x20C510`, specifically the call at `0x221E8C` to the routine at `0x196D30` (called "the hit routine" below). Both owner lookups in this region call the world creature lookup at `0x02F000`, which returns the creature stored under the projectile's leading 64-bit field, or null when no entry exists.

Two separate sources are held. The "cached source" is computed at `0x221465–0x22148B`: the lookup is made once, and if it returns nonnull it is made a second time and that result is kept; otherwise the cached source is null. The "hit source" is the result of a further lookup at `0x22156C`, made after the projectile's spatial values are prepared and kept for the whole candidate loop. Their equality under every possible lifetime change is not assumed.

Reaching this region has preconditions earlier in the same projectile update. Kind 2 requires an earlier lookup at `0x220AE9` to return nonnull and its clock to be at most 1200 before the clock advance; if either fails, the projectile takes the branch at `0x220D68` and does not enter the candidate region in that pass. The clock is advanced by the frame delta at `0x220CC1` before the region. Kinds other than 2 enter the region only when the advanced clock is at most 5000. Within the region, the candidate loop runs only when a step count computed at `0x2214C1` is positive. Further kind-2 conditions between `0x220B0C` and `0x220C9D` are not closed here.

At the first candidate admission boundary, each candidate is taken from a candidate entry at entry `+0x08` and must be nonnull. The caller rejects a candidate whose binary32 health at `+0x16C` compares ordered and nonpositive, before it looks at the hit source. An unordered health value does not take that rejection branch; later non-finite behavior is not established.

After those candidate checks, kind 3 with element 2 proceeds directly to the geometric checks, skipping the source-dependent checks even if the hit source is nonnull. For every other kind and element combination, a null hit source also proceeds directly to the same geometric checks; it is not a rejection. Only a nonnull hit source on that second route triggers the source-dependent checks, in this order: reject when the candidate is the source itself; reject when the relationship predicate at `0x1988A0`, given the source and the candidate, returns false; reject when the candidate's 64-bit identifier at `+0x08` equals the 64-bit value at source `+0x11C0`/`+0x11C4`.

All routes still require the geometric predicates at `0x194690` and `0x194660` (three each) and the reach predicate at `0x19EE90` with a binary32 distance argument of 200.0, followed by the lock and timing checks. A nonzero candidate lock word at `+0x128` stops this first attempt for that candidate whether or not the hit source is null; when the hit source is nonnull, the caller additionally passes the candidate's identifier to a routine at `0x07F000` operating on source `+0x11B4` before moving on. A null source gives no exception to the lock check.

The timing selector then admits, in this order: kind 0 with flag zero; kind 1 or 4 with flag zero; kind 3 when the clock divided by 1000 (signed, truncating) differs from the same quotient of the clock minus the frame delta; kind 2 when the clock is strictly greater than 300 and the corresponding quotient by 100 changes. Every other combination, including kinds 0, 1 and 4 with a nonzero flag, skips the hit attempt for that candidate. No step of the selector checks whether a source exists.

After timing admission, a source-dependent block runs only for flag zero, kind 0 or 2, and a nonnull hit source (described in the next section). A source-dependent Boolean, produced by the routine at `0x0444A0` on the hit source, starts false and stays false when the hit source is null; when true it multiplies a copy of the projectile binary32 value at `+0x48` by 2.0. The argument preparation for the later call contains no source-null rejection. Provided the candidate, geometry, lock and timing gates pass and the element byte is not 2, **kinds 0, 1 and 4 with flag zero can reach `0x221E8C` with the hit source, the second stack argument, equal to null**. This is positive caller admission only, not a claim that the callee accepts the hit or applies damage. The first stack argument is the candidate.

Kind 3 with an element other than 2 can likewise pass the source-dependent admission boundary with a null source, but still needs the 1000-unit quotient change before attempting the call. Kind 2's candidate boundary also does not reject null, but the earlier kind-2 lookup gate described above must succeed in the same update, and its attempt also needs the clock and 100-unit conditions. This document does not infer end-to-end kind-2 null-source reachability from the later boundary alone, nor assume that a source cannot change between the separate lookups.

The source-independent kind-3/element-2 skip has two limits. It does not skip the initial candidate and health checks, the geometry, the candidate lock or the kind-3 timing. And element 2, for any kind, later chooses a separate route and never reaches this first hit-routine call. That route requires the cached source to be nonnull, a false result from the predicate at `0x196CA0` given the cached source and the candidate, and a candidate control value other than 6. When the world mode is nonzero, the route's final world call at `0x195A60` additionally requires both the cached source and the candidate to equal world `+0xB8`. The early kind-3/element-2 skip therefore does not establish a null-source hit call, a guaranteed event, or a successful heal. The event semantics of that route are outside this contract.

## Effect of the world fields at this first call boundary

The first candidate source-admission check has no requirement that a nonnull hit source equal world `+0xB8`, and it does not turn a null source into a rejection when world mode is nonzero. Source-dependent relationship filtering is a separate predicate whose complete gameplay rules are not reconstructed here.

The world fields do appear in three nearby places. First, the source-dependent block after timing admission (flag zero, kind 0 or 2, nonnull hit source) adds a computed binary32 amount to hit source `+0x170` and clamps the result to at most 1.0, but only when world mode is zero or the hit source equals world `+0xB8`; with nonzero mode and a different source the addition is skipped. This block does not decide whether the hit call is attempted. Second, a producer at `0x221BBD–0x221CDF` uses the cached source: the cached source must be nonnull and either equal world `+0xB8`, or have a nonzero control value at `+0x60` while world mode is zero. That producer calls a routine at `0x0441A0` with binary32 argument 0.15, and continues only for projectile flag zero with cached-source bytes `+0x140` equal to 2 and `+0x141` equal to 1. A null cached source skips that producer; it does not skip the hit call for an otherwise admitted non-element-2 candidate. A null hit source alone does not prove that the cached lookup was null. Third, the element-2 route's world-mode condition is stated in the previous section.

Inside the hit routine at `0x196D30`, an ordered nonpositive candidate health returns false, and so does a nonzero world mode together with a candidate equal to world `+0xB8`. Both checks come before the routine looks at the source argument. This is a target-side gate after the caller has reached the call; it is not a null-source admission gate. With a null source argument the routine branches to a separate continuation at `0x197E3D`; that continuation, all other protection, damage and event effects, and ultimate hit success remain unresolved here.

The known client assignments explain why equality with `+0xB8` selects the controlled creature in these paths, while the server's constructor-null pointer supplies no comparable local creature. The field values alone do not establish an ownership model for every subsystem, nor which machine must author every combat result.

## Unresolved

- Whether the main-update use of the controlled-creature pointer at `0x09BF82` is the primary attack input; the earlier wording called it a primary-input site, which the listing does not by itself show.
- The meaning of the server world-object routine at server RVA `0x1322D0` and of the constructor that receives the server world at server RVA `0x149EE2`; they are described only as calls that receive the world.
- The purpose of the loop that follows the `+0x39C` store inside the client critical section, and of the routine at `0x087520` called at the start of disconnect.
- The gameplay meaning of the hit-source Boolean from `0x0444A0`, the `+0x170` addition, and the cached-source producer at `0x221BBD`; the earlier wording named the first a critical result and the last an owner-buff probability, which are interpretations, not confirmed facts.
- Kind-2 pre-region conditions between `0x220B0C` and `0x220C9D`, and the handling of projectiles that take the branch at `0x220D68`.
- Projectile list ownership, insertion and removal order: these are not established by this contract.
- The hit routine's null-source continuation, complete protocol validation, unknown callers, indirect or bulk field writes, client and server world lifetime, geometry details, source lifetime and complete hit resolution.

## Re-certification (2026-11-22)

A fresh source-only author re-checked every statement in this document against the original `Cube.exe` and `Server.exe` images and their original listings, and confirmed both image hashes. The behavioral claims about the mode byte, the controlled-creature pointer, the five reset sites, the worker and disconnect cleanup, the candidate health and source checks, the lock check, the timing selector and the hit-routine gates were confirmed. One source citation was corrected: the projectile candidate region lies in the routine at `0x20C510`, and `0x02F000` is the world creature lookup it calls, not the projectile routine. Newly confirmed details were added: the negative-identifier connection branch that skips the pointer store, the clock and step-count preconditions for reaching the candidate region, the world-gated `+0x170` addition, and the element-2 route's world-mode condition. Interpretive labels (primary input, critical result, owner-buff probability) were moved to the unresolved section. The items listed under Unresolved remain open.
