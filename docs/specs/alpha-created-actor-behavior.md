# Alpha created-actor setup behavior

**FINAL / STABLE / HELD**

Status: re-certified 2026-11-21 against the original image and listing. Full author readback completed.

This is a bounded original-client contract for the future update entries of the setup root and three child objects installed by the actor-creation branch ending at RVA `0x215BA6`. It closes root iteration, the third child's ordinary update, the second child's identifier/vector relations and the admission of its terrain/path continuation, and a bounded caller/state relation for the much broader first child. It also distinguishes update results, cloning and cleanup. A stored counter is not treated as actor lifetime without its consumer.

The original evidence root is `disassembled alpha cube world`. The supported image is `binary/Cube.exe`, a 32-bit image based at `0x00400000`, length 3,885,568 bytes, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`. All addresses below are RVAs. Evidence is the image, its original instruction listing `decompiled/client/assembly.txt`, and individually identified original function files under `decompiled/client/functions/`. No other project contract, reconstruction, implementation or runtime observation is evidence here.

The actor passed into an update is called the subject. The identifier stored by the second child is a lookup key; the actor obtained from that lookup is called the reference actor. The actor that ran the creation branch is called the creator. These terms establish object identities without assigning allegiance or ownership labels.

Updates receive their object pointer as the native receiver and four four-byte arguments: subject actor pointer, world pointer, signed 32-bit step, and shared output pointer. Their consumed result is the low result byte. Decompiled `void` signatures do not negate the explicit native low-byte result stores and the root's low-byte tests. Upper result-register bits are not a Boolean extension contract.

One verified world caller is at `0x211A96–0x211B75`. It first queries subject helper `0x044DB0`; when binary32 subject health `+0x16C` compares strictly greater than that rounded result it queries again and stores the second result as health. It then requires health to compare strictly greater than zero; zero, negative or unordered health leaves this route. The callback route further requires a nonzero subject discriminator byte `+0x60` and a zero world byte `+0xB4`. On that route it adds the world step to subject `+0x13C4`. If subject `+0x12C` is positive, the callback/clear boundary is bypassed entirely, the accumulator keeps its new sum, and the caller calls `0x02F160` on subject `+0x10` with arguments `0x80` and `0`; that helper is outside this contract. ## Root: repeated ordered admission, with no child removal

At `0x0DC390`, each invocation starts at the first node of the live child list whose header pointer is root `+0x04`. It calls each child's table-`+0` entry in list order with the same four argument values. A nonzero low result byte immediately ends root processing with low-byte result `1`. A zero result advances to the next list node. There is no persistent current-child index and no rule that the next invocation resumes after the child that previously returned nonzero. The first child is reconsidered on every invocation.

If the list is empty or all reached children return zero, the root writes three four-byte zeros to subject `+0x40`, `+0x44`, `+0x48`, then returns low-byte zero. It does not undo any other side effects of children that returned zero. Those children can already have changed flags, health, counters, action or path state before a later child is tried.

The update does not erase a list node, release a child, decrement the root's count or remove the subject on a zero result. Root `+0x08`, the list count, is not an iteration limit in this routine; traversal ends when the next node equals the header sentinel, re-read from root `+0x04` at each step. Null child pointers are not skipped internally. Valid objects and a valid list are caller obligations.

For the constructed three-child list, reaching the third child always yields a nonzero result, so the root's all-zero fallback is not reached merely because both earlier children return zero. The third child may leave an existing direction unchanged and still return nonzero. A child that is not reached does not have its counters reduced by this invocation. Root itself has no random/seed call or direct world mutation. Evidence: image/listing `0x0DC390–0x0DC3FA`; original `004dc390.c`.

## First child: bounded state relation for the broad update

The first child's entry `0x02CB20` contains extensive target selection, item use, action choice and movement/path work. Its complete action and navigation relation is not closed here. The following entry gates, local-state operations and selected exits are original-evidenced; unclosed later branches must not be replaced with a single timer rule. Unnamed helper queries below are identified only by address; their semantics are not supplied.

### Entry gates and early exits

Before its early admission exits, it clears bit `0x0004` in the complete 16-bit word at subject `+0x124`. It checks the subject's action byte at `+0x68`. If that byte is none of `0x53`, `0x52`, `0x54`, `0x4F` and signed 32-bit action clock `+0x6C` is strictly greater than `10000`, it writes action byte zero. Equality at `10000` does not take this action-clear route. It does not clear the clock at that store.

Next, a nonzero full 32-bit subject `+0x128` causes an immediate low-byte-`1` return. An action byte `0x50` with signed clock strictly below `3000` also returns `1`. Equality at `3000` continues. These early exits preserve the child's counters and make no direct random draw. They nevertheless retain the earlier subject flag/action changes. They prevent the root from trying either following child.

### Item-use route

It then queries `0x044DB0`, rounds the result to binary32 and multiplies by binary32 `0.25`. Only when that product is strictly greater than health `+0x16C`, and the signed action clock is strictly greater than the result of subject query `0x03D1A0`, does it scan the subject's inventory: an outer array of 12-byte containers at `+0x11DC..+0x11E0`, each holding records of `0x11C` bytes. The first record in outer-then-inner order whose four-byte count is nonzero, whose byte `+4` is `1` and whose byte `+5` is `1` qualifies. On a qualifying record it writes action byte `0x50`, zeroes the clock, applies helper `0x02C5E0` to subject `+0x1E8` with the item at record `+4`, and decrements the count. A decremented count at or below zero is stored as zero and record bytes `+4` and `+5` are cleared. It then makes two direct draws, `0x02CCC1` then `0x02CCE8`; each result is converted to binary32, multiplied by `4.0`, divided by `32767.0` and reduced by `2.0`. The first stores `+0x40`, the third component `+0x48` is zero, and the second stores `+0x44`, in that order. It returns low-byte `1` without touching the child's counters. Without a qualifying record, processing continues.

### Preliminary target and counter `+0x04`

The preliminary target is the actor that world map `+0x04` holds under the 64-bit key returned by subject helper `0x044BF0`, or none when the key is absent. When subject discriminator is `5`, the route also looks up subject `+0x198` in the same map. A found, nonnull creator whose action byte is `0x6A` causes an immediate low-byte-zero return at `0x02D2A7`; that exit precedes every counter store and leaves bit `0x0040`, `+0x0C` and `+0x10` unchanged. Any other found creator replaces the preliminary target: the route walks the creator's map at `+0x13AC` from beginning to end and keeps the entry whose binary32 value is strictly greater than the running best, which starts at `0.0`, and whose key resolves to a nonnull actor in world map `+0x04`. Ties keep the earlier entry; no qualifying entry leaves no preliminary target. An absent or null creator keeps the helper's target.

Without a preliminary target, if `0.5` times the rounded `0x044DB0` result is strictly greater than health and the discriminator is `3`, it writes action byte `0x50`, zeroes the clock, writes 16-bit `0x0401` at subject `+0x1E8` and copies the 16-bit value at subject `+0x190` to `+0x1F8`, zeroes `+0x40/+0x44/+0x48`, and returns low-byte `1` without touching the child's counters.

Every other route, with or without a preliminary target, reaches `0x02CE3A`: child signed 32-bit `+0x04` is reduced by the integer step, and a negative result is stored as zero. It then sets a local block flag when the subject's list at `+0x1178` holds a node whose byte `+8` is `8`.

### No-target candidate scan

With a preliminary target, the scan is skipped. Otherwise no scan occurs when the discriminator is `5` and the full 64-bit `+0x198` is nonzero, or when child `+0x10` is positive. The scan walks world map `+0x04` from beginning to end. A candidate must be nonnull, not the subject, have health strictly greater than zero and a discriminator other than `5`. Its squared distance is formed from candidate position minus subject position: three signed 64-bit differences, each converted to binary32 and multiplied by binary32 `1/65536`, then squared and summed in binary32. When candidate binary32 `+0x1190` is positive, the integer difference of the four-byte values at candidate and subject `+0x190` is converted to binary32 then binary64 and passed with binary64 `1.5` to the original `pow` import; the rounded result times candidate `+0x1190` is subtracted from `1.0`, a factor below `0.1` is replaced by `0.1`, and the squared distance is divided by the squared factor. The running best starts at the square of binary32 child `+0x08`. A candidate is considered only when the block flag is clear and the best is strictly greater than its adjusted squared distance. It is then accepted when world helper `0x196CA0` with subject and candidate returns nonzero, or when instead the discriminator is `5` with zero `+0x198`, the candidate's action byte is `0x52`, candidate byte `+0x1020` is `0x14` and candidate byte `+0x1021` equals the subject's four-byte `+0x64`. It also requires a nonzero result from world helper `0x19EE90` with subject position address, candidate position address, `1` and binary32 `200.0`. When subject helper `0x044680` returns nonzero, the same candidate action/`+0x1020`/`+0x1021` test is required again. An accepted candidate becomes the running best. Ties keep the earlier candidate. Child `+0x08` is never stored by this update.

When the scan selects a target, the subject map `+0x13A4` receives binary32 `1.0` under the selected actor's full identifier, then world helper `0x1A0970` is called with selected actor first, subject second and shared output third. The helper's full record-production body is outside this scope.

### Flag `0x0040`, counter `+0x10` and the no-target exit

All routes that pass the scan stage reach `0x02D237–0x02D281`. With a final target, bit `0x0040` of the 16-bit word `+0x124` is set when the action byte is zero, or when the signed action clock is strictly greater than the sum of three subject queries made with argument `-1`: the result of `0x044270` signed-divided by two with truncation toward zero, then `0x03CAA0`, then `0x047310`. Otherwise, and always without a final target, the bit is cleared. Next, child `+0x10` is reduced by the integer step and negative-clamped to zero at `0x02D288–0x02D29D`. Without a final target the route stores zero to child `+0x0C` and returns low-byte zero at `0x02D2A4–0x02D2A9`. Earlier target/flag effects survive that return.

### Final-target reach and action choice

With a final target, the route forms the scaled difference vector target minus subject as in the scan, without the level adjustment. It calls world helper `0x19EE90` with subject position address, target position address, `1` and `200.0`, and keeps that result. A reach value starts as twice subject binary32 `+0x80` plus target `+0x80`. When subject query `0x044520` and the kept result are both nonzero, reach becomes `50.0` unless the action byte is `0x57`, `0x56` or `0x59` and the signed clock is below the `0x03CAA0` result. Subject four-byte `+0x64` of `0x2F`, `0x6F`, `0x71` or `0x70` then makes reach `20.0`. Action byte `0x5F`, `0x1C` or `0x6C` then makes it `50.0`, and action byte `0x48` makes it subject `+0x80` plus target `+0x80`.

When child `+0x04` is zero and the subject's four-byte range at `+0x13E8..+0x13EC` is nonempty, direct draw `0x02D4AD` selects one entry by unsigned remainder over the entry count. Otherwise the selected value is zero. A selected `0x5D`, `0x5B`, `0x44` or `0x45` makes reach `20.0`; a selected `0x56` or `0x59` makes it twice subject `+0x80` plus target `+0x80`. A zero kept helper result makes reach `1.0`.

If the squared distance is strictly greater than the squared reach, or the kept result is zero, the approach route at `0x02EB24` adds the step to child `+0x0C`. When its signed result exceeds `20000`, it clears the subject's map at `+0x13A4`, invokes helper `0x02EF10`, sets child `+0x10` to `3000`, resets child `+0x0C` to zero, and returns low-byte zero. Equality at `20000` continues into the approach movement after `0x02EBAA`, whose full relation is unclosed. That continuation first changes action byte `0x5F` or `0x1C` to zero.

Otherwise the in-reach route stores zero to child `+0x0C`, calls `0x02EF10`, zeroes subject `+0x13E0`, and zeroes `+0x40/+0x44/+0x48`. One special branch follows: the block flag must be clear, the target's action byte `0x52`, target byte `+0x1020` `0x14` and target byte `+0x1021` equal to subject `+0x64`, and the case of discriminator `5` with nonzero `+0x198` is excluded. That branch copies the target's identifier to subject `+0x11D0/+0x11D4`; all its exits return low-byte `1` without consuming the selected value or storing child `+0x04`. Any other in-reach case sets bit `0x0004` of `+0x124`. A nonzero selected value then stores `20000` to child `+0x04` at `0x02D869`, writes the selected value's low byte to subject `+0x68`, zeroes `+0x6C`, and stores the three scaled difference components at `+0x160`, `+0x164`, `+0x168`. It then returns low-byte `1`. A zero selected value continues into later action logic after `0x02D87F`, which is unclosed. Thus child `+0x04` is the interval after which a new entry is drawn. While it is positive, a reached final-target route draws none.

## Second child: stored identifier and reached vector routes

The second child's update `0x03ACE0` reads its full 64-bit field at `+0x08` and looks up that exact key in world `+0x04`. It does not reject zero or a key that resolves to the subject itself, and does not derive the key from subject `+0x198` during this update. A missing map entry or null mapped actor returns low-byte zero before the later subject mutations. The routine makes no update store to its own identifier or its unused `+0x04`; there is no child countdown in this route. No positive-health test on the reference actor is added by the lookup admission.

With a nonnull reference actor, it subtracts subject position from reference position as three signed 64-bit differences from actor offsets `+0x10`, `+0x18`, `+0x20`. Helper `0x03AC20` forms a fixed-point three-component dot product: each component product retains native 64-bit multiplication width, is signed-divided by `65536` with truncation toward zero, and the three results are added at 64 bits. This call supplies that difference vector as both dot-product operands, producing a squared-distance-like quantity. In ordinary nonoverflowing inputs, the subject's word `+0x124` gains bit `0x0040` exactly when that signed quantity is strictly greater than `0x400000`; otherwise that bit is cleared. Equality clears it. Other bits survive. The full overflow/exceptional arithmetic domain is not supplied.

If subject discriminator byte `+0x60` is `5`, the routine also updates subject health before the following direction decision. It queries `0x044DB0`, rounds the returned scalar to binary32, converts the signed step to binary32, multiplies that step first by binary32 `0.001` (`0x3A83126F`) then `0.1` (`0x3DCCCCCD`), multiplies the first queried scalar by that product, and adds existing health in binary32. This result is stored at subject `+0x16C`. It queries `0x044DB0` again for the comparison; only if the new health is strictly greater does it make a third query and store that rounded result. Thus the route makes two queries, or three on the upper-clamp route. No lower clamp occurs at these stores. The created discriminator values `1` and `3` do not enter this conditional unless later state changes to `5`.

The routine then independently converts the same signed 64-bit positional differences to binary32 and multiplies each by binary32 `1/65536` (`0x37800000`). It zeroes the subject triplet `+0x40/+0x44/+0x48`. When the resulting three-component squared distance is below binary32 `16.0`, this route returns low-byte zero with that zero triplet; equality proceeds to the next test. This subject-vector result can therefore differ from the earlier integer distance gate used for flag `0x0040`.

At the reached distance boundary it calls world helper `0x209480` with subject, subject-position address, reference-position address, and the binary32 sum of subject `+0x80` followed by reference `+0x80`. This contract uses the helper's low-byte result without naming an unproved spatial predicate. A nonzero result leads to helper `0x02EF10` on the subject, then a direction based on the horizontal scaled differences multiplied by binary32 `5.0`; the third component is zero. If the squared length of that triplet is strictly greater than binary32 `900.0`, it normalizes using the original double square-root call, rounds the result to binary32, forms a binary32 reciprocal, and multiplies each direction component first by the reciprocal and then by binary32 `30.0`. At or below `900.0`, it retains the triplet multiplied by `5.0`. It stores `+0x40`, `+0x44`, `+0x48` in that order and returns low-byte `1`.

When `0x209480` returns zero, the continuation first searches terrain cells at the reference actor's horizontal coordinates through world helper `0x02F860`, which receives three signed 64-bit coordinates and a zero fourth argument. A cell whose byte `+3` masked by `0x1F` is `0` or `2` is open; any other value is solid. Starting at the reference position, the search moves down by `0x10000` while cells are open. If 21 probes are all open it returns low-byte zero. From the first solid cell it moves up by `0x10000` until an open cell is found. If 21 probes are all solid it returns zero. The found open cell's coordinates are the goal point.

It then builds a fixed-point offset whose third component is half of subject binary32 `+0x88`, scaled by binary32 `65536.0` and converted through the image's 64-bit conversion helper `0x28D946`, with zero first two components. It subtracts that offset and then the goal point from subject position. When the scaled squared length of that result is below binary32 `16.0`, it calls `0x02EF10`, zeroes the direction triplet and returns low-byte zero.

Otherwise, a zero path count at subject `+0x1464` causes path construction. The route calls `0x02EF10`, stores at `+0x1428` subject position plus an offset whose third component is `0.1` minus half of `+0x88`, and stores the goal point at `+0x1440`. It then calls world helper `0x034D10` with the goal's first two coordinates, each signed-divided by `65536` and then by `256` with truncation toward zero. A zero result returns low-byte zero. A nonzero result calls world helper `0x1A9F90` with the subject, stores binary32 `2.0` at `+0x1458`, calls `0x1AAAB0` and `0x1A7C90` with the subject, and zeroes the direction triplet. A nonzero existing path count skips construction.

Then, when subject `+0x1410` is zero, the route returns low-byte `1`. Otherwise it repeats at most 10 times. A path count above `50` returns `1`. A nonzero count also returns `1` when the square of `+0x1458` is strictly greater than the binary32 conversion of a wrapped 32-bit squared distance. That distance is measured between the integer coordinates of the last node of the list at `+0x1460` and helper `0x02F040` applied to `+0x1440`. In the remaining cases it calls `0x1AAAB0` then `0x1A7C90`. After the iterations it returns `1`. The internal effects of these helpers, the cell record layout beyond the masked type, and the conversion helper's rounding remain open. They must not be replaced by the nonzero-helper direction relation. The update has no direct `rand` or `srand` call, but that does not prove absence of transitive draws in these unresolved spatial helpers.

The reached clearing helper `0x02EF10` is a meaningful side-effect boundary: its direct stores restore empty header links and zero counts at subject `+0x140C/+0x1410`, `+0x1414/+0x1418`, and `+0x1460/+0x1464`; it releases their reached nodes, repoints subject `+0x1408` to the first header and reaches another container-clear helper. The full contents/lifetimes of these structures remain unclosed. Returning zero from the second child does not undo its flag, health, vector or clearing effects.

## Third child: complete ordinary counter and direction update

At entry `0x0DBF20`, the third child always clears bit `0x0040` in the subject's full 16-bit word at `+0x124`. It then subtracts the signed 32-bit step from its own signed 32-bit field `+0x04`, storing zero when the wrapped subtraction result is negative. If the stored result is nonzero, it returns low-byte `1` without changing subject direction or action. It does not yield zero merely while waiting.

A stored result of zero, including exact equality after subtraction, refreshes direction. The route compares the subject's horizontal position at `+0x10/+0x18` with the two signed 64-bit reference coordinates at subject `+0x1C0/+0x1C8`. Each horizontal difference is squared at native 64-bit width and signed-divided by `65536`; the two terms are added at 64 bits. The random-direction route is taken when that signed sum is at most `0x640000`, including negative sums. Equality takes the random route. The following ordinary relations exclude overflowing coordinate products and invalid floating-point operations.

On that random route, the first direct random draw determines the horizontal component stored at subject `+0x40`, and the second determines `+0x44`. Each result is converted from signed 32-bit integer to binary32, multiplied by `2.0`, divided by `32767.0`, reduced by `1.0`, then multiplied by `10.0`, rounding at each binary32 operation. This route does not normalize the two random components.

When the fixed-point sum is greater than `0x640000`, direction is based on reference coordinates minus subject position instead. Each horizontal signed 64-bit difference is converted to binary32 and multiplied by `1/65536`; the third direction component is set to zero. The routine also converts the third positional difference from reference `+0x1D0`, but it does not use it as the stored vertical direction. It sums squared direction components in binary32, promotes that sum to binary64 for the original square-root call, rounds the square root to binary32, forms a binary32 reciprocal, and multiplies each component by that reciprocal and then by `10.0`, storing `+0x40`, `+0x44`, `+0x48` in order. This route consumes no direction draws. The origin and future producers of subject `+0x1C0..+0x1D7` are not established here; they are not assumed to equal the subject's current or creation position.

After either direction-refresh route, one further random draw is reduced by signed remainder over `5000`, increased by `3000`, and stored as the child's new 32-bit `+0x04`. With the original imported generator's ordinary nonnegative results this gives `3000..7999`. Only after that store does the routine set subject action byte `+0x68` to zero. ## Cloning, cleanup and remaining lifetime limits

The root's table-`+4` entry allocates another `0x0C`-byte root and invokes copy construction `0x0DC200`; a null allocation returns null. The copy walks the source child list from first to last, calls each child's table-`+4` entry and appends each returned pointer to a newly built destination list. Normal successful cloning preserves child order. It does not run child updates.

First-child cloning at `0x02EFC0` copies its 32-bit `+0x04` and raw four-byte `+0x08`, while resetting destination `+0x0C/+0x10` to zero. Second-child cloning at `0x03B450` preserves the full identifier at `+0x08` and does not initialize or read its `+0x04`. Third-child entry `0x0DC1E0` constructs a new object with counter `+0x04` zero, rather than copying the source counter. These clones and the inspected list constructors make no direct random/seed calls. Null allocations and failed child cloning are not made safe by the root update's iteration; valid nonnull child objects remain required.

Concrete root cleanup at `0x0DC300` first walks the child list and passes each child pointer directly to deallocation thunk `0x28D66E`, which reaches the `MSVCR110.dll` scalar `operator delete` import at IAT `0x2FC3F0`, in list order. It does not invoke a child virtual update, clone or destructor entry at that point. It then restores the root list's empty header links, zeroes its count, frees the old nodes in forward order and frees the sentinel. Wrapper `0x0DC360` calls that cleanup, then additionally frees the root object when its supplied low-byte flag has mask `0x01` set. These cleanup operations have no established actor/world mutation or random/seed draw. Allocation thunk `0x28D668` reaches the scalar `operator new` import at IAT `0x2FC3EC`.

This cleanup is distinct from all actor-pointer release sites. For example, original actor teardown at `0x03C41A–0x03C42B` and reset at `0x046342–0x04634D` load a nonnull actor `+0x13E4` and pass it directly to the same deallocation thunk; they do not call the root cleanup wrapper through table `+8` at that observed boundary. The scoped replacement site `0x1EE8E0–0x1EE8EB` likewise directly releases the previous pointer before later storing another pointer at `0x1EE93C`. This contract therefore does not claim that every actor release route necessarily traverses and frees the root's child list. The full deallocation/runtime behavior and all callers of the root-specific cleanup remain explicit lifetime dependencies.

Direct gameplay random calls identified here use image IAT RVA `0x2FC468`, the `rand` import from `MSVCR110.dll`; image IAT `0x2FC4B4` identifies `srand`. The numeric square-root thunk `0x28D9C8` reaches the original `_libm_sse2_sqrt_precise` import at IAT `0x2FC460`, and thunk `0x28D8D4` reaches `_libm_sse2_pow_precise` at IAT `0x2FC454`.
