# Alpha client buff-event transmission

## Evidence boundary

This contract describes the original client output aggregate's buff list at byte offset `+0x58`, its promotion to the client network queue, and the game-owned packet-8 send boundary. It also records independently traced server ingress, resident application, and the separate server output-list distribution boundary. It does not equate receipt with successful delivery or assume that a received event is automatically echoed to other clients.

The supported client is `binary/Cube.exe`, SHA256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`. The independently examined server is `binary/Server.exe`, SHA256 `1ffbcbce251e1506a63c9ce18ab0009d5553fcbb9e6202be2bc3a7d870d34fb1`. Both use image base `0x00400000`; addresses below are RVAs unless explicitly called VAs. Evidence paths are relative to the original evidence root. No other contracts or replacement implementation material were used.

## Record and queue identities

The aggregate member at `+0x58` is an eight-byte native list object: a 32-bit sentinel pointer followed by a 32-bit count at `+0x5C`. Each list node has eight bytes of links before the 40-byte event value. The client event copier copies five successive eight-byte groups, including uninterpreted bytes. It neither reconstructs a resident from selected fields nor normalizes numeric or padding bytes. The analogous server copier has the same 40-byte behavior. [Evidence: `decompiled/client/functions/00466880.c`, RVA `0x066880`; `decompiled/client/functions/00451c70.c`, RVA `0x051C70`; `decompiled/server/functions/00420080.c`, RVA `0x020080`.]

The event separates two outer IDs from the resident payload:

| Event byte offset | Width | Established role |
| --- | --- | --- |
| `+0x00` | 64 bits | Outer source ID; this is the ID used by the client's outgoing eligibility check. |
| `+0x08` | 64 bits | Outer target ID; resident application resolves this ID. |
| `+0x10` | 24 bytes | Resident payload, copied intact into the creature resident list. |
| `+0x10` within the event | 8 bits | Resident type byte. |
| `+0x14` | 32 bits | Resident amount, used as binary32 by the illustrated producer. |
| `+0x18` | 32 bits | Resident time field. |
| `+0x20` | 64 bits | Source ID embedded in the resident payload. |

The transport paths do not interpret the remaining bytes of the payload. In particular, neither the three bytes after the type nor the four bytes at event `+0x1C` acquire a zero requirement from transport. The two outer IDs and the embedded source are distinct fields; their equality in one producer is not a transport invariant. [Evidence: `decompiled/client/functions/00596d30.c` and `decompiled/client/assembly.txt`, RVAs `0x1980D9`–`0x1981C9`; `decompiled/client/functions/005957c0.c`, RVA `0x1957C0`; `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x08FD00`–`0x08FD2F`.]

For example, the selector-17 portion of generic hit handling inserts a resident into the target before constructing an output event whose outer source is the attacker's creature ID and whose outer target is the target's ID. The resident's embedded source is also supplied from the attacker there. A different apply-and-emit wrapper at RVA `0x1957C0` applies its supplied 24-byte resident to its creature, sets both outer IDs to that creature's ID, and copies the supplied payload unchanged. That wrapper does not replace the embedded source with either outer ID. These are separate producer behaviors. [Evidence: `decompiled/client/functions/00596d30.c`, RVA `0x196D30`, selector-17 insertion and event construction at `0x1980D9`–`0x1981C9`; `decompiled/client/functions/005957c0.c`, RVA `0x1957C0`.]

## Local application and outgoing promotion

An output-list append is a 40-byte list insertion. The append routine itself does not resolve a target, apply a resident, compare IDs, or inspect creature roles. Local application is a separate action performed by particular producers before emitting their event. The selector-17 insertion above therefore does not depend on the later network queue accepting the event, and the apply-and-emit wrapper likewise performs application before emission. This establishes neither identical producer gates for every buff type nor an additional application step in packet transmission. [Evidence: `decompiled/client/functions/004460a0.c`, RVA `0x0460A0`; `decompiled/client/functions/005957c0.c`, RVA `0x1957C0`; `decompiled/client/assembly.txt`, RVAs `0x1980D9`–`0x1981C9`.]

The main client update constructs a fresh output aggregate. At its outgoing promotion stage, a zero socket field at client `+0x8006CC` skips the network-promotion block. With a nonzero socket field, the buff loop visits aggregate `+0x58` in list order. It reads both 32-bit halves of the event's outer source ID and compares them with the local player creature ID at creature `+8` and `+0x0C`, using the creature pointer stored at client `+0x8006D0`. Only exact 64-bit equality appends the event to client queue `+0x8006F4`, whose count is at `+0x8006F8`. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, aggregate construction at RVA `0x08CE2E`–`0x08CE35`, socket gate at `0x09C02F`–`0x09C036`, buff iteration and comparison at `0x09C0F4`–`0x09C1A3`; append call at `0x09C165`.]

That loop adds no target-ID check, embedded-source check, source-creature lookup, ownership lookup, role-byte test, class/specialization test, resident-type test, amount/time check, or target-presence requirement. It does not require the outer target to be the player. It does not substitute the embedded source for the outer source when deciding eligibility. Thus an outer source equal to the local player passes this stage regardless of a different embedded source; an outer source unequal to that player fails this stage even if the embedded source equals the player. This describes the traced promotion stage after an event already exists, not the gates imposed by every producer. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09C131`–`0x09C1A3`; `decompiled/client/functions/004460a0.c`, RVA `0x0460A0`.]

Promotion copies an accepted event and does not remove the original aggregate entry. Rejected entries remain in the temporary aggregate as well. This aggregate is destroyed at the end of the update, including its `+0x58` nodes and sentinel; skipped or rejected network entries are not retained there for another update. The queue at client `+0x8006F4` is separate storage that can accumulate accepted records until the send worker takes its snapshot. The update holds the world critical section across the traced promotion stage; the worker uses that same world section when snapshotting and clearing the shared queue. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x089020`–`0x08902F`, `0x09C131`–`0x09C1A3`, `0x09D2E4`–`0x09D2EA`, and `0x09D35E`–`0x09D365`; `binary/Cube.exe`, aggregate destructor bytes at RVAs `0x067CAA`–`0x067CDF`; `decompiled/client/functions/00601cb0.c` and `00601e90.c`, RVAs `0x201CB0` and `0x201E90`; `decompiled/client/assembly.txt`, RVAs `0x069CDB`–`0x069D14`.]

There is a separate local-host distribution call after this socket-dependent block. If the manager pointer at client `+0x8006C8` is nonzero, the client passes the whole output aggregate to RVA `0x0DC8E0`, including the complete buff list rather than only the player-source subset. Its buff-list transfer copies aggregate `+0x58` to each non-null connection's `+0x70` list. The inspected buff transfer adds no per-event source, target, embedded-source, role, ownership or distance check. The surrounding routine has distance handling for other event categories; that is not a gate on this buff-list copy. [Evidence: `decompiled/client/assembly-functions/00488ee0.asm`, RVAs `0x09C256`–`0x09C26D`; `decompiled/client/functions/004dc8e0.c`, RVA `0x0DC8E0`, connection loop and the 40-byte list-copy call to RVA `0x0544D0`.]

## Packet 8 and client queue lifetime

The client send worker at RVA `0x069C10` checks the worker-active byte at client `+0x800585` before entering its normal send cycle. Its initial four-byte packet-0 send precedes snapshotting. If that initial send returns `-1`, the cycle does not take and clear the buff snapshot. After that boundary succeeds, the worker enters the world critical section, creates a separate list containing all records from client `+0x8006F4`, then empties the shared list and sets its count to zero. This occurs before the remaining state-packet preparation and before any packet-8 record is sent. [Evidence: `decompiled/client/assembly.txt`, RVAs `0x069C74`–`0x069D14` and `0x069E77`–`0x069EB5`; `decompiled/client/functions/00458df0.c`, RVA `0x058DF0`; `decompiled/client/functions/004544d0.c`, RVA `0x0544D0`.]

The snapshot copier visits every source node in order and copies all 40 bytes. It performs no event eligibility checks. After the shared queues and player-state data have been collected, the worker leaves the world critical section. Records accepted into the shared queue after that release belong to a later snapshot; they do not change the existing snapshot. [Evidence: `decompiled/client/functions/00458df0.c`, RVA `0x058DF0`; `decompiled/client/functions/004544d0.c`, RVA `0x0544D0`; `decompiled/client/assembly.txt`, RVAs `0x069E77`–`0x069F26`.]

After the earlier state/chat/optional creature-state sends and the packet-7 records, the worker iterates its buff snapshot. For every node it calls the native socket send with a four-byte integer `8`, then calls it with exactly 40 bytes beginning at the node's event value. Both calls supply flags zero and use the socket stored at client `+0x8006CC`. The four-byte packet discriminator is separate from the 40-byte event; there is no per-event length, count, ID rewrite, field serializer, resident application, checksum construction or compression step between that discriminator and that event body in this loop. The next buff event receives another four-byte discriminator `8`. [Evidence: `decompiled/client/assembly.txt`, RVAs `0x06A153`–`0x06A1B1`; `decompiled/client/functions/00469c10.c`, RVA `0x069C10`.]

Each send result is compared only with `-1`. A result of zero or a positive result smaller than the requested byte count is not retried or completed by this loop. A `-1` leaves the normal send path, so unsent snapshot entries need not be reached. The shared queue has already been cleared, and the failure cleanup frees the snapshot rather than restoring it to the shared list. Normal cleanup also frees the completed snapshot. There is no acknowledgement or per-event replay state in these traced game-owned steps. This is a queue-consumption and socket-call contract, not a guarantee that the peer obtained a complete event. [Evidence: `decompiled/client/assembly.txt`, RVAs `0x06A17D`–`0x06A1B1`, failure branch to `0x06A5A2`; `binary/Cube.exe`, snapshot cleanup bytes at RVAs `0x06A65D`–`0x06A6A3` and `0x06A79D`–`0x06A7E2`; `decompiled/client/assembly.txt`, disconnect cleanup at `0x06A843`–`0x06A869`.]

## Independently traced server ingress and resident application

The server connection setup supplies the receive worker with the manager's buff-list address at manager `+0x3C`. Packet-8 handling initializes a 40-byte event temporary, requests 40 bytes from that connection's socket, and advances the destination and reduces the remaining count after each positive receive. Once that loop reaches the append boundary, it enters the world critical section and appends the entire 40-byte event to that manager list. It does not compare either outer ID or the embedded source with the authenticated connection's creature ID; it also does not resolve the target, inspect the type, or inspect creature role/ownership there. [Evidence: `decompiled/server/functions/004254a0.c`, RVA `0x0254A0`, receive-worker context construction; `decompiled/server/functions/00426b70.c`, RVA `0x026B70`; `decompiled/server/functions/00426020.c` and `decompiled/server/assembly.txt`, packet-8 branch at RVAs `0x0264E0`–`0x02655B`; `decompiled/server/functions/00411040.c` and `00420080.c`, RVAs `0x011040` and `0x020080`.]

The server receive loop handles a socket result of `-1` as an error and bypasses this append. A zero result takes a different path: it breaks the receive loop and reaches the append boundary without a separate complete-40-bytes test. The initializer does not initialize all 40 bytes, so the traced code does not establish a fully defined event on that zero-return path. Conclusions about accepted, complete records refer to the normal full-body path; incomplete/closed-stream behavior is not silently promoted into a validated-record guarantee. [Evidence: `decompiled/server/functions/004063d0.c`, RVA `0x0063D0`; `decompiled/server/assembly.txt`, RVAs `0x026515`–`0x02655B`.]

At the next server main-loop collection, RVA `0x028170` copies the manager `+0x3C` list into the input aggregate's `+0x58` list, then empties the manager list and resets its count at manager `+0x40`. The operation runs under the world critical section, retains record order and all record bytes, and adds no per-event filters. This collection happens before the world-update call. Manager entries are therefore retained until collection, not until successful resident application or forwarding. [Evidence: `decompiled/server/functions/00428170.c`, RVA `0x028170`; `decompiled/server/functions/00420bb0.c`, RVA `0x020BB0`; `decompiled/server/assembly.txt`, main-loop RVAs `0x14A05A`–`0x14A0AE`.]

The server world-update buff-input loop resolves only the outer target ID at event `+8`. If the lookup returns a creature, it supplies the 24-byte payload at event `+0x10` to the resident-application helper. A missing target skips that application. This loop adds no outer-source lookup/equality check, embedded-source lookup/equality check, role test, ownership test, or type filter before invoking the helper. The helper's resident behavior is independent of transport: types `1`, `2`, `3`, `6`, `7`, `9`, `10` and `11` replace the first same-type resident if found; otherwise a resident is appended. Type `4` uses the append behavior. [Evidence: `decompiled/server/assembly-functions/005322d0.asm`, RVAs `0x132B92`–`0x132C4B`; `decompiled/server/functions/00405420.c`, RVA `0x005420`; `decompiled/server/functions/00411740.c`, RVA `0x011740`.]

The buff-input application loop does not erase the input entries it visits. The nearby conditional clear uses the separate output aggregate's `+0x58` list when world byte `+0xB4` is nonzero; it is not a per-event target-success removal from the input list. The examined standalone server constructs its world with that byte initially zero. These observations establish the two aggregates' separation, not an automatic copy from received input to output. A direct packet-8-input-to-output echo has not been established in this scope and must not be inferred from the independently confirmed output distribution below. [Evidence: `decompiled/server/assembly-functions/005322d0.asm`, output argument saved at RVAs `0x13230C`–`0x132324`, input argument loaded at `0x132ADF`, input iteration at `0x132B92`–`0x132C4B`, output clear at `0x132C53`–`0x132C65`; `decompiled/server/functions/004c8570.c`, RVA `0x0C8570`; `decompiled/server/functions/00549c50.c`, RVA `0x149C50`.]

## Server output distribution and send retention

For records present in the server output aggregate, the distribution routine visits each non-null connection entry and appends the entire output buff list to connection `+0x70`, with count at connection `+0x74`. This buff-list copy is unconditional within that non-null connection iteration. It does not exclude the event's source connection, require a recipient to equal the target, apply a role/ownership check, or impose a buff-specific distance test. It preserves the outer source, outer target, embedded source and all other event bytes. It does not itself apply a resident. [Evidence: `decompiled/server/functions/004272d0.c`, RVA `0x0272D0`, connection loop and buff transfer; `decompiled/server/assembly.txt`, RVAs `0x0277C7`–`0x0277F0`; `decompiled/server/functions/00420bb0.c` and `00420080.c`, RVAs `0x020BB0` and `0x020080`; distribution invoked at main-loop RVA `0x14A0D0`.]

The connection send worker copies the connection aggregate beginning at `+0x18` into a temporary aggregate. Its buff member therefore comes from connection `+0x70`. It clears that shared buff list and count before the later socket sends. The output-side collection uses the world critical section; the inspected buff list does not wait in shared storage for a target-presence check or a delivery acknowledgement. [Evidence: `decompiled/server/functions/00423dd0.c`, RVA `0x023DD0`; `decompiled/server/functions/00423400.c`, RVA `0x023400`, member copy at `+0x58`; `decompiled/server/assembly.txt`, copy call at `0x024911`, buff clear at `0x024B52`–`0x024B88`.]

The server sends these output events inside packet `4`'s aggregate, rather than issuing one outgoing packet `8` per buff. In that aggregate's buff section, serialization writes a 32-bit list count followed by each 40-byte record in order. The whole aggregate then passes through the native buffer-preparation boundary at RVA `0x012C70`; the worker sends a four-byte resulting buffer length and the resulting buffer. The traced serializer does not modify individual IDs or select records by type/role/ownership. As on the client sender, the final length/body socket calls test only `-1`, not equality with the requested byte count, and there is no restoration of the already-cleared shared buff list in the inspected failure cleanup. [Evidence: `decompiled/server/functions/004219c0.c`, RVA `0x0219C0`; `decompiled/server/functions/00423dd0.c`, RVA `0x023DD0`, packet-4 construction; `decompiled/server/assembly.txt`, RVAs `0x024F8B`–`0x025013`; `decompiled/server/functions/00412c70.c` and `00413200.c`, RVAs `0x012C70` and `0x013200`.]

## Explicit limits

The established client network filter is the outer-source/player-ID equality at promotion, followed by unfiltered snapshot transmission. The established server ingress filter is socket/worker control flow, followed later by target resolution for resident application. The established output-distribution rule concerns records already present in the output aggregate. The unclosed input-to-output echo boundary must remain distinct from those confirmed steps.

Socket implementation behavior, network delivery, scheduling between collection cycles, reconnect retention, remote acknowledgements, buffer-transform internals and malformed-stream acceptance beyond the described receive-zero path are not closed by this original caller trace. No universal ownership or authorization policy is inferred from the absence of checks in these particular loops. Producer-specific eligibility, every possible resident producer, the full generic-hit resolver and the later periodic effects of residents remain outside this bounded transmission contract.
