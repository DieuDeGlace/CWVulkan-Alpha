# Alpha actor identifier and map publication

Status: FINAL / STABLE / HELD. This is an original-only contract for the identified client initialization, connection, receive and reset boundaries, and the server connection-actor assignment boundary. It does not establish every native actor generator.

Evidence is relative to `disassembled alpha cube world`. Supported images are `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf` (3,885,568 bytes), and `binary/Server.exe`, SHA-256 `1ffbcbce251e1506a63c9ce18ab0009d5553fcbb9e6202be2bc3a7d870d34fb1` (1,718,784 bytes). Both use preferred image base `0x400000`. Client and server RVAs below always name their respective image. Original native evidence is `decompiled/client/assembly.txt` and `decompiled/server/assembly.txt`, with the individually identified original function files named below. For the scoped listed routines and boundaries, 1,829 client and 1,040 server instruction entries matched the corresponding original image bytes. The client receive branch missing from the listing was additionally disassembled directly from `Cube.exe`. No reconstruction, earlier contract, implementation material or runtime observation was consulted.

**Three distinct identities.** An actor has a stored 64-bit identifier at byte offset `+0x08`. This occupies two 32-bit words and is separate from its 32-bit address. The world actor container at world `+0x04` maps full 64-bit keys to 32-bit actor pointers. A node has its key at `+0x10/+0x14` and its pointer value at `+0x18`. A container's sentinel is a node pointer, not a reserved numeric key. The client embeds its world at client `+0x2E4`, so that map lies at client `+0x2E8`. Client `+0x8006D0` is the controlled actor pointer; world `+0xB8`, equivalently client `+0x39C`, is a separate designated actor pointer. Equality of any of these values is not implicit in the layout.

Client actor constructor RVA `0x03B690` copies both words of its supplied identifier to actor `+0x08/+0x0C`, then initializes the actor state beginning at `+0x10`. It neither generates an identifier nor rejects zero or negative identifiers. Server actor constructor `0x006400` has the same two-word identifier-copy boundary before its state initializer. The state initializers and copies used below operate on actor `+0x10`; their zeros do not mean that actor `+0x08` was reset. (`decompiled/client/functions/0043b690.c`, `0043c100.c`; client assembly RVAs `0x03B6BA–0x03B6D1`; `decompiled/server/functions/00406400.c`, server RVAs `0x00642A–0x006441`.)

Exact client lookup `0x077D90` and its world wrapper `0x02F000` use the supplied full 64-bit map key. They perform no actor-stored-ID comparison and no designated/controlled-pointer exclusion. The wrapper returns zero for either an absent key or a present null pointer. Client slot helper `0x068AD0` uses full 64-bit equality and inserts a missing key with a zero 32-bit value before returning the value slot. Server lookup `0x130600` and slot helper `0x002B10` have the corresponding key/value boundaries. Signed 64-bit key ordering is implemented by signed comparison of the high word followed, when equal, by unsigned comparison of the low word. Numeric key zero is valid in all four map helpers; none substitutes an array index or treats key zero as the sentinel. Existing values are returned without validating the pointed actor. (`decompiled/client/functions/00477d90.c`, `0042f000.c`, `00468ad0.c`; `decompiled/server/functions/00530600.c`, `00402b10.c`.)

**Initial client publication.** In client constructor `0x059C40`, the embedded world is constructed at `0x059F57` with its mode argument byte zero. The world constructor `0x18EB00` copies that argument to world `+0xB4` and initializes designated pointer `+0xB8` to null. This is a mode byte, not an actor identifier. The controlled actor is created later, rather than being an actor pointer omitted from the world map by construction. (`decompiled/client/functions/0058eb00.c`; client assembly RVAs `0x059F31–0x059F57`, `0x18EC09–0x18EC1C`.)

At `0x061FDE–0x062022`, the client allocates `0x1E60` bytes and passes the explicit 64-bit literal 1 to the actor constructor: low word 1, high word zero. The constructor result is stored in client `+0x8006D0`. There is no random, seed, timer, machine identifier or socket-derived arithmetic forming this initial identifier. The value is not the controlled actor's array ordinal or allocated address.

After additional actor-state/appearance setup, the client obtains the embedded-world map slot under a separately prepared 64-bit literal 1 and writes the controlled actor pointer there at `0x062219–0x06221E`. It then calls `0x087E90` with that pointer; the helper writes world `+0xB8`. At normal completion of this publication, the stored actor ID is 1, map key 1 contains the same pointer as client `+0x8006D0`, and the designated pointer is that same actor. Map publication precedes designated-pointer installation. No key-zero entry is used for this initial publication. Allocation failure is not a safe alternate initialized state: the scoped path subsequently dereferences the result. (`client assembly`, RVAs `0x061FDE–0x06202D`, `0x0621EF–0x06222C`, helper `0x087E90–0x087E9D`.)

The surrounding constructor performs substantial unrelated setup. This audit closes the identifier's literal origin and publication operands, not every random draw or callback in all intervening appearance, inventory, resource or application initialization. In particular, absence of a random input to the ID must not be expanded into a claim that the complete client constructor consumes no randomness.

**Server assignment for a new connection actor.** In the successful protocol route of server accept worker RVA `0x0254A0`, assignment searches world map keys 1 through 10 in increasing numeric order. Each candidate is formed as a signed 32-bit value sign-extended to 64 bits. A missing entry or an entry whose pointer value is null makes that candidate available. A nonnull pointer makes the key occupied regardless of that actor's stored ID, pointer aliases, discriminator or health. The first available key wins. This second availability search is distinct from the earlier preliminary scan that also reads discriminator byte `+0x60`; the discriminator test is not part of this assignment search. (`server assembly`, RVAs `0x0257F4–0x025887`.)

The selected-ID local begins at 64-bit zero. If all ten keys have nonnull values, it remains zero and the socket is closed without this actor's allocation/publication. Successful selection stores the chosen 64-bit candidate and requires it to be nonzero. The success set for this bounded producer is exactly 1–10. It does not create key zero, a random 64-bit identifier, or a value obtained from a connection-vector slot. A null map value at one of those keys can be overwritten by the newly created pointer. The wider protocol admission before this route is not a general server-capacity contract. (`server assembly`, RVAs `0x0257FA–0x0258B9`.)

The availability scan precedes acquisition of the world lock at `0x02588D`. Allocation and actor construction with the selected 64-bit value then occur, followed by slot lookup under that same value and pointer store at `0x0258EC–0x0258F3`. The scan is therefore not itself an atomic reservation under that lock. The slot operation does not repeat an empty-value admission at publication: an intervening insertion can change the value that the final store overwrites. This contract does not assume that other threads can or cannot exploit that interval. At normal publication, both stored ID and map key originate from the same selected scalar. Further setup follows the map store before lock release at `0x025A9F`. (`server assembly`, RVAs `0x025887–0x02593C`, `0x025A91–0x025A9F`.)

A connection record is installed later in the server's pointer vector, using an available vector slot or an appended slot. Its `+0x10/+0x14` receives the selected 64-bit actor ID; its `+0x08` receives the socket. That vector slot number is separate from the ID and does not replace the chosen map key. Under a later world lock, the connection identity fields are written before release at `0x025CBA`. The server then sends message-kind DWORD zero, the selected eight-byte ID, and the `0x1168`-byte actor-state region beginning at actor `+0x10`, in that order. The actor's stored ID is not a field inside that state region; its separate eight bytes provide the publication identity. Send calls at this boundary are not retried into an asserted atomic full packet by this worker. (`server assembly`, RVAs `0x025B54–0x025CBA`, `0x025CFC–0x025D4F`; `decompiled/server/functions/004254a0.c`.)

The accept loop calls named `KERNEL32.dll!Sleep` with 200 before socket acceptance. The inspected successful assignment uses availability lookup and integer increments, with no direct random/seed call or sampled timer in its ID calculation. Protocol reads and acceptance precede selection; creation and map publication precede the later identity/state sends. Some rejecting protocol routes sleep 500 before closing; these delays do not become identifier bits. The original socket imports are from `WS2_32.dll`, using ordinal 1 for the acceptance boundary, 16 for reads, 19 for sends, and 3 for closure, as reached by original thunks `0x14A536`, `0x14A52A`, `0x14A530`, and `0x14A542`. Nested actor setup after publication, allocation/exception internals and worker scheduling are not a closed random-stream contract. (`server assembly`, RVA `0x0254F2–0x025527` and scoped assignment/send regions; original Server import table.)

**Client connection identity replacement.** Client connection routine `0x06FC50` first sets the embedded world's mode byte at client `+0x398` to 1 before attempting the socket connection. It performs protocol negotiation before actor identity adoption. On the accepted reply-`0x10` route, the next 32-bit message kind must be zero. An eight-byte local ID is initialized to zero, received separately, and followed by a receive into an initialized `0x1168`-byte state region. The adoption gate is a signed 64-bit comparison against zero: negative IDs bypass actor replacement, while zero is admitted. This is weaker than the ordinary server producer's 1–10 range; the client does not enforce that range. (`decompiled/client/functions/0046fc50.c`; client assembly RVAs `0x06FC97–0x06FCAB`, `0x0700BB–0x070206`.)

The receive loops accumulate positive reads. Their end-of-stream and error handling must not be silently treated as a proof that every accepted buffer is complete: a zero return can leave the receive loop, while particular −1 returns jump away. This contract's normal adoption relation assumes a complete, successfully received kind, ID and state body. Partial-read and transport-failure outcomes remain bounded by those native loops, not repaired by an invented valid-message requirement. A negative-ID bypass is not asserted to terminate all connection setup: later code can proceed to worker setup outside that adoption block. (`client assembly`, RVAs `0x0700D2–0x070200`, `0x070571–0x07058B`.)

For an admitted ID, the routine takes the embedded-world lock, preserves selected state from the old controlled actor, then traverses the existing actor map and invokes each nonnull actor's deleting virtual method with argument 1. This clearing traversal does not exempt the old controlled pointer. It then clears map nodes. The saved position/inventory/metadata-related state is used to restore selected local data after replacement; complete destructor effects and full actor-state restoration semantics are outside this identity contract.

After clearing, the routine still performs an explicit world lookup of the received ID and stores its result in client `+0x8006D0`. If the result is null, it allocates an actor with that exact full 64-bit ID, stores the result as the controlled pointer, obtains the map slot under the same received ID, and writes the pointer there. It does not replace the ID with 1 or reject zero. The literal default ID zero and the map's null pointer default have different roles. An ordinary completed clear makes the lookup missing, but the actual lookup and null-result branch remain part of the native boundary. Constructor/destructor callbacks or concurrent/exceptional mutation must not be used to erase those operations from the contract. (`client assembly`, RVAs `0x070206–0x070333`.)

State copying starts at actor `+0x10` and therefore leaves the constructed ID unchanged. The new controlled pointer is subsequently copied to client `+0x39C`, the designated world `+0xB8`, at `0x070408`. Identity map publication precedes this designation change. Lock release occurs later at `0x070549`, after additional world setup. On ordinary adoption of an ID in 1–10, the new actor's stored ID, its map key, the controlled pointer and the designated pointer have the matching relation described above. On admitted ID zero, the same publication operands produce key zero and stored ID zero. Allocation failure and nested fatal callbacks are not a successful null-controlled-actor mode. (`client assembly`, RVAs `0x070333–0x070408`, `0x070529–0x070549`; `decompiled/client/functions/0044b040.c`.)

**Ordinary actor snapshot publication and key preservation.** The receive worker `0x06B740` dispatches message kind zero to `0x06BAAD`, as verified from the original jump tables at RVAs `0x06D1A4/0x06D180`. After obtaining the message payload, it reads an eight-byte actor key into a zero-initialized local before world locking. It looks up that full key. A missing or null pointer causes construction with the same key and publication under that key, inside the world lock. No zero or signed-negative rejection is present at this allocation/publication boundary. Existing nonnull pointers are reused. (`binary/Cube.exe`, directly disassembled RVAs `0x06BAAD–0x06BC52`; scoped stream-length/decode semantics are not generalized here.)

The actor-state region is copied to a temporary while locked, the body is decoded outside the lock, and publication of the decoded state occurs under a second acquisition. The final pointer comparison excludes the current controlled pointer from the ordinary remote-state copy. For other actors, the destination is actor `+0x10`. Thus an existing map entry whose key differs from the pointed actor's stored ID is neither rejected nor repaired by this body update: lookup uses the map key, while the stored ID bytes are not rewritten. The matching ID/key relation is established by normal construction operands, not by a permanent container invariant enforced on every access. Full snapshot field selection, interpolation and failed-decoder aftermath remain outside this identity boundary. (`Cube.exe`, disassembly RVAs `0x06BC52–0x06BE20`; client state-copy helper `0x04B040`.)

Message kind 2 has a different map scan: after receiving its key set, it walks the embedded actor map and considers a nonnull pointer for removal only when it differs from the controlled pointer and the node's full 64-bit map key is absent from that received set. It uses node keys for membership, not the pointed actor's stored ID. Removal is deferred through a list of selected map iterators, then the actor is deleted and that map node erased. Null mapped values and controlled-pointer entries survive this particular scan. There is no key-zero special case in its pointer/membership admission. Distinct keys aliasing the controlled pointer all receive the pointer exclusion; a different pointer with the same stored ID does not. (`client assembly`, RVAs `0x06BE25–0x06BF0D`, with dispatch table kind 2.)

**Offline/world-change reset and retained identity.** Client routine `0x0719F0` is admitted by byte `+0x800585` being nonzero. It first calls the actor-save helper, clears that byte, closes a nonzero socket and clears its 32-bit field `+0x8006CC`, and clears world mode byte `+0xB4`. It waits for nonzero worker handles in `+0x800590/+0x800594` through `WaitForSingleObject` with full 32-bit timeout −1 and clears the handle fields afterward. After a guarded mode reset and notification work, it calls client world-change routine `0x06F620`. The close thunk reaches `WS2_32.dll` ordinal 3; the wait import is named `KERNEL32.dll!WaitForSingleObject`. Neither the mode-byte zero nor socket-field zero is an actor-ID reset. (`decompiled/client/functions/004719f0.c`; client assembly RVAs `0x071A1C–0x071B35`.)

World-change routine `0x06F620` takes the embedded-world lock and a second client critical section, then traverses the world actor map. It collects every entry whose pointer differs from client `+0x8006D0`, deletes nonnull actors in those entries and erases those nodes. The controlled pointer is preserved by pointer comparison, without comparing the node key or stored ID. Consequently ordinary offline/world-change cleanup retains the controlled actor's current stored ID and its existing map entry or aliases; it does not unconditionally restore literal ID/key 1 after a connection-assigned identity. This audit found no actor-ID or controlled-pointer replacement in that complete routine. The statement applies to these identified reset paths, not to every unaudited character-selection or restart path. (`decompiled/client/functions/0046f620.c`; client assembly RVAs `0x06F653–0x06F809`.)

Embedded-world locking helpers `0x201CB0/0x201E90` enter/leave the critical section at world `+0x8000C0`, equivalently client `+0x8003A4`. World-change cleanup additionally enters/leaves the critical section at client `+0x8005D0`. The former wrapper identities are original named `KERNEL32.dll!EnterCriticalSection/LeaveCriticalSection`. This identifies the publication/cleanup lock objects; it does not prove that every caller or unrelated native map mutation obeys them. (`decompiled/client/functions/00601cb0.c`, `00601e90.c`; client assembly RVAs `0x06F659–0x06F66D`, `0x06F7FD–0x06F809`.)

The save helper `0x087520` constructs a separate temporary actor with supplied 64-bit ID zero and copies actor state from the live actor's `+0x10`. That temporary is serialized and deleted; the inspected helper does not put it in the world map or write zero to the live actor's ID. An ID-zero temporary is therefore not evidence of an ID-zero controlled actor. The complete save format and loading callers are not reconstructed here. (`decompiled/client/functions/00487520.c`; construction near client RVA `0x087612`.)

**Membership, draws and remaining limits.** Normal initial and connected publication explicitly include the controlled actor in the actor map. A lookup does not remove that membership merely because the pointer is controlled. Several scans then add their own pointer exclusions: world-change cleanup preserves it, kind-2 key-set cleanup preserves it, and ordinary kind-0 state application skips its remote body update. The connection replacement traversal instead deletes all nonnull old entries, including it. These are individual caller policies, not a global rule that actor scans omit the controlled actor or that numeric ID 1 means controlled. The controlled/designated pointer can identify a different numeric key after a successful connection.

All identifier values closed here arise from an explicit literal, availability-selected integer, exact received eight bytes, or unchanged constructor input. No direct random or seed operation supplies those operands. API waits/sleeps and socket-call order are stated where they surround assignment; no sampled clock/timer value was found as an input to these producers. This does not close randomness in complete startup, actor appearance, save serialization, destructor callbacks, runtime allocation hooks or other world generators. Those dependencies must not be collapsed into a claim about a global RNG stream or a universal sequential-ID algorithm.

There is no established universal exclusion of stored ID zero, no automatic synchronization of an existing actor's stored ID to a lookup key, and no established map-index identity. Sentinels, absent entries, present null values, numeric zero keys, and zero-ID temporary objects remain distinct. Ordinary successful producers described here make the stored ID and publication key equal because they pass the same 64-bit value to both operations. Arbitrary aliases, invalid pointers, allocation failure, incomplete messages, callback mutation, concurrent map changes, every other actor generator, and broader client/server state and lifetime rules remain explicit limits rather than inferred behavior. All earlier held artifacts remain unchanged.
