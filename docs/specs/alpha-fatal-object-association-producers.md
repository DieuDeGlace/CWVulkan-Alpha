# Fatal object association: producer and snapshot boundaries

This is a bounded, original-client source contract. The supported image is `binary/Cube.exe`, SHA-256 `84a7a132a84d4282338e7ea45a1940d32066d64e39cbafed8f2418d5a6dc30bf`, in the original Alpha evidence root. Addresses below are RVAs; the image base is `0x00400000`. Relative evidence paths refer to that root. Native instructions in the image were checked directly, including blocks omitted by the exported function bodies. No runtime observation or replacement implementation is evidence for this document. Infinite-Cubes material supplied navigation leads only; its field names and comments are not native findings.

The constructor, copies, publication helpers, fatal consumer, descriptor admission and static snapshot receiver are established below. **A concrete original writer that first gives a selector-5 record a valid descriptor ordinal remains unclosed.** None of the established constructor, relocation, append or snapshot operations derives such an ordinal. This does not establish that the fatal match is unreachable, that every record always contains minus one, or that no additional writer exists. It prevents treating a copied number or an independent descriptor admission as proof of the missing association producer.

## Identities and the precise consumer relationship

There are two independently stored collections in the spatial object returned by lookup RVA `0x034D10`. Its `+0x0C/+0x10/+0x14` fields describe contiguous records of `0x188` bytes. Its `+0x18/+0x1C/+0x20` fields describe a collection of four-byte pointers to separately allocated descriptors. Constructor RVA `0x2240F0` initially empties both collections. These are different element types and different ordinal spaces. The object constructor at RVA `0x18EAA0` and copy at `0x18EA10` identify the first record type independently of unrelated native structures that also happen to have an offset `+0x178`. [Evidence: `decompiled/client/functions/006240f0.c`, `0058eaa0.c`, `0058ea10.c`; `binary/Cube.exe`, RVAs `0x18EA10–0x18EAF6`.]

At fatal RVAs `0x196193–0x196219`, the creature supplies the two 32-bit cached coordinates at `+0x1B0/+0x1B4`. After spatial lookup, the scan walks the `0x188`-byte record collection in increasing record ordinal. A record qualifies when its first 32-bit selector is exactly 5, its 32-bit `+0x178` equals the creature's 32-bit `+0x1B8`, and its byte `+0x30` is nonzero. The first qualifying record is used. The equality itself has no nonnegative or descriptor-count test. Thus even the word “ordinal” here describes the relationship sought by the surrounding work, not validation performed by this particular equality. [Evidence: `binary/Cube.exe`, RVAs `0x196193–0x1961D8`; `decompiled/client/assembly.txt`, corresponding original addresses `00596193–005961d8`.]

The fatal output uses the two cached coordinates and the scan's **record** ordinal as its three-word key. It does not substitute record `+0x178` for that third key word. Later fatal work separately interprets creature `+0x1B8` as a signed index into the descriptor-pointer collection: it rejects negative or out-of-count values before indexing. Those later checks do not retroactively validate the earlier record match. No equality of a record ordinal and descriptor ordinal is established merely because both are counted from zero. [Evidence: `binary/Cube.exe`, RVAs `0x1961EE–0x196219`, `0x196C13–0x196C49`.]

## Construction and the common-prefix word at +0x38

RVA `0x18EAA0` performs the following explicit writes, in this order. The offsets in this table are relative to the `0x188`-byte record itself.

| Offset | Width | Construction value or action |
| --- | --- | --- |
| `+0x30` | 8 bits | 1 |
| `+0x34` | 32 bits | 0 |
| `+0x38` | 32 bits | 0 |
| `+0x40` | 32 bits | 0 |
| `+0x44` | 32 bits | 0 |
| `+0x48` | nested state | Initialization through RVA `0x03C020` |
| `+0x178` | 32 bits | `0xFFFFFFFF`, signed minus one |
| `+0x17C` | 32 bits | `0xFFFFFFFF` |
| `+0x180` | 32 bits | `0xFFFFFFFF` |
| `+0x184` | 32 bits | 0 |

The nested initialization is confined to the nested state ending before `+0x178`; it does not supply a descriptor ordinal. This constructor does not assign the selector at `+0x00`, the position triplet at `+0x08`, or the words at `+0x20–+0x2C`. The unassigned bytes, including alignment gaps, have no all-zero guarantee from this constructor. [Evidence: `decompiled/client/functions/0058eaa0.c`, `0043c020.c`; `binary/Cube.exe`, RVAs `0x18EAA0–0x18EAF6`.]

The common-prefix copy at RVA `0x068670` explicitly transfers the full 32-bit word at `+0x38`. Its read is at RVA `0x0686C2` and its destination write at `0x0686C5`. It does not skip this word, narrow it, combine it with `+0x34`, clamp it, or reconstruct it from another value. All 32 input bits survive. This word is initialized to zero by the record constructor but can acquire other bit patterns through a copy or received snapshot. No semantic name, meaningful range, arithmetic interpretation or separate global “unused” guarantee is established for it by these operations. [Evidence: `decompiled/client/functions/00468670.c`; `binary/Cube.exe`, RVAs `0x068670–0x0686D9`, especially `0x0686BC–0x0686D1`.]

The copy's entire transferred field set is the 32-bit words at `+0x00`, `+0x08`, `+0x0C`, `+0x10`, `+0x14`, `+0x18`, `+0x1C`, `+0x20`, `+0x24`, `+0x28`, `+0x2C`, `+0x34`, `+0x38`, `+0x40` and `+0x44`, plus the byte at `+0x30`. The words are transferred in the listed order, with the byte transferred between the words at `+0x2C` and `+0x34`. The holes at `+0x04–+0x07`, `+0x31–+0x33` and `+0x3C–+0x3F` are not transferred. The common prefix occupies `0x48` bytes; field-wise transfer is not a promise to overwrite all 72 bytes. In particular, `+0x38` is a transferred field, while `+0x3C` is a skipped gap. [Same evidence.]

## Full copies, append and ordinary publication

The complete record copy at RVA `0x18EA10` first invokes the common-prefix copy, then copies the nested state beginning at `+0x48`, including the portions at `+0x54`, `+0x58`, `+0x170` and `+0x174`. It subsequently transfers `+0x178`, `+0x17C`, `+0x180` and `+0x184` as four separate 32-bit words. The `+0x178` source read and destination write are at RVAs `0x18EA58` and `0x18EA61`. There is no range check, subtraction of a collection base, or derivation from a descriptor pointer. This preserves an already supplied association bit pattern; it does not establish where that pattern originated or whether it is currently valid. [Evidence: `decompiled/client/functions/0058ea10.c`; `binary/Cube.exe`, RVAs `0x18EA10–0x18EA92`.]

Record relocation RVA `0x18E8E0` advances through records by `0x188` and uses that complete copy. Growth RVAs `0x1949D0/0x194B40` allocate and relocate the collection, then replace its storage pointers. Append RVA `0x1A0E00` also uses the complete copy and advances the end by `0x188`; when the source already lies inside the collection, it preserves the source record's ordinal across possible growth so that it can find that same source again. That temporary ordinal belongs to the record collection. It is not written as a new descriptor association into `+0x178`. [Evidence: `decompiled/client/functions/0058e8e0.c`, `005949d0.c`, `00594b40.c`, `005a0e00.c`.]

Reviewed inline construction/copy paths also retain the constructor sentinel rather than supply the missing association: RVA `0x1AD320` initializes a temporary association to minus one before its inline append; RVA `0x1DC6E0` has corresponding temporary association initializations to `0xFFFFFFFF` before inline record copies; RVA `0x1F0CE0` initializes its temporary association to `0xFFFFFFFF` and transfers it into the appended record. These are concrete default-and-copy paths. Their existence does not prove how selector 5 is produced elsewhere, nor does it justify assigning every record in these large generators the same provenance. [Evidence: `decompiled/client/functions/005ad320.c`, `005dc6e0.c`, `005f0ce0.c`; native inline destination transfers include RVAs `0x1AD9F3`, `0x1DE242`, `0x1DE7E4`, `0x1F1B14`.]

Descriptor publication has a different concrete route. For example, RVAs `0x1BA3ED–0x1BA50C` allocate `0x10F0` bytes, construct a descriptor through RVA `0x1ADB20`, fill its fields and append its pointer to the spatial object's collection at `+0x18` through RVA `0x26ADD0`. That append publishes one four-byte pointer and advances its end by four bytes. The value 5 written at descriptor `+0x28` in this route is a field of that descriptor; it is not evidence of a selector-5 `0x188`-byte record or a write to such a record's `+0x178`. [Evidence: `binary/Cube.exe`, RVAs `0x1BA3ED–0x1BA50C`; `decompiled/client/functions/005adb20.c`, `0066add0.c`.]

World admission provides a genuine descriptor-ordinal producer, but its destination is the creature. Around RVAs `0x20FB89–0x20FC02`, the descriptor-pointer collection is traversed by a counter starting at zero, and descriptor `+0x48` supplies the lookup identifier. At RVAs `0x2100BA–0x2100FA`, the spatial object's two words at `+0x60/+0x64` and that descriptor counter become the creature's three 32-bit words at `+0x1B0/+0x1B4/+0x1B8`. This cached triple is not computed by converting the creature's current position. Crucially, this sequence does not assign the counter to a spatial record's `+0x178`. Neither matching coordinates nor the creature's own identifier or map entry key supplies the missing record writer. [Evidence: `binary/Cube.exe`, RVAs `0x20FB48–0x20FC02`, `0x2100BA–0x2100FA`; `decompiled/client/assembly.txt`, corresponding original addresses `0060fb48–0060fc02`, `006100ba–006100fa`.]

## The 88-byte static snapshot receiver

The original receive dispatcher at RVA `0x06B740` routes packet kind 4 to RVA `0x06CC0E`; this is confirmed by the image's dispatch table at RVAs `0x06D180/0x06D1A4`. It receives a four-byte payload length and the corresponding byte buffer, passes the buffer through RVA `0x0494B0`, and then reads its ordered aggregate lists. The static snapshot list is read at RVA `0x06CD49` through helper `0x058780`. This paragraph identifies the route into the snapshot reader; it does not close the buffer transformation, imported decompression behavior or hostile framing behavior. [Evidence: `binary/Cube.exe`, RVAs `0x06B8A7–0x06B8BD`, dispatch table bytes, `0x06CC0E–0x06CD49`; `decompiled/client/functions/0046b740.c`, `00486b60.c`, `004494b0.c`, `00449540.c`.]

Helper RVA `0x058780` reads a 32-bit signed list count, then, for each positive-count iteration, requests exactly `0x58` bytes, or 88 decimal bytes, from the current buffer position. There is no per-record selector or association test in this helper. The record boundary is:

| Snapshot offset | Extent | Relationship at application |
| --- | --- | --- |
| `+0x00` | 32 bits | First spatial lookup coordinate |
| `+0x04` | 32 bits | Second spatial lookup coordinate |
| `+0x08` | 32 bits | Signed ordinal in the contiguous `0x188`-byte record collection |
| `+0x0C` | 4-byte gap | Not transferred by the field-wise snapshot copy |
| `+0x10` | `0x48` bytes | Common-prefix extent described above |

Within this layout, the common-prefix `+0x38` word is snapshot `+0x48`, and it is included. Full-record `+0x178` is outside the snapshot and has no corresponding transmitted field in this reader. The nested state beginning at full-record `+0x48`, and all four trailing metadata words beginning at `+0x178`, are also outside the received common prefix. [Evidence: `decompiled/client/functions/00458780.c`, `00452060.c`; `binary/Cube.exe`, RVAs `0x058780–0x05885C`, `0x052060–0x05209D`.]

Before each body read, the receiver initializes only the temporary prefix's byte `+0x30` to 1, words `+0x34/+0x38` to zero and the two words `+0x40/+0x44` to zero. A successful body read copies all 88 bytes into this temporary, including incoming bytes occupying alignment gaps. Insertion through RVA `0x052060` transfers the three key words, then invokes the field-wise common-prefix copy; it does not retain all padding from that raw read. There is no numeric conversion of the common-prefix word at `+0x38` at either step. The separate helper RVA `0x0DC8B0`, used to construct snapshots from a key and existing common state, likewise transfers the three key words and invokes the same prefix copy. [Evidence: `binary/Cube.exe`, RVAs `0x0587D1–0x058818`, `0x052079–0x052093`, `0x0DC8B0–0x0DC8D8`; corresponding original function files.]

The well-formed count/body boundary must not be generalized into robust malformed-input admission. If a requested body does not fit, the reader moves its cursor to the buffer end and still reaches the insertion path without performing that body's 88-byte copy. The explicitly initialized temporary fields therefore do not establish values for the other fields. If the count word itself is unavailable, the read does not assign it a zero default. This contract gives no deterministic snapshot value or safe rejection guarantee for those incomplete-input cases, and does not close signed arithmetic overflow or allocation-failure behavior. [Evidence: `binary/Cube.exe`, RVAs `0x05879B–0x05881D`.]

After aggregate parsing, the received static list is appended in its existing order to client `+0x800660` at RVAs `0x06CFA7–0x06CFC1`. The surrounding enter/leave calls are RVAs `0x201CB0/0x201E90`, called with client `+0x2E4`; these wrappers use their input's `+0x8000C0` critical section, therefore client `+0x8003A4`. This protects the shown publication sequence. It is not proof of synchronization for every generation, replacement or later object access. [Evidence: `binary/Cube.exe`, RVAs `0x06CEDD–0x06CEE8`, `0x06CFA7–0x06CFC1`, `0x06D080–0x06D088`; `decompiled/client/functions/00457cc0.c`, `004548e0.c`, `00601cb0.c`, `00601e90.c`.]

## Later application preserves the local association

In the enclosing client routine RVA `0x088EE0`, RVAs `0x08F435–0x08F530` iterate client `+0x800660`. Each snapshot's first two key words are passed to lookup RVA `0x034D10`. A missing spatial object skips replacement. For an existing object, the third key word must be signed nonnegative and less than the current record count, calculated from the contiguous collection's `0x188`-byte stride. There is no creation of an absent spatial object or append of a missing record on this path. For an admitted record, the snapshot prefix at `+0x10` replaces the existing record's common fields through RVA `0x068670`, then spatial byte `+0x74` becomes zero. [Evidence: `binary/Cube.exe`, RVAs `0x08F435–0x08F530`; `decompiled/client/functions/0044e890.c`, `0044b560.c`.]

The snapshot's third key word selects a record; it is not stored into that record's `+0x178`. The receiver does not compare that key word to the descriptor-pointer count. The replacement preserves the existing nested state and `+0x178/+0x17C/+0x180/+0x184`. It can replace the selector, byte `+0x30`, the word `+0x38` and other common fields while preserving an old association bit pattern. Consequently it can change whether a pre-existing association becomes eligible for the fatal scan, but it cannot be cited as the first numeric assignment of a descriptor ordinal to that field. A constructor sentinel stays `0xFFFFFFFF` through this replacement unless some other operation has already changed it. [Same evidence; prefix transfer RVA `0x068670`.]

## Invalidation, mutation and remaining limits

The matched fatal record's synchronous state operation is RVA `0x1A58E0`, called with requested byte state zero. Its record writes affect byte `+0x30` and word `+0x34`; it does not clear or produce record `+0x178`, and it does not write record `+0x38`. The common-prefix snapshot is made after that operation. The later fatal descriptor writes of 1,200,000 to descriptor `+0x38` and world `+0x800160` to descriptor `+0x3C` belong to the separately indexed descriptor. They are not writes to the spatial record's equally numbered common-prefix offsets. [Evidence: `decompiled/client/functions/005a58e0.c`; `binary/Cube.exe`, RVAs `0x1961DA–0x196219`, `0x196C2A–0x196C49`.]

One independently established descriptor-lifetime boundary occurs in RVA `0x1D8750`. For each admitted loaded spatial object, RVAs `0x1D89C3–0x1D8A0A` start at its `+0xA0` count, invoke destruction for each nonnull descriptor pointer through the current end, then resize the pointer collection to that saved count through RVA `0x00D9D0`. This removes the tail's current indexed descriptors without an accompanying direct rewrite of the `0x188`-byte records' `+0x178` in the shown sequence. A previously in-range number can therefore cease to pass the later fatal descriptor-count test. Subsequent pointer append can occupy a removed ordinal again; the cited field copies and index checks contain no identity-generation test tying an old record value to the new pointer. The nested destruction effects and every other reset, erase or regeneration path are not exhaustively closed here. [Evidence: `decompiled/client/functions/005d8750.c`, `0040d9d0.c`, `0066add0.c`; `binary/Cube.exe`, RVAs `0x1D89C3–0x1D8A0A`.]

The construction, prefix copy, full copy and snapshot field transfers described here perform integer/byte movement, not floating-point conversion or random selection. No random draw appears in their established field-assignment work. Large generators do make random calls, but their complete draw streams, every nested helper, every selector-5 creation route and every possible alias-based association writer have not been closed. No claim of a whole-image absence of additional `+0x178` writers follows from this audit.

The central remaining dependency is a first producer that intentionally places a current descriptor ordinal into an actual selector-5 record's `+0x178`. The constructor supplies minus one, a full copy supplies its source value, relocation and append preserve it, descriptor admission supplies the creature's cached index, and the 88-byte receiver supplies only common state. None completes that dependency. This contract also leaves record reordering/erasure, wider generation scheduling, descriptor replacement through untraced routes, malformed transport recovery and any server counterpart unresolved. It establishes the stated client boundaries without inventing association semantics or reachability beyond the original evidence.
