ALPHAVULKAN · CLEAN-ROOM SPECIFICATIONRevision 30 · 2026-11-17Target: Cube World Alpha (Cube.exe and Server.exe)

AlphaVulkan Clean-Room Implementation

AlphaVulkan is a 64-bit Vulkan replacement engine for Cube World Alpha that aims for 1:1 behaviour with the player's own Alpha client and server. This document has four parts: the interoperability facts any implementation may reuse, the functional specification the engine must meet, the material those facts come from, and the tests that confirm the behaviour matches the original.

Part A

Interoperability facts

Facts the engine needs to read the player's Alpha installation and saves, talk to original Alpha clients and servers, and behave the same. They are functional facts rather than creative expression, so the contracts state them as plain values, each cited by RVA in the Alpha image it comes from.

A1What may be copied

Stated directly in specs and code
  • File-format layouts: store schemas, record fields, widths, versions and encodings
  • Key derivations and unscrambling tables needed to open the player's own files
  • Packet ids, handshake codes, byte layouts, the port and section order
  • Constants, thresholds, timings, divisors and magic numbers, with their exact bit patterns
  • Record offsets and identifiers that saves or packets carry
  • The order of decisions and random draws, where generated worlds or combat must match
  • Dictionary keys, store keys and file names the game itself looks up
Never copied
  • Code, pseudocode or decompiler output, or its structure and expression
  • Names a decompiler or the Infinite-Cubes reconstruction invented
  • Game content: models, sounds, music, pictures, dictionary text, item and creature tables. These are read from the player's installation at run time.
  • The player's saves, captures and recordings
Rule of thumb
A value that a save file, a packet or a matching result depends on is a fact and may be written down. Anything that is the game's content, or how its programmers chose to write it, stays out. Where a table is game content (for example the 2,857 voxel models or the two dictionaries), the contract says where the game finds it and the engine reads it from the owner's install through the setup tool.

A3Network protocol

TCP over IPv4 on the fixed port 12345; neither image has a datagram path or a port setting. Every message starts with a u32 id, values little-endian. Handshake: the server sends 17, the client answers with protocol version 3, the server replies 16 (accepted, then the player id, a creature record and packet 15 with the seed) or 3 (wrong version). The "server full" reply 18 exists but can never be sent by the original server.

IdPacketDirectionBody
0Creature updatebothu32 length + zlib(u64 id, creature delta); a length of 0 closes the connection
1Creature batchserver → clienti32 count, then u64 id, u64 mask and fields, uncompressed (understood, not sent)
2End of creature batchserver → clientempty; unlisted creatures are deleted
3Static objectsserver → clientu32 count × 120 bytes (understood, not sent in game)
4World updateserver → clientu32 length + zlib of 13 sections
5Clockserver → clientu32 day, u32 time of day in ms
6 · 7 · 8 · 9Item · hit · buff event · shootclient → serverfixed records: 300, 72, 40 and 112 bytes
10Chatbothi32 n + UTF-16 units (from the server, prefixed with the sender's u64 id)
11 · 12Zone request · map region requestclient → serveri32 x, i32 y
15World seedserver → clientu32 seed (handshake only)

Creature deltas carry a 64-bit field mask over 48 fields; a field is sent when its typed value differs from the record last listed to that receiver. Senders pace each pass against one shared 20 ms timestamp. Full layouts are in alpha-net-packets, alpha-net-transport and alpha-net-server.

When a packet omits those fields, the receive keeps them from its starting record. A received clock field replaces that value even when it equals the value in an earlier packet.

The visibility ray contract has been independently re-certified for the original client. Native unloaded-column and loader acceptance remain open.

The revision 12 and revision 16 Vulkan builds joined the original Alpha server over loopback using protocol 3, received creature ID 1, adopted seed 41 and rendered the Lands of Gami with the HUD and minimap. The original game client, combat timing and longer sessions still need acceptance.

The original client startup trace identifies the hidden window, initial Direct3D 9 device request, XAudio2.7 activation and input setup. The isolated original opened a responsive desktop window with normal Windows access. Desktop capture timed out before the menu could be inspected. Original menu, gameplay and visual comparisons remain open.

The engine read the original server's world clock record. The original server then advertised the clock the engine wrote into a separate copy of that save. Wider zone, character and map save interchange remains open.

The dedicated server handles mixed item requests at the sender's turn and answers zone requests in their received order, including duplicates. Connected clients replace placed-object lists at the zone-content boundary.

The offline blueprint consumer processes queued kind-7 requests using live selection, rotation, position and aim. Cells are visited in stencil order with live protection checks. It removes unsupported ground-resting plants and sprites in the admitted zones. An owned-content Vulkan diagnostic placed and rendered all 600 cells of the wooden floor.

At each world-piece tail the full current terrain list appends to the loaded zones' ordered histories. Signed zone division and repeated records are preserved. The save contract keeps the ordered 20-byte edits and uses the wrapped signed day-minus-three cutoff on reload. Anchor placements remain live. A fresh engine save reopened all 1,800 records across three world pieces of the owned wooden floor test. Stock build-mode activation, local model selection and original-client save and placement interchange remain open.

Open behaviour questions stay in each contract's unresolved section and in docs/roadmap.md. An unproved point stays open and is never filled in by guessing.

C3Third-party and provenance

  • zlib and SQLite formats are public standards. Alpha links zlib 1.2.3 and SQLite 3; AlphaVulkan uses its own copies under their own licences.
  • Build dependencies are pinned: Vulkan-Headers 1.4.304, volk 1.4.304, glm 1.0.1, GLFW 3.4, miniaudio 0.11.21 and stb at a fixed commit. No Vulkan SDK is needed.
  • CubeVulkan: the sister project's GPL water surface shader is reused for the owner's shared-water extension.
  • Continuation audit: sources copied on 2026-11-07 from the earlier project are not certified by their presence. Every inherited contract is re-checked by a fresh author against the original images before release, and contracts that described engine extensions or compared against engine output were reclassified rather than re-certified.

Regression rule
Every behaviour change from a corrected contract gets a focused check that pins the corrected value, and the implementer reports which checks fail on the previous behaviour. Changes that need a window are covered by the live runs instead.

E2Feature lifecycle

  1. Triggershared

    An open roadmap item, an unresolved contract question, an audit finding or a conflict between contracts.

  2. Briefimplementer

    A bounded question for a fresh author, naming the evidence and contracts it may read. It never includes engine code, test results or implementation history.

  3. Contractauthor

    The author reads only the assigned evidence, writes code-free prose citing RVAs, reads it back against the evidence and marks it held.

  4. Intakeimplementer

    The implementer checks the hash, reads the whole contract and records it in docs/CLEANROOM.md.

  5. Implement and testimplementer

    Change the engine where it differs, in its own structure, with a focused regression for each behaviour change.

  6. Validateimplementer

    Run the full gate (D2) and review the live-run screenshots.

  7. Freeze and publishshared

    An exact-path commit, audited, pushed and confirmed on the remote.

E4Exposure-stop rule

Rule
A role exposed to prohibited material stops and reports it without repeating the contents. Ignoring it does not restore separation. Further work on that topic needs a new author context, and the exposure is recorded in docs/CLEANROOM.md.

E5Publication

  • Every tested checkpoint is committed and pushed to the public repository; history is never rewritten or force-pushed.
  • The audit refuses to run unless the changed paths match the checkpoint's exact list; files another author is still editing are held back.
  • Held-contract hashes, credentials and whitespace are checked, and a public mirror of the tree is scanned for prohibited content.
  • A push counts as done only after the remote head is confirmed.
  • Never published: owner assets, the game's data, saves, captures, recordings, private diagnostics or the local handoff.

E6Release gates

  • Specification provenance: every remaining inherited contract re-certified, and every held contract's hash recorded (docs/provenance-audit.md).
  • Native acceptance: captures from the original game compared for gameplay, visuals and generated worlds; save interchange with the original client.
  • Human acceptance: controller play on real hardware, and multiplayer against original Alpha clients and servers.
